# H4 手動測試案例(用正式 app 執行)

`docs/design/254-h4-harness.md` 裡有四塊原本要由 harness 自動化(新卡期限、BLE 認領、加入網路、手機連線與 C0),
實作時被工具的安全機制擋下(H4-U13、H4-U14,2026-11-03)。使用者決定改成**用正式的 provisioning app 手動執行**。

- 這些案例**不在每日全套裡**:#254 列為自動化缺口;**每次發版前**手動跑一次,結果與證據回填該版的驗證紀錄。
- 每個案例都要留證據:app 截圖、節點端的 log 行(主機用 ssh 唯讀抓)、時間。沒有證據 = 沒跑,不算 PASS。
- 節點用 bench 的 04 / 02;執行前 P9 必須乾淨,執行後要回到 S0(`s0_assert`)。
- 判定欄位:PASS / FAIL / INVALID(前提不成立,例如手機沒連上、app 當掉),FAIL 要附原因或標 ❓ 未歸因。

## 0. 事前準備與設定(每次執行都先對一遍)

**設備**
- 節點:04、02(bench),燒好受測版本;04 有 eth 線接實驗室交換器(主機要能 ssh 到 04)。
- 手機 A:測試手機(S20),已照 `s20-setup.md` 的 A 段設定好;裝好受測版本的 provisioning app。
- 手機 B:第二支手機或 app 的第二個帳號(M1 的負向測試用),**不要**登入擁有者帳號。
- 主機:能 ssh 到 04 / 02(只做唯讀檢查,指令照下面各案例抄)。

**手機 A 的設定(執行前檢查)**
| 項目 | 設定值 | 在哪裡 |
|---|---|---|
| 行動數據 | 關 | 設定 → 連線 → 數據使用量 |
| 家用 Wi-Fi | 刪除,或關掉「自動重新連線」 | 設定 → 連線 → Wi-Fi → 該網路 → 齒輪 |
| 藍牙 | 開 | 快速設定 |
| 位置 | 開(Android 掃描 BLE 需要) | 快速設定 |
| Termux / Termux:Boot 電池 | 不受限制 | 設定 → 應用程式 → 該 app → 電池 |
| 螢幕 | 執行期間保持亮著(或接電源 + 開發者選項「保持喚醒」) | 設定 → 開發人員選項 |
| app 版本 | 記下版本號(寫進紀錄) | app 的「關於」 |

**記錄**:每個案例開始前記下時間、節點版本(主機:`ssh root@<04> 'sed -n s/^BATMAN_VERSION=//p /etc/batman-build'`)、app 版本。

## M1. 用 app 經 BLE 認領新卡(取代 S0-pre 的 BLE 認領;H4-U14)

**前提**:節點剛燒好、未認領(app 掃描時顯示 unclaimed);手機藍牙開啟,離節點 1 公尺內。

| 步驟 | 預期 |
|---|---|
| 1. app 掃描附近節點 | 列出目標節點;顯示的序號末 4 碼 = 節點 `identity/sn` 的末 4 碼(主機 ssh 讀) |
| 2. 選目標 → 認領(依 app 指示) | app 顯示認領成功 |
| 3. 主機唯讀檢查節點 | `prov.meta` state = claimed;lock-status = LOCKED;節點 log 有 claim 成功的那一行 |
| 4. app 重新連線、以擁有者身分登入 | 成功;app 顯示的狀態 = claimed |
| 5. **負向**:另一支沒有擁有者金鑰的手機(或 app 的另一個帳號)對同一台認領 | 被拒;節點狀態不變(仍是原擁有者) |
| 6. **負向**:附近有另一台節點時,確認 app 只連到選定的那台 | 另一台的狀態與 log 沒有變化 |

**證據**:步驟 1、2、4、5 的截圖;步驟 3 的唯讀輸出;步驟 5、6 另一台的前後狀態。

## M2. 用 app 加入網路(S0-pre 的 network/join)

**前提**:M1 完成;app 已建立測試網路 N0(US、ch 40)。

| 步驟 | 預期 |
|---|---|
| 1. app 把節點加入 N0 | app 顯示成功 |
| 2. 等節點完成設定與一次重開(約數分鐘) | 主機依 eth MAC 重新找到節點 |
| 3. 主機唯讀檢查 | `STATUS` state = member;mesh 上看得到另一台(`batctl n`) |
| 4. 對第二台(02)重複 1–3 | 兩台互為 mesh 鄰居 |

**證據**:app 截圖、`batctl n` 輸出、兩台的 `STATUS`。

## M3. 新卡測試的主機中斷(H4-U13 的缺口)

**目的**:確認 F 測試進行中主機中斷時,一次性 dead-man 的實際行為;並記錄已知缺口(B 每次開機不到 25 分鐘就重開時,dead-man 可能不觸發)。

| 步驟 | 預期 |
|---|---|
| 1. 開始一個 F 測試(chain1),等 04 進入 B 的新卡狀態 | chain1 印出 dead-man 已在 B 上就位 |
| 2. 中斷主機(關掉 harness 的視窗或拔主機網路),**不要**動節點 | — |
| 3. 等 30 分鐘 | 04 自己回到 A(主機恢復後依 MAC 找到它在 A) |
| 4. 主機恢復後,依 chain1 的 `restore_all` 步驟收尾 | `s0_assert` 成立 |
| 5. **已知缺口(不必刻意重現)**:若在步驟 3 期間 04 一直在 25 分鐘內重開,記下來 | 若 04 沒有回 A:人照 `restore_all` 處理;標 FAIL(已知缺口),附重開次數與時間 |

**證據**:chain1 輸出、04 回 A 的時間、`/opt/batdata/dv-prov/ch1-deadman.log`、步驟 4 的 `s0_assert`。

## M4. 手機連上節點熱點(取代 harness 的手機前置檢查與 C0 QR;2026-11-03 使用者決定)

**目的**:手機 A 以「手機 MAC」連上 04 的測試熱點 C0,之後所有經手機的測試才有意義。

**C0 的值**:由使用者自己保管(密碼管理器或紙本),**不經過對話、log、指令列**。在手機上手動輸入。

| 步驟 | 手機上的操作 / 預期 |
|---|---|
| 1. 新增網路 C0 | 設定 → 連線 → Wi-Fi → 新增網路:名稱 = C0 的 SSID、安全性 = WPA2/WPA3-Personal、密碼 = C0 |
| 2. 進階設定 | 「MAC 位址類型」= **手機 MAC**(不是隨機 MAC);IP 設定 = DHCP |
| 3. 連線 | 狀態顯示「已連線」;記下手機上顯示的 IP 與 MAC(設定 → 關於手機 → 狀態) |
| 4. 同樣新增第二個測試網路 ALT | 存好即可,不必連上;MAC 位址類型同樣 = 手機 MAC |

**主機唯讀檢查(04 上)**:

| 檢查 | 指令(主機 → 04) | 通過條件 |
|---|---|---|
| a. 手機已通過認證 | `ubus list 'hostapd.*'` 找出 AP 介面,再 `ubus call hostapd.<介面> get_clients` | 手機 MAC 那一筆 `"authorized": true` |
| b. 手機在 AP 介面的轉送表上 | `bridge fdb show br br-ahwlan \| grep -i <手機 MAC>` | 出現在 AP 介面(`phy1-ap0` 之類) |
| c. 手機拿到 IP | `grep -i <手機 MAC> /tmp/dhcp.leases` | 有一筆,IP = 手機上顯示的 |
| d. 手機連得到 04 | 手機的瀏覽器開 `http://<04 的 br-ahwlan IP>/` | 頁面打得開(HTTP 200) |

任一項不過 → 後面所有經手機的案例都記 **INVALID**,先修好手機連線再測。

**證據**:手機 Wi-Fi 詳細資訊截圖(含 MAC 類型)、a–c 的輸出、d 的截圖。
