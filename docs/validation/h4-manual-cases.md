# H4 手動測試案例(用正式 app 執行)

`docs/design/254-h4-harness.md` 裡有三塊原本要由 harness 自動化,實作時被工具的安全機制擋下(H4-U13、H4-U14,
2026-11-03)。使用者決定改成**用正式的 provisioning app 手動執行**。

- 這些案例**不在每日全套裡**:#254 列為自動化缺口;**每次發版前**手動跑一次,結果與證據回填該版的驗證紀錄。
- 每個案例都要留證據:app 截圖、節點端的 log 行(主機用 ssh 唯讀抓)、時間。沒有證據 = 沒跑,不算 PASS。
- 節點用 bench 的 04 / 02;執行前 P9 必須乾淨,執行後要回到 S0(`s0_assert`)。
- 判定欄位:PASS / FAIL / INVALID(前提不成立,例如手機沒連上、app 當掉),FAIL 要附原因或標 ❓ 未歸因。

## M1. 用 app 經 BLE 認領新卡(取代 S0-pre 的 BLE 認領;H4-U14)

**前提**:節點剛燒好、未認領(app 掃描時顯示 unclaimed);手機藍牙開啟,離節點 1 公尺內。

| 步驟 | 預期 |
|---|---|
| 1. app 掃描附近節點 | 列出目標節點;顯示的序號末 4 碼 = 節點 `identity/sn` 的末 4 碼(主機 ssh 讀) |
| 2. 選目標 → 認領(依 app 指示) | app 顯示認領成功 |
| 3. 主機唯讀檢查節點 | `prov.meta` state = claimed;lock-status = LOCKED;節點 log 有 claim 成功的那一行 |
| 4. app 重新連線、以擁有者身分登入 | 成功;app 顯示的狀態 = claimed |
| 5. **負向**:另一支沒有擁有者金鑰的手機(或 app 的另一個帳號)對同一台認領 | 被拒;節點狀態不變(仍是原擁有者) |
| 6. **負向**:附近有另一台節點時,確認 app 只連到選定的那台 | 另一台的狀態與 log 沒有變化 |

**證據**:步驟 1、2、4、5 的截圖;步驟 3 的唯讀輸出;步驟 5、6 另一台的前後狀態。

## M2. 用 app 加入網路(S0-pre 的 network/join)

**前提**:M1 完成;app 已建立測試網路 N0(US、ch 40)。

| 步驟 | 預期 |
|---|---|
| 1. app 把節點加入 N0 | app 顯示成功 |
| 2. 等節點完成設定與一次重開(約數分鐘) | 主機依 eth MAC 重新找到節點 |
| 3. 主機唯讀檢查 | `STATUS` state = member;mesh 上看得到另一台(`batctl n`) |
| 4. 對第二台(02)重複 1–3 | 兩台互為 mesh 鄰居 |

**證據**:app 截圖、`batctl n` 輸出、兩台的 `STATUS`。

## M3. 新卡測試的主機中斷(H4-U13 的缺口)

**目的**:確認 F 測試進行中主機中斷時,一次性 dead-man 的實際行為;並記錄已知缺口(B 每次開機不到 25 分鐘就重開時,dead-man 可能不觸發)。

| 步驟 | 預期 |
|---|---|
| 1. 開始一個 F 測試(chain1),等 04 進入 B 的新卡狀態 | chain1 印出 dead-man 已在 B 上就位 |
| 2. 中斷主機(關掉 harness 的視窗或拔主機網路),**不要**動節點 | — |
| 3. 等 30 分鐘 | 04 自己回到 A(主機恢復後依 MAC 找到它在 A) |
| 4. 主機恢復後,依 chain1 的 `restore_all` 步驟收尾 | `s0_assert` 成立 |
| 5. **已知缺口(不必刻意重現)**:若在步驟 3 期間 04 一直在 25 分鐘內重開,記下來 | 若 04 沒有回 A:人照 `restore_all` 處理;標 FAIL(已知缺口),附重開次數與時間 |

**證據**:chain1 輸出、04 回 A 的時間、`/opt/batdata/dv-prov/ch1-deadman.log`、步驟 4 的 `s0_assert`。
