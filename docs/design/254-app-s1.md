## 0. 一句話

Android 12+ 的 Flutter app,對**今天的 P2 節點**(wsl.22)走完:掃描 → 輸入 QR → Noise 握手 → 驗節點證書 → 認領
(中斷後以 `claim/replay` 恢復)→ 建立新網路(network/join,第一台)→ info;之後找回自己的節點、重新登入。

## 4. Keystore(219 §6)

- 首次安裝:產生四把金鑰;每把先試 StrongBox,`StrongBoxUnavailableException` / ProviderException → TEE;**產生後立刻做一次該用途的
  操作**(簽一次 / ECDH 一次 / 加解密一次),失敗 → 該機不支援;**等級依 §4.1 讀出並判定**。實測(facts §9):Keymaster 4 手機
  **有** ECDH,但 keystore2 以軟體模擬、靜默降級 → field 版禁止認領,dev 版允許(§4.1)。**偏離 219 §6**:§6 的退路是
  「軟體金鑰 + Keystore AES 包裝」;S1 不提供(那條路正是 v1 審查否決的可匯出私鑰),之後若有不支援 AGREE_KEY 的目標手機再議。
- 簽章:Keystore 回 DER → raw r‖s(各補零 32 B)→ low-s(s > n/2 → n − s)→ 斷言 s ≤ n/2;k 由 Keystore 產生。
- ECDH:KeyAgreement 回 z 到 app 記憶體(推 psk_replay;owner_tag_key 本來就在 app 記憶體 → 可接受,明寫);用完清零。
- 備份:`allowBackup=false` + `dataExtractionRules`(cloud-backup 與 device-transfer 全排除);release 非 debuggable。
- Keystore 金鑰消失但紀錄在 → 解密失敗 → 顯示明文索引「這些節點需要重燒卡回收」,不刪紀錄。
- log 只印 sha256 前 8 碼;K / PSK / root_password / SAE / net_root / z 從不進 log;root_password 頁 `FLAG_SECURE`。

### 4.1 金鑰安全等級(v8.3,依實測 facts §9)

**事實**:Keymaster 4 手機(例:S20 SM-G9810,Android 13,`hardware_keystore=4`)可以做 `PURPOSE_AGREE_KEY`,但 keystore2 以**軟體**
實作,就算 `setIsStrongBoxBacked(true)` 也**不丟**例外。「ECDH 成功」不代表金鑰在硬體 → 一律**讀** `KeyInfo.securityLevel`。

**owner_enc 的真實用途(v8.2 漏掉的)**:① psk_replay(認領中斷恢復);② P3 的 `member_secrets` — 網主把 **net_root** 加密給成員擁有者的
`owner_enc_pub`(219-protocol.md §7.4;cddl member-secrets 3 = SHA-256(owner_enc_pub));S1 已把 owner_enc_pub 寫進 members v1。
③ 節點只要有一位擁有者,**一直**接受 psk_replay(node.go:391-395),不限恢復期間。所以軟體 owner_enc 外洩 = 這支手機所有網路(過去
與未來)的 net_root(→ psk_member / adv_member)+ 永久的節點辨識(reacquire 連線可讀 info 1–8:device_id / 型號 / fw;一般人對已認領
節點只拿到假 msg2)+ 在藍牙範圍內**無限期**擋住恢復(每小時 10 次的滑動窗口,node.go:571-584)。

**規則**(每次 app 啟動、每次認領 / 恢復 / 登入 / 建網前**即時**讀等級;判定只看即時等級是否在下表的**允許集合**內 — 不在 → 該功能 fail-closed 並說明;紀錄裡的等級只供顯示,與即時不同只顯示變化、不據此停用(升級後等級變好不會鎖死 app);紀錄缺 → 重讀並寫回):

| 金鑰 | field 版 | dev 版 | 不符時 |
|---|---|---|---|
| 紀錄 AES-256-GCM | 硬體 | 硬體 | **整個 app 停用**(紀錄無法安全存放) |
| owner 簽章 | 硬體 | 硬體 | 禁止認領 / 登入,明示原因 |
| admin 簽章 | 硬體 | 硬體 | 禁止建網,明示原因 |
| owner_enc(AGREE_KEY) | **硬體** | 硬體或 **SOFTWARE** | field:禁止認領(同 v8.1);dev:允許,見下 |

- 硬體 = `SECURITY_LEVEL_STRONGBOX` / `TRUSTED_ENVIRONMENT` / `UNKNOWN_SECURE`(-2,平台定義為「安全硬體、類型不明」,記 log);
  `SOFTWARE` 與 `UNKNOWN`(-1)都不是硬體。
- 產生:先 StrongBox;**讀回**的等級若是 SOFTWARE → 刪掉剛產生的那把、改 TEE 再產一次,依讀回的等級取較好的(STRONGBOX > TEE >
  UNKNOWN_SECURE > SOFTWARE;KeyMint 手機的 TEE 可能有硬體 ECDH ⚠️);要 StrongBox 卻拿到 TEE → 記 log。
- **安裝完成標記**:四把都通過等級判定與用途自測後,先寫「安裝完成」標記(fsync),之後才可能有任何紀錄。**沒有標記且沒有任何紀錄**時,缺任何一把 → 刪掉這次產生的全部、下次啟動重來(首次安裝途中被殺)。**有標記之後絕不刪金鑰**:缺一把 → 依下面「單一金鑰遺失」處理。
- **單一金鑰遺失**(有標記之後;例:系統更新、Keystore 被部分清除):紀錄 AES 缺 → app 停用,顯示明文索引「這些節點需重燒回收」(§4,不刪紀錄);owner 簽章缺 → 不能登入 / 認領 / 恢復,紀錄仍可讀(顯示 root_password 等),節點需重燒回收;admin 缺 → 不能建網或改網路;owner_enc 缺 → 不能恢復中斷的認領(已有 pending 的節點需重燒),其他照常。都不自動重產(重產的新 owner 金鑰節點不認得)。
- **S1 期間的事實(2026-11-08 實測)**:**所有節點都是 dev 憑證** — 節點金鑰庫只收 `file` 後端(keystore.go:266-267),DAC 一律自簽 `CN=dev:<id>`(:107-108);HAT 上的 608 在 02 / 04 都**不回應**(bus 1 0x59,喚醒後全掃,02 有其他裝置回應作正對照;#300),且依 2026-10-06 決定要換空白 SSHDA、節點用晶片要等 #255。→ field 版今天認領不了任何節點;dev 版能認領**所有**節點。#254 本階段本來就「只限內部開發、不可出貨」→ **使用者決定(2026-11-08)接受**:S1 用 dev 版 + 軟體 owner_enc(S20)開發、測 bench 節點;這些節點與網路的 net_root 風險(上述)落在開發環境。
- **dev 版 + SOFTWARE owner_enc**:第一次認領**之前**明示「這支手機的恢復 / 成員金鑰是軟體保護,只能用於開發,不可用於實際部署」,使用者確認才繼續;此後每個節點紀錄標記 `dev-soft-enc`。
- **#255 之後的界線(雙向、編譯期)**:field 版拒 dev 憑證(既有);**dev 版拒任何串到正式根的 DAC**(新增;今天 app 沒有正式根,兩版都拒,`verify_first_contact` 對非 `dev:` CN 一律 Untrusted — 加入正式根時 dev 版必須仍拒);兩版不同 applicationId(上)。→ 正式節點永遠碰不到軟體 owner_enc。
- **P3 合約(可檢查的寫法)**:field 網主**不收 DAC 為 dev 憑證的成員**(join-request 帶 node_cert,網主可驗);dev 版建的網路是開發網路。另列 P3 checklist:owner_enc 輪替(owner/add 重加會換 EncPub,node.go:855-860)、reacquire 連線佔用 ops 通道(⚠️ 只在有 psk_replay 的人身上可能 — field 版不給軟體 owner_enc,實質只剩 dev 版)。
- dev 與 field 兩版用**不同 applicationId**(各自的 Keystore 別名、紀錄、桌面名稱),不能互相覆蓋安裝。
- 換手機 / 備份:紀錄已排除於備份與裝置轉移(§4);Keystore 金鑰不隨 Smart Switch / Google 轉移(⚠️ 未驗證,一般如此)→ 新手機上等同「解除安裝」:節點重燒回收。
- 金鑰只在首次安裝產生、不自動重產。系統升級(含 keystore2 `upgradeKey`、Keymaster → KeyMint):靠每次即時讀等級把關;等級變差 →
  fail-closed;要升級到硬體 owner_enc 只能重裝 app(= 紀錄失效 → 節點重燒回收,§4)。
- 沒有使用者驗證綁定(無生物辨識閘,§6)→ 移除螢幕鎖不影響金鑰;寫明。
- `KeyInfo` 是系統回報的自我檢查,被攻破的系統可以說謊 — 但那時它也能直接使用硬體金鑰,故對「本機弱硬體」的檢查足夠;不做 attestation。
- 誠實界線:硬體 AES 只防**離線**取出紀錄;當下拿到 root 的人可直接呼叫 app 的金鑰解開 K / owner_tag_key / root_password。軟體金鑰的差別在
  「事後帶走、長期有效」— 正是 net_root 與節點辨識的風險,所以 field 版不接受。
- ⚠️ 未驗證(記入 facts,實作時查):keystore2 軟體金鑰 blob 的保護方式(AOSP km_compat / 軟體 KeyMint;離線取出是否需要 root);
  `setUnlockedDeviceRequired` 對軟體金鑰的加密效果。這兩項只影響 dev 版的風險描述,不影響 field 版(field 不收軟體 owner_enc)。

### 5.1 認領
1. 取 QR `{1: device_id, 2: K}`;挑廣播:STATUS key 5(末 4 碼)== QR 的末 4 碼(旁邊可能有別人的未認領節點)。

3. 寫 claim-pending(落地)。4. `claim/begin` → nonce,**不等使用者**直接算 response / sig_enc(55 s、閒置 30 s)→ `claim/finish`。

5. **對手實作**:Rust 核心對節點的 Go provd(經手機 BLE);向量另由 Python `verify.py` 獨立重算(219 §10-11);**PR-H1 對手交握**:
   Rust 核心在主機上與 `verify.py` 做 Noise NX / NXpsk0 交握(只在主機、不碰節點、不是擁有者 client)— 在用掉任何節點之前先證明
   Noise 互通。主機端打 provd 的
   路徑(frame socket)不做 — 等同主機端的擁有者 client,使用者已決定不寫。
6. **各 actor 的負向**:假節點(突變 node_cert 的假 msg2 由測試用 Rust 對端送)、中間人(把 h 換掉 → 節點拒 owner-op)、
   備份(`adb backup` / `bmgr` 取不到紀錄)、field flavor + dev 憑證 → 拒、Kotlin 拒簽沒有允許標籤的位元組、Rust 拒對未驗
   sig_ecdh 的 ecdh_pub 加密、自己的節點關機 + 02 / 04 在旁 → app 不得提示「被別人認領」也不得自動忘記(實機)。
7. **實機前提**:一台**未認領**節點(02 / 04 都是 N0 成員)→ `prov-bench-s0-254.sh` 新卡流程(破壞性)。副作用(動手前列細、等使用者
   同意):離開 N0;join 改寫它的 mesh_id / key / channel;被手機金鑰認領後 harness 無法做擁有者操作;還原 = 重燒卡。
   **重燒次數與順序**(每次 = 一次新卡流程):卡 1 依序做 ② finish 後斷線 → replay 恢復、④ join 中斷線 / 斷電、① 建網 + info + 重新登入、
   ⑤ Keystore 金鑰消失(之後節點只能重燒);卡 2 做 ③ 負對照(關掉 replay 的建置 → 節點變孤兒)。合計 **2 次重燒 + 最後 1 次把節點
   還原成 N0 成員**(`prov-bench-s0-254.sh fresh` + join N0),每次都先問。
