## 2. 做法

| 槽 | 金鑰 | 只能做 | v2.0 的用途 |
|---|---|---|---|
| 1 | 身分金鑰 | 內部簽章 | 公鑰決定節點 id，是憑證的主體金鑰；**v2.0 不簽任何東西** |
| 0 | 連線金鑰 | 外部簽章 | 每次連線的身分證明（簽「固定標籤 ‖ 交握雜湊」的摘要） |
| 2 | 解密金鑰 | ECDH | 給節點的密碼包的加密對象 |

- **節點 id** = SHA-256(槽 1 公鑰，SEC1 未壓縮 65 位元組，含開頭的 `04`；晶片回傳 64 位元組，由 helper 補上) 的前 9 位元組，與檔案後端相同（`keystore.go:40`）。
- **晶片序號只用在認領證明**：認領比對時晶片只用序號裡固定的 3 個位元組（SN[8]、SN[0:1]，F§4），所以 app 算認領證明時用晶片序號，它取自憑證的擴充欄位。**節點與 app 其他地方的 `sn` 仍是節點 id 的 9 個位元組**（與今天相同：provd 的 `deviceID = hex(sn)`，`server.go:357`；app 的 `device_id = hex(sn)` 並比對憑證主體的 serialNumber，`nodecert.rs:118-121`）。這樣 Noise prologue、廣播、PSK 都不受影響（審查 v4set-A M1）。機身 QR 不帶序號。
- **金鑰的證明 = 開發根簽的憑證**：主體金鑰是槽 1 公鑰，憑證另外載明槽 0 公鑰、槽 2 公鑰與晶片序號（格式見 `255-608b-impl.md` §3.1）。開發根只在燒錄時、讀回設定與鎖定狀態完全符合後才簽（§5）。app 驗證連線證明與加密對象時，公鑰**一律取自這張憑證**，不取自節點另外送來的欄位。
- **開發根的簽章代表什麼**：「開發者在自己掌控的節點上燒了這顆晶片」，**不是**晶片自己的證明。讀回的資料是節點回報的，所以燒錄只在剛燒好卡、開發者在場的實驗台或 bench 節點上做（§5）。開發版 app 不能把它說成更多。
- **節點不驗開發根的簽章**，只檢查結構：憑證主體金鑰 = 槽 1 公鑰、擴充欄位的槽 0 / 2 公鑰與序號 = 晶片的。信任與否是 app 的事；這樣映像裡不必有開發根公鑰，換開發根也不必重建映像（審查 v4set-A M2）。
- **為什麼沒有晶片背書**（v4 起）：開發根在燒錄時已經讀回並確認了設定，再讓憑證載明三把公鑰，C2、C3 就成立；背書在 bench 上不增加保護，卻要釘住 55 位元組訊息、整個 #255 卡在一個原廠程式都不支持的假設上（審查 v3-A M2、M4）。量產晶片是另一顆，背書移到 §10。
- **槽 1 為什麼仍是「只能內部簽章」**：設定位元組不變（各輪審查都確認過），且身分金鑰本來就不該簽主機給的任何東西。v2.0 它只產生一次、公鑰進憑證。
- **連線金鑰簽什麼**：只簽 helper 組成的「固定用途標籤 ‖ 32 位元組交握雜湊」的 SHA-256，由主機以直通 nonce 載入暫存區後外部簽章（F§2.3）。用途是固定的列舉（`255-608b-impl.md` §2.1）。provd 提供交握雜湊，所以被攻破的 provd 可以讓槽 0 簽任何雜湊；這等於 provd 本身被攻破（它握有連線金鑰），不是新的洞。
- **給節點的密碼包**（`net_secrets`）的加密對象是憑證載明的槽 2 公鑰。

## 3. 槽位規劃

| 槽 | 用途 | 燒錄時 | 規則 |
|---|---|---|---|
| 0 | 連線金鑰 | 資料區鎖定後產生，再個別鎖定 | 只准外部簽章 |
| 1 | 身分金鑰 | 同上 | 只准內部簽章（v2.0 不用） |
| 2 | 解密金鑰 | 同上 | 只准 ECDH；結果不寫入下一槽 |
| 5 | 認領秘密 | 資料區鎖定前寫入開發者電腦產生的值；之後永不可改 | 只能比對；不可讀；NoMac |
| 8 | 開發根簽的憑證（完整 DER，≤ 416 位元組，格式與大小預算見 `255-608b-impl.md` §3.1） | 鎖定前寫全 0；燒錄最後一步寫入 | 明文可讀；**bench 上不個別鎖定**（§5.3） |
| 3、4、6、7、9–15 | 不使用 | 鎖定前寫全 0（含 36 位元組槽的全部 36 位元組） | 永不可寫、不可讀、NoMac |

- 沒有任何槽的 `ReadKey` 是 0（比對後複製的功能不會開啟）；認領秘密在奇數槽。
- **不使用的槽是公開的已知值（全 0）且 NoMac**，可以被拿來做 GenDig / CheckMac。這不構成風險：沒有任何槽的 WriteKey / ReadKey / AuthKey 指向它們，也沒有驗證者接受晶片的 MAC 或內部簽章（C2）。

## 4. 設定區數值

**設定區的校驗值每顆晶片不同**（位元組 0–15 含序號），所以交付物是「位元組 16–127 的固定影像」，校驗值由燒錄模式對每顆晶片讀出 0–15 後計算。影像在 E1 讀到空白值後產生，實際影像與雜湊在 §8.3；開發者電腦上另以一個獨立的實作（不同於燒錄模式的程式）重算 112 位元組的影像，兩者相同才鎖；這對 E4 用的**變體影像**與 F1 用的最終影像都適用。影像的雜湊（`se-lab image` 印出的 `image_sha256`）定義為位元組 16–127 共 112 位元組的 SHA-256，其中不寫入的位元組（52–67、84–87）一律以 `0x00` 計；獨立重算用同一條規則。校驗值由 `se-burn` 從讀回的 128 位元組計算；算錯時晶片拒絕鎖定（fail-safe），所以不另外獨立重算（審查 v6set-A）。

| 位元組 | 設定 |
|---|---|
| 13 | 唯讀（AES_Enable），E1 記錄。**實測 `0x61`**（§8.3） |
| 16 | `0xC0`（7 位元 0x60） |
| 17 | 維持 E1 讀到的空白值。**實測 `0x00`**（§8.3） |
| 18 | `0x00` |

| 20–51 | 各槽 SlotConfig（下表） |

## 5. 燒錄（bench）

### 5.1 誰、在哪、怎麼做

- **燒錄是 helper 的命令列模式**（`batman-provhelper se-burn …`），由開發者經 ssh 以 root 執行。它**只在以下條件都成立時**才動晶片：helper 常駐程式已停止（procd 服務停止，且取得晶片鎖）；不是試用開機（`batman-slot is-trial` 回 1）；`/etc/batman-dev-open` 存在。最後一條只是「刻意的一步」的標記，**不是**安全控制：root 可以自己建立它（審查 v4set-A m2、B m3）。
- **晶片鎖**：所有碰晶片的程式（helper 常駐、燒錄模式、實驗工具）先對開啟的 `/dev/i2c-N` 本身取得獨占 `flock`（不阻塞；不另設鎖檔，PR D1 程式碼審查 B-M1）；常駐程式終生持有。拿不到就拒絕執行。常駐程式內部另有一個序列器，一次只跑一個指令序列（喚醒 → … → 閒置）。不碰晶片的 helper 命令列模式（`--boot`、`--persist-now` 等）不取鎖，也不讀晶片（`255-608b-impl.md` §2.3）。
- **`se-burn status`**：唯讀，輸出 JSON：晶片狀態（S0–S4 或其他）、序號、三把公鑰（已產生時）。它也要取晶片鎖。
- **`se-sign resume <host>`**：中斷後接續用。讀 status；紀錄是「待寫入」就送「預期序號 + 秘密」（S1 或 S3 需要）；紀錄是「已鎖定」就只送預期序號（S2、S3 不需要秘密）；狀態是 S3 就接著做簽章與 `se-burn cert`（審查 v6set-A）。
- **認領秘密由開發者電腦產生**：`se-sign` 先以 `se-burn status` 讀到序號。該序號**沒有任何紀錄**時，以自己的 CSPRNG 產生 32 位元組秘密，寫進新的燒錄紀錄（狀態「待寫入」）；已有「待寫入」的紀錄時，**沿用同一個秘密**；已有其他狀態的紀錄時拒絕。秘密一經寫入紀錄就不再覆寫（S1 在資料區鎖定後中斷再重跑 `begin`，晶片裡的就是這個秘密，審查 v5set-A m6）。再經 **stdin**（不是命令列參數）把「預期序號 + 秘密」交給 `se-burn`。`se-burn` 讀到的序號與預期不同就拒絕。節點不把秘密寫進檔案、log 或 stdout。
- **開發根的簽章在開發者電腦上做**：節點輸出資料包（設定區原始 128 位元組、序號、三把公鑰），開發者電腦**自己**重算設定區校驗值、依 §4 的比對規則比對、確認兩區與三個金鑰槽都已鎖，通過才簽。

- 每一步都可以在中斷後重跑同一個命令，從讀回的狀態接續。stdin 在 S1、S3 以外的狀態不被讀取。
- `se-burn cert` 寫入槽 8 前檢查憑證與晶片的結構相符，且**覆蓋層與 p5 都還沒有身分快取**（燒錄中，或剛重燒卡、helper 還沒寫出快取）。身分一旦寫出，覆蓋層與 p5 的身分「只寫一次」（`batman-config-save:435-436`），換憑證會讓兩者不同而凍結（審查 v5set-B M1），所以之後要換只能重燒卡（§5.3）。

### 5.3 槽 8 與憑證更換

- **bench 上不個別鎖定槽 8**：憑證格式或開發根若要改，鎖住的晶片就永遠帶著錯的憑證。不鎖的代價：有 root 的人能覆寫槽 8，結果只是 app 驗不過（拒絕服務），因為憑證是對開發根驗的。
- **更換憑證 = 重燒卡**：app 釘住整張憑證 DER（`nodecert.rs:126-133`），節點的身分快取只寫一次。所以要換憑證：停 helper → 重燒卡（晶片映像）→ `se-burn cert` 寫新憑證 → 開機寫出快取 → 重新認領。與換 HAT 的復原方式相同。
- 開發根遺失、外洩或要更換：產生新的開發根 → 每台 bench 晶片節點依上一條重燒卡、換憑證、重新認領 → 開發版 app 換成新的開發根公鑰。節點映像不必重建（節點不驗開發根，§2）。

### 5.4 燒錄紀錄與開發根的保管

- **兩個分開的目錄**，都在 DSKT-MOONLIGHT 的 WSL ext4 檔案系統（`chmod 0600` 在這裡才有效；NTFS 上用 Git Bash 的 `chmod` 不生效）（審查 v4set-A m12）：
  - **燒錄紀錄**：每顆晶片一筆（序號、節點 id、三把公鑰、認領秘密、狀態）。驗證工具只讀這個目錄。
  - **開發根私鑰**：以密碼加密存放。只有 `se-sign` 用，驗證工具碰不到。
- 不進任何 git repo、不進 log。
- `se-sign sign` 拒絕：紀錄不是「已鎖定」的資料包；序號與紀錄不同的；槽 1 公鑰或節點 id 已屬於另一筆紀錄的（避免某台 bench 節點的 root 拿另一台的公開槽 1 公鑰配上自己的槽 0 / 2，騙到一張冒充那台的憑證，審查 v4set-A m3）。
- 驗證工具從燒錄紀錄取認領秘密，在**主機端**回答認領挑戰；用哪一筆紀錄由驗證工具的節點清單決定，**不**依節點印出的任何內容（審查 v4set-A m12）。這是「印成 QR 後刪除」的 bench 例外：bench 晶片終生是開發單元，保留秘密才能自動化驗證。
- `se-sign` 產生的機身 QR 圖檔含秘密：寫在燒錄紀錄的目錄裡，印出後刪除（秘密仍在紀錄裡）。
- 備份：使用者把兩個目錄（加密後）另存一份到可移除媒體；保管說明寫進 Batman-P（只寫做法，不放秘密）。

## 6. 實驗台與晶片分配

## 8. 實驗

### 8.0 規則

- 實驗工具 `se-lab` 是開發者工具，**不進任何映像**；放在實驗台的 tmpfs 執行；取得晶片鎖後才動作；只對開發者電腦傳入的「犧牲晶片序號清單」上的晶片動作，其他一律拒絕。能下鎖定指令的建置也受這個清單限制。它實作產品驅動沒有的指令（UpdateExtra、KDF、SHA 到暫存區、AES、Random、PrivWrite、GenDig 各區、MAC、GenKey 各模式）。這是 C8 的明文例外：實驗台不是帶有身分的節點。
- 每條「應該失敗」都寫明預期狀態碼，並有對照：同一個指令只改受測條件、或同一個指令對另一個槽，要成功。沒有對照的列寫「只靠文件」，不算 C7 的證明。
- 每次動實驗台前取得使用者同意；E0–E3 不留下永久改變。**E4 以後要等本文件 v7 的修改完成**（v6 兩位審查對 E4 都是 APPROVE-WITH-CHANGES，條件就是本版的修改）。E1 讀到的版本不是 `00 00 60 03` 就停。

### 8.1 變體影像（第 1 顆）

與 §4 相同，只改三個不使用的槽作為對照（值與 v3 相同，各輪審查已逐位元確認）：

| 槽 | SlotConfig | KeyConfig | 對照用途 |
|---|---|---|---|
| 3 | `0x0F8F` | `0x003C` | 秘密、可明文寫、**沒有 NoMac**：E8 的 MAC 類指令與 AES 在這裡做對照 |
| 4 | `0x2083` | `0x0073` | 私鑰槽、可 GenKey、可個別鎖定：E6 的 PrivWrite 對照、E17 的 GenKey / 鎖定、E9 的「已鎖定的私鑰槽」目標 |
| 6 | `0x0F0F` | `0x003C` | 一般資料、隨時可寫、可個別鎖定：E6、E9、E13 的寫入與鎖定對照 |

硬規則：沒有任何 WriteKey / ReadKey / AuthKey 指向槽 5，讓 E8 對槽 5 的結論可以套用到最終影像。

**順序**（審查 v5set-A m1、m2）：E0a → E1 → E2 → E3 → E4 → E5 → E6（資料區鎖定）→ E8 → E11 → E17（鎖住槽 4）→ E9（槽 0 保持空的）→ E10（先對槽 1、2 GenKey）→ E12 → E13（鎖住槽 6）→ E15 → E16。資料區的限制只在資料區鎖定後生效（F§2），所以 E8、E10、E15 都在 E6 之後。 **操作手冊（`docs/255-rig-runbook-e4.md`）把 E12 放到最後**（E13、E15 之後）：萬一「位元組 85 不影響位址」的假設是錯的，晶片斷電後會離開 0x60，排在它後面的實驗就全部做不了；E13、E15 不依賴 E12（PR D2 審查 A-r5）。

**斷電**：E4、E12 的「斷電後」要切掉晶片的 3.3 V。Pi 重開機不會切。做法：照 §8.3 的「斷電方法」切智慧插座（2026-11-27 實測：這台的電池不會接手，切插座就是真的斷電）；每次先取得使用者同意（審查 v5set-B m8）。

## 10. 移到「選量產晶片」時才處理的

- **晶片背書**：要不要讓晶片自己證明金鑰屬於它（K16 的晶片版本）、怎麼做。v3 的 E7 清單與審查 v3-A M2、M3 的修正是起點；要在量產晶片上做。
- **入庫計數器**（U9）：顯示「最多被入庫過 N 次」（v2 的「至少」方向錯了，U9 的措辭要請使用者確認）；何時加一（認領證明與擁有者簽章都驗過之後）；計數器簽章。
- 機身 QR 是否終身固定、標籤遺失怎麼辦。
- 晶片壞掉時節點的行為與使用者要接受的代價。
- 晶片與主板的綁定（自家 HAT v1 有 TPM，一起看）。
- 出廠站、原廠根、批次燒錄、量產生命週期。
- 預先設定版（608C TrustFLEX）的槽位由 Microchip 決定，要確認能否做到三金鑰分工。
