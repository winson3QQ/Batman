### 用詞

| 詞 | 意思 |
|---|---|
| 信任錨 | 節點信任的最上層金鑰。家庭：家長手機的金鑰；小隊：機關的根金鑰 |
| 授權者 | 信任錨，以及信任錨授權出去的範圍。**永遠指金鑰與它的權限，不指某個人** |
| 發證者 | 被信任錨指定、可以再發證書的金鑰 |
| 發證站 | 執行發證的系統（小隊：ICS_COMMAND） |
| 管理員 | 持有網路權限的人 |
| 入庫 | 把節點登記到某個信任錨之下。家庭部署裡等於今天的「認領」 |

## 2. 現況事實（✅ main 4eba26d，四份審查複核過）

1. 節點身分是自簽的 P-256 金鑰，存成檔案；沒有任何根簽它；app 拒絕所有非 `dev:` 的身分，並要求 `device_id == SHA-256(公鑰)[:9]`（`keystore/keystore.go:42-46, 111-131`；`nodecert.rs:146-156, 177-190`）。
2. 手機金鑰在 Android Keystore，不可匯出；量產版須為硬體，開發版允許軟體的加密金鑰（`KeyPolicy.kt:64-66`）；沒有設使用者驗證，也沒有要金鑰證明（`Keys.kt:64-98`）。
3. 節點留了 4 把擁有者金鑰、4 把管理員金鑰的位置，實際各用 1 把（`provstore/provstore.go:146-189`；`provd/session.go:68-69`；`joinflow.rs:157`；`rekey.rs:102`）。
4. 第一次加入網路要擁有者當場簽章；之後的更新只認上一版管理員的簽章，而且只收連續版本（`node/node.go:774-787, 1106-1117, 1192-1201`）。兩位管理員同時改會讓節點分成兩群，沒有收斂的路（與 `219-protocol.md:367` 不一致）。
5. provd（非 root、面對藍牙與 HTTP）是加密通道的終點，看得到所有回覆的明文，今天就包含 root 密碼（`provd/noise.go:38-39`；`node.go:609, 672`）。
6. 一台節點一個網路；套用變更有交易與回滾（`provstore.go:9`；`node.go:1242-1311`）。試用開機期間 helper 拒絕改狀態（`node.go:258-259`）。
7. `prov.cbor` 只有 helper 解析，上限 64 KiB，舊版嚴格解析，完整性只有一個沒有金鑰的雜湊（`provstore.go:1-3, 10, 66, 112-131`）。
8. 節點端沒有任何時鐘效期檢查（`keystore.go:148-168`）。
9. 移除成員不送任何東西到節點；節點不讀名單，沒有撤銷清單。移除擁有者不清他裝的 SSH 金鑰，也不換 root 密碼（`rekey.rs:1-10`；`node.go:966-995, 1214`）。
10. 節點的手機 Wi-Fi、網路孔與 mesh 是同一座橋（設定檔 `meshpoint-1.8.0:66-70, 85, 111-113`；`bulk.go:19, 122`；`batman-http.nft:24`。審查 v3-B 對過原始碼，未在節點上擷取）。
11. 身分後端是寫死的 file 實作；「這把金鑰只能簽哪種東西」只靠 helper 軟體把關（`keystore.go:43-103, 266-267`）。
12. 邀請、成員、移除三條流程只存在於開發版；目前沒有對外部署，bench 上兩台節點。

## 5. 第 2 期要解的問題（不是解法）

每題附已知的陷阱。完整清單與出處在威脅模型的附錄。

1. **撤銷怎麼撐過恢復出廠。** 陷阱：把下限交給發證者自己簽，就成了自己證明自己；發證站被入侵可把下限設到最大，鎖死節點。
2. **第二位管理員怎麼拿到目前的網路密碼與成員名單。** 陷阱：經 provd 傳就是明文經過面對藍牙的程式；被撤銷的管理員可從還沒收到撤銷清單的節點讀到新密碼。
3. **家長手機遺失後怎麼接回節點。** 陷阱：用機身 QR 導出的金鑰永遠不能換；608B 之後機身 QR 重燒也不失效，等於永久的秘密。
4. **新密碼怎麼送到每一台，包括關機的。** 陷阱：經 mesh 轉送可能把多跳網路切成兩半（新舊密碼並存未驗證）；只靠管理員手機逐台送，比今天每人同時處理自己那台還慢。
5. **兩位管理員同時改怎麼收斂。** 陷阱：只比版本號與雜湊，可能悄悄把「移除遺失節點」這個動作蓋掉；版本號可被推到最大值。
6. **換掉信任錨之後既有網路怎麼辦。** 陷阱：把單位 id 定成信任錨金鑰的雜湊。
7. **哪些動作要使用者在場確認。** 陷阱：每次使用金鑰都驗證 = 8 台換密碼要按 16 次。
8. **誰能做軟體更新。** 陷阱：歸到等同 root 的權限，就變成每次更新都要根金鑰儀式，或現場手機上常駐一張等同 root 的憑證。
9. **發證站在解鎖狀態下就是活的簽章工具。** 操作員的登入狀態、主機上的自動化程式、從備份還原，都能發出現場有效的憑證。
10. **隊員怎麼找到自己那台、拿到它的手機 Wi-Fi 設定**，而不依賴出勤當下連得到發證站。
11. **社團（只有網路權的外部授權者）**能發什麼、不能發什麼。
12. **新舊兩種授權方式不能同時管同一台節點**：從第一個用新模型的版本到最後一個用舊模型的版本之間，每台節點只能由其中一種管。現在沒有對外部署，處理成本最低（審查 v1-B B3、威脅模型 §8.1-30）。
13. **現場沒有發證站時的運作**：現場用的憑證要有明確的上限（能做什麼、多久），發證站離線多天時現場仍能運作（威脅模型 R30、R31）。

各期的平台狀態：第 1 期 = 沒有 secure boot、有晶片；之後有一段只完成其中一部分的混合期；全部完成後才是出貨狀態。每期設計要說明它在當時的平台狀態下能宣稱滿足哪些需求。
