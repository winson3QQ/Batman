### 4.2 `BleGate`

- 整個 app 只建立一個 `FlutterReactiveBle`，包在 `BleGate` 裡；F23 的四處改成拿 `BleGate`（各頁面現有的 `ble` 注入參數，F17）。

- 每個掃描 / 連線要求都帶一個由佔用登記表發的憑證；憑證不是目前有效的那一個 → 拒絕。

### 4.3 `NodeLink`

#### 4.3.1 每台節點的狀態

| 狀態 | 意思 | 畫面 |
|---|---|---|
| `unread` | 這次開 app 還沒讀到 | 有 `ui/state-v1` 的舊資料：unk +「上次讀取 HH:MM，當時…」；沒有：unk +「還沒讀到狀態」 |
| `reading` | 正在登入或讀取 | 保留上一個畫面 + 小的進行中記號；從來沒讀過 → busy |
| `read(view, readAt)` | 讀到了 | 未滿 180 s：照 `view` 的顏色。滿 180 s：unk +「上次讀取…」 |
| `unreachable(reason)` | 連不到，原因見 §4.3.4 | warn + 原因 + 下一步 |

另外兩個記號（記憶體）：`expectOffline(until)`（只有軟體更新 controller 在「套用」送出時設，`until` = 當時 + 6 分鐘；畫面是 busy「節點正在重開，預計 HH:MM 前回來」；讀到一次就清掉；過了 `until` 回到一般規則）與 `swPending`（§4.8）。

180 s 的來源：一輪失敗一次仍然不變色所需的時間（60 + 30 + 60 + 約 25 s）。

#### 4.3.2 什麼時候讀一輪（T12）

只有同時成立才會自動開始：首頁或全隊頁是最上層的頁面、app 在前景（`resumed`）、沒有佔用。觸發點：

- 啟動檢查通過；
- 成為最上層 / 回到前景，且上一輪結束已滿 60 s（未滿就排到滿的時候）；
- 上一輪結束後 60 s；第一次找不到某台時 10 s（T14）；
- 藍牙從關閉變成打開；
- 使用者按重新整理（不看 60 s，但受掃描次數上限管）。

背景不讀。佔用釋放後，被那個操作動到的節點立刻排一輪。

#### 4.3.3 一輪怎麼讀

1. 先看前提：藍牙開著（`statusStream`）、有權限（**只檢查，不彈系統對話框**；F28 的 `blePermissions` 只在使用者按 2.2 的按鈕時呼叫）、金鑰可用。不成立 → 每台都是 `unreachable(該原因)`，不掃描。
2. 開**一次**掃描（服務 UUID、lowLatency）。自動輪的掃描窗 30 s（A9 ⚠️；量出來不夠就用 60 s），整輪上限 90 s。使用者自己在節點頁按的登入維持現況的 60 s。
3. 掃描持續的同時，對候選一個一個試（現有 `_tryLogin`）：登入成功 → 知道它是哪一台 → `requestStatusPage` → 記下結果 → **斷線** → 下一個候選。每台的結果一出來就更新畫面，不等整輪。
4. 候選備忘（記憶體）：這次開 app 以來，BLE 位址 → 「是我的節點 Y」或「不是我的」。「不是我的」只在握手得到**明確的驗證失敗**時記（逾時、連線失敗不記；A17 ⚠️ 兩者分不出來時就都不記）。之後的輪先試記為 Y 的、跳過記為「不是我的」。位址換了（RPA，N7）備忘自然失效。備忘只影響順序與要不要試，**身分仍然只由登入的金鑰驗證決定**（A2）；不存檔。
5. 這輪結束時還沒讀到的節點：照 §4.3.4。
6. 取消：使用者開始任何操作（要求佔用、打開節點頁）或 app 進背景 → 立刻停掃描；握手中的連線直接放掉；狀態請求已經送出的最多等 15 s 的回答再斷線。沒讀到的節點維持原狀態。
7. 自動輪收到任何「要寫紀錄」「要問使用者」的步驟（§4.5）→ 放棄那一台、斷線、什麼都不寫。讀狀態不該出現這些步驟；出現就是程式錯，記進文字紀錄。
8. 網路名稱表：`_netNames`（F10）不再每次讀狀態都解開所有網路紀錄。改成啟動時與每次佔用釋放後各算一次，只留「網路代號 → 名稱」在記憶體，解開的內容立即丟掉。紀錄只有在佔用下才會被寫（§4.4），所以這兩個時間點足夠。

握手次數（對 N4 的 20 次 / 分）：每一輪對每個 BLE 位址最多握手一次，兩輪至少隔 10 s、平常隔 60 s 以上。有備忘時，一支手機對一台不是自己的節點每個 RPA 週期（約 900 s）一次；備忘不能用時每輪一次，也就是每支手機每分鐘約一次。

#### 4.3.4 什麼時候說「連不到」（T14）

| 情況 | 處理 |
|---|---|
| 藍牙關閉、沒有權限、手機金鑰不可用 | 立刻 `unreachable`，對應 2.3 / 2.2 / 2.4 |
| 登入被拒（握手明確驗證失敗，對象是備忘記為這台的位址，或節點回登入錯誤） | 立刻 `unreachable(登入被拒)`；下一步 = 技術資訊、找維修人員 |
| 掃描窗內沒找到，或登入 / 讀取途中連線斷了 | 有上一次的 `read`：**維持原畫面**（會隨 180 s 規則變成 unk），10 s 後提前再讀一輪；連續第二輪還是這樣 → `unreachable(找不到)`。從來沒讀到過：第一輪就 `unreachable(找不到)` |
| 節點回 E_RATE（`fresh == false`） | 不算失敗也不算讀到：狀態與 `readAt` 都不動（F10） |
| 節點在沒有請求進行時主動斷線（閒置逾時 N2） | 不是失敗，畫面不變（§4.3.5） |

`unreachable(找不到)` 的文字：「手機連不到節點 X：可能沒開機、離太遠，或另一支手機正在連它」。它與「節點沒有連上隊伍網路」（讀到了，但狀態是紅）是兩件事，用語與樣式分開（5.4 對 5.2）。

同一條規則也用在重新整理與節點頁的重讀。F22 仍然是 ❓：本設計不解釋它、不宣稱修好；PR 1 的真機量測 M-1 先做歸因用的翻轉測試（§9.3）。

#### 4.3.5 節點頁上的連線

使用者停在某台的節點頁、app 在前景時，`NodeLink` 對那一台**保持連線**（接下來的操作不必每次重新登入 11 s）：

- 進頁面：登入 + 讀狀態；每 60 s 重讀一次。節點如果已經把連線關了（N2），重讀時自己重新登入；這不是失敗。
- app 進背景且沒有請求在進行 → 斷線；回前景 → 登入 + 讀。
- 離開節點頁 → 斷線（等斷線完成才開始下一輪）。
- 從節點頁開始的流程（佔用）直接接手這條 session，不重新登入。

代價（寫明）：使用者停在節點頁的期間，那台節點不廣播（N1），別的手機找不到它；首頁顯示多台時，別台只在使用者回首頁後才更新。

#### 4.3.6 這個做法的成本

- 每一輪每台約 11 s 的連線（F22）；兩台 → 每 80 多秒裡約 22 s 手機是連著的。這 11 s 內該節點不廣播。
- 附近有別人的節點時（廣播沒有身分，N7）：第一輪會對每個陌生位址握手一次才知道不是自己的，之後靠備忘跳過。每次陌生握手的時間未量（A11 ⚠️）；一輪上限 90 s，沒輪到的節點下一輪接著試，備忘保證每輪都有進展。
- 每輪會用擁有者金鑰簽一次登入、解開一筆節點紀錄（§8）。
- 一台節點平常只有認領它的那支手機會登入（A14 ⚠️）；會互相擋的情況 = 同一支手機的 dev 與 dev2、或維修時兩支手機同時操作。

### 4.4 佔用（一次只有一個操作能用藍牙與寫紀錄）

| 項目 | 規則 |
|---|---|
| 兩種 | **session 佔用**：流程 controller 用 `NodeLink` 的 session 做事。**原始佔用**：頁面有自己的藍牙程式（`ClaimPage` 與它裡面的 `ClaimRecovery`、`ScanPage`、舊版控制台；從舊版控制台打開的軟體更新頁算在控制台的佔用裡），拿到的是 `BleGate` 的使用權 |
| 誰要先拿 | 任何會用藍牙的操作，以及**任何會寫金鑰紀錄的操作，包含不連線的**（收下邀請、匯入同意碼、忘記節點、產生更新包） |
| 一次一個 | 第二個要求被拒絕，畫面顯示「另一個操作還在進行：<名稱>」（§3.2）。不排隊、不默默 return |
| 拿到之前 | 取消進行中的自動輪（§4.3.3-6）並等斷線完成；最長約 15 s，期間畫面顯示「正在結束上一個讀取…」 |
| 佔用期間 | 不開始自動輪；前景 / 背景事件不影響它（流程照自己的逾時走完）；需要時可以重新登入，包含在背景；有超過 30 s 的等待時保持螢幕開啟 |
| controller 放哪裡 | 佔用登記表持有 controller 物件，不是頁面。頁面被關掉或重建，寫紀錄的步驟照樣做完 |
| 釋放 | 流程結束（成功、失敗、使用者取消且沒有請求在進行）時釋放；先等斷線完成。佔用者被銷毀而沒有釋放（頁面被系統回收、例外）→ 登記表在它的 `dispose` 或下一次要求時收回 |
| 釋放之後 | 重算網路名稱表與待辦（§5.1）；被動到的節點立刻排一輪 |

### 4.5 session 步驟的契約（F24 的每一種）

| 步驟 | 誰做 | 沒有對象 / 失敗時 |
|---|---|---|
| Write、Sign、SignAdmin | `NodeLink` 的 run loop（現有程式搬過來） | 現有錯誤路徑 |
| PersistNet / PersistPend / PersistMnet | `NodeLink` 經「紀錄寫入包裝」（seal + `storeWriteCas`，順序不變）。包裝檢查目前有佔用，寫入者 = 佔用者 | 沒有佔用 → 拒絕、該請求以錯誤結束、什麼都不寫（§4.3.3-7） |
| ConfirmCountry | 佔用者登記的回應函式開對話框；使用者想的時間不算進逾時（現況） | 沒有登記、或頁面已經不在 → 回答「不要」（fail-closed） |
| ConfirmRemoved | 現況：請求以一個回答結束，controller 問使用者、再重新開始加入 | 頁面不在 → 流程停在這裡；下次從待辦「加入沒有做完」進來重新問 |
| Wait | run loop 的計時器（值不變） | — |
| LoggedIn、Answer、Ended | 交給送出請求的人（controller 或 `NodeLink` 自己） | 送出的人已經不在 → 結果記進文字紀錄；下一輪讀狀態會反映實際情況 |

不經 session 的離線操作（nodes.dart:741-750、:1359-1368）用同一個紀錄寫入包裝，所以同樣要有佔用。

### 4.6 `ui/state-v1` 契約

| 項目 | 內容 |
|---|---|
| 寫入者 / 讀取者 | 只有 `UiState` 寫；頁面經 `UiState` 讀 |
| 位置與格式 | 紀錄庫 `ui/state-v1`（符合 F7 的路徑規則），用現有 `storeSealParams` / `storeWriteCas`；內文是 CBOR map |
| 欄位（白名單，測試鎖住） | 1 版本（= 1）；2 看過歡迎頁；3 看過首頁提示；4 節點表 `{device_id → {1 暱稱（≤ 24 字）, 2 上次狀態種類（ok / warn / bad / unk 四選一）, 3 上次狀態一句話（Rust 的句子，≤ 64 字）, 4 讀取時間（UTC 秒）}}`。**沒有**別的欄位：沒有位址、沒有勾選、沒有「上次打開的節點」 |
| 什麼時候寫 | 旗標或暱稱改變時；一輪結束時**只有**某台的狀態種類或句子變了才寫；app 進背景時如果讀取時間比檔案裡的新，寫一次。整筆替換（CAS，generation +1） |
| 不存在 | 全部用預設值。**手機已有節點紀錄時不顯示歡迎頁**（舊使用者升級） |
| 檔頭壞（`NotARecord` / `UnknownVersion`，例：檔案長度 0） | 當成不存在；下一次寫入前先 `storeRemove` 再寫（F39：這兩種情況直接寫會被拒絕） |
| 檔頭正常但解不開 / 內文壞 / 內文版本不是 1 | 當成不存在；下一次寫入用讀到的 generation 做 CAS 覆蓋 |
| fail-open 的理由 | 內容只影響顯示；**沒有任何決定讀它**（不決定連哪一台、不決定能不能做什麼、不決定金鑰）。測試鎖住：`UiState` 的值只流向顯示用的 widget |
| 舊資料 | 只用 unk 樣式顯示（T2）；讀取時間在未來 → 只寫「之前讀過」，不寫時間 |
| 節點紀錄被忘記 | `UiState` 載入時刪掉節點表裡已經沒有對應 `node/<id>` 的項目 |
| 信任邊界 | app 私有目錄；備份關閉（F9）；能寫這個檔的人已經能寫所有紀錄 |
| 不能放的東西 | 任何金鑰、密碼、邀請 / 申請 / 同意碼、QR 內容、節點傳來的原始字串。T-U6 以白名單與搜尋假秘密兩種方式檢查 |

`ui` **不加進** `RECORD_KINDS`（F8）：金鑰能否重新產生的判斷不該被一筆顯示用的紀錄影響。後果：只剩 `ui/` 的手機（其他紀錄與安裝記號都沒了）→ `firstRun` 重新產生金鑰（F34）→ 舊的 `ui/state-v1` 解不開 → 當成不存在 → 歡迎頁再出現一次。這是預期行為。

### 4.7 流程 controller

每條流程一個 controller：持有步驟狀態，拿佔用，經 `NodeLink` 送請求。現有函式整段搬移：

| 流程 | 現有程式 | 佔用 | 畫板 |
|---|---|---|---|
| 新增節點 | `ClaimPage`、`ClaimRecords`、`ClaimRecovery` | 原始 | 3.1–3.7 |
| 建立 / 加入 / 檢查網路 | `_makeNetwork`、`_joinNetwork`、`_confirmNetwork`、連線檢查 | session | 4.1–4.5 |
| 邀請（隊長） | `_makeInvite`、`_checkRequest`、`SasConfirmView` | session（產生邀請、收申請不連線，也要佔用） | 7.1、7.3–7.7 |

**搬移規則**：紀錄的寫入順序、簽章步驟、gate、逾時值一個都不改；每搬一條流程，該流程現有的測試檔必須不改判定就通過（只改建構方式與 §3.4 的字串）。

### 4.8 軟體更新

- 佔用只在「更新頁開著」或「有請求 / 上傳在進行」時持有；進行中不能離開頁面（現況的 PopScope）。
- 更新做到一半（已準備、還沒套用）而頁面關了：`SwHold` 留在 controller（記憶體，現況也是記憶體）。這台節點標 `swPending`：**自動輪跳過它**，首頁該列是 busy「軟體更新還沒做完」，待辦多一項，點進去回到更新頁。跳過的理由：對一台已準備更新的節點重新登入會不會影響那次更新，未驗證（A13 ⚠️，PR 4 上機量；量出來沒有影響就拿掉跳過）。
- 「套用」送出時設 `expectOffline`（§4.3.1）。
- 舊版控制台裡的軟體更新不變：`SwHold` 是控制台頁面的欄位，控制台在堆疊上的整段時間都是它的佔用，關掉控制台時 `SwHold` 跟著消失（F27）。

### 5.3 新增節點（3.1–3.7）

- 整條流程是一個原始佔用（§4.4）；`ClaimPage` 與 `ClaimRecovery` 改用 `BleGate`，其餘邏輯不變。

### 5.7 邀請、加入、成員、移除（7.x、8.x）

- 三段式不變：邀請碼 → 申請碼 → 同意碼。確認碼核對畫面保留現有設計（大數字、單一按鈕、提醒不要在傳碼的同一個聊天核對）。
- 每一段的碼用 `CodeView`：QR +「複製文字」。QR 內容 = 現有 16 進位文字轉大寫（`from_hex` 接受大寫，F36），點陣由 Kotlin 用 ZXing 產生。同意碼 2082 個字元是三者最大；S20 掃不掃得到在 PR 5 開始前先量（A4 ⚠️），掃不到的那一種只留「複製文字」。
- 收的一方：「掃描 QR」（現有 `scanQr`）+「貼上文字」。貼上後立刻清剪貼簿（現況對邀請已如此，F31）。
- 複製之後：按鈕旁出現「清除剪貼簿」，離開這一頁時再提醒一次。app 不自動清（使用者可能還沒貼到通訊軟體）。
- 隊員名稱必填，上限 32 個 UTF-8 位元組（F37）：輸入時顯示「還可以輸入 N 個位元組（約 M 個中文字）」，超過就不能送出；10 個中文字可以、11 個不行。暱稱（1–24 字，只在手機）是另一個欄位，兩處的說明文字不同。
- 選網路時同名的網路後面加建立日期與網路代號後四碼。
- 移除成員（8.3 → 8.4）：
  1. 8.3 的前置條件勾選「全隊的節點都已更新到新版軟體」**文字不改、位置在按下移除之前**（F32；沒勾 Rust 拒絕）。
  2. 確認只一次，按鈕寫後果。
  3. 之後進 8.4：每位留下的隊員一列，「複製更新包」與一個勾（已交出）。勾選只在記憶體（T15）、每個網路一份，新的一次移除成功或 app 被關掉就清空；**不參與任何判斷**，沒勾完也能離開。頁面寫「這些勾只是幫你記，app 不知道對方換好了沒」。
  4. 回到成員頁時，如果這次開 app 做過移除而且還有沒勾的，成員頁頂端顯示「還有 N 位隊員沒交更新包」。
- 「放棄這次加入」（現況的忘記加入中的成員，隊長端）在開發者選項；隊員自己的「放棄申請」在 7.9。
- 這一整區只在 devTrust 版本顯示（F14）；本單不改 gate。

## 8. 安全

**資產**：擁有者 / 管理者金鑰（Keystore）、節點紀錄裡的 K 與 root 密碼、認領 QR 的秘密、手機 Wi-Fi 密碼、邀請 / 申請 / 同意碼、更新包、確認碼。

**逐個角色**：

| 角色 | 本設計新增或改變的面 | 處理 |
|---|---|---|
| 附近的攻擊者（藍牙） | app 在前景時每 60 s 自動掃描並嘗試登入，次數比現況多很多；假節點可以廣播同一個服務 UUID 引來連線、拖時間 | 登入是現有的雙向驗證（A2），假節點拿不到 session、不能讓任何節點變成「讀到」。拖時間：每個位址每輪只試一次、整輪上限 90 s、明確驗證失敗的位址記為「不是我的」之後跳過；假節點能做到的最壞情況 = 讓真節點晚幾輪才讀到（畫面是不明，不是假的綠燈）。候選備忘只影響順序，不存檔 |
| 附近的攻擊者（看廣播） | 手機每分鐘連線一次，使用 app 的規律比現況容易被觀察 | 接受：節點廣播本來就看得到；手機用隨機位址。寫明不處理 |
| 別人的節點（我們自己造成的負擔） | 自動輪會對不是自己的節點握手，消耗對方每分鐘 20 次的配額（N4） | §4.3.3 的握手次數規則；T-L11 鎖住「每個位址每輪最多一次」 |
| 同一支手機上的其他 app | 新檔案 `ui/state-v1`；剪貼簿 | 檔案在 app 私有目錄、加密、不放秘密（§4.6）。剪貼簿：能用 QR 的地方不必用；貼上後清除；複製後提供「清除剪貼簿」（現況複製後不清，F31） |

| 拿到已解鎖手機的人 | 首頁直接顯示節點狀態；自動登入 | 能做的事與現況相同（現況點一下就登入）。金鑰用途的 gate 不變 |
| 拿到手機的人（鎖著） | — | 不變。金鑰沒有綁使用者驗證（F40）是現況，不在本單 |

| 供應鏈 | QR 點陣產生 | 用已經在依賴裡的 ZXing core（F36），不新增套件；A16 |
| 我們自己的錯 | 舊綠燈誤導；搬移流程時改到寫入順序；兩個地方同時寫紀錄 | T2 + 180 s；§4.7 的搬移規則 + 既有測試不改判定；§4.4 佔用 + 紀錄寫入包裝 |

**自動登入的代價（寫明）**：前景時每 60 s、每台節點：解開一筆節點紀錄（`RECORD_AES`）+ 用擁有者金鑰簽一次登入。現況是使用者點節點時才做。金鑰沒有綁使用者驗證（F40），所以這不需要使用者在場；也就是說「app 在前景」就等於持續使用金鑰。網路紀錄（含網路密碼）不在每輪解開（§4.3.3-8）。背景不做。

**攻擊面變化**：新的使用者輸入 = 暱稱（長度與字元限制）、隊員名稱（已有 `check_name`，畫面加位元組計數）、Wi-Fi 名稱與密碼（新增長度檢查，節點端檢查不變）、掃進來的 QR 文字（進現有的 `from_hex` 與各自的解析，與貼上是同一條路）。Kotlin 新增兩個 method：只檢查權限（不帶資料）、文字轉 QR 點陣（輸入是 app 自己產生的 16 進位文字，長度上限 4096 個字元，超過回錯誤）。沒有新的埠、intent、深層連結、網路請求。

**權限**：不新增 Android 權限。

**秘密**：不進文字紀錄、不進 `ui/state-v1`、不進截圖。文字紀錄只在記憶體；`BMAPP` logcat 行原樣（F38，既有檢查照跑）。

**失敗模式**：連線、登入、金鑰 gate、ConfirmCountry 沒有對象、沒有佔用的紀錄寫入，全部 fail-closed。唯一 fail-open 的是 `ui/state-v1`（§4.6，理由已寫）。

**負向測試**：T-S1–T-S4（§9）。
