# Design: payload config golden — bake the tenant's declarative config into the image, refresh p6 on every boot

## Problem (observed on manet01, 1.4.9, this session)

A reflash + reboot of manet01 left OTS coming up under the **wrong container restart policy**:
the p6 manifest `/opt/batdata/apps/opentakserver/ots.manifest` still says `RESTART on-failure:5`,
while the repo (`deploy/ots/ots.manifest`, regenerated by #206) says `RESTART unless-stopped`.

Root cause is architectural, not a code bug:

- The payload tenant's config (manifest / fw4.uci / hardening.env / net.alloc / verify / reconcile /
  guardian init) lives **only on persistent p6**, hand-installed once (`deploy/ots/README.md`: "copy
  this dir to /opt/batdata/apps/opentakserver/"). It is **not baked into the image** and **not
  refreshed from any version-controlled source**.
- #192 (`95-batman-storage` → `batdata-mount`) restores only the **guardian init** from p6 on every
  boot. It never refreshes the rest of the tenant config, and there is no image-side source to refresh
  *from*.

Consequence: the p6 config is a floating, un-versioned artifact. It drifts (as it has), and a fix
applied live (`docker` recreate, hand-edit of the manifest) is not reproducible — a fresh operator, a
new node, or a doubt about "what policy is actually deployed" has no source of truth. This is exactly
the "patch it live, it comes back next reboot/upgrade" failure the fix must end.

Note: the guardian (#206) *does* auto-recover OTS after a reboot (measured ~49 s, unattended, even
under on-failure:5). So this is **not** a service-availability bug. It is a **provenance / drift /
reproducibility** bug: the deployed config is not sourced from the image, so it cannot be trusted to
be correct after a reflash, and correcting it by hand does not stick as a versioned fact.

## Goal

One baked FW such that manet01/02, reflashed A/B repeatedly with zero manual/AI intervention, always
converge to the **image's** canonical tenant config (incl. `unless-stopped`), and full daily-validation
is green every cycle. No live patch that a reflash/reboot can undo.

## Non-goals

- Baking the ~3.3 GB docker images into the FW (that is #159 fleet mass-provisioning; images stay
  p6-resident). This design carries only the small **declarative config**.
- Auto-installing OTS onto a node that is not already an OTS node (must not turn manet02 into an OTS
  node). See the gate.
- Baking secrets (postgres password, TAK certs) into the image.

## Design

### 1. Bake the tenant's declarative config into the image (golden defaults)

Ship `deploy/ots/`'s **declarative, non-secret** files into the rootfs at a read-only golden path:

```
/usr/share/batman/payload-golden/opentakserver/
    ots.manifest            # RESTART unless-stopped (source of truth)
    ots.fw4.uci
    ots.net.alloc
    ots-db.hardening.env  ots.hardening.env  rabbitmq.hardening.env
    rabbitmq-extra.conf
    verify-profile-ots.sh
    reconcile-resources.sh
    batman-payload-opentakserver.init
```

Excluded (dev/build artifacts, or secret): `Dockerfile`, `build-arm64.sh`, `footprint-spike.sh`,
`run.sh` (a shim), `profile.yaml` (the source the manifest is generated from), and any `secrets/`.

This is carried by the **`batman-payload-host`** package (already board-gated to bcm2711 / the
payloadhost variant, session-18) — so the plain mesh image never ships it, and only OTS-capable boards
even have the golden.

**[REVIEW B1 — single source, no committed copy]** The golden must NOT be a hand-maintained second
copy of `deploy/ots/*` (that reintroduces the very drift this design kills, just moved from p6 to the
rootfs, and `check-payload-manifest.sh` / `payload-manifest-sync.yml` only watch `deploy/**` + `scripts/`,
never `feed/**`). Instead:
- `Package/batman-payload-host/install` copies the whitelisted files **at build time** straight from
  `$(CURDIR)/../../deploy/ots/` into `/usr/share/batman/payload-golden/opentakserver/`. No second copy
  is committed. This also makes the bytes identical to `deploy/ots` (kills the CRLF/emitter-churn
  MINOR m1 — cmp on-node converges).
- `scripts/check-payload-manifest.sh` + the workflow `paths:` are extended to assert, per baked tenant,
  that the golden set the package would install `cmp`-equals the corresponding `deploy/<profile>/*`
  outputs (`.init/.manifest/.net.alloc/.fw4.uci/*.hardening.env/verify-*/reconcile-*/rabbitmq-extra.conf`),
  so the two can never diverge in CI.

### 2. Refresh p6 from golden on every boot — REFRESH-EXISTING ONLY (the gate)

Extend the existing every-boot payload step in `batdata-mount` (installed by `95-batman-storage`,
runs at S11 after p6 is mounted, before dockerd). New function `refresh_payload_config()`, called
right before the existing `restore_payload_guardians()`:

```
for golden in /usr/share/batman/payload-golden/*/ ; do
    tenant=$(basename "$golden")
    dst=/opt/batdata/apps/$tenant
    # GATE [REVIEW B2]: refresh only an ALREADY-provisioned tenant = one that already has a manifest.
    #   `[ -d $dst ]` alone false-positives on an empty/half dir (stray mkdir, failed install) and would
    #   then pour the whole golden (incl. guardian .init) in -> restore_payload_guardians starts it ->
    #   no images -> crash-loop. Requiring an existing *.manifest blocks that.
    ls "$dst"/*.manifest >/dev/null 2>&1 || continue   # manet01 -> refreshed; manet02 / bare node -> skipped
    for f in "$golden"* ; do
        b=$(basename "$f")
        [ "$b" = secrets ] && continue          # never touch p6 secrets/
        cmp -s "$f" "$dst/$b" 2>/dev/null && continue   # idempotent: only write on change (#41 no-churn)
        # [REVIEW M1] cp -p keeps the golden's mode (+x on *.sh/.init preserved from the 0755 the package
        #   install sets); busybox chmod has NO --reference. [REVIEW R2 atomicity] &&/|| so a failed cp
        #   (e.g. disk full) never gets promoted to the live file as a truncated write.
        tmp="$dst/.$b.tmp.$$"
        if cp -p "$f" "$tmp" && mv -f "$tmp" "$dst/$b"; then
            note "payload config refreshed from golden: $tenant/$b"
        else
            rm -f "$tmp"; note "payload config refresh FAILED for $tenant/$b (kept old)"
        fi
    done
done
```

Properties:
- **Gate = `ls "$dst"/*.manifest`** — pure file test, no docker needed (fits S11). Only refreshes a
  tenant the node already runs (has a manifest). manet02 / bare nodes untouched; an empty/half dir does
  NOT trip it (review B2).
- **Preserves** p6-only state: `secrets/`, docker volumes (in docker root, not the tenant dir),
  runtime logs. Only the declarative files are overwritten, and only when they differ.
- **Atomic per file** (tmp + rename on the same fs), idempotent (cmp-gate), safe to run every boot.
- After refresh, the existing `restore_payload_guardians()` reinstalls the (now-refreshed) init.

### 3. unless-stopped takes effect

The refreshed manifest carries `RESTART unless-stopped`. Existing containers keep their old policy
until recreated; the #206 guardian recreates the stack via `payload-run` whenever any container is
down (which a reboot causes) → containers come back `unless-stopped`. So within the first post-reflash
reboot the live policy converges to the manifest. `unless-stopped` then means docker itself restarts
them across future reboots (belt), with the guardian as suspenders.

### 4. daily-validation regression (new suite, tier A, non-destructive)

`payload-config-golden`: for every baked golden tenant that is provisioned on the node
(`ls /opt/batdata/apps/<t>/*.manifest`), assert — generically, iterating tenants, not hard-coding
`ots` (review m2):
1. the deployed p6 config `cmp`-equals the baked golden per file (guards against a refresh that
   silently failed to write, e.g. the M1 mode bug leaving a stale file);
2. **[REVIEW m2 — the real outcome, not the tautology]** every LIVE container of that tenant has
   `docker inspect -f '{{.HostConfig.RestartPolicy.Name}}'` == `unless-stopped`. The cmp in (1) is
   near-tautological right after the same boot's refresh; the live restart-policy check is what proves
   the policy actually converged (it depends on the post-dockerd guardian rebuild, README ~49 s, so
   this suite is tier A / scheduled — run well after boot, not in the boot window);
3. **[REVIEW M2 — manifest↔image coupling]** every `IMAGE` referenced by the deployed manifest is
   present (`docker image inspect`), so a manifest that got refreshed to reference an image not yet
   loaded on p6 surfaces as FAIL here rather than as a silent guardian crash-loop.

On a node with no provisioned tenant (manet02, bare node) the suite is a legitimate PASS (nothing to
check) — NOT a skip.

## Alternatives considered

1. **Hand-fix the p6 manifest to unless-stopped (live patch).** p6 persists across reflash, so it
   would actually survive — but it is exactly the un-versioned live patch the user rejected: no image
   provenance, invisible to a fresh node, silently driftable. Rejected.
2. **Bake config AND auto-install to every node (create $dst from golden unconditionally).** Turns
   manet02 into a broken OTS node (config present, images absent → guardian crash-loops). Rejected in
   favour of refresh-existing-only.
3. **Bake images too (#159 full mass-provisioning).** Solves fresh-node zero-touch but is a ~3.4 GB
   image and a much larger change; out of scope for "make 01/02 reflash-green". Deferred.
4. **A one-shot uci-default instead of every-boot.** A one-shot runs once per fresh slot's firstboot;
   an A/B reflash makes a fresh slot so it *would* re-run — but placing it in the every-boot
   `batdata-mount` (as #192 already does for the guardian) is strictly more robust (self-heals a boot
   where p6 mounted late) and co-located with the code it extends. Chosen.

## Failure modes

- **Golden present but $dst absent (manet02, fresh node):** gate skips. No tenant installed, no
  guardian, clean mesh node. ✓
- **Operator hand-edited the p6 manifest:** the refresh OVERWRITES it with golden on next boot. This
  is intended (golden = source of truth) but means live edits are transient — documented; the correct
  path to change config is the image, not p6. (Matches the user's explicit "no live patches" intent.)
- **secrets/ dir:** explicitly skipped; never overwritten or baked.
- **[REVIEW M3] inline credentials in the manifest** (`POSTGRES_PASSWORD=password`,
  `RABBITMQ_ERLANG_COOKIE=batman-ots-cookie`, the SQLAlchemy URLs): these are inline in the manifest,
  NOT in `secrets/`, so the refresh DOES overwrite them with the golden values every boot. That is a
  hazard iff an operator hand-changes credentials on p6: the persistent `ots-pgdata` volume was
  initialised with the OLD password, so a golden-reset to a different value breaks DB auth. Ruling:
  **credentials must be changed in the image (profile), never hand-edited on p6.** Verified consistent
  on the current fleet (manet01 p6 manifest and volume are both `password`). Externalising these to
  the SECRET/env-file mechanism is a follow-up (noted, not blocking — values are placeholders identical
  to what initialised the volume). The design doc's "never bake secrets" wording is corrected here:
  non-secret declarative config is baked; the inline DEFAULT credentials are baked too and are the same
  values that seeded the volume.
- **[REVIEW M2] manifest references an image not on p6** (a future version bumps an IMAGE tag without
  the image being loaded): the refresh installs the new manifest, `payload-run`'s `docker run` fails,
  guardian crash-loops. Mitigation: the daily-validation `payload-config-golden` suite asserts every
  referenced image is present, surfacing this as a caught FAIL. Rule: an image-tag change is a
  provisioning step (load the image on p6 first), NOT a zero-touch config refresh. Config-only version
  bumps are zero-touch; image-set changes are #159 territory.
- **p6 not mounted / mount late:** runs inside batdata-mount after the mount gate; if p6 is absent the
  gate `ls "$dst"/*.manifest` is false → no-op, fail-safe.
- **Partial write / power loss mid-refresh:** per-file `cp -p && mv || rm` — a failed/partial cp is
  removed and never promoted; a crash leaves either the old or the new file, never a truncated manifest.
- **LUKS tactical variant:** p6 is the LUKS-mapped data area once mounted; the refresh operates on the
  mounted path identically. No new LUKS interaction.
- **cmp/cp busybox availability:** both are in busybox on-node (cp supports `-p`); no `chmod
  --reference` is used. The golden's `*.sh`/`.init` must be installed 0755 by the package (INSTALL_BIN)
  so `cp -p` propagates +x — asserted at build/CI.

## Verdict (author)

SOUND, minimal, and aligned with the existing #192 restore mechanism. Turns the p6 tenant config from
a floating hand-installed artifact into an image-sourced, every-boot-reconciled fact, gated so it only
ever touches nodes that already run the tenant.

## Review outcome (adversarial review R1) + revisions applied

Verdict R1: **SOUND-WITH-CHANGES**. All must-fixes folded into this doc:
- **B1** (golden double-source drift) → §1: build-time copy from `deploy/ots` (no committed copy) +
  extend `check-payload-manifest.sh`/`payload-manifest-sync.yml` to `cmp` the baked golden ≡ deploy.
- **B2** (empty-dir false-positive → breaks manet02) → §2: gate is `ls "$dst"/*.manifest`, not `[ -d ]`.
- **M1** (busybox has no `chmod --reference`) → §2: `cp -p`.
- **M2** (manifest↔image desync) → §4 + failure modes: daily-validation asserts referenced images
  present; image-tag change is a provisioning step, not zero-touch.
- **M3** (inline credentials overwritten) → failure modes: ruling + consistency check + wording fix.
- **m1** (CRLF churn) → solved by B1 build-copy (bit-identical). **m2** (tautological check / timing) →
  §4: live restart-policy check + per-tenant, tier A run after boot window.

**Scope boundary confirmed by review + user Q:** this design makes an *already-provisioned* OTS node
(manet01, or a manet04 provisioned once like manet01) converge to the image's config on every
reflash/reboot, zero-touch. It does NOT auto-install OTS on a bare node (keeps manet02 clean); truly
flash-and-go fresh OTS (ship the ~3.3 GB images in the card) is #159 and out of scope here.
