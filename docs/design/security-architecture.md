**這份文件定什麼**：現在不定、之後就得重做的東西。也就是：系統有哪幾種信任根、每把金鑰放哪、身分與授權怎麼分開、每個平台狀態能宣稱什麼、v2.0 不能弄壞哪些已出貨的保護、新舊授權模型之間怎麼切換。

**不寫程式、不改節點。** 審查等級 L3。標記：✅ 對過原始碼或文件；⚠️ 推論或未驗證；❓ 未知。
基準：main dfac71f，加上設計分支 `design/255-key-authority` e9a2ccb（PR #431；PR #379 是 `Identity` 介面的程式碼）。

## 2. 五個信任根，互不替代

| # | 信任根 | 回答的問題 | 誰持有 | 簽什麼 | 不能做什麼 |
|---|---|---|---|---|---|
| T1 | **原廠根**（bench 用開發根） | 這是不是我們做的節點、金鑰是不是在晶片裡 | 我們。開發根只在開發者電腦，只簽 bench 晶片 | 節點憑證（§4.1） | 不能管理任何已入庫的節點、不能加入任何網路（K22） |
| T2 | **單位信任錨** | 誰能管這台節點、這個網路 | 今天：擁有者手機的金鑰（✅ `provstore.go:6`）。之後：家庭仍是家長手機，小隊是機關的離線根（U1、D1、D6） | 管理動作的授權 | 不能偽造節點身分 |
| T3 | **TAK CA** | 這支手機能不能連 TAK server | 小隊：ICS 發證站。家庭：節點上的 OTS | TAK server 與 client 憑證 | 不能授權任何 Batman 管理動作（D5） |
| T4 | **發行根 R** | 這個映像是不是我們發的 | 我們，離線 | 背書簽章金鑰 K；K 簽發行物件（✅ `release/release.go:1-4`） | 不能讓節點安裝更新（還要 T2 的授權，§5 I-6） |

- **開發與量產的根分開**。開發根、測試根 T（✅ `release.go:2`）只存在於開發建置，量產建置不含它們的公鑰。bench 608B 的憑證只由開發根簽，所以量產版 app 不接受它（✅ `255-608b-impl.md` §3.2 `trust_gate`）。**這只是 app 端的檢查**：mesh 第一層只看密碼，知道密碼的 bench 節點在無線層一樣連得上（§7 的界線）。
- 發行根的公鑰只從映像的唯讀 rootfs 讀（✅ `release/release.go:110-111`），執行期放一個檔案加不了根。
- **節點目前不驗其他節點的憑證**，映像裡也沒有根公鑰（✅ `255-608b-config.md` §2）。v1 寫「量產節點拒絕開發根的憑證」沒有依據，已拿掉。節點之間要不要互驗、公鑰從哪來，是 #16 的題目（§10 O-16）。
- 開機映像簽章金鑰（#405）和 K 是不同的金鑰。它的公鑰雜湊燒進 OTP；燒了之後能不能換，見 V4。

## 4. 身分與授權分開

### 4.1 節點憑證只說「這是哪一台」

| 欄位 | 內容 |
|---|---|
| 簽發者 | T1。驗證者用**內建的根公鑰**判斷，不看簽發者名稱的文字 |
| 主體與主體金鑰 | 節點 id = SHA-256(N1 公鑰) 前 9 位元組；N1 公鑰 |
| 擴充 | N2 公鑰、N3 公鑰、晶片序號 |
| 有效期間 | 固定值，沒有人檢查（D4） |
| **永遠不放** | 角色、單位、網路、擁有者、任何會變的東西 |

- 格式與大小（≤ 416 位元組）已在 `255-608b-impl.md` §3.1 定案，本文件不改。**#255 的 PR 3 不用等本文件。**
- 量產憑證用同一組欄位、由原廠根簽。放不放得進量產晶片取決於 #426（V2）；放不下時另找地方放，憑證是公開資料，只影響「換卡後還在不在」。
- 理由：憑證寫進晶片後不能改；而且 T1（我們）不該有權決定誰管誰（K22）。

### 4.2 授權永遠來自 T2，寫在另外簽的物件裡

- 今天：擁有者金鑰清單與管理員金鑰清單存在節點的紀錄裡（✅ `provstore.go:6-8`），管理動作由擁有者當場簽（§5 I-1）。
- 之後（信任模型）：改成 T2 之下簽發的授權物件（D1–D3）。**它的欄位、排序、撤銷都還沒設計**（§10）。本文件只定三件事，讓之後加得進去而不用重做 v2.0：
  1. 節點憑證不帶授權（§4.1），所以新模型不用重燒晶片。
  2. 節點上的授權紀錄有版本欄（✅ `prov.cbor` 鍵 1 `v=1`），新模型用新的版本值，切換照 §6。
  3. 所有判斷都在 helper 的同一個地方做（✅ `node.go:770-787` 的動詞表），之後換模型只換這一處（K12）。

### 4.3 節點自己簽的東西

N2 只簽 helper 自己組的「固定用途標籤 ‖ 資料」，用途是寫死的清單（✅ `keystore.go:78-98`；`255-608b-impl.md` §2.1 目前只有 `Session` 一種）。之後要加用途（#16 的 WireGuard、#97 的狀態證明）就是在這張清單加一項，各自過 L3；本文件不預先定義它們。S-A、S-B 這張清單只靠 helper 把關，持有節點的人可以繞過（威脅模型 S5）。

## 6. 紀錄格式與模型切換：之後的設計必須滿足的條件

**v2.0 不做任何轉換，v2.0 的單也不改節點紀錄的鍵集合。** 核對過：#255 的設計與 §8 重置表的兩個新動作都不需要新的鍵。#255 把檔案身分換成晶片身分時節點 id 會變，等於一台新節點，重新入庫（`255-608b-impl.md` §7），不是轉換。信任模型來的時候才會有「舊模型紀錄 → 新模型紀錄」，那個動作在當時設計並過 L3。這一節只定它**必須滿足的條件**，以及 v2.0 現在就要守的兩條格式規則。前幾輪審查提過三次（§5-12）；v2 把它寫成具體動作，結果和程式不符，所以改成條件。

**v2.0 現在就要守的**
- F1：**節點紀錄的鍵集合一有變動，就換版本號**，`prov.cbor` 的鍵 1 與 `prov.meta` 的 `v=` 一起換。理由：舊映像的解析是嚴格的（✅ `provstore.go:112-131`）；在同一個版本號下加鍵，另一槽的舊映像會把它當成「損毀」而不是「太新」，走到另一條處理路徑（✅ `boot.go:236-271`）。**換版本號本身就是「另一個槽讀不懂的紀錄」**（鍵 12 當年是在 `v=1` 下加的，是不該再有的前例），所以 v2.0 的單如果真的非改鍵不可，第一次寫入新版本就要符合下面的條件 2–4 與 7，並在那張單過 L3。
- F2：**嚴格解析的格式（節點紀錄、發行物件 ✅ `release.go:162, 262-263`）要加新意義時，用新的版本或新的內容類型，不在舊格式裡加鍵。**

**之後設計轉換時必須滿足的**
1. 一台節點在任何時刻只由一種模型管；helper 不同時接受兩種模型的授權。
2. 新版映像不在開機時自動改寫紀錄；轉換是舊模型最高權限的人當場簽的明確動作。
3. 轉換在新版 commit 之後才允許，本身是交易（I-4）。
4. **只有在另一個槽的映像也讀得懂新紀錄時才允許轉換。** 理由：轉換後如果自動退回讀不懂的舊槽（#401 的觀察期會在沒有人在場時做這件事），舊映像只凍結會改狀態的動詞（I-10），`update.*`、`diag.bundle`、`bulk.*` 會改看它自己 overlay 裡**轉換前的舊名單**（✅ `node.go:796-797`、`wtxn.go:262-273`）。已被移除的擁有者就又能授權更新（違反 K13）。另一槽讀得懂哪個版本，helper 今天沒有現成的方法知道；映像裡放一行「我讀得懂的最高紀錄版本」即可，由實作轉換的單加。這一行要從已寫入另一槽的映像本身讀，**不放在發行物件裡**（發行物件是嚴格解析的，F2）。
5. 已收回的權力不能因為升級或退回而復活（K13）：轉換時不把已被移除的人帶進新紀錄。
6. 同一個網路裡新舊模型的節點並存時怎麼管，要在那次設計裡回答（§10 O-20）。
7. **紀錄換成新版本之後，helper 拒絕安裝讀不懂目前紀錄版本的映像**（更新與允許的降版都一樣）。條件 4 只在轉換當下檢查；加上這一條，自動退回才真的不會遇到讀不懂的紀錄。

負向測試（實作轉換的那張單）：新版開機後未轉換就退回 → 仍可管理；另一槽讀不懂新紀錄時要求轉換 → 拒絕；被移除的擁有者在轉換後、退回後都不能授權 `update.apply`；同時送兩種模型的授權 → 只收紀錄版本對應的那一種；紀錄已是新版本時安裝讀不懂它的映像 → 拒絕。v2.0 的回歸：v2.0 映像寫出的紀錄，v1.6 的映像讀得懂（鍵集合沒變）。

## 10. 還沒解的問題（信任模型）

**這一節是之後設計的起點，不是設計。** 每題記下陷阱，包含 v1 這次踩到的。

**在哪裡設計、什麼時候**（使用者 2026-11-25：資訊對齊）：信任模型是 **v2.5 A 權限群的一份聯合設計，由 #52 主持**（#52、#393、#95、#97，加上 #54），開始條件是 #255 完成（608B 在 bench 上通了，U6）而且本文件已合併。#423 只負責本文件這份地基，合併後就可以關單，所以 v2.0 與 `2.0.0` 不用等信任模型。O-16 由 #16 與 #383 的聯合設計處理；O-17、O-23 的晶片部分是 #426 的評估項目；O-18 歸 #74、#115。「擋住」欄是在它解決前不能開始實作設計的單。

## 16. 安全檢查

- **攻擊面**：本文件不新增任何輸入。它要求兩個新的狀態轉移（§8 重置表第 1、2 列），各在 #402、#255 實作時過 L3；第 1 列的觸發不能從無線或非 root 程式到達。
- **權限**：判斷與晶片操作都在 root 的 helper；provd 非 root、只轉送。
- **秘密**：不進紀錄、不進 URL。網路密碼不以明文經過 provd（I-3）；**root 密碼今天會**（§3.2 A2），K10 的這個缺口留給信任模型。
- **失敗模式**：預設拒絕；放行都列在 §8 並各有理由。

**負向測試（最小集合；由 §14 對應的單實作）**
1. 開發根簽的節點憑證，量產版 app 拒絕。
2. 重置設定後、以及換卡後，重放舊的網路設定加密碼包（沒有擁有者當場簽）→ 拒絕（I-1）。
3. 已在網路的節點收到舊版本、跳號版本、同版本不同內容 → 拒絕（I-2）。
4. 秘密包換一台節點、換一個網路 id、換一個版本 → 解不開，交易失敗（I-3）。
5. 套用到一半斷電 → 回到之前的狀態（I-4）。
