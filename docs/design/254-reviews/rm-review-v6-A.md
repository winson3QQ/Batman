## 3. MAJOR

### MAJOR-1 一人多台:第二台的同意包先貼、更新包後貼 → 更新包被規則 4 整份拒,句子叫人重新邀請 B(沒用),第一台 A 在狀態頁沒有任何提示,靜靜留在舊的那一邊

**情境(使用者要走的「成員的第二台節點」流程)**
1. 成員 M 有節點 A(mnet v1,k7 = A)。網主移除 Y → v2,作廢所有未用邀請,為 M 產更新包 P(此時 k11 裡 M 只有 A → P 只有 A 的 v2 secrets)。
2. M 要加第二台 B:舊邀請已作廢 → 網主發 v2 的新邀請 → 同意 B(k10 = v2)。
3. M 手上同時有 P 和 B 的同意包,**先貼了同意包**:`existing()` 走 +1 路(approve.rs:303-310);A 是 applied、沒有 prev_country → me = 新的 B joining(approve.rs:319-322 → import :388-399);§2.2 +1 路 k10 清空;k5 = B 的 v2 secrets。A 的 v2 secrets 從來不在 mnet。
4. 再貼 P:鏈全部 ≤ mnet 版本 → §3.4「已經匯入過」分支;P 有 A 的 secrets、k10 沒有 → 「一樣跑規則 3–6」→ **規則 4:mnet 有 k7(B),P 裡沒有 B → 整份拒**,句子「這份更新包沒有你這台節點(…B)的新密碼,請網主重新邀請這台」。
5. B 其實沒事(k5 已是 B 的 v2)。照句子重新邀請 B → 新同意包同版 → 沿用 → 仍然沒有 A 的 v2 secrets;再貼 P 仍被拒(k7 = B 不在 P)。
6. A:§2.0 成員定義 = k7 或 k10 有目前版 secrets → A 都不是 → §3.5 狀態頁**不顯示任何東西**(手機 v2 > A 的 k9 = 1,但 A 不在集合裡)。§2.0 入口 3 的句子又是「請網主重新邀請這台」—— 也錯(正解是新的更新包)。

**後果**:A 留在舊 SAE,和已換的那一邊斷開;M 沒有任何畫面告訴他要跟網主要新的包,兩句話都把他導向重新邀請。只有網主剛好又為 M 產一次包(網主清單確實一直列著 M,§2.1)才會好。不漏秘密,但這是使用者點名要走的流程,而且順序(哪份先貼)是成員隨手決定的。

**證據**:§3.4 規則 4 與「已經匯入過 … 一樣跑規則 3–6」;§2.2「+1 路 → k10 清空」;§2.0 成員定義與入口 3 句子;§3.5 只對「網路裡的自己節點」顯示;approve.rs:319-322 / :388-399(新 me)。T29 只測「之後產的包」,沒有這個順序。

**修法(改一個條件 + 兩句話,不加機制)**:
1. 規則 4 的「包裡必須有 k7 那台」只在**會把 k5 換掉的那條路**(+1 匯入)才要求;「已經匯入過」分支(k5 已是目標版本的 k7 secrets)不要求 k7 在包裡,照樣把包裡其他自己節點的 secrets 補進 k10。
2. 入口 3 不符、以及 §3.2-3「沒有 → …」的句子統一成「這台的新密碼不在這支手機,請網主重新產生你的更新包(若網主說這台不在名單上,再請他重新邀請)」。
3. §3.5:成員手機擁有(node/)、info k10 = 本網、k9 < mnet 版本、但不是「網路裡的自己節點」的節點 → 顯示上面那一句(不給按鈕)。這只是顯示,不放寬送出。

**測試**:T29 加一臂:同意(B,+1)先貼 → 再貼 B 之前產的包 → 被接受、k10 有 A 的 v2、A 可送;負對照:v6 規則 4 → 拒。狀態頁那句一臂;負對照:沿用 §2.0 集合 → 沒有提示。
