但有三類洞會讓現場出事:

- NU §3 交接清單有幾項沒處理:版號取 max、wsl.24 閘門、AP 提示;

## MAJOR

### M1 §3.4 規則 3 / 4 沒有要求 net_secrets / member_secrets 的網主簽章:任何人都能把自己選的 net_root 加密給受害者

情境:
- ECDH-ES 的發送方是匿名的(219-protocol.md §7.3),而 owner_enc_pub 是公開的:它在每份 members 裡,剪貼簿和通訊軟體都會經手。
- 被移除者,或讀得到剪貼簿的 app,可以組一份包:真的鏈(公開物件)+ 自己做的 member_secrets(net_root 由攻擊者選)+ 假的 net_secrets。
- 規則 3 / 4 只比 target / net_id / version 和「能解開」,所以全部通過 → mnet k5 / k6 被換成攻擊者的值。

後果:
- (a) 轉交時節點回 `E_BAD_OBJECT`,但 mnet 已經寫了(§3.4「這一步失敗不影響已寫入的 mnet」)。真包再貼一次,鏈「逐 byte 相同 = 已有」,什麼都不做,mnet 一直是壞的。
- (b) 將來有成員連線時,這支手機用的是攻擊者知道的 psk_member,攻擊者就能冒充節點。

證據:設計 §3.4 規則 3 / 4 的原文。現有的 bind 對三個 Sign1 都驗簽(approve.rs:281-286),新路徑卻沒寫。

修法:
- 規則 3 / 4 明寫:以目標版本的 admins 驗 Sign1(本單 = 前一版 admins)、exact keys、same_net。
- 再貼同一版、但 secrets 不同的包時,要定義行為:以驗過的新 secrets 取代,或拒絕。
- T12 加兩個負對照:非網主簽、但內容確實加密給受害者的 member_secrets;非網主簽的 net_secrets。

### M2 換密碼前發出的邀請,在網主端仍是「未使用」:網主照樣同意,留下一筆幽靈 approved 成員

情境:
- §3.6 說「同意時 bind() 會因 netcfg 版本不同而失敗」。但 bind 在**加入者**匯入那一端(approve.rs:275-298);網主端的 `check_joinreq` 只看 k12 的 used(approve.rs:71-74)。
- 所以網主會同意:簽 v2 secrets、把 invite 標成 used、在 k11 加一筆 approved(approve.rs:160-182)。
- 加入者匯入時才在 `same_net` 失敗(版本 2 ≠ pend 的 v1),看到的是一般的「another net_id / version」,不是設計寫的那句話。
- 這筆幽靈項之後會:進每一版的 members;佔掉 16 人上限(netrec.rs:20);出現在下次換密碼的 k14,網主還會替它產更新包。

修法:
- §3.1 的 commit 寫入時,把 k12 所有未使用的邀請一起標成作廢(used,或新增的 revoked)。members key 7 的 revoked 填不出 invite_id(R10)沒關係,app 端擋就夠了。
- 網主端 `check_joinreq` 遇到作廢的邀請,回「這張邀請在換密碼前發出」。
- 加入者端如果還要顯示友善訊息,要有可區分的錯誤值。
- 測試:換密碼前發邀請 → 換密碼 → 申請 → 網主端拒絕、k11 不變。負對照:拿掉作廢這一步。

### M3 removed 永遠往下帶,和「被移除者之後要重新邀請」直接矛盾;重新加入的路沒有定義

情境(重新被邀請之後):
- §2.4:removed = 這次的 DAC + 前一版的 removed,沒有拿掉的規則。§3.4 規則 5 要求自己的節點「不在 removed」。
- 被移除者重新被邀請、被同意:`check_joinreq` 不看 removed,而且 k11 已經刪掉他的項目,所以他被當成新節點。
- 結果他的 DAC 同時出現在下一版的 members 和 removed → 他之後的每一份更新包都被規則 5 拒絕,畫面還寫「你已被移出這個網路」。
- NU §3 交接寫「之後審核加入申請時擋 member_list 的 removed 名單」,設計沒有處理。

情境(被移除者自己的手機):
- 他的 mnet 留在 v1;離開流程不寫 mnet(254-app-leave.md:69)。
- 新的同意包是 v3,`existing()` 會回 TooOld(approve.rs:313-314),所以就算重新邀請,他也匯入不了。
- 另一條路是隊員模式重新加入(R19),但送的是 mnet 裡的 v1 secrets,會回到舊的那一邊。

修法:
- 定義 removed 的語意:只記這一版移除的;或者重新同意時,從下一版的 removed 拿掉。
- 審核申請時,遇到 removed 裡的 DAC 要明確提示網主。
- 為被移除者那支手機定義「忘記這個網路」(刪 mnet),或讓 TooOld 的同意包可以走重新加入。
- 生命週期表加一列「被移除者重新加入」,並附測試。

### M4 「已複製」就把成員的 k10 推到目標版本;成員沒匯入的話,下一次換密碼就永遠補不上

情境:
- §3.3 產包時,把該成員各節點的 k10 設成目標版本 v2。但設計自己寫了「已複製 ≠ 已換好」。
- 成員沒匯入(包丟了、剪貼簿被蓋掉),之後網主又移除一人(v3)。
- 這個成員的包從 k10 = v2 起,只有 v3;他的 mnet 還在 v1,只會得到「請網主給你從 v2 起的包」。
- 網主端唯一的入口「重新產生更新包」也是用 k13 與 k10,做不出來 → 只能離開再加入。

修法:
- k10 只在同意時設定(= 成員已知的最低版本),不因「已複製」前進。成員端本來就會去掉已有的前綴(§3.4)。或者讓網主可以選起始版本。
- 8 塊 / QR 大小檢查照做。
- 測試:複製但不匯入 → 再移除一人 → 新包從 v2 起,成員匯入成功。負對照:「已複製」就推 k10。

### M5 一個人有多台節點時,只有 mnet k7 那一台會被轉交;其他台被困住,誰都看不到

情境:
- 設計說「移除 = 一個人名下的所有節點」(R17:一個 owner_pub 可以有多台),更新包 key 3 也是每台一份。
- 但 mnet 只存一台(k5 / k7,mrec.rs:7-8);`existing()` 遇到第二台會換掉 me(approve.rs:319-322);§3.4 規則 3 和轉交也只處理 k7 那台。
- 結果同一個人的第二台節點留在舊 SAE,和被移除者在同一邊。沒有任何畫面會提示:網主看不到別人的節點,成員的 mnet 也不知道有第二台。

修法:
- mnet 存「target DAC → net_secrets」的對照表,保存包裡所有驗過的 net_secrets。
- 轉交時,以擁有者連線驗過的 node_cert DAC 選對應的那份(219-field-provisioning.md §6.6「確認對方 DAC 就是封包的目標」)。
- 成員畫面列出包裡每一台的狀態。
- 如果決定不支援一人多台,就要在 §0 寫明,並在同意時擋。
- 測試:同一 owner 兩台 → 兩台都能轉交;用 A 的 secrets 登入 B → 不送。

### M6 新版號只取紀錄的版本,沒有取 max(紀錄, 節點 info k9);k9 > 目標也沒有分支 → 紀錄倒退後會重簽同一版號,造成分叉

情境:
- NU §3 明確交接了兩條:
  - 「新版號取 max(app 紀錄的版本, 各節點 info key 9)+ 1(app 紀錄還原或倒退後重簽同一版號,只有一位網主也會造成分叉)」;
  - 「key 9 > 目標時不可無限追」。
- 設計 §2.4 的 v 只取紀錄;§3.2 只有「k9 = 目標」和「k9 < 目標」兩個分支。
- 紀錄倒退是會發生的:store 不偵測回滾(store.rs:9-11);§5 的降級列也寫了舊 app 會丟掉 k13 / k14。
- 已套用另一份 v2 的節點,之後每一版都接不上(NU F18,`E_STALE_VERSION`),只能全部離開再加入。

修法:
- §3.1 簽名之前,先以擁有者連線讀至少一台自己節點的 info k9。若 k9 ≥ 紀錄版本 + 1 → 不開始,顯示「這支手機的紀錄比節點舊」。
- §3.2 加一個分支:k9 > 目標 → 停下、告警、不送。
- 測試:紀錄 v1、節點 k9 = 2 → 不簽(簽章次數 0)。

### M7 網路裡還有 wsl.24 節點時,設計只給每台一句提示;NU 要求的是「不得開始」,而且 F10 會讓「k9 = 目標」變成假的成功

情境:
- wsl.24 接受舊形狀 `{1:[cfg], 2: secrets}`,而且 secrets 沒有綁版本(NU F10)。
- 被移除者手上有公開的 v2 cfg(從任何一份更新包取得)。他也可能有 X 節點的 v1 secrets:X 當初的同意包走過 QR / 剪貼簿,而且是以 X 的 DAC 為對象。
- 他用舊 psk_member 開成員連線到 X(X 還在舊版,R15 允許成員連線送 update),送 v2 cfg + v1 secrets → X 的 k9 = 2,但 SAE 還是舊的。
- X 的擁有者轉交時讀到 k9 = 目標 → §3.2 / §3.4 判定「已確認」。實際上 X 留在被移除者那一邊。

證據:NU §3「網路裡還有 wsl.24 節點時不得開始移除成員」;NU F10 的探針 `v2 cfg + v1 secrets -> code 0`。

修法:
- §3.1 前置條件加上:自己的每一台節點 info k4 ≥ wsl.25。
- 成員端轉交前也讀 k4:wsl.24 時不送,顯示「先更新軟體」,而且不能把 k9 = 目標算成功。
- 網主沒辦法檢查別人的節點:寫成誠實界線(要求全隊先升級)。

### M8 「改手機 AP 密碼」的提示只出現在網主的結束畫面,成員看不到;本單沒換掉的東西也沒有列出來

情境:

- 每位擁有者都要改**自己**節點的 AP 密碼,但成員 app 在匯入 / 轉交之後沒有任何提示。

修法:
- 成員 app 轉交成功後,顯示「請改這台節點的手機 Wi-Fi 密碼」;如果已經有 settings.set,直接提供入口。
- §0 / §6 列出「本單不換:手機 AP、Meshtastic 頻道、OTS 憑證」,並寫出後果。

## MINOR

- **m1 T4 的寫法和 §3.1 矛盾。** T4 寫「簽章次數 = 0」,但 §3.1 註寫「secrets 需要時用 k5 / k6 重產」:續做時送自己的節點,要 SignAdmin net_secrets。改成「netcfg / members 的簽章次數 = 0」。
- **m2 §3.4 轉交缺兩件事。** 要比對登入節點的 DAC 是否等於 secrets 的 target(219-field-provisioning.md §6.6-1);info k9 > mnet 版本、k10 不是本網、k11 = true 這幾個分支要寫出來(§3.2 有寫,§3.4 只寫「同 §3.2」)。
- **m3 kind 4 的解析沒有上限與邊界。**
  - 要有 exact keys,以及鏈長 / 總大小上限:貼上一份很大的鏈,會讓 app 做大量驗簽;
  - 鏈的起點早於 mnet k9 第一項時,要定義怎麼比對;
  - mnet k9 / net k13 沒有上限。
- **m4 網主手機遺失。** ADMIN_SIGN 不需要使用者驗證(Keys.kt:70-80),拿到解鎖手機的人可以一鍵把所有人移出、接管網路。至少在「移除」前要求裝置密碼 / 生物辨識,或在 §6 明寫這是誠實界線。
- **m5 現場最常見的觸發沒有寫出後果。** 最常見的是「節點遺失 / 被抓」和「成員手機遺失」(219-field-provisioning.md:133、:417「回報遺失」)。依使用者決定只能移除整個人,所以要寫出:那個人其他的節點要離開再加入;手機遺失時,他的節點要用新手機重新認領。
- **m6 生命週期表少了幾列。**
  - 「成員 app 降級」:舊 mrec encode 寫回時會丟掉 k9(和網主端同樣的邊界);
  - 「Keystore / 封存失敗」;
  - 「剪貼簿被其他 app 換成舊包」:要說明是重送無害,還是只會 DoS。
- **m7 kind 4 與剪貼簿要用 dev-trust build 擋住**,和邀請一樣(invite.rs:12 的做法)。正式版走通訊軟體轉貼時,包裡的成員名單(名稱、owner_pub、DAC hash)會被第三方伺服器看到 → 寫成誠實界線。
- **m8 NU §3 交接清單要逐條對表。** 每條寫「處理」或「不適用 + 原因」:
  - 成員連線 pin DAC → 本單只用擁有者連線,不適用;
  - LoRa PSK;
  - 審核時擋 removed(M3);
  - 版號取 max(M6);
  - wsl.24(M7);
  - AP 提示(M8)。
- **m9 `open_netcfg_current` 本身沒問題,但要補三點。** 對新的加入者來說,信任錨本來就是 SAS / 當面,自簽的 v2 不比自簽的 v1 差。它也不會讓別人偽造的網路被當成真的:邀請整份由 admin_pub 簽,netcfg 必須含 admin_pub 並由它簽 ✅。要補的是:
  - (a) 它不提供新鮮度,舊邀請照樣打得開(→ M2);
  - (b) 「由它自己的 admins 簽」只在本單不換 admins 時成立。將來 vN 由 vN−1 的 admins 簽、而 admins 有變動時,邀請會全部失效 → 寫明這個限制;
  - (c) 依據是節點 `netJoin` 接受任何版本號(node.go:1035-1050),要補進 §1。
- **m10 「結束」之後的網主自己節點。** 網主自己沒換成功的節點沒有地方顯示 → 狀態頁要比照成員端,顯示「紀錄版本 > 節點 k9 → 送新密碼」。
- **m11 永久分裂沒有提示。** 被移除者的節點如果是唯一的中繼,換完之後就是永久分裂;確認對話框只講了暫時分裂 → 加一句提示。
- **m12 成員端規則 2 沒有檢查 members 的 prev_hash 鏈。** NU §2.2-3 說結構正確由 app 負責,建議加上,成本很低。

## 依角色的攻擊結論

| 角色 | 結論 |
|---|---|
