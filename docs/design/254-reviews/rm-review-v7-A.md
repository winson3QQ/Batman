## 3. MINOR

1. **m1「忘記」導向:pending 分支永遠走不到;只靠 UI 擋。**
   - **情境**:§3.6「只有紀錄 pending 時保留今天的『忘記』」,還有「『忘記已同意的項』對話框(pending 時)加一句」。可是邀請、同意、join2 都要求紀錄是 applied(invite.rs:181-184、approve.rs:124、join2flow.rs:304-306),所以 approved 項只會出現在 applied 紀錄裡。pending 紀錄沒有 k11,只有建立者(netrec.rs:255-258)。這兩句是 v5 / v6 留下來的,和「approved 項不再有單獨的忘記」放在一起讀,會讓人以為某些情況還能忘記 approved 項;第一句也可能被讀成「applied 時一律沒有忘記」,這又和同一段「自己的 joining 項可以忘記」相反。
   - **證據**:approved 的忘記今天在 Rust 是允許的(netrec.rs:342 只排除 Applied;bridge owner.rs:131-140),T39 只測畫面。
   - **修法**:改寫成「approved 項不提供忘記(這種項只會出現在 applied 紀錄裡);自己的 joining 項照今天可以忘記,對話框加『排除這台』」,並刪掉 pending 那一句。在 `forget_joining` / `net_forget_joining` 拒絕 Approved,和 creator 的檢查同一層;否則 Dart 漏一個分支就回到第 6 輪 B-M1 的情境。T39 加一臂 bridge 層的負對照。

2. **m2 正式版不能「排除這台」,但忘記對話框照樣提供。**
   - **情境**:§3.6 build 閘門規定「排除自己的一台」只在 dev-trust build。§3.6「自己卡在 joining 的節點:忘記對話框同時提供『排除這台』」沒有限定 build,而 join2 在所有 build 都有。
   - **修法**:寫明只在 dev-trust build 才出現。正式版的忘記對話框維持今天的說法,加一句「只忘記不會撤銷它已拿到的密碼」。T36 已有「非 dev-trust 沒有排除入口」,把忘記對話框加進同一組。

3. **m3 狀態頁 §3.5 第一條沒有限定是成員:網主被排除的節點會看到錯的句子。**
   - **情境**:網主手機擁有(`node/`)一台被排除的節點,它 info k10 = 本網、k9 < 紀錄版本,而這支手機「沒有它的目前版 secrets」(它不在 k11,入口 1 不送)。照 §3.5 第一條字面,網主的狀態頁會顯示「請網主重新產生你的更新包」。§2.0 入口 1 的句子(「已被排除…只能離開網路」)才對。
   - **修法**:第一條限定「成員手機」;網主手機上,擁有、在本網、但不是「網路裡的自己節點」的節點,顯示入口 1 那句。T37 的狀態頁臂加網主一臂。

4. **m4 先貼更新包、後貼「換密碼前」產的第二台同意包 → 一定要重新邀請;網主其實知道會發生,可以先提醒。**
   - **情境**:M 有 A;網主在 v1 同意 B;網主移除別人 → v2,產給 M 的包含 A、B(B 在 k11)。M 先貼更新包 → k10 = {A, B};再貼 B 的 v1 同意包 → SameVersionDifferent(approve.rs:313-316)→ 「請網主重新邀請這台」。B 的 v2 secrets 明明已在 k10,但 B 不是 k7,不能走隊員模式加入(join2flow.rs:339-341)。反過來貼(同意包先)就沒事。
   - **後果**:不漏秘密,有出路(重新邀請 → `replaces_approved`,approve.rs:78-80 → 同版匯入),但現場是多一輪遠端往返:邀請 → 申請 → 同意。
   - **修法(只改字)**:網主 §3.3 產包畫面看得出這種情況:這個人有 approved 項的 k10 < 目前版本,也就是換密碼前才同意的。這時在那一列加一句:「〈名稱〉有一台(…後 4 碼)在換密碼前被同意:請他先貼那份同意包,再貼這份更新包」。成員匯入成功畫面也加:「如果你還有沒貼的同意包,先貼同意包,再貼一次這份更新包」。測試:§3.3 那句出現的條件一臂。

5. **m5 只在 k10 裡的成員節點被叫去「離開再加入」,但它離開之後不能自己再加入;離開對話框還說可以(R19 的結論「隊員句不變」不成立)。**
   - **情境**:§3.2-3「這台落後太多版,請讓它離開網路再重新加入」與 §3.5 第三條的「請先按『離開網路』再加入」也會套到 k10-only 的節點上。離開對話框(254-app-leave.md:31)只看「mnet 有 key 7」,就說「之後可以按『加入隊伍網路』再加入」。可是離開之後 §3.2-1 會說「這台要請網主重新邀請」(NotThisNode)。使用者照畫面做完,才發現要找網主。
   - **修法(只改字)**:成員端的這兩句,依「這台是不是 k7」分開寫:非 k7 →「請讓它離開網路,再請網主重新邀請這台」。離開對話框的隊員句也加同一個條件(跨文件,記在 leave.md 附錄;R19 的處理從「不變」改成「依 k7 分句」)。T5 加一臂:非 k7 + 落後太多 → 那句含「重新邀請」。

6. **m6 缺 k10 的預設與降級再升級:特殊條件只撐一版,而 §2.1 的定義沒跟上。**
   - **情境**:§2.1「可能還要包的人 = k10 < 目前版本」沒有 §2.3 / §3.3 的「或 k13 只有一項而目前版本 > 1 且缺 k10」。降級再升級後,只要再換一次版,k13 就有兩項,特殊條件失效。缺 k10 = k13 最舊項(升級時的版本 v3)→ start = v4。停在 v2 的成員明明可以靠 k13 裡的 v3 接上,卻被判「資料太舊」,只能重新邀請。
   - **修法(更簡單,拿掉特殊條件)**:缺 k10 一律當成「k13 最舊一項的版本 − 1」,也就是 start 包含最舊那一版。
     - 第一次換密碼(最舊項是 v1):start = 1,鏈多帶 v1 一步,成員端與 mnet k3 / k4 逐 byte 比對相同(§3.4-2),沒有影響。
     - 降級再升級:每一次都包含升級時那一版,停在前一版的成員接得上。
     - 「升級前的版本不明」的標示保留,判斷條件不變。§2.1、§2.3、§3.3 三處統一成同一條。
     - T3 / T10 改寫,加一臂:降級再升級 → 再換一版 → 停在升級前一版的成員仍匯入成功;負對照:今天的預設 → 「資料太舊」。

7. **m7 TooOld 取代不只用在被移除的人:一般成員落後 ≥ 2 版又加第二台時,也會被引到取代,而取代會讓第一台只能重新邀請。**
   - **情境**:M 在 v1(包都沒貼),網主換到 v3,同意 M 的第二台 B(v3)。M 先貼 B 的同意包 → TooOld → §3.6-2 問「要換成新的嗎?」→ 歷代重設為只有 v3、k10 清空 → 之後的包補得進 A 的 secrets,但 A 在 v1,§3.2-3 判「落後太多版」→ 離開 → 非 k7 → 重新邀請。
   - **證據**:§3.6-2 的條件沒有限定「被移除的人」;§3.4 末「比 mnet 歷代還舊的版本略過、不存」。
   - **修法(只改字)**:取代的確認框在舊 me 不在 removed 時加一句:「如果網主也給了你更新包,請先按取消、先貼更新包,再貼這份同意包(不然你的其他節點要重新邀請)」。

8. **m8 §2.4 只把 NotApplied 排除在 k9 檢查之外;OtherNetwork / InProgress 沒有寫。**
   - **情境**:網主自己的節點已離開 A 網、加入 B 網(離開不寫紀錄,leave.md:69,所以它還在 A 的 k11)。它的 info k9 是 B 網的版本。照字面「連得上的每一台:k9 > v → 不開始」,B 網的版本較大時,A 網的換密碼會被一個誠實的節點擋住,告警還說「這支手機的紀錄比節點舊,出路 = 重建網路」,而那是破壞性的出路。
   - **修法**:寫明「只算 join_state = Applied(info k10 = 本網)的節點」;其他(NotApplied / OtherNetwork / InProgress / Unknown)一律當成不檢查。T15 加 OtherNetwork 且 k9 > v → 可以開始一臂。
