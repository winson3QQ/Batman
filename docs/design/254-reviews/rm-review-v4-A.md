## 2. BLOCKER

### BLOCKER-1 §2.0 的對象守則擋掉了使用者決定要支援的重新邀請 / 加回 / 新節點;設計自己的 T14、T26 和 §3.6 都和它矛盾

§2.0 原文:「§3.2 送 network/update、網主 join2、隊員模式加入之前,目標的 dac_hash 必須是『網路裡的自己節點』,且不在目前版本 members 的 removed」。網主的「網路裡的自己節點」= k11 中 owner_pub = 自己的項;成員的 = 在 members key 4,或是 mnet k7。

**情境 A:重新邀請被移除的人(使用者 2026-11-11 決定允許;T14 就是這個情境)**
1. dev 移除 dev2,commit v2:02 的 DAC 進了 v2 的 removed。
2. dev2 讓 02「離開網路」;dev 重新邀請 dev2,dev2 申請,dev 同意。這時 k11 加回 02,k10 = 2。**同意包的 members 就是 k8 = v2 的 members**(approve.rs:156-157、§3.6「同意:members / secrets 用目前版本」),02 還在它的 removed 裡。v2 不會重簽,只有下一版才會把它從 removed 拿掉(§2.4)。
3. dev2 匯入同意包。走 +1 路或同版路都一樣:2b 不沿用 me,改建一個新的 joining k7 = 02。
4. dev2 對 02 按「加入網路」(隊員模式)。§2.0 檢查:02 的 dac_hash 在 mnet 目前版本(v2)members 的 removed 裡,所以**不送**,畫面說「這台已被排除在隊伍網路外,只能『離開網路』」。可是 02 早就離開了。
5. 在下一次換密碼之前,這個人都回不來;而下一次換密碼要等網主又移除某個人。T14 的「02 以目前版本加入、鄰居恢復」照設計寫的規則做,一定失敗。

**情境 B:網主加回找回來的自己節點(§3.6)**
§3.6 寫的是「join2 前顯示『這台之前被排除…確定嗎?』,確認後才建 k11 項」。但 §2.0 在 join2 之前就要求它是 k11 的項,而且不在 removed。它兩個條件都不滿足,所以對話框永遠沒有機會出現。T27 寫的「被排除的自己節點 → join2 不送」也和 §3.6 衝突。

**情境 C:網主加一台新節點(含 T26「排除最後一台 → 之後 join2 新節點以目前版本加入」,和平常的第二台節點)**
join2 網主模式的 k11 項是 join2 自己建的(join2flow.rs:298-325,見 §0)。一台新節點在 join2 之前不在 k11,所以照 §2.0 字面上的規則,「網主 join2 之前,目標必須是網路裡的自己節點」**永遠不成立**。T26 的後半段和 S1 既有的 join2 都會被擋。就算實作者把它讀成「只檢查 removed」,情境 A 和 B 還是被擋。

**根因**:「在不在 removed」只能說明這台**曾經**被移出,說明不了它**現在**有沒有被重新同意。重新同意不會重簽目前的 members(同版只簽一次),所以被重新同意的節點,在下一版之前一直都在 removed 裡。v3 B-B1 建議「join2 / 隊員模式加入時目標在 removed → 不送,要重新加入就走一般的重新邀請 / 同意」,這個建議本身就漏了這一點,v4 照著寫了進去。

**修法(只改條件,不加機制)**:
- **網主 §3.2(送 network/update)**:目標必須在 k11(被排除的已經在 commit 時刪掉了);**拿掉 removed 檢查**。重新同意或加回的節點本來就在 k11 裡。net_secrets 的 ecdh_pub 只取自那一項(這部分不變)。
- **網主 join2**:目標在目前 removed 裡,或者在 `node/` 裡卻不在 k11 → 顯示 §3.6 的確認對話框,不是直接擋;確認後才由 join2 建 k11 項。新節點不需要先在 k11 裡。對被抓的節點:攻擊者要先把節點重設成 NotApplied,網主還要親手確認,和 v3 B-B1 想擋的「照畫面按一下就送出」不同。
- **成員端(§3.2 與隊員模式加入)**:目標 = mnet k7,或者在目前 members key 4 裡(加上 k10 中有它的那幾台);**拿掉 removed 檢查**。成員自己的節點會出現在 removed,只有一種可能:這個人被整個移除了。被移除的人拿不到之後的任何版本,除非網主重新同意他,而重新同意正是 2b 的情況。所以成員端的 removed 檢查只會在合法的重新加入時觸發,沒有任何保護作用。
- **T27 改寫**:被排除的自己節點(node/ 有、k11 沒有)→ §3.2 送出 0 次。join2 → 出現確認對話框,不確認就 0 次送出,確認後以目前版本加入。負對照:拿掉 k11 檢查 → §3.2 送出 1 次。**加一臂**:被移除後重新同意(02 在 v2 的 removed、k7 = 02)→ 隊員模式加入照樣送出;負對照:照 v4 的 §2.0 → 被擋。T14 不改,修好後它就是真機的正向證明。T26 加「新節點 join2 不需要先在 k11」的斷言。

## 3. MAJOR

### MAJOR-1 一人多台的成員,在兩次換密碼之間加第二台節點後,第一台會永遠換不了密碼(+1 路帶上過期的 k10,而規則 6 擋掉補救的路)

**情境(現場:成員離隊一陣子,回來時多帶一台節點)**
1. 成員 M 有節點 A(k7 = A),已經匯入 v2 的更新包:mnet = v2,k10 = {A: v2 的 secrets},A 也已換到 v2。
2. 網主移除 Z,commit v3(v3 members 有 A)。M 不在場,沒有匯入 v3。
3. M 帶著新節點 B 回來。網主以 v3 同意 B,k11 中 B 的 k10 = 3。M 匯入同意包:這是 +1 路(v2 → v3),而 A 的 me 是 applied,所以 `existing()` 回 Ok(None)(approve.rs:319-321)。結果 k7 = B,k5 = B 的 v3 secrets。§2.2 規定「+1 路把舊 mnet 的 k9 / k10 帶過去」,所以 **k10 = {A: v2 的 secrets}**,但 mnet 已經是 v3。
4. A 的狀態頁:手機 v3 > A 的 k9 = 2,所以出現按鈕。§3.2-3 依 dac_hash 從 k10 找到 A 的那份,也就是 v2 的 secrets,送出「v3 + v2 secrets」。節點依 NU §2.2-5 回 `E_BAD_OBJECT "net_secrets"`,k9 不變,畫面顯示「沒有換成功,可再試」,而且**每一次重試都一樣**。
5. 就算 k10 沒有帶(或被清掉),出路是「請網主重新給你更新包」。網主那邊會列出 M(A 的 k10 = 1 < 3),產出的包有 A 和 B 的 v3 secrets。M 匯入時走「鏈全部已有、目前版本 = mnet 版本 → 補 k10」,這一步要「一樣跑規則 3–6」。規則 6 是「mnet 有 k7 時它必須在 members」,但 k7 = B 是在 v3 簽好**之後**才同意的,不在 v3 的 members 裡,所以**被拒**(「你這台節點不在新的成員名單裡」)。要等到下一次換密碼才補得上。
6. A 不是 k7,隊員模式也不能讓它離開後再加入(join2flow.rs:339-341)。在下一次換密碼之前,唯一的出路是網主重新邀請 A。

**證據**:§2.2「approve::import…走同版或 +1 路,把舊 mnet 的 k9 / k10 帶過去」;§2.2「k10 本版給自己節點的 secrets」(語意是「本版」);§3.2-3 依 dac_hash 選 secrets,不看版本;§3.4 補 k10 那段「一樣跑規則 3–6」;§3.4-6;approve.rs:156-157 同意包的 members = k8 原樣,不會因為同意就重簽。第 3 輪 A-MAJOR-5 只要求「不要清掉」,沒有考慮帶到新版本後內容會過期。

**修法(改兩個條件)**:
1. §2.2:+1 路**只帶 k9**(把新的一版接上去),**k10 清空**;同版路才帶 k10(依 dac_hash 保留其他台的那份)。§3.2-3 選 k10 / k5 時再加一條:secrets payload 的版本必須 = mnet 版本,否則當作「這台的新密碼不在這支手機」。這一條很便宜,也順便擋掉降級寫回之類的過期內容。
2. §3.4 補 k10 那條路(鏈全部已有、目前版本 = mnet 版本):規則 6 **只檢查 removed**,不要求 k7 在 members 裡。這些 members 在匯入同意包時已經接受過,而 k7 在兩次換密碼之間被同意,本來就不會出現在目前的 members 裡。新版本的路(目前版本 > mnet 版本)維持原規則:那一版是在 k7 被同意之後才簽的,一定有它。

**測試**:T28 加「+1 路 → k10 清空、k9 = 舊 + 新」。新增一臂:照上面的情境(A 在 v2、B 在 v3 被同意)→ A 的 §3.2 顯示「新密碼不在這支手機」,送出 0 次;網主產包 → M 補上 A 的 v3 secrets → A 換到 v3。負對照:照 v4 的寫法 → A 送出 v2 secrets、節點拒絕;或者補 k10 時被規則 6 擋。

## 4. MINOR

1. **m1 §2.1 說 k13「版本遞增、連續」,但修剪規則會造成中間有缺口。**「保留最近 32 版 + 永遠保留最舊一項」= {v1, v(n−30)…vn}。產包的 start 公式因為有 −15,剛好不會用到缺口(n > 32 時,n − 15 一定大於缺口之後的第一版)。但這件事要寫明:「連續」只指最近那一段,§3.2 與 §2.3 組鏈只用最近那段連續的部分;T3 / T8b 加一臂(33 版以上)。
2. **m2 §2.4:自己的節點 k9 ≤ v、但 k9 那一版不在 k13 裡,這種情況沒有定義。** 降級再升級之後(k13 只剩目前版本),或者自己的節點落後超過 32 版,都會碰到。照現在的文字,只有「在 k13 裡 → 可以」,不在 k13 裡會怎樣沒寫。要寫明:這不是回滾的訊號,而是「這台落後太多,請讓它離開網路再加入」。並且說清楚它算不算「連得上的那一台」:建議不算。T15 加一臂。
3. **m3 前置裡的不對稱會擋住緊急換密碼。** 自己的節點一台都不剩 → 可以開始,對話框寫明無法檢查回滾。但還剩一台、只是連不上(關機、在別處)→ 不能開始。現場的情境:網主有兩台節點,一台被抓,另一台在車上沒開機,這時要等找到另一台才能換密碼。回滾檢查本來就「只擋得住部分情況」(§6),兩種情況應該用同一條規則:連不上的話,顯示同一句誠實界線,讓使用者確認後開始。這是簡化,不是新機制。T15 的「一台都連不上 → 不開始」要跟著改。
4. **m4 §3.3 的「升級前的版本不明」標示(第 3 輪 A-m10)其實永遠不會出現。** 降級再升級之後,缺 k10 = k13 最舊一項 = 目前版本,所以「k10 < 目前版本」的清單是空的,標示也沒有地方可以標。改成:k13 只有一項而目前版本 > 1 時,把缺 k10 當作「不明」,**列出每一個人**並加上標示,產出的包只有目前那一版;或者把標示放在畫面層級。
5. **m5 2b 和 `existing()` 的 PreviousNode 撞在一起。** 被移除的人,如果舊 mnet 的 me 是 joining 或有 prev_country(例如他的節點加入到一半就被移除),而重新邀請時 DAC 不同,`existing()` 會先回 PreviousNode(approve.rs:319-321),2b 根本執行不到,重新邀請就失敗。要寫明:me 在 removed 的時候,2b 優先(不沿用,也不回 PreviousNode)。country 的還原另外交給「離開網路」。T17 加一臂。
6. **m6 成員匯入後會自動轉交(§3.4 末),在網主還在發包時就把傳包的路切斷。** 確認對話框只提醒「網主自己的節點」和「被移除者的節點是唯一轉送路徑」這兩種情況。但開發版的剪貼簿包,現場是經由 mesh 上的 app 傳的,先匯入的成員一轉交,他的節點就換到新那一邊,經過他轉送的其他人就收不到包。QR 當面傳就沒有這個問題,所以只需要一句誠實界線:在對話框或成員的匯入畫面寫「如果你的節點替別人轉送,等網主說包都發完了再按」。不加機制。
7. **m7 測試的負對照不齊。** T26 沒有負對照(例如「照 v3 的前置 3 → 被拒」);T27 要依 BLOCKER-1 改寫,加正向的那幾臂;T13 有「轉交前確實分裂」的負對照,但沒有寫要斷言 02 在轉交前的 k9 = 1。
8. **m8 §2.0 成員端「網路裡的自己節點」的定義會把正常的節點顯示成「已被排除」。** 在兩次換密碼之間同意、而且已經不是 k7 的節點(例如 M 在 v2 先加 B、再加 C,k7 = C),既不在 v2 的 key 4,也不是 k7。它用不著換密碼,但如果狀態頁拿 §2.0 來標示,就會顯示「已被排除」。BLOCKER-1 的修法(k7、key 4,或 k10 中有它)要連同這個情況一起寫進去。
