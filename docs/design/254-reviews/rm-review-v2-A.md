## 2. MAJOR

### MAJOR-1 網主先換掉自己的節點,才產更新包:現場唯一的傳遞管道就是 mesh,網主一換完就送不出更新包
- 情境(現場):一人一節點、手機連自己節點的手機 AP,隊伍的通訊(TAK 聊天、通訊軟體)跑在 mesh 上,沒有外網(memory「OTS 現場情境」;R16 說正式版走通訊軟體 / QR)。網主按移除 → §3.1 commit → §3.2 立刻送給自己的節點(§0-1 的順序「送給自己的節點 → 為每位留下的成員產更新包」)→ 04 換成 v2 SAE,與所有還在 v1 的節點斷開 → 網主手機的 IP 路徑只剩 04 → 再按 §3.3 複製更新包,**貼到通訊軟體也送不到任何人**。成員那邊同理:誰先匯入誰先斷,但成員不需要再傳東西;只有網主要對外送 N 份包。
- 結果:接受的是「暫時分裂」(決定 a),但這裡變成網主與所有人之間沒有傳遞管道,只能等當面(QR 還沒做)或外網。這是傳遞路徑的死結,不是分裂。
- 證據:§0-1、§3.1 末「→ 送給自己的節點 → 為每位留下的成員產更新包」;§3.3 才產包;commit 點是紀錄寫入(§3.1),送自己的節點與產包互不依賴。
- 修法(只改順序,不加機制):commit 後直接進 §3.3(產包);自己的節點走 §3.5 的共用按鈕「把新密碼送給節點」,在網主按的時候才送。§3.3 加一句:「先把更新包送給每位隊員,再換你自己的節點;換完之後,你的節點會和還沒換的隊員斷開。」確認對話框的「你的節點這支手機會直接換」改寫。
- 測試:commit 後、使用者按「送給節點」之前,network/update 送出次數 = 0、§3.3 可產包;負對照:照 v2 順序 → commit 後立刻送出 1 次。真機 T13(§8 建議)的步驟順序也照這個。

## 5. §8 意見:一支手機、兩台節點怎麼測正向轉交

做得到,不需要第二支手機或第三個 flavor,也不需要產品裡的測試入口:
1. dev(網主)建網在 04;dev2 以遠端邀請把 02 加入(現有流程),04 / 02 鄰居存在(正對照)。
2. **合成的第三人**:用主機端測試工具(放 tests/tools 或 batman-proto 的 example,不進 app)產一把 owner 簽章 / 加密金鑰 + 一張自簽 `dev:<SHA-256(DAC)[:9]>` 的 node_cert(dev-trust build 的 `verify_offline` 收,nodecert.rs:140-162;NU §6 的向量已有測試用 DAC 私鑰可沿用),對 dev 發的邀請簽出加入申請。dev 以剪貼簿貼上 → SAS → 同意 → k11 多一筆 approved(他的節點不存在、永遠不入網,這不影響測項)。
3. dev 移除第三人 → commit v2 → 產 dev2 的更新包(MAJOR-1 的順序:先產包)→ dev 再把 04 換到 v2 → **斷言 04 / 02 鄰居消失**(證明鄰居恢復是轉交造成的,不是本來就連著)→ 切到 dev2 匯入、轉交給 02 → 02 k9 = 2 → **鄰居恢復**、02 的 SAE = 04 的。
4. 再跑 T14(移除 dev2 → 鄰居消失 → 02 離開、重新邀請 → 恢復)當被移除者那一邊的負對照。

誠實界線:第三人的節點不存在,「被移除者的節點進不了新 mesh」只由 T14 證明;第三人的手機那一邊(§3.7)只有 Rust 單元。
