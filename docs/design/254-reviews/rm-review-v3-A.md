## 2. MAJOR

### MAJOR-1 前置 4 要求「自己的節點 k9 = v」,第二次移除因此被擋住,除非網主先換掉自己的節點;這和 §0-1 的順序與 §5「第二次移除:可以」互相矛盾

- **情境(現場)**:兩個人同一天離隊,或者移除 A 之後才發現 B 也要移除。設計只能一次移除一個人(使用者決定),所以要做兩次。
  1. 第一次移除 A:commit v2。照 §0-1 和確認對話框的順序,網主**還沒**換自己的節點(先發更新包)。這時他的節點 k9 = 1。
  2. 第二次移除 B:前置 4 要求「至少一台自己的節點連得上、它的 k9 = v」,而 v = 2,所以不能開始。
  3. 網主唯一能做的,是先把自己的節點換到 v2。但這正是 v2 第 2 輪 A-MAJOR-1 修掉的死結:他一換,就和所有還沒換的人斷開,兩份更新包都送不出去。
- **證據**:§3.1 前置 4、§2.4 第一句「它的 info k9 = v」;§5「第二次移除(第一次還沒全員換好) | 可以」;T20 沒有指定網主節點的版本。這也是 v1 第 1 輪 A-MAJOR-5(「第二次移除強迫先結束」)換了個入口又回來:k14 拿掉了,但這條前提重新造成同樣的關卡。
- **為什麼不需要 = v**:回滾偵測要擋的只有「節點比紀錄新」(k9 > v)。k9 < v、而且 k9 這一版在 k13 裡,和紀錄是一致的,這正是正常的「網主最後才換自己的節點」狀態。
- **修法(只改條件)**:前置 4 與 §2.4 改成「至少一台自己的節點連得上,它的 k9 ≤ v,而且 k9 這一版在 k13 裡(或者 k9 ≥ k13 最舊一版)」;任何一台 k9 > v 仍然不開始(出路照舊)。
- **測試**:T20 改成「第一次移除後網主的節點還在 v1(network/update 送出 0 次)→ 第二次移除可以開始 → 為成員產的包含 v2、v3」;負對照:照 v3 的 `k9 = v` 條件,第二次移除被拒。T15 的「k9 = v + 1 → 不開始」維持。

### MAJOR-2 被排除的自己的節點(遺失 / 被抓)仍然被當成「自己在這個網路的節點」:狀態頁會主動提示,網主一按,就把新密碼送給它

- **情境**:網主的節點 N2 被抓,網主「排除這台」→ v2 → 他按「把新密碼送給節點」換掉其他自己的節點。之後抓到 N2 的人把它開機,放到網主的 BLE 範圍內;或者網主之後找回了 N2。
  1. 網主手機仍有 N2 的 node/ 紀錄(設計沒說要刪),擁有者連線照樣登得進去(擁有者 PSK 不隨 mesh 換密碼,loginflow.rs:1-5)。
  2. N2 的 info k10 = 本網、k9 = 1 < 2。§3.5 的共用規則是「對每一台**自己擁有、在這個網路**的節點:手機版本 > k9 → 『把新密碼送給節點』」,所以按鈕會出現。
  3. §3.2-3 裡,網主的 secrets 是「現產」的,對象是任何擁有的節點,**沒有檢查這台在不在 k11 / members 裡**。結果 N2 拿到 v2 的 SAE,又回到新的 mesh,而 v2 的 members 裡沒有它。
- **後果**:排除是使用者為「節點被抓」要的功能(上游決定 2026-11-11),現在 app 自己的畫面就會一步把它還原。找回節點的正常情況也沒有正確的路(應該是先離開網路,再用 join2 加回 k11)。
- **證據**:§3.5 第一點;§3.2 開頭「對一台自己擁有的節點」;§3.2-3「網主:現產」;§3.1 commit 只寫「k11 刪排除對象」,沒有任何 node/ 紀錄的處理;T5、T7 都沒有這一臂。
- **修法(只加一個條件)**:網主端的 §3.2 與 §3.5 只對「DAC 在目前 k11 裡」的節點產 secrets、顯示按鈕。擁有、在這個網路、但不在 k11 的節點(被排除的、被忘記的)顯示「這台已被排除在隊伍網路外;要再使用,請先按『離開網路』,再按『加入網路』」。join2 會把它以目前版本加回 k11(leave.md L7)。成員端已經由 mnet k10 限制(包裡只有 k11 那幾台的 secrets),不必改。
- **測試**:排除 N2 → N2 的 info k9 = 1 → 沒有按鈕,§3.2 產生 secrets 的次數 = 0,畫面顯示「已被排除」那句;負對照:拿掉 k11 檢查 → 送出 1 次 network/update。真機可以併進 T13 / T14(04 以外再認領一台,或者用 02 由同一位擁有者做)。

### MAJOR-3 「排除網主自己的某一台」在現場最常見的情況做不到:一人一台節點的網主,節點被抓了就無法換密碼

- **情境**:現場的配置是每人一台節點、手機連自己節點的手機 AP(memory「OTS 現場情境」)。所以網主的節點被抓,通常就是他唯一的那台。
  - 前置 3 規定「不能把自己最後一台也排除」;
  - 前置 4 規定「至少一台自己的節點連得上、k9 = v」。

  兩條都過不了。被抓的節點帶著目前的 SAE 和 net_root,全隊卻沒有任何換密碼的路;B-M4 在 v2 指出的洞,在最常見的情況下仍然存在。
- **證據**:§3.1 前置 3、4;上游決定「網主自己的某一台節點遺失 / 被抓時,可以換密碼並排除那一台」;§0 沒有說明這個限制的理由。
- **這條限制不是必要的**:
  - join2 只要求紀錄 APPLIED + 網主金鑰 + 不滿 16 台(join2flow.rs:298-316),不需要「已經有一台自己的節點」;
  - creator() 改成讀 k13 最舊那一項之後,建立者被排除也只會讓保護不觸發(§2.1 已寫);
  - 前置 4 的回滾偵測只是緩解:store 的回滾本來就要 root 才做得到(store.rs:9-11、R4),而且 §2.4 已經接受「自己的節點有連不上的」這種情況。
- **修法(二擇一,屬使用者決定)**:
  - (a) 允許排除最後一台。這時沒有自己的節點可以做 k9 檢查,改成在確認對話框寫一句誠實界線(「這支手機無法確認紀錄是不是最新的;如果你曾還原過手機資料,不要繼續」)。commit 後,網主認領一台新節點,用 join2 以目前版本加入。沒有自己的節點時,網主的手機沒有 mesh 可以傳包,要當面或用別人的手機 AP 傳,也寫在對話框裡。
  - (b) 維持限制,但寫進 §0「不做」與 §6 的誠實界線:「網主只有一台節點、而它被抓時,只能重建網路」,並回報給使用者,說明他的決定在這種情況下不成立。
- **測試(a)**:網主 k11 只有一台 → 排除 → commit、k11 沒有自己的項、network/update 送出 0 次 → join2 新節點以 v2 加入;負對照:照 v3 的前置 3 → 被拒。

### MAJOR-4 「start > k10 + 1 → 不產包」加上「k10 永遠不前進」:同意之後第 17 次換版起,每一位成員都拿不到包,即使他一直都有跟上

- **情境**:Carol 在 v1 被同意(k10 = 1)。之後她每一份包都準時匯入,mnet 已經到 v17。網主做第 17 次換版(移除人、排除自己的節點都算),變成 v18。
  - 依 §2.3,start = max(1 + 1, 18 − 15, 最舊一版) = 3 > k10 + 1 = 2,所以不產包,畫面要網主「讓他的節點離開網路、再重新邀請他」。
  - 但 Carol 其實只缺 v18 一版。換成 start = 3 的鏈(v3…v18,16 步)給她,§3.4-2 會把她已經有的前綴去掉,照樣匯入成功。
  - 所有在 v1 加入的成員會在同一次一起卡住,全隊都要離開再重新邀請。
- **證據**:§2.3 第一點;§2.1「複製更新包不推進它」(這條是對的,是 v1 BLOCKER 的修法);§3.4-2 去掉 ≤ mnet 版本的前綴、「第一版 > mnet 版本 + 1 → 你的資料太舊」。v2 第 2 輪 A-MAJOR-2 的修法 (1) 是「起點 = max(...),真的落後太多的人由**成員端**回『你的資料太舊』」。v3 照抄了起點公式,卻另外加了網主端的拒絕,所以這一項**沒有真的關掉**。B-m11 提議的「出路 = 重新邀請」只適用於真的落後的人,不適用於一直跟上的人。
- **修法(拿掉一條規則)**:網主端一律從 start 產包,不拒絕。§3.3 的固定說明加一句:「如果對方落後超過 16 版,他匯入時會看到『你的資料太舊』,那時請他的節點離開網路、再重新邀請他。」

### MAJOR-5 mnet 新的 k9 / k10 有兩個既有的寫入者沒有列進契約;同一個人加第二台節點時,這兩個欄位會被悄悄清掉

- **情境**:隊員 D 有一台節點 A,已經匯入過更新包,所以 mnet k9 = 歷代、k10 = {A 的 v3 secrets}。D 再用一張新邀請加第二台節點 B(R17、B-M5 都說一個人可以有多台)。
  1. 同意包匯入走 approve::import,它是**從頭建一個新的 MNet**(approve.rs:401-410),不是 decode → 改 → encode。舊 mnet 只沿用 `me`(:388-389),其他欄位都不帶。
  2. 結果 mnet 的 k9 和 k10 消失:A 的新密碼不在這支手機了;分叉比對的歷代也沒了。
  3. 之後 A 被關機、版本落後時,§3.2-3 會說「這台的新密碼不在這支手機,請網主重新給你更新包」。這條路可以救回來(網主端 A 的 k10 不前進,所以還產得出包;§3.4 的「已經匯入過 + 補 k10」會補上),但要網主在場,而且設計沒有提過這條路。
- **另一個寫入者**:join2 隊員模式的 `MNet { me, ..m.clone() }`(join2flow.rs:238)只在 MNet 結構含 k9 / k10 時才會保留。設計只寫了網主端的 NetRec(§2.1 末)。
- **證據**:§4 擁有權表 mnet 那一列只寫「成員 app 的 Rust store(CAS,兩段)」;§2.1 末「所有寫回紀錄的流程(R24)…原樣保留」只講 net/;R24 只列網主端;T18 只測 approve / invite / forget / join2 對 net/ 的寫回。依通用規則,「每個資源只有一個擁有者,其他寫入者要明列」,這裡是寫入者漏列,而且後果是資料悄悄被清掉。
- **修法**:
  1. MNet 結構加 k9 / k10;R24 補上 approve.rs:401 與 join2flow.rs:238。
  2. approve::import 遇到既有 mnet 時要寫明規則:同版或 +1 版 → 帶上舊的 k9(+1 版再把新的一版接上去)與 k10(依 dac_hash,保留其他台的那份);TooOld 取代(§3.6-2)→ 明寫整份丟掉,畫面告訴他「你其他節點的新密碼要請網主重新給更新包」。
- **測試**:T18 加 mnet 那一臂:有 k9 / k10 的 mnet → 第二台節點的同意包匯入 → 舊的 k9 與 A 的 k10 都還在;join2 隊員模式寫回後 k9 / k10 不變;負對照 = 現在 approve.rs:401 的寫法 → 兩個欄位消失。
