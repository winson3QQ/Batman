## 1. MAJOR

### M1 §2.0 對象守則照字面會擋掉所有 join2,包括加新節點與加回找到的節點;§3.6、§3.1、T26 與它矛盾

**守則原文(§2.0)**:「§3.2 送 network/update、網主 join2、隊員模式加入之前,目標的 dac_hash 必須是『網路裡的自己節點』(網主 = k11 中 owner_pub = 自己的項),且不在目前版本 members 的 removed。」

**情境 1:排除最後一台之後加一台新節點**(§3.1 末、T26 後半)
- 新節點 N 不在 k11,因為 k11 項正是 join2 自己建立的(join2flow.rs:12-13 step 4)。
- 照守則,N 不是「網路裡的自己節點」,所以 join2 被拒。網主永遠無法再有節點。
- 一般情況也一樣:網主任何時候加第二台、第三台自己的節點都會被擋。

**情境 2:找回之前排除的自己節點**(§3.6「確認後才建 k11 項」)
- 這台不在 k11,而且在目前 removed 裡。守則兩個條件都不過,所以 §3.6 的確認對話框永遠到不了。
- §5 那一列「被排除的自己節點回到 BLE 範圍 / 被重設 | … 不送、不 join」也和 §3.6 矛盾。T27 斷言 join2「不送」,沒有「確認後可以」那一臂。

**情境 3:守則的檢查時機**
- join2 在送之前會先寫 k11 joining 項(PersistNet)。如果守則放在那之後才查,目標一定已經在 k11 裡,守則就失效。
- §3.5 的「join2 回 5 → 接得上 → 直接送」同樣發生在 joining 項寫入之後。

**為什麼是 MAJOR**:這裡是 fail-closed,不會漏秘密。但它擋掉了使用者決定的功能。實作者最自然的「修法」是把 join2 從守則裡拿掉,而 join2 的 secrets 是對登入的 ecdh_pub 現產的(join2flow.rs:363),守則一拿掉,第 3 輪 B-B1 的第 5 條路(被抓的節點重設 → NotApplied → join2 拿到新密碼)就回來了。

**修法**(只改寫守則,不加機制):把三個入口分開寫。
- **網主送 network/update(§3.2、§3.5)**:目標 ∈ k11,而且 owner_pub = 自己。k11 就是權威,commit 時已刪掉被排除的項,所以不必再看 removed;再看 removed 反而會擋掉 M2 的「加回」。ecdh_pub 只取自那一項。
- **網主 join2**:守則在任何 PersistNet 之前查。
  - 目標在目前 members 的 removed 裡 → 顯示 §3.6 的確認;不確認 → 0 次 SignAdmin、紀錄不變。
  - 目標不在 removed → 照今天的 join2。
  - §3.5 的「回 5 → 直接送」走 network/update 那一條(此時目標已在 k11)。
- **成員**:見 M2。
- **§5 那一列**改成「不送;只給『離開網路』;要加回 → join2 + 確認」。

**測試**:
- T26:排除最後一台 → join2 新節點 → 以目前版本加入。
- T27 加三臂:
  - 被排除的節點 join2 → 出現確認;按否 → 0 次 SignAdmin,紀錄 bytes 不變;按是 → 加入,下一版 removed 不含它。
  - 被排除的節點按「把新密碼送給節點」→ 0 次。
  - 守則放在 PersistNet 之後(mutation)→ 測試失敗。
- 負對照:照 v4 的字面 → T26 失敗。

### M2 重新邀請被移除的人之後,他的節點被成員端守則擋住,無法加入;T14 的最後一段照字面一定失敗

**情境**(就是 T14 的流程):
1. dev 移除 dev2 → v2:02 的 dac_hash 進 v2 的 removed。
2. 02「離開網路」→ dev 重新邀請 dev2 → dev 同意。
   - 同意只在 k11 加 approved 項,**不產新版 members**。同意包 key 2 = k8 = v2 members,而 02 仍在它的 removed 裡(approve.rs:155-156)。
3. dev2 匯入同意包:+1 路,§3.6-2b 的「me 不沿用」生效,mnet k4 = v2 members(02 在 removed),k7 = 02。
4. dev2 按「加入網路」(隊員模式)。§2.0 成員守則的第一個條件過了(02 是 k7),第二個條件「不在目前版本 members 的 removed」不過,所以畫面顯示「這台已被排除在隊伍網路外,只能『離開網路』」。
   - 結果:被重新邀請的人要等網主**再換一次密碼**才進得來,而且設計沒有說要這樣。
   - T14 寫的「02 以目前版本加入、鄰居恢復」照字面做不到。
- 網主那一側(M1 情境 2)是同一個根因:「加回」發生在同一版本裡,而 removed 要到下一版才會清掉(§2.4 `− key 4`)。

**為什麼守則在成員端本來就不是防線**:成員手機上能送的 secrets 都是網主簽、加密給特定節點 ecdh_pub 的(mnet k5 / k10)。被排除的節點沒有對應的私鑰,拿到也解不開(§3.7,node.go:936-956)。成員端守則只是畫面提示。它擋錯的代價是功能壞掉,不擋的代價是 0。

**修法**:成員端守則改成「目標 = mnet k7,或 mnet k10 有它的目前版 secrets」,也就是網主在目前版本為這台簽過 secrets。拿掉「不在 removed」;removed 只在 §3.4-6(匯入**更新包**)時用。§2.0 同時寫明:「removed 是歷史,k11 / 網主為目前版本簽的 secrets 才是現況」。

**測試**:
- 新 T17b(Rust):移除 → 同一版內重新邀請、同意、匯入 → 隊員模式加入的守則通過、送出 1 次。
- 負對照:照 v4 的字面 → 0 次。
- 真機 T14 最後一段就是它的端到端證明。

## 2. MINOR

1. **§5「成員落後 > 16 版 / 超出歷代 | 不產包」與 §2.3「網主端一律產包」矛盾。** 這一列是 v3 的殘留,照它實作會讓第 3 輪 A-M4 / B-M1 回來。改成「照產;成員端回『資料太舊』→ 離開再重新邀請」。T8b 已經是對的。
2. **128 KiB 的上限要寫明量的是什麼。** 16 人 × 16 步約 70 KB(§2.3);如果量的是 qr-object 的 hex 文字,會是約 141 KB > 131 072,合法的最大包會被拒。寫明「解碼後的 bytes ≤ 128 KiB」,並加一個 16 人 × 16 步的邊界測試。
3. **k4 規則的正規式。** `-wsl\.(\d{1,9})` 對 `-wsl.2500000000` 會匹配前 9 位而通過,和「位數超過 9 = 不通過」相反。改成 `-wsl\.(\d+)`,再判斷長度 ≤ 9;或者要求匹配之後的下一個字元不是數字。T5 的「數字溢位」那一臂要用 10 位數。另外補一句前提:wsl.N 單調遞增,而且 ≥ 25 的 build 都從含 fbc01ae 的 feed 編出。分支 build 可能打破這個前提;這是 dev 才有的界線,寫明即可。
4. **回滾不一定要 root。** `allowBackup` 預設 true,紀錄在 filesDir。同一台手機、Keystore 金鑰還在的情況下,開了 USB 偵錯的人用 `adb shell bmgr restore` 可能把舊的封存檔放回來(⚠️ 推論,未實測)。這會讓 §6「回滾要 root」不成立,也讓 §3.2 的「唯一能造出同版號另一份的是第二位簽署者」不成立:回滾後網主會重簽同一版號(F18)。
   - 修法二擇一:manifest 設 `android:allowBackup="false"`,或用 dataExtractionRules 排除紀錄目錄(一行);或者在實機驗證之後改寫 §6 / §3.2 的說法。
   - §3.2 的理由要加「或紀錄被回滾(§6)」。
5. **網主 app 降級後沒有對象守則。** 舊版 join2 會把被排除(被抓)的節點以目前版本加回去。降級是使用者自己的動作,寫進 §5 降級那一列就好(誠實界線),不加機制。
6. **§2.4 少了一個分支:自己節點的 k9 < k13 最舊一版**(32 版沒換)。寫明「不開始,請它離開再加入」,或者「把它當成連不上」。另外,k9 > v 的告警要寫出是**哪一台**回報的:被抓、但還沒排除的自己節點只要謊報 k9 就能擋住換密碼。這時的出路是先排除那一台,而不是 §2.4 寫的「重建網路」。
7. **removed 只增不減,會讓每一步變大。** 每次移除或排除都加 32 B,永遠不清,而 §2.3 / §3.2 的塊數估算(16 人約 4.4 KB / 步)沒有算它。寫一句上限:例如 removed > 64 筆時,丟掉最舊的;代價只是 SAS 畫面少了「之前被移出過」那句提示。或者寫明這筆成本可以接受,並在 T9 用滿 removed 的情況實算塊數。
8. **共同擁有者的界線。** 節點端已有 `owner/add`(最多 4 位,254-p3-impl F3),app 沒有這個流程。「移除一個人」看的是 k11 的 owner_pub,不看節點上的擁有者清單。若將來某個留下的節點把被移除者加成共同擁有者,他就能用擁有者 / root 權限讀到新 SAE。今天不會發生(app 沒有這個入口);寫進 §6 的誠實界線,並在 §9 checklist 加一句「app 加 owner/add 時,移除一個人要一併 owner/remove」。
9. **把「網主只有一位」從不變式變成前置檢查。** §3.2「k9 = 目前就足以判定」與 §3.4-3 都靠「admins 只有這支手機」。前置 1 只檢查「這支手機在 admins 裡」。改成「admins == [這支手機的 ADMIN_SIGN 公鑰]」,不符就不開始。這是一行檢查,把假設變成機制,並加進 mutation 清單。
10. **合成第三人的工具放哪裡要寫明。** 第 2 輪 A §5 建議放 `tests/tools` 或 batman-proto 的 example,不進 app。v4 只寫「主機端測試工具」。寫明路徑,以及「不進 app、不進節點 image」;T25 順便斷言非 dev-trust build 不含它的入口。
