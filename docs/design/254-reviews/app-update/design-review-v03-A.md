## 2. 新發現

### MAJOR

**N1. §3.4 的「百分比在增加 → 有人在上傳 → 換密碼並停止」,以及「百分比停住就可以提早重試」:在現場訊號差的情況下會誤報安全警告,也會提早用掉 3 次的額度。建議兩段都刪掉。**

情境:人在節點旁邊、訊號差,PUT 卡住。35 s watchdog 觸發,app 關掉 socket,結果算「其他」。

- **(a) 誤報有人在上傳**
  - D4 只寫「關掉 socket」,沒有設 `SO_LINGER(0)`。一般的 close 是優雅關閉:kernel 會繼續把 send buffer 裡已經接受、還沒送出的資料送出去(Android 的 TCP buffer 可以到 MB 級)。
  - 訊號一恢復,provd 那個還沒結束的 PUT 就會繼續收到 bytes。它要等 30 s 讀取期限才會放掉(F12,provd/http.go `copyUpload` 每次讀都重設期限)。helper 每 4 s 的 poll 會把百分比往上推(bulk.go:147-149)。
  - app 依 §3.4-2 看到「我們沒在傳,百分比卻在增加」,就叫使用者「請換節點 Wi-Fi 密碼」,然後停止。
  - 這是一個錯的安全指示,而且正好發生在最常見的現場狀況(訊號差、斷斷續續)。
  - 同樣的事也會發生在 U6 取消時,以及 Specifier 網路 `onLost` 時。
- **(b) 提早重試,額度很快用完**
  - §3.4-1 寫「至少 31 s,**或者**百分比停住(兩次讀到相同值)」。
  - provd 每 4 s 才回報一次百分比;放棄的 PUT 停止進資料後,百分比一定會先「停住」。所以兩次讀取在幾秒內就會相同 → app 提早重試。
  - 這時 `putting` 還是 true → provd 在讀 body 前就回 409 → 結果又是「其他」,而且依 §3.4-4 計一次。
  - 3 次的額度可能在 1 分鐘內就用完,顯示「傳送一直中斷」。
- **證據**:F12(http.go:46、:540、:571-572);bulk.go:145-149(百分比只來自 provd 的 poll);§3.4-1、-2;D4 沒提 SO_LINGER;T5 第 3、4 臂把這兩條當成規格在測。
- **修法(刪除)**
  - 等待一律固定 ≥ 31 s,刪掉「或者百分比停住」。
  - 刪掉「有人正在對節點上傳」的偵測、§6 對應的那一列、T5 那一臂。
  - 真的有人搶先 PUT 的情況,已經由 P3 :517 原句涵蓋(連續 3 次 → 「…可能有人在節點 Wi-Fi 上干擾,請換節點 Wi-Fi 密碼…」),不需要另一套偵測。
  - 如果作者堅持保留偵測,至少要做到兩件事:取消、watchdog、`onLost` 時用 `setSoLinger(true, 0)` 送出 RST;判定前要在 31 s 之後間隔 ≥ 8 s 連續兩次讀到值增加。但這是加機制,不建議。
- **負對照**:T8 加一臂。假節點在 app 關掉 socket 後繼續讀,app 不得顯示「有人在上傳」。刪掉之前這一臂應該 FAIL,刪掉之後 PASS。

### MINOR(進 checklist)

- **m1. 每次重試都會重新請求 Specifier,TAK 每次都斷兩次**
  - D5 寫「PUT 結束後 `unregisterNetworkCallback`」,而 §3.4 每次重試都會重新走 U5。
  - 在單 STA 手機上(F25),每次重試 TAK 都會斷兩次,也可能每次都跳對話框。
  - 修法:Specifier 網路留到整個上傳階段結束(prepare 成功、取消,或 3 次用完)才放掉。
- **m2. 直連路徑上連線逾時 3 s 就改走 Specifier,太容易誤判**
  - 現場訊號差時,3 s 內可能只送出 2 個 SYN,而且都丟了。這時連線逾時並不代表「不是這台的 AP」:直連路由已經涵蓋節點 IP,證據本身就夠強。
  - 誤判的後果:在同一個 SSID 上走 Specifier → TAK 斷兩次,還會跳對話框(§6 那一列)。
  - 修法:直連路徑上,逾時先重試 2–3 次再退到 Specifier。
- **m3. U7 收到 200 之後先送 `bulk/open`,它失敗會導致整份重傳**
  - 例如防火牆檢查暫時沒過,回 21 → §3.4 → status 1 → 走 U4 → 重傳 126 MB。但 prepare 根本不需要 HTTP。
  - 修法:U7 的 `bulk/open` 只在 BLE 重連過之後送,而且它失敗也照樣送 prepare;或者整個拿掉,接受窗只剩 60 s 的邊界(v0.2 m7)。這也算刪機制。
- **m4. §3.3 第 3 列的寫法會讓人以為要多送一次 check**
  - 第 3 列寫「手上有同一份 manifest → 自動重送 check 一次」。但 phase 3 本身就代表 pending 有效,這時重送 check 沒有作用;一位擁有者的情況下還會覆寫 pending,有兩位時會回 E_BUSY。
  - 這條本意是 apply 回 15 之後才做(§3.4 最後一條),應該移到那裡,避免實作照字面多送一次。
- **m5. U2 最多要等 340 s,畫面沒有說明**
  - 修法:顯示「節點正在檢查(最多幾分鐘)」,並註明這段時間不能取消,否則使用者會以為當掉。
- **m6. 擷取向量的程式不能留到之後**
  - 「擷取程式放哪」放在 §12-1 checklist,但 T4–T7 依賴這些向量。
  - 必須在寫 T4–T7 **之前**就完成,並且和本功能一起交付;否則 T4–T7 會退回成自己寫的假節點,v0.2 M8 的問題又回來了。

## 3. 還能刪的機制(使用者偏好)

1. **N1:刪掉偵測和「或者百分比停住」**。效果:少一條誤報路徑,也少一個 T5 測試臂。
2. **m3:U7 的 `bulk/open` 改成只在重連後送,或拿掉**。
3. 其餘新機制都是必要的,不建議刪:
   - raw socket(B1);
   - 每次 PUT 前送 `bulk/open`(讓 409 分類消失);
   - 35 s watchdog(否則寫入卡住時 TCP 很久才放棄);
   - targetSdk 固定成 36 + 建置檢查(成本一行,防的是 flutter 升級後 PUT 悄悄失效);
   - D8 拆成三個 Kotlin 呼叫(秘密只在需要時經過 Dart);
   - 「先讀 status」這一條總規則(它取代了好幾套分流,整體上是少了機制)。
