# #255 第 1 期實作設計：bench 上以 608B 作為節點身分（v1，未審查）

範圍：把 bench 上的空白 ATECC608B（`255-608b-config.md` v3 的設定）接成節點的身分後端，並讓協定、app、驗證工具配合。**只在開發版生效**：field 版 app 第 1 期之後仍拒絕所有節點（量產根要等選定量產晶片與 #256）。
不含：信任模型（第 2 期）、量產晶片、secure boot。
依據：`255-608b-config.md` v3（晶片設定、§9 的 13 項）；`255-key-authority.md` v3.1（K13–K16、K20、K21 約束本期）；`255-threat-model.md` v2.1。
基準：main 4eba26d。節點路徑以 `feed/batman-prov/src/` 為根；app 的 Rust 以 `app/rust/` 為根。現況事實由一次唯讀核對取得，每條附行號；標記：✅ 對過原始碼；⚠️ 推論或未驗證。

## 0. 決定（技術細節，由作者定案並說明理由）

| # | 決定 | 理由 |
|---|---|---|
| P1 | **晶片驅動用純 Go 自己寫**（helper 內，經 `/dev/i2c-1`），不用 cryptoauthlib，也不用第三方 Go 套件 | helper 目前不用任何 C 函式庫；驗證工具與 CI 都以 `CGO_ENABLED=0` 建置（`dv-sbx.sh:69,80`、`tests/wbox/gen/gen.sh:40`）✅；cryptoauthlib 沒有 OpenWrt 套件。現有的純 Go 套件一個已封存、一個是零星的分支，沒有人審過（F§15）。本期只需要十來個指令，自己寫較可控。訊息格式以 cryptoauthlib 的主機端程式（`lib/host/atca_host.c`）為參考並用它產生測試向量 |
| P2 | **身分後端由建置決定，不在執行期探測。** 新增建置參數 `BATMAN_PROV_SE=1`：這種映像的 helper 只有晶片後端，**永遠不會產生檔案身分**；沒有這個參數的映像只有檔案後端（沒有 HAT 晶片的開發機、CI、模擬器） | 執行期探測時，晶片暫時無回應會讓有晶片的機器產生軟體身分，違反 K20（審查 v3-B 的疑慮）。在建置時決定，K20 由構造保證。今天已有同類的建置參數 `BATMAN_PROV_TEST`（`Makefile:23-30`）✅ |
| P3 | **節點證書有兩種樣式，app 依憑證判斷**：「開發檔案樣式」= 今天的自簽 `dev:` 憑證（行為不變）；「晶片樣式」= 開發根簽的憑證 + 兩份背書。**兩種都只有開發版 app 接受** | 檔案後端只給沒有晶片的開發機，金鑰本來就是可讀的檔案，替它加背書沒有意義；維持現狀改動最少 |
| P4 | **每次連線的身分證明放在 msg2 之後的第一個請求**：app 送 `id/prove`（無內容），節點回 `sign_session("batman-node-session-v1" ‖ h)`；app 驗過才送下一個請求 | msg2 之後才有最終的交握雜湊 `h`，所以證明無法放進 msg2（`noise.go:105`）✅；今天 app 在 msg2 後第一個送的就是 `auth/owner` 或 `claim/begin`，前面插一個請求不影響其他流程 |
| P5 | **背書由 helper 開機時做一次，放記憶體，不落地** | 背書是固定事實；不需要每次連線都做（晶片設定 §2） |
| P6 | **檔案後端也改用每次連線的證明，拿掉 `sig_static`** | 兩種樣式用同一條登入路徑，app 只有一套流程；檔案後端用身分金鑰簽（它本來就只有這一把） |
| P7 | **不做相容**：`node_cert` 改版後，舊 app 不認新節點，新 app 不認舊節點 | 目前沒有對外部署；bench 節點會重燒、重新認領（晶片設定 §7） |
| P8 | **燒錄是 helper 的一個模式**，開發根的簽章在開發者電腦上做，經 ssh 來回 | 只有 helper 碰晶片（K21）；開發根私鑰不放節點 |

## 1. 現況（✅ main 4eba26d）

- 身分：`keystore.Keystore` 是具體型別（`keystore.go:34-40`）；`Backend()` 固定回 "file"，載入時拒絕其他值（`:69, :266-267`）。只有 helper 連結它；provd 只透過 helper 拿結果（`server.go:16`）。
- 產生身分只在 helper 開機流程（`main.go:484`、`boot.go:207, 231`），已有身分時不產生（`boot.go:189-230`）。
- 節點證書由 provd 組成：`{1:[cert], 2:s_node, 3:boot_id, 4:ecdh, 5:sig_static, 6:sig_ecdh, 7:sn}`（`server.go:306-363`），快取一次；沒有它 provd 不服務（`:530-532`）。
- app 驗證：`nodecert.rs` 的 `common`（`:89-123`）檢查 `sig_static`、`sig_ecdh`、`sn` 等於憑證序號、`device_id = hex(sn)`；`trust_gate`（`:146-156`）只接受自簽 `dev:` 且開發版；`verify_offline`（`:161-170`）要求剛好 1–7 號欄位。
- 認領證明：`CheckMacInput` 用 `sn[8]`、`sn[0:2]`（`proto.go:54-70`）；app 的 `sn` 取自 `node_cert` 第 7 欄（`claimflow.rs:172`）。`ClientChal` 雜湊整張憑證（`proto.go:48-52`）。QR = `{1: device_id, 2: claim.secret}`，由 `provhelper qr` 產生（`main.go:598-623`）。
- ECDH：app 因 `sig_ecdh` 驗過才信 `ecdh_pub`（`nodecert.rs:113-117`）；節點以 `SHA-256(DACPub)` 當密碼包的對象（`wtxn.go:132-135`）。
- `peers/challenge`：provd 拒絕（`session.go:68-69`）；helper 有 `sign.peer`（`node.go:412-430`），沒有人用。
- 試用開機：helper 沒有可用身分時不開始服務（`main.go:632-636`），provd 不寫穩定標記，試用逾時回退（`stable.go:30-51`、`batman-autocommit:500-515, 192-255`）。
- helper 簽章全域限每秒 2 次（`node.go:376-388`）。
- 碰身分檔的驗證工具與測試：約 35 個檔案（現況核對逐一列出），另有 4 支量產用的節點腳本寫死檔案清單（`prov-lock.sh:7` 等）。
- 登入基準（#329）：連線到讀完狀態 2.8–5.6 秒；10 次登入 9 次 ≤ 20 秒（`329-app-uiux.md:998, 1021`）。

## 2. 節點端

### 2.1 身分介面

`keystore.Keystore` 改成介面 `Identity`，現有方法保留語意：

| 方法 | 檔案後端 | 晶片後端 |
|---|---|---|
| `DeviceID()` | 不變（`SHA-256(DAC 公鑰)[:9]`） | `SHA-256(槽 1 公鑰)[:9]` |
| `ChipSN()` | 同 `DeviceID` 的位元組（認領證明照舊） | 晶片序號（設定區 0–3、8–12） |
| `Cert()` | 自簽 `dev:` 憑證 | 槽 8 的開發根憑證 |
| `IdentityPub()` | DAC 公鑰 | 槽 1 公鑰 |
| `ECDHPub()`、`ECDH(peer)` | 檔案 ECDH 金鑰 | 槽 2，明文輸出模式（bench 不開匯流排保護，晶片設定 §6.4 已接受） |
| `SignSession(label, h)` | DAC 簽 | 槽 0 簽（外部簽章，含亂數 nonce） |
| `Endorsements()` | 無 | 開機時產生的兩份背書（P5） |
| `CheckMac(chal, resp)` | 軟體計算（不變） | 晶片的比對指令，槽 5 |
| `Counter()`、`CounterInc()` | 檔案欄位（今天的 `claimed_counter`） | 晶片計數器 1 |
| `Backend()` | "file" | "se" |

- `SignPurpose` 的三種用途改為：`Static` 刪除（P6）；`ECDH` 只在檔案後端存在；`Peer` 改走 `SignSession`。晶片後端沒有任何「替外部資料背書」的方法（K16）。
- 簽章仍受每秒 2 次的全域限制；登入只多一次簽章。

### 2.2 晶片驅動（`se608` 套件）

- I2C：`/dev/i2c-1`，`ioctl(I2C_SLAVE = 0x0703, 0x60)`（常數自己定義，vendored 的 `x/sys` 沒有），100 kHz。
- 喚醒：對位址 0x00 寫一個位元組（產生喚醒脈衝），讀回 `0x11`；每個序列結束送閒置，跨序列不保留暫存區。
- 封包：計數 + 指令 + CRC-16（多項式 0x8005，F§9）；輪詢等待，逾時用 cryptoauthlib 的最快時脈上限（F§9）。
- 本期需要的指令：Info、Read、Write、Lock、Random、Nonce（含亂數模式與直通）、GenKey、Sign（外部、內部）、ECDH、CheckMac、Counter、GenDig（只用於實驗）。
- **不實作**：UpdateExtra、DeriveKey、PrivWrite、KDF、AES、SHA 的暫存區輸出（只在實驗程式裡另行實作，見 §5）。驅動沒有這些指令，就不會被誤用。
- 驗證：單元測試以 cryptoauthlib 主機端程式（Python 重寫或擷取其向量）產生的預期值比對封包、CRC、內部簽章訊息與認領比對的雜湊輸入。

### 2.3 開機流程（晶片映像）

1. 讀晶片：版本（`00 00 60 03`）、設定區、鎖定狀態、序號。
2. 判斷：
   - 兩區已鎖、槽 0/1/2/5/8 已鎖、設定與影像相符 → **已燒錄**。
   - 其他任何狀態（空白、部分鎖定、設定不符）→ **燒錄未完成**：不服務，回報狀態，等燒錄模式處理。
   - 晶片無回應 → **身分不可用**：不服務；每 30 秒重試；回應後走第 1 步。
3. 已燒錄：讀三把公鑰與憑證；產生兩份背書並以本機參考驗證程式驗過（驗不過 = 身分不可用）；與資料分割區的身分紀錄比對節點 id，不符（換過 HAT）→ 舊紀錄作廢，狀態改為未認領。
4. 開始服務。

試用開機：第 2、3 步不通過就不服務 → provd 不寫穩定標記 → 試用逾時自動回退（沿用今天的機制，不新增）。已確認的映像上，「身分不可用」時 mesh 照常運作（網路設定不經 helper），helper 持續重試；這就是晶片設定 §7「不閂鎖」的實作方式。

### 2.4 身分紀錄與腳本

- 晶片映像的身分目錄只放：`backend`（"se"）、`device_id`、`chip_sn`、`cert`（槽 8 的副本，供 shell 讀取）。沒有私鑰、沒有認領秘密。
- `prov-lock.sh:7` 等四支腳本寫死的檔案清單，改成依 `backend` 決定清單。
- 晶片映像的 helper 若看到 `backend` 是 "file" 的身分目錄：不載入、不刪除，回報「後端不符」（例如把檔案映像的卡改刷晶片映像）；要重新燒卡。

### 2.5 燒錄模式（`batman-provhelper --se-burn`）

只在 console 或 `/etc/batman-dev-open` 存在時可執行（同 `provhelper qr` 的規則，`main.go:598-623`）。步驟與晶片設定 §5 相同，分成兩段：

1. **節點上** `--se-burn stage1`：檢查版本 → 寫設定影像、讀回、鎖設定區 → 寫資料（認領秘密以晶片亂數產生）、鎖資料區 → 產生金鑰、逐槽鎖定 → 讀回設定與鎖定狀態 → 輸出一份 JSON：序號、設定讀回、三把公鑰、兩份背書（含亂數輸入輸出）、認領秘密。**認領秘密只出現在這一次輸出裡。**
2. **開發者電腦上** `se-sign`（新工具，`tools/se-sign/`）：驗證讀回的設定與影像完全相同、背書可由參考驗證程式驗過 → 用開發根簽出憑證 → 產生機身 QR 圖檔 → 把燒錄紀錄存到開發者電腦（不進 repo）→ 輸出憑證。
3. **節點上** `--se-burn stage2 <cert>`：寫入槽 8、讀回、個別鎖定 → 寫身分目錄。

- 任何一段中斷：重跑同一段；stage1 依晶片目前的鎖定狀態從中斷處接續（鎖定前的步驟可重做；金鑰已產生但未全部鎖定 → 這顆報廢，與晶片設定 §7 一致）。
- 燒錄工具在 E0–E3 階段另有一個「不含任何鎖定指令」的版本（建置參數控制），用來做可回復的實驗。

### 2.6 provd

- `buildNodeCert` 改組新欄位（§3.1）；不再呼叫 `sign.static`、`sign.ecdh_proof`。
- 新請求 `id/prove`：所有角色（含匿名）都可送，每條連線只能送一次，回 `sign_session(h)`。
- `peers/challenge` 維持拒絕（本期不實作）；之後實作時用 `SignSession`。

## 3. 協定

### 3.1 `node_cert` v2（`219-protocol.cddl` 同步修改）

| 欄位 | 檔案樣式 | 晶片樣式 |
|---|---|---|
| 1 憑證 | 自簽 `dev:` | 開發根簽發，主體 `se:<device_id>` |
| 2 s_node | 有（不再另外簽） | 有 |
| 3 boot_id | 刪除 | 刪除 |
| 4 ecdh_pub | 有 | 槽 2 公鑰 |
| 5 | 刪除（原 `sig_static`） | 刪除 |
| 6 sig_ecdh | 有（只在檔案樣式） | **不可出現** |
| 7 sn | `device_id` 的位元組 | 晶片序號 |
| 8 session_pub | DAC 公鑰（與憑證相同） | 槽 0 公鑰 |
| 9 endorsements | 不可出現 | `{0: 槽 0 的背書, 2: 槽 2 的背書}`，各含簽章、亂數輸入、亂數輸出 |

### 3.2 app 的驗證（`nodecert.rs`）

- 依憑證判斷樣式；欄位組合必須完全符合該樣式，多一個少一個都拒絕。
- 晶片樣式：憑證由開發根簽（開發根公鑰編進開發版 app）；`device_id = SHA-256(憑證公鑰)[:9]`；對槽 0、槽 2 的背書，**用常數重建 55 位元組訊息**再驗（晶片設定 §2 的常數表），公鑰取自第 8、4 欄；`sn` 是第 7 欄，與 `device_id` 無關。
- 兩種樣式共同：收到 msg2 後立刻送 `id/prove`，以第 8 欄驗 `"batman-node-session-v1" ‖ h`；驗過之前不送任何其他請求。
- `trust_gate`：開發版接受兩種樣式；field 版兩種都拒絕（今天的 field 版本來就拒絕所有節點，§1）。
- `verify_offline`（離線驗證加入申請裡的節點證書）：沒有 `h`，無法驗當場證明。檔案樣式照舊；晶片樣式只驗憑證與背書。這條路只存在於開發版的三段式加入，第 2 期會移除（信任模型 Q5）。
- `ecdh_pub` 的可信來源：檔案樣式 = `sig_ecdh`；晶片樣式 = 槽 2 的背書。所有用到 `ecdh_pub` 的地方（`joinflow.rs:208, 227`、`approve.rs:186`、`rekey.rs:179, 587`、`join2flow.rs:358, 405`、`updflow.rs:167-168`、`replayflow.rs:64`）不改，因為它們都從已驗過的紀錄取值。
- 節點端的密碼包對象：`SHA-256(IdentityPub)`（`wtxn.go:132-135` 改用介面方法），兩種樣式一致。

### 3.3 認領

- `CheckMacInput` 不變；`sn` 來源不變（第 7 欄），只是晶片樣式下它是晶片序號。
- QR 不變：`{1: device_id, 2: 認領秘密}`。晶片映像的 `provhelper qr` 回「不支援」（認領秘密讀不出來），QR 由燒錄時的 `se-sign` 產生。

### 3.4 測試向量

`tests/vectors/219-protocol/` 加入晶片樣式：以 cryptoauthlib 主機端程式的算法產生背書訊息、認領比對輸入；E7、E8 在真晶片上擷取的實際輸出回填為第二組向量（真機證據）。

## 5. 晶片實驗程式

`tools/se-lab/`（開發者用，不進映像）：在節點上執行，實作驅動沒有的指令（SHA 輸出到暫存區、KDF、AES、UpdateExtra、DeriveKey、PrivWrite、GenDig 各區），執行晶片設定 §8 的 E0–E16。它和燒錄模式一樣只能在 console 或開發模式下執行，並且**會拒絕在已燒錄成正式設定的晶片上執行 E7–E13 以外的寫入**。E0–E3 用不含鎖定指令的建置。

| 燒錄紀錄（含認領秘密） | `se-sign` | 開發者 |
| `node_cert` | provd（由 helper 提供材料） | app、對端工具 |

| 介面 | 寫 → 讀 | 缺漏或錯誤 |
|---|---|---|
| `id/prove` | provd → app | app 拒絕連線 |
| `node_cert` v2 | provd → app | 欄位組合不符或驗不過 → 拒絕 |
| `identity-info` | helper → 腳本 | 非零結束碼；腳本判 FAIL，不當成通過 |
| 燒錄 stage1 輸出 | 節點 → 開發者電腦 | `se-sign` 驗不過就不簽 |

## 8. 安全

- 新的輸入：`id/prove`（任何人都能送，每條連線一次，受全域簽章速率限制）；`node_cert` v2 的新欄位（app 端解析）；燒錄模式（只限 console 或開發模式）；`identity-info`（唯讀，不含秘密）。
- 開發根：私鑰在開發者電腦；外洩的後果 = 能做出開發版 app 信任的假節點。開發版本來就不對外，可接受；field 版不信任它。
- 認領秘密只在燒錄時出現一次，存在開發者電腦的燒錄紀錄；不進 repo、不進 log。
- 晶片的 ECDH 明文輸出經過 I2C：bench 接受（晶片設定 §6.4）。
- provd 是加密通道的終點，看得到 `id/prove` 的回覆（只是簽章，不是秘密）。
- 本期不改變：PSK、網路密碼的保管、認領鎖定。
