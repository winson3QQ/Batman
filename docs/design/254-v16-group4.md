## 1. `prov-ac-flap-254` asserts the P3 rule

**Premise.** A trial whose helper keeps exiting is not commit-worthy: §3.7.6(a) and (b) hold it back, and the deadline revert removes it even while held.

**Determinism** (review A, verified):
- `provd-stable` needs a 60 s provd connection; the helper never lives that long.
- So every poll's why is "svc batman-provhelper down" or "batman-provd not stable…", and HELD cannot occur under the mutant.

**Flow** (the shape of `prov-ac-radio1off-254.sh`):
1. `pr_begin 3000`, precondition `ble-ok`, then `pr_ota_b "$PR_V.dirty.wbox-helper-flap" B`.
2. In the trial boot, poll every 10 s until the trial's own deadline (read from `$RUNDIR/autocommit.deadline`) minus 30 s:
   - log every `autocommit.why` sample (the evidence the wsl.35 run lacked);
   - require at least one sample that **contains** `svc batman-provhelper down`. The why can be compound, so the match is a substring.
   - Kept from the old unit: mutant live (at least 2 `WBOX-helper-flap-f4703b1d: exiting` lines) and health file fresh (this boot's, at most 60 s old; F14).
3. `pr_wait_reverted`. It FAILs on HELD, bounds the wait by deadline + DEFER_MAX + 120, renews the lease on deferral, and is INVALID on a panic.
4. `PR_REVERT_LINE` (this trial boot only) must contain `svc batman-provhelper down` or `batman-provd not stable`.
5. `pr_end revert`.

The why samples (step 2) are what show that (a), the helper gate, fired. A run where only (b) is ever seen FAILs with "(a) never observed".

**Judge as a function.** Steps 2 and 4 are a pure judging function, `acflap_judge <why-samples-file> <revert-line>`, so they can be tested offline.

**Negative controls.**
- **Offline** (`scripts/dv/test-acflap-254.sh`), synthetic inputs labelled as such:
  - (i) samples with (a) + revert (a) → PASS;
  - (ii) samples with only (b) → FAIL "(a) never observed";
  - (iii) revert reason `mesh not joined` → FAIL;
  - (iv) no samples → FAIL. An empty input must never pass.
- **On the device:** the old unit's judgement FAILs on wsl.35 (the log above). The new one must PASS on wsl.36 with the samples logged.
- The HELD branch is `pr_wait_reverted`'s, already covered by `prov-ac-radio1off`.

**Dropped, and where it goes.** The dry-run arm ("DRYRUN decision: COMMIT") asserted the old premise. Its timestamped run measured E-H5 #2, the time to the decision with the canary (`254-h23-harness.md:989`). That timed dry run moves unchanged into `prov-autocommit-p3-254` on its healthy trial, so E-H5 #2 is still measured. Review A m3 was right that this unit did not measure it before.

### 3.2 A product reboot during a unit is recognised, not taken for "already on A"

- `back_to_a` and `pr_restore_cycle` compare the boot with the trial's landing boot (`PR_LAND_BOOT`).
- **A new boot on A** means the product reverted the trial or a watchdog fired:
  - say `product rebooted the node (boot X → Y): <last autocommit.log TRIAL-* line for X>`;
  - `pr_find`, then `pr_acquire` with the remaining run budget (this also replays the undo journal; `prov-254.sh:205-216`);
  - then continue.
- **A on the same boot, still in a trial** (an A trial): leave it with `reboot_guarded <boot8> A 0 prov-dv-254` (one-shot tryboot back to the committed slot), not by answering "already on A" (review A m4, B m6). A refusal is a FAIL with the guard's answer.

**Negative control** (offline, `scripts/dv/test-restore-254.sh` style, `qr` / `q` / `pl` stubbed):
- landing boot `X`, state `slot=A boot=Y trial_rc=1`: main says "already on A" and the next renew fails. The fix re-acquires (stub `pl acquire` called), with the message.
- `slot=A boot=X trial_rc=0`: main returns 0. The fix sends `reboot_guarded … A 0`.

### 3.3 p5 restore: what the harness mounted is unmounted, anything else is named

The node-side p5 restore (`node/prov-base-254.sh:213-227`):
- Prints `P5-MOUNTED <mountpoint>` for every p5 line of /proc/mounts.
- **Unmounts only the harness's own mountpoints.** Those are the directories under `/tmp/run/batman-dv/` (`pbm.` `p5s.` `p5k.` `p5d.` `ch1.`) and under the node DV dir `$DVD` (`p5ro.` `p5w.`); every one is created by `mktemp -d` there (file:line in `v16g4-sites.md` / review B M3).
- Uses a plain `umount` (not lazy): a mount still in use fails, and that is reported.
- **Never touches** a product mount: `autocommit.p5` (an autocommit running unlocked), `cfgsave-mnt.*` (config-save's rw mount under its lock), or anything else. Those are named, and the result is NEEDS-PERSON.
- Re-checks, then dies listing what is left.
- The host prints every `^(P5-|FAIL)` line.

Review A M7 and B M3: v1 would have unmounted product mounts. No reproduction of a leftover mount exists, so the rule is the conservative one.

**Test seam** (review A M8):
- `PB_MOUNTS` (a file read instead of /proc/mounts), `PB_P5` (the device path) and `PATH` stubs for `mount` / `umount`.
- All honoured **only** when `PROV_BASE_TEST_ROOT` is set **and** `id -u` ≠ 0 **and** `PB_P5` is a regular file under the test root. Otherwise the script refuses with a FAIL line, so it never touches `/dev`.
- The test runs as an ordinary user in WSL.
- Cases:
  - a `pbm.` line → the stub `umount` is called, PASS;
  - a `cfgsave-mnt.` line → named, FAIL, no `umount` call;
  - a busy harness mount (stub `umount` rc 1) → named, FAIL;
  - main → no names (negative control).

## 4. Slot commands go through a guard, or are allowlisted with a reason

**The rule.** Every host- or node-side command in `scripts/` that reboots, rolls back or commits a bench node either goes through a guard or is allowlisted with a reason, and the lint enforces this.

**Not in scope:** `reboot -f`, sysrq and Shelly cuts that are the test itself (allowlisted), product-initiated reboots, and killpoints.

### 4.1 Guard changes (`slot-guard-254.sh`)

- **`commit_guarded <boot8> <slot> 0`**: a new `_sg_cmd` action. Same boot and slot, in a trial (is-trial rc 0) → `batman-slot commit` → `SENT` + the commit's own output. Anything else → WRONG-STATE, no commit. There is no DISARM: a commit does not reboot.
- **`pre=<cmd>`**: an optional action run on the node **after** every check passed and **before** the slot command, in the same shell. Its rc ≠ 0 → `PRE-FAILED`, no slot command. This is for overlay-wipe's `firstboot -y` (review B M2). On WRONG-STATE the node is untouched.
- **Ownership note** (review A m7, B m8): the guard's DISARM (vcmailbox) writes the product-owned tryboot flag. It is a second writer, outside batman-slot's slot lock. That is accepted because it only ever clears the flag on a committed node, the product's own disarm does the same, and it is the only way to make a plain reboot safe. A clear that fails = no reboot (fail-closed).
- **Pi 3:** the word-5 read was never captured on a Pi 3 (`254-v16-group1.md:59`). An unanswered tag reads as unknown, so `rb_guarded` / `reboot_guarded` refuse there (fail-closed). `commit_guarded` / `release_guarded` do not DISARM. The bench is Pi 4 only; the Pi 3 sites are listed below and stay allowlisted.

## 9. Security

- **Assets:** control of the two bench nodes (slot, boot, p5 identity).
- **Main actor: our own mistakes.** An unguarded reboot boots an armed test slot. A restore unmounts a product write. A wipe runs and then the reboot is refused. A test can no longer fail. Each is addressed above.
- **A local unprivileged host process** could edit the harness or a patch file. That is the same trust as today; the patches are repo content reviewed like code. The host-derived mutant runs only in a dry-run bind on the node, never installed.
- **A compromised node:** the harness already trusts node answers for its own judgements. No new privilege is given to node output. The DISARM, PRE and commit actions run on the node only after the node-side checks pass.
- **Attack-surface delta:**
  - no new port, node env or secret;
  - the `PB_*` seams are test-only and gated (§3.3);
  - `pre=` takes a fixed string from the harness source, never node or user input.
- **Privilege:**
  - The node-side restore runs as root (as today) and unmounts only mountpoints under two harness dirs, matched by prefix on the /proc/mounts entry.
  - A non-root node process cannot create a mount there, because mount needs root.
- **Failure mode:** fail-closed throughout. A refused guard, a failed disarm, an unknown mount or a patch that does not apply all stop, with names.
- **Secrets:** none touched. The dead-man IRK case is unchanged in exposure (§4.2).
