## 1. L175 — a tryboot GET counts only when the tag was handled (Pi 4)

**Mailbox answer.** `vcmailbox 0x00030064 4 4 0` prints the words `<size> <code> <tag> <len> <reqresp> <value> <end>`.

- The VideoCore property interface marks a handled tag by setting `reqresp` to `0x80000000 | response-length`, which
  is `0x80000004` here. Firmware that does not know the tag leaves `reqresp = 4`. `value` then stays the request's
  `0`.
- **Decision:** the check is the exact string `${5} = 0x80000004`, the form the harness already uses
  (`scripts/dv/slot-guard-254.sh:33`). It is not a bit test.

**One predicate, one place.** Add `bf_vc_ack <words…>` to `bootfacts.sh`:

- it returns 0 iff `$2 = 0x80000000`, `$5 = 0x80000004` and `$6` is non-empty;
- `bf_get` uses it;
- `batman-slot` sources `bootfacts.sh` at its arm and disarm sites, as `cmd_reboot` already does (`:1006`).
  `bootfacts.sh` is in `RAMFS_COPY_DATA` (`platform-ab.sh:42`), so stage 2 has it. That makes one copy, not three.
- `bf_vc_ack` uses only its positional parameters. It sets no global, because `bootfacts.sh` already uses bare `h` /
  `v` and `batman-slot` has its own global `v` (`:525,575,870`) (review v2 B m2).
- **Library missing** at the arm or disarm site (`bf_vc_ack` undefined after the source; review v2 A m1, B m1):
  - arm dies ("bootfacts.sh missing — cannot verify the arm");
  - disarm takes its layout's "unreadable" path (Pi 4: warn; Pi 3: die, as today).
  - `batman-slot` runs under `set -u`, so the check is `type bf_vc_ack`, never a bare call.
  - The offline tests point the lib path at a stub through `BATMAN_LIB` (test seam, defaulting to
    `/usr/lib/batman`).

**Pi 3 is unchanged.**

- Pi 3 is not supported (P-U14, owner 2026-10-23) and manet03 is retired. No Pi 3 word 5 has ever been captured
  (review v1 A-M3, B-M1: the earlier "Pi 3" evidence was 04, a Pi 4).
- So the new rule applies only when `layout = pi4`. Pi 3 keeps today's parse exactly.
- `bf_get`'s consumers already act only on Pi 4 cards:
  - `batman-slot reboot` (`:1009`) and `ota_s2_explicit_restart_if_not_armed` (`platform-ab.sh:307`) check `bf_pi4`
    first;
  - K90 `batman-reboot` acts only on a want-file that `cmd_reboot` writes on Pi 4.
- `bf_get` may therefore use the new predicate unconditionally. The Pi 3 restriction is needed only in batman-slot's
  arm and disarm.

**Behaviour.** "Unacknowledged" means code `0x80000000`, but word 5 ≠ `0x80000004`.

## 2. L111 — the boot Finish is retried, bounded

**Today.**

- `BootFinish` holds `n.mu`, waits for the radio (≤ 120 s; not for a forget) and runs `finish("boot")` once.
- On failure, `noteFinish` raises the shared backoff: 60 s, doubling, capped at 30 min.
- `.txn` stays, so:
  - `--save` without the token refuses;
  - `--on-join` yields;
  - `--check` reports stale, which blocks OTA.
- Only a verb or the next boot finishes it. A node that nobody talks to stays that way.
- The worst case is a committed **leave** whose boot forget failed: the node keeps the network key and stays on the
  old mesh. 254-wireless-txn §19.2 (`:561-566`) says a forget that gets rc 3 is recovered by retrying (review v2
  B-M1).
- ⚠️ The field trigger is a slow boot: netifd is still pending, so setkey returns rc 2 or rc 3. It has never been
  seen in a log. The device reproduction below is injected, and says so.

**Cause, typed.** `finish()` records why it failed in `n.lastFinishCause`, one value per return path (review v2 A-M2,
B m4). Only the classes marked "yes" are retried. Anything else, including an unknown cause, is not.

| Cause (return path in `finish()`) | Bound of one try | Retried |
|---|---|---|
| `resolve` failed (p5 / overlay unreadable) | seconds | yes |
| txn token rewrite / marker write failed (run dir, `.txn` write) | seconds | yes |
| `desired()` failed with a **transient** `CheckRestorable` error (exec failure, uci rc ∉ {0,1}; `wtxn.go:184-191`) | ≤ 60 s (`--check-only`) | yes |
| `desired()` failed for any other reason | — | no |
| setkey / forget **rc 2** (lock busy 90 s or settle 30 s, nothing changed) | ≤ 2 min | yes |
| setkey / forget **rc 3** (not verified on the air; for a forget, the radio still carries the key) | ≤ 3 min (lock 90 + settle 30 + read-back 60 s; forget 30 + 10 s) | yes — §19.2's recovery |
| setkey / forget **rc 124**, or any exec deadline | 300 s | no |
| save rc ∉ {0, 6, 124} (`--save --txn`) | ≤ 70 s (lock 10 s + write) | yes |
| save rc 124 | 300 s | no |
| hand-off (radio switched off by hand: rc 3 + `handOff()`) | — | not a failure (finished in uci, `wtxn.go:331`) |

**Change.** When the boot Finish fails with a retryable cause, one goroutine keeps retrying.

- **Schedule:** retries at 60, 120, 240, 480, 960, 1800, 1800 and 1800 s after the previous try ended. That is 8
  retries in ≈ 2 h 6 min. The boot's own try is try 0 and is not counted.
- A retry whose cause is not retryable ends the goroutine with the line "not retried: <cause>".
- **Gates before each try,** checked under `n.mu`:
  - `.txn` is gone (a verb finished it) → stop;
  - `n.otaBusy()` or `n.Sys.IsTrial()` → postpone 60 s without counting. Verbs have the same rule
    (`node.go:254,263`).
    - `otaBusy` reports busy when it cannot tell, so postponing has no bound: a broken flock file postpones for good.
    - That is harmless, because nothing runs. It is logged once per postponed stretch, not every 60 s (review v2
      A m3, B m6).
  - otherwise `finish("boot retry N")`.
- **Backoff stays separate.** A failed retry does NOT raise the shared verb backoff. A successful retry calls
  `noteFinish(nil)`, which resets it.
- **Ends:** on success, on `.txn` gone, on a non-retryable cause, or after 8 failed retries. The last case logs
  `CRIT boot finish: gave up after 8 retries — .txn kept; the next verb or boot finishes it`.

**Mutex hold.** A retried try holds `n.mu` for at most about 3 min plus about 70 s for the save (the retryable
classes above). The 300 s classes are never retried, and the radio wait (`waitRadioUp`, 120 s) is not repeated.

- Read-only verbs (status, info, health) never take `n.mu` (`readonly.go:4`).
- State-changing verbs wait. Commit-only verbs (`owner.add` / `owner.remove`) also queue behind a try, as they do
  behind today's boot Finish.

**Not done:** `satisfied()` also requiring netifd up (A2 N7).

- No path produces the orphan without a reload from outside the lock (§19.5).
- Each retry re-reads the radio. This stays one line on #254.

**Docs.** 254-wireless-txn.md §4.3 and §19.5 are updated in the same PR.

**Ownership.**

- `.txn` and the txn marker belong to the helper, unchanged. The retry goroutine is the helper, under `n.mu`.
- `finishFails` / `lastFinishFail` (the verb backoff) are written by `noteFinish`, from verbs, the boot try and
  successful retries.
- `lastFinishCause` is written by `finish()` only, under `n.mu`.
- The retry's own counter is local to the goroutine.

**Contracts.** Nothing new on the wire. Log lines (the harness unit in §7 parses them):

- `boot finish retry N: <reason> (cause <class>)` for a failure, or `txn … finished (boot retry N)` for a success
  (the existing line format);
- `boot finish: not retried (cause <class>)`;
- `boot finish retry postponed: <ota busy|trial>` (once per stretch);
- the CRIT line above.

**Lifecycle.**

| Path | Today | After | Test |
|---|---|---|---|
| Boot, Finish ok | `.txn` gone | same, no goroutine | existing |
| Boot, rc 2 (slow netifd) | `.txn` kept until a verb / boot | retry at +60 s → ok | unit (a); device §2 |

**Security** (per actor):

- **Remote attacker / BLE peer.** Cannot start, speed up or extend retries: there is no new input. Their verbs are
  gated as today.
- **Local unprivileged process.** No new socket, file or flag. It cannot fake `.txn` (root-only `/etc/batman-prov`)
  or `otaBusy` (a root-only run-dir flock).
- **Compromised provd (uid provd).** Same verbs as today. Retries add no new verb.
- **Our own mistakes.** The bound (8 retries, retryable causes only) caps radio reloads and p5 writes at 8 extra per
  boot. Retrying a forget's rc 3 closes a fail-open: a node that left keeping the key.
- **Member-role peer (review v3 A m1, B m1).** A member-role session can forward `network/update`, and the helper
  runs a pending Finish (`node.go:269-270`) before it checks the chain and signatures (`:300`). That already lets such

  verb, so the rate stays as today.
- **Negative test (unit (g)).** During the retry window, `network/update` calls with an invalid chain from a
  member-role session trigger at most one Finish per verb backoff, the same count as on main.

## 3. L96 — a dry run writes nothing real

`DRY` is a test seam: it is never set in production. A dry run must not change what a real run in the same boot
sees, or what the operator or the app is shown.

**Change.**

- With `DRY=1`, every autocommit run-dir marker lives in `$RUNDIR/autocommit.dry.d/`. The markers: `run`,
  `decided`, `committed`, `wd`, `why`, `deadline`, `start`, `hold-consumed`, `hold-discarded`, `canary-ok`,
  `ble-warned`, `warn-*`, and `ctl` (today `autocommit.ctl.dry`).
- **The directory's lifecycle** (review v2 A-M1, B-M2). One dry run at a time, each from an empty directory:
  - at start, a dry run takes `$RUNDIR/autocommit.dry.lock` (mkdir) and records its pid there. A lock whose pid is
    alive → the dry run exits 1 ("another dry run is running"). A lock whose pid is gone → taken over.
  - Then `autocommit.dry.d` is removed and re-made 0700. `rm -rf` removes a symlink as a link and never follows it.
    The new directory gets `CTL`'s root-owned, not-a-link check (`:55-59`).
  - If it cannot be made, the dry run exits 1. It never falls back to the real names.
  - The dry watchdog subshell is the dry run's own child and shares its directory.
  - At the end, the main dry run waits for its watchdog subshell (`wait $WDPID`, already the case in DRY), then
    removes the lock. The directory is left for inspection, and the next dry run empties it.
- `otalog` / `otalog_k` are no-ops in DRY. The p6 OTA trace is the real record that `halow-status` and the app's
  "last OTA" read.
- `aclog` already goes to the run-dir dry log (`:44`).
- `rm -f $ST/ota-armed.mesh` in the watchdog (`:238`) moves after the DRY exit (`:241`).
- Writes to p6 `$ST` in DRY, audited with a `grep` of `batman-autocommit`:
  - `:99`, `:292` and `:298` are already guarded.
  - `:196` and `:245` come after a DRY exit.
  - `:238` is fixed here.
  - `:583` is on the commit path, which DRY never reaches: it exits at `:572`, before the claim and the commit
    (verified, review v3 A m5 / B m3).
- `held()` in DRY READS the real `autocommit.hold-consumed` as well as its own, and writes only its own. The harness
  (`scripts/node/prov-misc-254.sh:83`) plants the real one so that the DRY watchdog stands down.
- **Accepted** (review v2 A m6). These are not state a real run reads:
  - a dry run still writes syslog / kmsg lines, prefixed as today;
  - its pre-commit canary still imports and prunes the `batman-canary:<tag>` image on p6. That is the same
    idempotent image a real run builds.
- `scripts/rundir-paths.txt` gains `autocommit.dry.d` and `autocommit.dry.lock` (the run-dir lint).

**Ownership.**

- Real markers: the real autocommit only.
- `autocommit.dry.d/` and `autocommit.dry.lock`: the dry run that holds the lock.
- The real `hold-consumed`: written by the real autocommit and by the harness on the bench, and read by both runs.

**Lifecycle.**

- **Production.** The marker variables are renamed through one prefix, so every real path changes in its text. The
  regression evidence is the non-dry autocommit units on the bench image (review v2 B m8):
  - `fw-boot-254`;
  - the OTA units (`prov-ota-*`);
  - `prov-ac-flap-254` and `prov-ac-noarm-254` (real trials).
- A dry run on a real trial boot no longer leaves a real `decided` / `hold-consumed`. Today those can stop the real
  watchdog from reverting.
- Two dry runs in a row in one boot: each starts empty, and both reach their decision.
- A dry run killed midway: the next one takes the stale lock over and empties the directory.

**Security.**

- `autocommit.dry.d` and the lock are in the root-only run dir, with the same planted-dir handling as `CTL`.
- A local unprivileged process cannot reach the run dir (#280).

**Tests.**

- Offline (`scripts/node/` style, stubbed run dir and p6): DRY + FORCE_TRIAL + TIMEOUT=1, then:
  - no file outside `autocommit.dry.d` / the lock is created or removed (a full before / after listing of the run
    dir and `$ST`);
  - `ota-armed.mesh` is kept;
  - no otalog line;
  - two dry runs in a row both reach the watchdog's REVERT decision;
  - a second dry run while one runs exits 1;
  - a planted symlink `autocommit.dry.d`: the link is removed and its target is untouched.
- Negative control on main: the real `decided` is created, `ota-armed.mesh` is removed, an otalog line is written,
  and the second run's watchdog exits silently (`wd` exists).

## 12. Addendum (implementation finding, 2026-11-21): the deadline's SIGKILL never reaches a TERM-ignoring member

**Found by the A4 m3 test** (`provstore/exec_group_test.go` `TestExecKillsTheGroupThatTrapsTERM`, new). The command
`sh -c "sh -c 'trap \"\" TERM; …' & wait"` runs under a 1 s deadline. The grandchild ignores TERM, and it was still
alive 10 s after `Exec` returned rc 124. That is real Linux process behaviour, not a stub.

**Cause.** `Exec` (`provstore/exec.go:38-52`) and `ExecSplit` (`:104-117`) send SIGTERM to the group, then wait up to
10 s for `Wait`. The direct child dies on TERM, so `Wait` returns: at the latest after `WaitDelay` (5 s), when the
grandchild still holds the pipe. Because `Wait` returned, the SIGKILL branch never runs, and every group member that
ignores TERM survives.

That breaks `Exec`'s own contract ("at the deadline the whole group gets SIGTERM, 10 s later SIGKILL", `:18-20`) and
review 3 A m5 ("a grandchild — e.g. the `wifi reload` of a halow-setkey — must not run on after the helper gave up").

- **`Exec` runs:** `halow-setkey`, `batman-config-save` and `uci` from the helper.
- **`ExecSplit` runs:** `batman-slot` (OTA writes) and is also used on cancel.
- **Field likelihood:** ⚠️ low. Those children do not trap TERM, as far as known (not verified per child). The
  failure mode is a write that continues after the helper reported a timeout and moved on (for example to a Finish
  or a retry).

**Change (v2 of this addendum, after review v4: A-M1, B m1–m5).** In both functions, the deadline / cancel path is:

1. Send SIGTERM to the group.
2. **Poll the group** every 100 ms with `kill(-pgid, 0)`. Stop when the group is empty (ESRCH), or when 10 s have
   passed since the TERM.
   - Every member, not only the leader, keeps the full TERM grace.
   - Example (review v4 A-M1): under `settings.set`, `halow-setkey --rollback` is the leader and dies on TERM at
     once. The `batman-config-save` it started is a member, and its TERM trap does `sync; umount` of p5
     (`batman-config-save:131-140`). An immediate KILL would leave p5 mounted rw.
3. If the group is still not empty after 10 s, send SIGKILL to the group. It goes only to a group that `kill(…, 0)`
   just found non-empty. While a member is alive, the pgid cannot be given to a new group, so the KILL cannot hit
   another process (review v4 A m1, B m2). The window left is the microseconds between the check and the kill,
   which needs a member to exit and a pid wrap (`pid_max` 32768 on 04 and 02, read 2026-11-21; cyclic allocation)
   inside it. Accepted.
4. Wait for `Wait` as today: up to 10 s after the KILL, or at once if it already returned.
5. The text returned with `RCTimeout` / `RCCanceled` gains one line when step 3 ran: "group member(s) outlived TERM:
   killed". If a member is still there 10 s after the KILL (uninterruptible sleep), the line is "a group member could
   not be killed". That case used to be silent: a leader that died on TERM hid it (review v4 A m2, B m4).
   - The rc is unchanged.
   - The abandoned case (the leader itself unkillable) is unchanged.

**Timing.** In the normal case (every member dies on TERM) `Exec` returns as soon as the group is empty, so as fast
as today. `execsplit_test.go:36` (a cancel returns in ≤ 5 s) keeps holding. Only a group with a TERM-ignoring member
takes the full 10 s, as the contract always said (review v4 B m1).

**Evidence about the children** (review v4 A m4, B m3; grep of the product tree):

- No child ignores TERM. Only PIPE is ignored (`halow-setkey:236`), and HUP (`batman-slot:953`).
- The TERM handlers that clean up are in `batman-config-save` (`:131-140`) and `batman-slot` (`:185-186`). They run
  both as leaders and as members (config-save under halow-setkey), and step 2 gives them the grace either way.
- Assumption for future children: a TERM handler finishes within 10 s.

**Interactions.**

- **§2.** rc 124 stays not retried, and the rc and text are unchanged (plus the line above). The helper mutex is held
  at most ≈ 10 s longer, and only on the deadline path. After rc 124 no member keeps writing, and halow-setkey's lock
  fd is released, so the next try does not get a spurious rc 2. An unkillable member that still holds the lock does
  make the next try rc 2, which is retried within the bound.
- **OTA `ExecSplit` cancel.** batman-slot (the leader) runs its own TERM / EXIT cleanup (`:185-186`), and the poll
  waits for it. Its mounts also die with its private namespace. Children it started with `setsid` (`:954`, `:1058`)
  left the group and are not touched, as today.
- **Docs.** The `Exec` / `ExecSplit` comments (`exec.go:18-20`, `:85`) and 254-wireless-txn §15.2 (`:240-241`) state
  this rule.

**Ownership / contracts.** No new resource. `Exec`'s documented contract becomes true.

**Lifecycle.** Only the deadline / cancel path changes. The normal exit path, crash, power loss, upgrade and
downgrade are untouched: an older helper keeps today's behaviour. Pi 3: same code, not run (unsupported).

**Security.** No new input. A command's descendants can no longer outlive the helper's decision.

**Tests.**

- **(1)** `TestExecKillsTheGroupThatTrapsTERM`: a TERM-ignoring grandchild is gone after `Exec` returns, and the text
  carries "outlived TERM". It fails on main.
- **(2)** `TestExecGivesMembersTheTERMGrace`: a member with output to /dev/null traps TERM, sleeps 2 s, then writes a
  marker. The marker exists when `Exec` returns. It fails on an "immediate KILL" mutant (review v4 A-M1).
- **(3)** `TestExecReturnsPromptlyWhenTheGroupDies`: a group whose members all die on TERM returns within 2 s of the
  deadline (review v4 B m1).
- **(4)** ExecSplit twins of (1)–(3), for both timeout (rc 124) and cancel (rc 125).
- Existing tests keep passing: `TestExecKillsTheGroup`, `TestExecDeadline` (the daemonised grandchild leaves the
  group), and the ExecSplit tests.

## 13. Review v5 (A and B: APPROVE-WITH-CHANGES, MINORs only) — binding for §12's implementation

- **B m1 (option b) + A m1 / B m2 + B m3.** The poll in §12 step 2 scans `/proc` for the group's members instead of
  using `kill(-pgid, 0)`. A member is a pid whose `stat` pgrp equals the group id; a zombie (state Z) does not count.
  - At 10 s after the TERM, SIGKILL every member that has no TERM handler (TERM not in `/proc/<pid>/status`
    `SigCgt`). That covers a member that ignores TERM (`SigIgn`) and one blocked in uninterruptible sleep with the
    default action pending, so the D-state / abandoned timing stays as today (10 + 10 s).
  - Members with a TERM handler (config-save's `sync; umount` of p5 on a slow card) get up to 30 s. After that,
    SIGKILL whatever is left. The helper mutex is held up to 20 s longer, only in that case.
  - Kills go to the individual pids just seen, never to `-pgid`, so a reused group id can never be hit. The
    remaining pid-reuse window is the ≤ 100 ms between a scan and its kill, which needs a 32768-pid wrap inside it.
- **A m3 / B m4.** The extra text goes BEFORE the "timed out" / "canceled" line, because callers log the last line:
  "group member(s) outlived TERM: killed (<n>)". Test (1) asserts that the last line still says "timed out".
- **A m4.** When the group emptied without a KILL, `Wait` is still bounded by the 5 s `WaitDelay`.
- **A m2.** The "as far as known" sentence in the Cause section is replaced by the grep evidence: config-save and
  batman-slot trap TERM, and nothing ignores it.
- **A m5 / B m5.** §1 evidence, captured 2026-11-21 on 04 and 02:
