# 不友善環境下的存活策略:HaLow + LoRa 雙網(#181)

狀態:**DRAFT v2**(2026-09-28;v1 2026-09-27)。依據:#181 的 W10 co-site 量測(2026-09-26~27,manet04+02,含整晚量測與 1 分鐘 idle/loaded 區塊分析)、同分支的 `docs/design/181-lora-halow-tak-integration.md`(REV2,本 PR #220)、`docs/field-resilience.md`、`docs/led-indicator.md`。修訂內容見文末「修訂紀錄」。
相關單:#181、#220、#219(統一 app)、#53/#128(狀態燈)、#122(電池)、#15(跳頻)、#92(TW 域)、#174(時間)。

> 標記慣例:**【事實】** = 本專案實測或原始碼/規範可查證;**【推論】** = 由事實推出、尚未實測;**【決策】** = 本文提出、待 review 拍板。

---

## 0. 一句話

**使用者只看到「現在能做什麼」和「這則訊息到了沒」,永遠不必知道是哪張網在送。**
系統在背後把 HaLow 當主網、LoRa 當備援,而且**一次只讓一種電台主動發射**;切換要慢、要穩、要誠實,寧可晚一點切,也不要讓畫面來回跳。

## 2. 使用者心智模型(UX 原則,最高優先)

使用者不懷疑系統的前提是:**系統說的話永遠是真的,而且不會一直改口。** 由此推出六條規則【決策】:

1. **講「能做什麼」,不講「用哪張網」**。操作者介面只有三個狀態(類比手機的 5G → 只能傳簡訊 → 無服務,這是大家已經懂的模型):

   | 狀態 | 對使用者的一句話 | 背後 |
   |---|---|---|
   | 🟢 **完整** | 語音、照片、地圖都可用 | HaLow 通 |
   | 🟡 **精簡** | 只能傳文字和位置,可能要等 1 分鐘 | HaLow 不通,LoRa 通 |
   | 🔴 **離線** | 訊息先存著,恢復後自動送出 | 兩者都不通 |

   HaLow、LoRa、batman 這些字**只出現在管理員視圖**(`docs/personas-and-roles.md` 的 ② 網管 / ④ 開發者),不出現在操作者視圖。

2. **每則訊息有自己的誠實狀態**,和網路狀態分開顯示:`排隊中` → `已送出` → `已送達`(收到端對端確認才打勾)。經 LoRa 送出的,小字標「經備援送出」。位置廣播本來就沒有確認,就寫「已廣播」,**絕不假裝已送達**。

3. **不讓按鈕騙人**:精簡狀態下,語音(PTT)/照片按鈕變灰並寫原因(「目前只能傳文字」),而不是讓人按了再失敗。按下照片時提供「先存著,恢復後送出」或「改傳一段文字描述」。

4. **狀態不閃爍**:狀態切換要經過去抖動(§4.2);若短時間內反覆切換,就**停在一個誠實的穩定狀態**(🟡 精簡,附註「連線不穩,已改用可靠方式」),而不是在 🟢/🟡 之間跳。**來回跳比一直黃燈更傷信任**。

5. **降級時說一次原因和該做什麼**,之後不重複騷擾:
   - 超出範圍 → 「移到高處或靠近隊友」
   - 疑似強干擾(噪聲底突然升高)→ 「此區域訊號受阻,移動位置」
   - 電量低 → 「已進入省電,只保留文字與位置」
   - **電磁靜默中**(§3.4)→ 「靜默中:只在求救時發送」

6. **備援本身壞了要先講**(像備胎警示燈):在 🟢 完整狀態時,以小圖示顯示「備援就緒 / 備援不可用」。**判斷依據用本機 serial API 健康檢查(RAK 有回應、設定讀回正確),不靠週期性的 LoRa 發射**(§3.4 EMCON)。不要等到真的需要時才發現 LoRa 早就卡死(F11)。

## 3. 系統模式(每台節點本地的狀態機)

### 3.1 四個模式

| 模式 | 進入條件 | HaLow | LoRa | 對應 UX |
|---|---|---|---|---|
| **H — 主網** | 預設 | 正常收發 | **只收不發**(例外見下)。收到的備援訊息經 HaLow 轉給目的地 / OTS | 🟢 |
| **H+ — 主網不穩** | 反覆切換被阻尼(§4.2)或逐則升級頻繁(§4.3) | 正常收發 | 關鍵訊息(SOS、文字)**雙發**,受 H 模式預算限制 | 🟡「連線不穩」 |
| **L — 備援** | 所有 wlh0 鄰居 batman last-seen > 60 s(§4.1) | **保持入網、維持正常功率、不送應用資料**(只剩 beacon/ELP/OGM 等控制流量),用來聽鄰居是否回來 | 依 EMCON 政策(§3.4)收發 PLI / 文字 / SOS,受 airtime 預算限制 | 🟡 精簡 |
| **X — 離線** | L 模式下 LoRa 也超過 T 分鐘沒聽到任何受信任節點 | 同 L | 同 L,但 PLI 拉長間隔省電 | 🔴 |

**H 模式下 LoRa 只收不發的例外**【決策】(都算入預算):
- **LoRa 出口**:目的地是某台 L 模式節點,且本節點被選為它的出口(§5.2)時,代它發一次(含對 L 節點 SOS 的確認)。
- ~~點名~~:v1 的「每約 6 小時發一個點名證明 LoRa 活著」**改為預設關閉**:週期性發射是可被測向的信標(§3.4)。「備援就緒」改用本機 serial 健康檢查(規則 6);只在 EMCON=off 且部署需要 RF 路徑證明時才開。

### 3.2 為什麼不在 H 模式同時開 LoRa 發射

F1:LoRa 發射會把自己的 HaLow 打到剩一半或更少;F2/F14:在 920–925 MHz 內靠分頻擋不住。所以「兩張網同時全開 = 兩張網一起變差」【推論,由 F1+F2 直接推出】。**一次只讓一種發射**是量測逼出來的結論,不是偏好。

### 3.3 為什麼 L 模式不降 HaLow 功率(v1 → v2 改動)

v1 在 L 模式把 HaLow 降功率(依 F4)以減少對 LoRa 收訊的影響。審查指出兩個會讓整隊卡死的問題【推論】:
- **連鎖**:A 進 L 並降功率後,原本只靠 A 連線的葉節點 B 聽不到 A → B 的鄰居 last-seen 也超過 60 s → B 也進 L,可能一路擴散。
- **互鎖**:大家都在 L、都降了功率,**誰都聽不到誰的 ELP**,回切條件(聽到鄰居)永遠不成立。
- 另外 F4 顯示 ≥ 20 dBm 的設定根本沒效果,這個控制手段本身不可靠。

因此【決策】:**L 模式 HaLow 維持正常功率,只停止送應用資料**。L 模式下 HaLow 的控制流量(beacon ~1/s、ELP 500 ms、OGM 1 s)仍會降低自己的 LoRa 收訊(F3),這是為了「隨時能被鄰居聽見、也聽得見鄰居回來」所付的代價。若 V4 證明在特定部署下不會連鎖 / 互鎖,才考慮把降功率當成可選項,而且回切探測窗口必須用全功率。

### 3.4 電磁靜默(EMCON)政策【決策,預設值待拍板】

對手只要壓制 HaLow,節點就會進 L 模式並開始在 LoRa 上發 PLI —— 這等於**告訴對手「干擾有效」**,也給了他**測向目標**。所以 L 模式的發射行為必須可選:

| EMCON 等級 | L 模式行為 | 適用 |
|---|---|---|
| **AUTO** | 自動發 PLI(§5.1 預算內)+ 文字 + SOS | 民用 / 救災:讓指揮所看得到人比隱蔽重要 |
| **SOS_ONLY** | 平常不發;只在使用者按求救時發 SOS | 戰術預設候選 |
| **SILENT** | 完全不發(只收);求救需操作者明確解除靜默 | 高威脅環境 |

- 等級由部署設定 + 管理員視圖切換;操作者看到對應的一句話(規則 5)。
- PLI 間隔用**指數分布**隨機化(v1 的均勻 ±30% 仍有週期特徵),平均值依預算。
- H 模式的「出口」發射同樣受 EMCON 限制(SILENT 時不代發)。

## 4. 切換邏輯:慢、穩、誠實

### 4.1 觸發器(依 F6/F7/F8/F9)

| 方向 | 條件 | 理由 |
|---|---|---|
| H → L | **所有 wlh0 上的**鄰居 batman last-seen > 60 s(只計 HaLow 介面,排除 eth 等其他 hardif) | F6:last-seen 每秒 +1、正常 < 1 s,訊號乾淨;F7:半殘時最多 5–8 s,60 s 約 7.5× 餘裕;F8:二元條件不受環境雜訊絕對值影響 |
| L → H | 任一 wlh0 鄰居 last-seen < 2 s,**且在「本機 LoRa 靜默」的時段內持續 ≥ 20 s**(扣除本機 LoRa 發射時段,只看靜默期樣本) | **與進入條件對稱、只看本地**(v2 改動,見下) |

- **開機 / 重設寬限期**:開機後、或 HaLow 設定被改動(含 F10 還原)後 **3 分鐘**內不評估 H → L(F9:primary 改變時重新入網要 40–70 s)。
- **gateway / OTS 可達性只寫進狀態,不當回切條件**(v2 改動):v1 要求「ping 到 gateway/OTS 才回 H」,審查指出若鄰居已回來但 OTS 剛好掛了,節點會**卡在 L 模式、在 H 鄰居旁邊持續發 LoRa**(正好打到它們的 HaLow,F1)。現在 OTS 不可達只影響「逐則升級」(§4.3)和 UX 上的指揮所圖示。
- **L 模式看門狗**:在 L 模式超過 30 min 且期間曾聽到鄰居但未滿足回切條件 → 記錄並上報(管理員視圖),不自動改設定。

**不用的訊號**:802.11s peer 消失(被干擾時不逾時,F6)、batman 移除鄰居(200 s 太慢)、LoRa/HaLow 的絕對掉包率(F8)。

**回切偵測被 LoRa 遮蔽的問題**:L 模式下自己的 LoRa 發射會蓋掉自己的 HaLow 接收(F1)。緩解【決策】:
- lora-sched 匯出本機 LoRa 每次發射的起訖時間,回切判斷只用非發射時段的樣本。
- 每次 LoRa 發射後,本節點強制 LoRa **靜默至少 5 s**;另每 120 s 保證至少 10 s 連續靜默。
- 別台 L 模式節點的 LoRa 也會遮蔽,但每台都受 airtime 預算限制(§5.1),遮蔽比例有上限【推論,待測】。

**觸發器的已知盲點**(v2 補充):last-seen 只反映「**我聽得到對方**」。若本機 HaLow **發不出去但還收得到**(例如本機 PA 故障、或只有我的發射被壓制),我會一直留在 H 模式,而鄰居那邊會看到我消失。緩解:逐則升級(§4.3)對「我送的訊息沒被確認」仍會啟動;另可從 batman 的 originator TQ(鄰居對我的回報)輔助判斷【推論,待 V13】。

### 4.2 防抖動:遲滯 + 翻轉阻尼

參考 BGP 的路由翻轉阻尼(route flap damping,IETF RFC 2439,美國 IETF 標準):一條路線反覆上下時,就先不要相信它恢復了。

- **非對稱時間**:下切 60 s(夠慢,避免短暫遮擋就切);上切要持續 20 s 的穩定證據 + 穩定期(夠確定才回來)。
- **翻轉計分**:每次 H→L→H 算一次翻轉;10 分鐘內翻轉 ≥ 2 次 → 穩定期倍增(30 s → 2 min → 5 min 上限),並把 UX 固定在 🟡「連線不穩」(模式 H+),直到連續 10 分鐘沒翻轉才回 🟢。
- **UX 去抖動**:操作者看到的狀態,任兩次變化間隔至少 30 s;模式機內部可以更快,顯示層不跟著跳。

### 4.3 逐則訊息升級(處理半殘與網路分割)

節點層級的觸發器看不到兩種情況:HaLow 半殘(F7)、HaLow 被切成兩塊(本地鄰居都在,但到不了指揮所)。改用**逐則訊息**判斷【決策】:

- 文字 / SOS 走 HaLow 送出後,若 **T 秒內沒收到端對端確認**(SOS 10 s、文字 30 s),自動再經 LoRa 送一次;UI 顯示「已改走備援送出」。**受 H 模式預算限制(§5.1),SOS 除外**。
- 目的地在 batman 路由表(originator table)已經看不到 → 直接走 LoRa,不必先等 HaLow 逾時。
- 「目的地不可達」要持續 ≥ 20 s 才算,**單次逾時不算**,避免半殘時每則訊息都往 LoRa 擠(這正是 F1 會自我強化打垮 HaLow 的路徑)。
- 兩條路都到的重複訊息,由收端依 **(來源節點, 訊息 ID)** 去重(Meshtastic 本身有 packet id 去重【事實】;HaLow 那條要我們自己帶 ID)。

**孤島情境**(整個小隊一起離開 gateway 範圍,彼此仍是 HaLow 鄰居,沒有人會進 L):位置 / 文字送往指揮所時,目的地不在 originator table → 每台各自逐則走 LoRa(受 H 預算)。這讓孤島不會「永久消失」,但 N 台各發一份較浪費。【決策,待拍板】v2 先用逐則處理;**孤島代理**(用 HaLow 選一台,把全島 PLI 打包成一則從 LoRa 送)列為 v3 選項,需要時再做。

這讓「系統送不到」變成少數情況,而且每次升級使用者都看得到原因,不會覺得訊息神秘消失。

## 5. LoRa 用量控制(不讓備援打爛主網)

### 5.1 硬性 airtime 預算【決策,數字待 P5 延伸實測校正】

TW 區域法規佔空上限是 100%(F12),Meshtastic 的禮貌門檻 25%(F13)對我們太寬(F1:28% 佔空已讓 HaLow 砍半)。所以:

| 模式 | 每節點 LoRa 發射預算(滾動 10 分鐘) | 約等於 |
|---|---|---|
| H / H+ | ≤ 1% | 約 6 s,例如 10 個短包 |
| L | ≤ 5% | 約 30 s,例如 50 個 PLI 大小的包(約 0.6 s/包) |
| SOS | 不受預算限制,但每則最多重送 3 次 | — |

- 預算用 token bucket 實作,由 lora-sched 在**送出前**扣;預算要涵蓋**所有**經本機 RAK 發出的封包(包含出口代發)。
- 預算用盡時:位置只保留**最新一筆**(舊的丟掉,新位置覆蓋);文字排隊;UI 照實顯示「排隊中」。
- 附近有多台 L 節點時,依「最近 10 分鐘聽到的 L 節點數」縮放每台的 PLI 頻率,避免全隊同時湧入 LoRa【推論】。

### 5.2 洪泛控制(Meshtastic 洪泛會把用量放大 N 倍)

- **所有 RAK 在 provisioning 時設為 `CLIENT_MUTE`**(或等效的「不轉發他人封包」設定),**永遠不在執行期改**(F15:改角色會延遲重開 RAK)。理由(F16):`CLIENT` 角色下韌體會自行轉發,Pi 端管不到 → H 模式節點會在 LoRa 上重播 L 節點的封包,違反「只收不發」,也繞過預算。【待 V10 上機確認 CLIENT_MUTE 只抑制轉發、不影響本機主動發送與接收】
- **跳數由送端逐則決定**:Meshtastic 的 `MeshPacket.hop_limit` 可逐包設定【事實,Meshtastic protobuf `mesh.proto`】。因為沒有節點會轉發,實務上 LoRa 只走**單跳**;多跳改由 HaLow 骨幹承擔。
- **HaLow 取代 LoRa 轉發**:H 模式節點聽到 LoRa 包,**經 HaLow 轉**,不在 LoRa 上重播。只有「到得了 HaLow 的節點」都在同一張 HaLow 網上時,這相當於用 HaLow 當 LoRa 的骨幹【推論】。
- **出口選舉**:H 模式節點把「我最近在 LoRa 上聽到哪些節點、SNR 多少」經 HaLow 分享(沿用現有 alfred 健康資料通道);要送給 L 模式節點 X 時,由聽到 X 的 SNR 最好的那一台當唯一出口,避免 N 台一起發。
- **多台 L 節點之間**:只能直接單跳互通(沒有人轉發)。若部署需要 L 節點之間多跳,要另設少數「中繼」節點(角色不同),屬 v3 決策。
- Meshtastic 韌體設定在佈建時一次定好:自動位置廣播 / 遙測 / NodeInfo 關閉或拉到最長(位置由 Pi 端依模式與預算決定何時送)。驗收用「H 模式 24 小時內非預期 LoRa 封包數 = 0」(V1)。

### 5.3 模式切換不碰會重開 RAK 的設定

依 Meshtastic 韌體原始碼(`AdminModule.cpp`,master 分支)【事實】:LoRa 設定裡只有 region、preset、頻寬、SF、CR、**tx_power**、頻率等無線電參數變動才需要重開機;`tx_enabled` 切換不需要重開機,但會寫一次 flash。本機韌體是 2.7.15 / 2.6.11,**需上機確認行為相同**(V6;F15 顯示兩版行為不完全一致)。

因此【決策】:
- 模式切換**只用 Pi 端送出策略**(送不送、送什麼、hop 多少)來控制 LoRa 發射,平常不動 RAK 設定;韌體轉發已由 §5.2 的 CLIENT_MUTE 關閉。
- 若需要硬性保險(防 Meshtastic 自己的自動封包),才用 `tx_enabled`;翻轉阻尼(§4.2)保證這一天只會寫幾次 flash。
- **LoRa 的 preset / 頻率 / 功率永遠不做執行期自適應**:改了就跟其他節點說不同語言,等於在最需要備援時把備援網切碎。LoRa 頻率由佈建決定,建議 923.0 MHz(F14)。
- Pi 端控制 RAK 的程序:停止時先送 SIGINT、再 TERM,**永不 SIGKILL**(F11);斷線自動重連;以 USB 序號辨識裝置。

### 5.4 信任(過渡期)

- 只把**白名單公鑰**簽章的 LoRa 封包轉進 HaLow / OTS;白名單正式機制屬 W13(尚未完成)。
- **過渡期**:OTS 上把經 LoRa 來的訊息標為「未驗證來源」;公鑰只用 provisioning 時預先登錄的,不從 LoRa 上自動學習。
- alfred 名單資料目前沒有認證 → 名單內容只當提示,不當信任依據;長期由 provisioning CA 簽章。
- 偽造 / 重放的 SOS 可能觸發 H 節點的出口確認(暴露位置、消耗預算)→ 確認要防重放(訊息 ID + 時間窗)並限速。

## 6. 各種不友善情境的應對

| 情境 | 系統行為 | 使用者看到 | 依據 |
|---|---|---|---|
| **走出 HaLow 範圍** | 60 s 後進 L;依 EMCON 送位置 / 文字 | 🟡 精簡 +「移到高處或靠近隊友」 | F6 |
| **HaLow 半殘**(掉包、延遲) | 不切模式;逐則升級(§4.3,受預算) | 🟢,個別訊息顯示「已改走備援送出」 | F7 |
| **HaLow 被切成兩塊 / 孤島** | 本地通訊照常;到不了的目的地逐則走 LoRa | 🟢;送往遠方的訊息顯示「經備援送出」 | §4.3 |
| **窄頻干擾打在 HaLow 頻道上** | HaLow 死 → L;LoRa 有機會活(LoRa 在 SNR 約 −17.5 dB 仍可解調,HaLow MCS7 要 +20 dB 以上)| 🟡 +「此區域訊號受阻」 | 【推論】 |
| **全頻段干擾(920–925 全蓋)** | 兩張都死 → X;全部存起來;不自動重開機、不亂改頻 | 🔴「訊息已保存,恢復後自動送出」 | 兩者同頻段【事實】,LoRa 只提供波形多樣性不是頻段多樣性 |
| **對手壓制 HaLow 以誘使我們發 LoRa** | 依 EMCON 等級:SOS_ONLY / SILENT 下不自動發位置 | 🟡 +「靜默中:只在求救時發送」 | §3.4 |
| **環境雜訊時好時壞**(如清晨) | 觸發器是二元的,不受影響;翻轉阻尼吸收 | 至多一次 🟡「連線不穩」,不閃爍 | F8、§4.2 |
| **指揮所 / OTS 掛了** | HaLow 內點對點照常;**不因此進 L**;LoRa 仍可走 Tier 0(手機↔手機) | 🟢(隊友間);地圖上指揮所圖示轉灰 | §4.1、REV2 §1 三層退化 |
| **RAK USB 卡死 / 備援電台壞** | Pi 端偵測 serial API 無回應 → (有 GPIO→RST 線路時)自動重置;否則記錄並上報 | 🟢 旁的「備援不可用」小圖示;管理員視圖寫原因 | F11 |
| **電量低**(#122) | 進「省電求生」:HaLow 關、只剩 LoRa,PLI 間隔拉長 | 🟡 +「電量低,只保留文字與位置」 | 【推論】HaLow 功耗高於 LoRa 待命 |
| **Tier-0 手機(Meshtastic app)在旁邊發 LoRa** | 不受我們控制,可能打到附近節點的 HaLow(F1 的鄰機版,未測)| — | 部署文件建議手機端設定;V11 |

## 7. 刻意**不**做的事

| 不做 | 原因 |
|---|---|
| 自動改 HaLow 頻道 / 頻寬(例如自動縮成 1 MHz,F5) | 必須全網同時換,否則把 HaLow 網切碎;這是 #15 跳頻的題目。未來若做,要 ① 經 LoRa 送**簽章**過的換頻指令(#13)② 保留 F10 那種「時限內沒回來就自動還原」的保底 |
| L 模式降 HaLow 功率(v1 有,v2 移除) | 連鎖 / 互鎖風險(§3.3) |
| 動態改 LoRa preset / SF 對抗干擾 | 會讓備援網分裂(§5.3) |
| 在 H 模式同時全開 LoRa | F1/F2 |
| H 模式週期性 LoRa 點名(v1 有,v2 預設關閉) | 週期發射 = 測向信標(§3.4) |
| 讓操作者自己選「用 HaLow 還是 LoRa」 | 把系統的難題丟給使用者 = 困惑的來源;管理員視圖可以強制,操作者不行 |
| 自動重開機救網路 | 沿用 `joinwatch` 原則:人正在反覆開關機時,自己重開只會毀證據(`docs/field-resilience.md` 決策 4) |
