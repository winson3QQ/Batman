# 不友善環境下的存活策略:HaLow + LoRa 雙網(#181)

狀態:**DRAFT v1**(2026-09-27)。依據:#181 的 W10 co-site 量測(2026-09-26~27,manet04+02)、`docs/design/181-lora-halow-tak-integration.md`(REV2,分支 `design/lora-halow-tak-integration` / PR #220)、`docs/field-resilience.md`、`docs/led-indicator.md`。

## 0. 一句話

**使用者只看到「現在能做什麼」和「這則訊息到了沒」,永遠不必知道是哪張網在送。**
系統在背後把 HaLow 當主網、LoRa 當備援,而且**一次只讓一種電台主動發射**;切換要慢、要穩、要誠實,寧可晚一點切,也不要讓畫面來回跳。

## 2. 使用者心智模型(UX 原則,最高優先)

使用者不懷疑系統的前提是:**系統說的話永遠是真的,而且不會一直改口。** 由此推出六條規則【決策】:

1. **講「能做什麼」,不講「用哪張網」**。操作者介面只有三個狀態(類比手機的 5G → 只能傳簡訊 → 無服務,這是大家已經懂的模型):

   | 狀態 | 對使用者的一句話 | 背後 |
   |---|---|---|
   | 🟢 **完整** | 語音、照片、地圖都可用 | HaLow 通 |
   | 🟡 **精簡** | 只能傳文字和位置,可能要等 1 分鐘 | HaLow 不通,LoRa 通 |
   | 🔴 **離線** | 訊息先存著,恢復後自動送出 | 兩者都不通 |

   HaLow、LoRa、batman 這些字**只出現在管理員視圖**(`docs/personas-and-roles.md` 的 ② 網管 / ④ 開發者),不出現在操作者視圖。

2. **每則訊息有自己的誠實狀態**,和網路狀態分開顯示:`排隊中` → `已送出` → `已送達`(收到端對端確認才打勾)。經 LoRa 送出的,小字標「經備援送出」。位置廣播本來就沒有確認,就寫「已廣播」,**絕不假裝已送達**。

3. **不讓按鈕騙人**:精簡狀態下,語音(PTT)/照片按鈕變灰並寫原因(「目前只能傳文字」),而不是讓人按了再失敗。按下照片時提供「先存著,恢復後送出」或「改傳一段文字描述」。

4. **狀態不閃爍**:狀態切換要經過去抖動(§4.2);若短時間內反覆切換,就**停在一個誠實的穩定狀態**(🟡 精簡,附註「連線不穩,已改用可靠方式」),而不是在 🟢/🟡 之間跳。**來回跳比一直黃燈更傷信任**。

5. **降級時說一次原因和該做什麼**,之後不重複騷擾:
   - 超出範圍 → 「移到高處或靠近隊友」
   - 疑似強干擾(噪聲底突然升高)→ 「此區域訊號受阻,移動位置」
   - 電量低 → 「已進入省電,只保留文字與位置」

6. **備援本身壞了要先講**(像備胎警示燈):在 🟢 完整狀態時,以小圖示顯示「備援就緒 / 備援不可用」。不要等到真的需要時才發現 LoRa 早就卡死(F11)。

## 3. 系統模式(每台節點本地的狀態機)

### 3.1 四個模式

| 模式 | 進入條件 | HaLow | LoRa | 對應 UX |
|---|---|---|---|---|
| **H — 主網** | 預設 | 正常收發 | **只收不發**(例外見下)。收到的備援訊息經 HaLow 轉給目的地 / OTS | 🟢 |
| **H+ — 主網不穩** | 反覆切換被阻尼(§4.2)或逐則升級頻繁(§4.3) | 正常收發 | 關鍵訊息(SOS、文字)**雙發** | 🟡「連線不穩」 |
| **L — 備援** | 所有鄰居 batman last-seen > 60 s | 保持入網、**降功率**(F4),只為「聽是否恢復」 | 收發 PLI / 文字 / SOS,受 airtime 預算限制 | 🟡 精簡 |
| **X — 離線** | L 模式下 LoRa 也超過 T 分鐘沒聽到任何受信任節點 | 同 L | 同 L,但 PLI 拉長間隔省電 | 🔴 |

**H 模式下 LoRa 只收不發的例外**【決策】(都算入預算):
- **LoRa 出口**:目的地是某台 L 模式節點,且本節點被選為它的出口(§5.2)時,代它發一次。
- **點名**:開機時(HaLow 還沒起來,不傷主網)、之後每約 6 小時發一個約 20 B 的點名(約 0.4 s,F1 顯示短而稀疏的包對 HaLow 影響小【推論】),用來證明 LoRa 射頻路徑真的活著,餵給「備援就緒」指示(規則 6)。

### 3.2 為什麼不在 H 模式同時開 LoRa 發射

F1:LoRa 發射會把自己的 HaLow 打到剩一半或更少;F2:在 920–925 MHz 內靠分頻擋不住。所以「兩張網同時全開 = 兩張網一起變差」【推論,由 F1+F2 直接推出】。**一次只讓一種發射**是量測逼出來的結論,不是偏好。

## 4. 切換邏輯:慢、穩、誠實

### 4.1 觸發器(依 F6/F7/F8)

| 方向 | 條件 | 理由 |
|---|---|---|
| H → L | **所有**鄰居的 batman last-seen > 60 s | F6:last-seen 每秒 +1、正常 < 1 s,訊號乾淨;F7:半殘時仍 0.74 s,60 s 門檻不會被半殘誤觸發;F8:二元條件不受環境雜訊絕對值影響 |
| L → H 第一階段 | 任一鄰居 last-seen < 2 s | 先確認「聽得到了」 |
| L → H 第二階段 | 恢復 HaLow 全功率 → 連續 3 次 ping 到 gateway/OTS 成功 → **穩定期**(預設 30 s,見 4.2)內沒再掉 | 功率要先拉回來,否則 L 模式下的低功率讓對方聽不到我們,ping 會假失敗【推論】 |

**不用的訊號**:802.11s peer 消失(被干擾時不逾時,F6)、batman 移除鄰居(200 s 太慢)、LoRa/HaLow 的絕對掉包率(F8)。

**回切偵測被 LoRa 遮蔽的問題**(#181 設計審查指出):L 模式下自己的 LoRa 發射會蓋掉自己的 HaLow 接收(F1)。緩解【決策】:每次 LoRa 發射後,本節點強制 LoRa **靜默至少 5 s**,讓 HaLow 在這段時間裡收得到鄰居的 ELP(BATMAN_V 每 500 ms 一次,F6)。別台 L 模式節點的 LoRa 也會遮蔽,但因為每台都受 airtime 預算限制(§5.1),遮蔽比例有上限【推論,待測】。

### 4.2 防抖動:遲滯 + 翻轉阻尼

參考 BGP 的路由翻轉阻尼(route flap damping,IETF RFC 2439,美國 IETF 標準):一條路線反覆上下時,就先不要相信它恢復了。

- **非對稱時間**:下切 60 s(夠慢,避免短暫遮擋就切);上切要 2 階段 + 穩定期(夠確定才回來)。
- **翻轉計分**:每次 H→L→H 算一次翻轉;10 分鐘內翻轉 ≥ 2 次 → 穩定期倍增(30 s → 2 min → 5 min 上限),並把 UX 固定在 🟡「連線不穩」(模式 H+),直到連續 10 分鐘沒翻轉才回 🟢。
- **UX 去抖動**:操作者看到的狀態,任兩次變化間隔至少 30 s;模式機內部可以更快,顯示層不跟著跳。

### 4.3 逐則訊息升級(處理半殘與網路分割)

節點層級的觸發器看不到兩種情況:HaLow 半殘(F7)、HaLow 被切成兩塊(本地鄰居都在,但到不了指揮所)。改用**逐則訊息**判斷【決策】:

- 文字 / SOS 走 HaLow 送出後,若 **T 秒內沒收到端對端確認**(SOS 10 s、文字 30 s),自動再經 LoRa 送一次;UI 顯示「已改走備援送出」。
- 目的地在 batman 路由表(originator table)已經看不到 → 直接走 LoRa,不必先等 HaLow 逾時。
- 兩條路都到的重複訊息,由收端依訊息 ID 去重(Meshtastic 本身有 packet id 去重【事實】;HaLow 那條要我們自己帶 ID)。

這讓「系統送不到」變成少數情況,而且每次升級使用者都看得到原因,不會覺得訊息神秘消失。

## 5. LoRa 用量控制(不讓備援打爛主網)

### 5.1 硬性 airtime 預算【決策,數字待 P5 延伸實測校正】

TW 區域法規佔空上限是 100%(F12),Meshtastic 的禮貌門檻 25%(F13)對我們太寬(F1:28% 佔空已讓 HaLow 砍半)。所以:

| 模式 | 每節點 LoRa 發射預算(滾動 10 分鐘) | 約等於 |
|---|---|---|
| H | ≤ 1% | 約 6 s,例如 10 個短包 |
| L | ≤ 5% | 約 30 s,例如 50 個 PLI 大小的包(約 0.6 s/包,F 表 airtime 推算) |
| SOS | 不受預算限制,但每則最多重送 3 次 | — |

預算用盡時:位置只保留**最新一筆**(舊的丟掉,新位置覆蓋);文字排隊;UI 照實顯示「排隊中」。

### 5.2 洪泛控制(#181 設計審查:Meshtastic 洪泛會把用量放大 N 倍)

- **跳數由送端逐則決定**:Meshtastic 的 `MeshPacket.hop_limit` 可逐包設定【事實,Meshtastic protobuf `mesh.proto`】。H 模式節點當出口時送 `hop_limit=0~1`;L 模式節點的 SOS 用 3,其餘用 1–2。
- **HaLow 取代 LoRa 轉發**:H 模式節點聽到 LoRa 包,**經 HaLow 轉**,不在 LoRa 上重播。只有「到得了 HaLow 的節點」都在同一張 HaLow 網上時,這相當於用 HaLow 當 LoRa 的骨幹【推論】。
- **出口選舉**:H 模式節點把「我最近在 LoRa 上聽到哪些節點、SNR 多少」經 HaLow 分享(沿用現有 alfred 健康資料通道);要送給 L 模式節點 X 時,由聽到 X 的 SNR 最好的那一台當唯一出口,避免 N 台一起發。
- Meshtastic 韌體設定在佈建時一次定好:自動位置廣播 / 遙測關閉或拉到最長(位置由 Pi 端依模式與預算決定何時送)。**不在執行期改角色(role)**——角色變更屬 device 設定,會觸發 RAK 重開機【推論,依 Meshtastic `AdminModule.cpp` 的 requiresReboot 預設】,而 RAK 重開 = USB 重新列舉 = F11 卡死風險。

### 5.3 模式切換不碰會重開 RAK 的設定

依 Meshtastic 韌體原始碼(`AdminModule.cpp`,master 分支)【事實】:LoRa 設定裡只有 region、preset、頻寬、SF、CR、**tx_power**、頻率等無線電參數變動才需要重開機;`tx_enabled` 切換不需要重開機,但會寫一次 flash。本機韌體是 2.7.15 / 2.6.11,**需上機確認行為相同**。

因此【決策】:
- 模式切換**只用 Pi 端送出策略**(送不送、送什麼、hop 多少)來控制 LoRa 發射,平常不動 RAK 設定。
- 若需要硬性保險(防 Meshtastic 自己的自動封包),才用 `tx_enabled`;翻轉阻尼(§4.2)保證這一天只會寫幾次 flash。
- **LoRa 的 preset / 頻率 / 功率永遠不做執行期自適應**:改了就跟其他節點說不同語言,等於在最需要備援時把備援網切碎。

## 6. 各種不友善情境的應對

| 情境 | 系統行為 | 使用者看到 | 依據 |
|---|---|---|---|
| **走出 HaLow 範圍** | 60 s 後進 L;位置每 2–5 分鐘或移動時送;文字走 LoRa | 🟡 精簡 +「移到高處或靠近隊友」 | F6 |
| **HaLow 半殘**(掉包、延遲) | 不切模式;逐則升級(§4.3) | 🟢,個別訊息顯示「已改走備援送出」 | F7 |
| **HaLow 被切成兩塊** | 本地通訊照常;到不了的目的地逐則走 LoRa | 🟢;送往遠方的訊息顯示「經備援送出」 | §4.3 |
| **窄頻干擾打在 HaLow 頻道上** | HaLow 死 → L;LoRa 在另一端頻率有機會活(LoRa 在 SNR 約 −17.5 dB 仍可解調,HaLow MCS7 要 +20 dB 以上)| 🟡 +「此區域訊號受阻」 | #181 §2.1 推論 |
| **全頻段干擾(920–925 全蓋)** | 兩張都死 → X;全部存起來;不自動重開機、不亂改頻 | 🔴「訊息已保存,恢復後自動送出」 | 兩者同頻段【事實】,LoRa 只提供波形多樣性不是頻段多樣性 |
| **環境雜訊時好時壞**(如清晨) | 觸發器是二元的,不受影響;翻轉阻尼吸收 | 至多一次 🟡「連線不穩」,不閃爍 | F8、§4.2 |
| **RAK USB 卡死 / 備援電台壞** | Pi 端偵測 serial API 無回應 → (有 GPIO→RST 線路時)自動重置;否則記錄並上報 | 🟢 旁的「備援不可用」小圖示;管理員視圖寫原因 | F11 |
| **電量低**(#122) | 進「省電求生」:HaLow 關、只剩 LoRa,PLI 間隔拉長 | 🟡 +「電量低,只保留文字與位置」 | 【推論】HaLow 功耗高於 LoRa 待命 |
| **指揮所 / OTS 掛了** | HaLow 內點對點照常;LoRa 仍可走 Tier 0(手機↔手機) | 🟢(隊友間);地圖上指揮所圖示轉灰 | REV2 §1 三層退化 |

## 7. 刻意**不**做的事(v1)

| 不做 | 原因 |
|---|---|
| 自動改 HaLow 頻道 / 頻寬(例如自動縮成 1 MHz,F5) | 必須全網同時換,否則把 HaLow 網切碎;這是 #15 跳頻的題目。未來若做,要 ① 經 LoRa 送**簽章**過的換頻指令(#13)② 保留 F10 那種「時限內沒回來就自動還原」的保底 |
| 動態改 LoRa preset / SF 對抗干擾 | 會讓備援網分裂(§5.3) |
| 在 H 模式同時全開 LoRa | F1/F2 |
| 讓操作者自己選「用 HaLow 還是 LoRa」 | 把系統的難題丟給使用者 = 困惑的來源;管理員視圖可以強制,操作者不行 |
| 自動重開機救網路 | 沿用 `joinwatch` 原則:人正在反覆開關機時,自己重開只會毀證據(`docs/field-resilience.md` 決策 4) |
