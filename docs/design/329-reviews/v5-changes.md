# 329-app-uiux v4 → v5：第四輪發現的逐條對應

第四輪：審查 A = APPROVE-WITH-CHANGES（0 BLOCKER、0 MAJOR、9 MINOR）；審查 B = APPROVE-WITH-CHANGES（0 BLOCKER、3 MAJOR、9 MINOR）。原文在同目錄的 `review-v4-A.md`、`review-v4-B.md`。
「改在哪」指 v5 的章節。有 MAJOR，所以 v5 整份重審（第五輪，兩位新的審查）。

## MAJOR

| 發現 | 改了什麼 | 改在哪 |
|---|---|---|
| B-M1 「是別台」的位址沒有從「沒找到 / 還沒輪到」的條件裡排除：一台讀到、另一台不廣播時，不廣播的那台永遠是「還在找」，不會變成連不到 | 備忘加一條定義：一個位址只會是一台節點，位址有備忘「是 Z」就等於對其他每筆紀錄都有備忘「不是」。順序、沒找到、還沒輪到都用這個定義 | §4.3.3-5、§4.3.4、T-L2(b) |
| B-M2 提前再讀沒有上限、目標是全部：一台一直讀不到時，手機幾乎不停地掃描，並且每 10 s 對已經讀到的節點再登入一次 | 提前再讀只在「兩輪規則的第一輪」或「還沒輪到」時發生；目標只有觸發的那幾台；連續最多 3 輪，之後每 60 s；已經顯示連不到的節點不觸發。「上一輪結束」寫成定義。掃描開著的時間比例寫進成本 | §4.3.2、§4.3.5、§4.3.7、T-L2(c)、T-L3、R-2 |
| B-M3 紀錄順序依賴 `ui/state-v1`：PR 1 沒有它、冷啟動時是空的、和 §4.6「沒有任何決定讀它」矛盾 | 順序只看節點紀錄檔 `node/<id>` 的最後寫入時間（新的先）。不讀 `ui/state-v1`。新假設 A23（附原始碼證據）；限制寫明 | T19、§4.1、§4.3.3-6、§4.3.5、§4.3.7、T-L11(h)、R-1、A23、§13 |

## 我自己寫錯的事實（v4）

- 「沒找到 / 還沒輪到」的條件漏了「是別台」（B-M1）。
- 提前再讀的規則在 §4.3.2 與 §4.3.5 不一致，而且沒有上限（B-M2）。
- 順序規則引用了 PR 2 才有的 `ui/state-v1`（B-M3）。
- F25 寫 10 處，實際 14 處（A-m3）。
- 「必須先把節點重置」：這一版做不到（A-m5）。
- §4.3.7 寫已經認出來的節點「不受影響」，說得太滿（B-m1）。

## 沒有照建議做的

沒有。A-m4 的處理是加一個待驗的假設，不是現在就刪掉那兩列（刪之前要有證據）。
