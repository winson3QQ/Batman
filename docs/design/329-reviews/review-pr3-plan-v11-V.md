## 3. MAJOR

### V-M1　結果頁建立那一列的「再試這一台」沒有定義；照字面就是第二個沒有條件的「建立網路」

- **情境（現場）**：4.1 勾 04、02，建立模式。04 建立途中拔電 → 有 `rel`、重讀是 pending → 自動檢查一次 → 04 還在開機，`loginFor` 60 s 沒成功 → 整個流程停 → 結果頁 04 那一列。§2.5 寫結果頁有「再試這一台」和「檢查網路」兩種動作，**沒說哪一列給哪一種**，也沒說建立列的「再試」做什麼。最自然的實作是「再做一次這一列的動作」，也就是再 `makeNetwork` 一次。04 開機後使用者按「再試這一台」→ 04 登入成功 → 又建一個新的 net（owner.rs:1067-1089 建立時不看既有紀錄）。如果 04 在拔電前其實已經套用了第一個網路，現在它被換到第二個網路，手機則留下一筆再也確認不了的 pending。這正是 Q-M2 / S-M1 想擋的「節點其實已在網路裡，頁面卻讓人再建一次」。這個入口不在 §2.4 / §2.8 / D6 的「沒有已建立的 net 才建立」規則裡。
- **另一面**：建立列如果**沒有** `rel`（登入失敗，或在寫 pending 紀錄之前就被拒絕）→ 什麼都沒寫、也沒送出（join2 §3.1：先寫 pending 紀錄再送；nodes.dart:51 `_notSent`）。這時「再試 = 再建立一次」是安全的，也就是使用者重新按開始時會發生的事。
- **證據**：plan §2.5「結果頁：逐台列結果；『再試這一台』『檢查網路』借用同一個佔用 … 結果頁本身沒有『建立網路』」；D6 的清單沒有結果頁；§6 第 5 步沒有建立列「再試」的測試；設計 329-app-uiux.md:750「結果不明 … 下一步按鈕 =『檢查網路』… 不自動重送」。
- **修法（一句話，不加機制，照設計 :750）**：§2.5 寫明結果頁每一列的下一步：
  - 建立列有 `rel`（pending）→ 只有「檢查網路」，**沒有**「再試這一台」；
  - 建立列沒有 `rel` → 「再試這一台」= 同一台再建立一次（什麼都沒寫過）；
  - 加入列 → 「再試這一台」= `joinNetwork(rel)`（D5）。建立模式中建立沒成功時，「還沒做」的加入列要寫明：建立列確認成功之前不給「再試」（Rust 會用 `Pre::NotApplied` 拒絕，owner.rs:506，無害但會誤導），或照 V-m5 由檢查網路頁「完成」回來後再給。
  - 在 D6 的清單補上「結果頁：沒有 `rel` 的建立列可以再試」。
  - 測試（附改壞）：建立列有 `rel` → 結果頁沒有「再試這一台」、`makeNetwork` 呼叫 0 次（改壞 = 給再試 → FAIL）；沒有 `rel` → 再試會呼叫 `makeNetwork`。

## 4. MINOR

**V-m1　「拿到回答」要限在 confirm 那一步的 Rust Answer；`InProgress` / `Unknown` 的處理要寫一句（S-M1 第 3 點）。**
- Dart 自己的 `_makeUnclear` = `'[NET_STATE] 結果不明，稍後在這台按「檢查網路」'`（nodes.dart:50），和 Rust 的 confirm 回答用同一個標籤。`OwnerConsole` 是從舊控制台複製的，§2.8 應寫成「confirm 請求的 `OwnerKind::Answer` 步驟、detail 以 `[NET_STATE]` 開頭」，不是「頁面拿到的句子以 `[NET_STATE]` 開頭」。`OwnerKind::Ended`（連線出錯）不算。
- 照 v11 的定義，`NoChange(InProgress)` / `NoChange(Unknown)` 都算「拿到回答」，所以會給次要建立。這時畫面上 Rust 的句子是「請一分鐘後 / 稍後再按『檢查網路』」（owner.rs:476、:479）。`Unknown` 也包含**誠實的節點**在 info.net 撞到 `E_RATE`（flow.rs:149-150）。舊控制台一直給建立，是基準，不要求改；但請在 §2.8 寫一句「`InProgress` / `Unknown` 照基準給次要建立（句子叫人稍後再檢查）」，§6 加一條測試把它固定下來，免得實作者自己決定。

**V-m2　檢查網路頁在佔用中的兩個輸入沒有來源：pending 清單、「手機沒有任何已建立的 net」。**
- §2.6 只規定「判斷**某一筆**有沒有建立完成時重讀那一筆」。但 §2.8 還需要兩個集合：要檢查的 pending 清單，以及「沒有任何已建立的 net」。`NetIndex` 在佔用中不重算。從結果頁借用進來時，剛建立的那一筆是在 `NetIndex` 算完之後才寫的，`NetIndex` 裡沒有它，它的 `MemberView.creator` / `dacHash` 也就沒有來源。「先檢查剛建立的那一筆」暗示要把它加進去，但沒說怎麼拿。
- 自己拿佔用的時候：`acquire` 只等 `NodeLink` 讀紀錄（§2.1），不等 `NetIndex`。上一個佔用剛釋放時 `NetIndex` 可能還在「計算中」。若實作者把「計算中」當成「沒有已建立的」，在「已建立 A + pending B（例如 T-M1 的出口用過之後）」的情況下，檢查 B 拿到 `NotApplied` 就會給建立 → 拆成兩個網路。
- 修法：§2.8 寫明拿到佔用後**在佔用下重新列一次檔**（和 §2.4「按開始時重新列一次」同一個函式），用它得到 pending 清單與「有沒有已建立的」。列不出來、或有打不開的紀錄 → 不給建立（fail-closed，因為打不開的紀錄可能是已建立的）。測試：`NetIndex` 計算中 + 已建立 A + pending B → 沒有建立（改壞 = 讀 `NetIndex` → FAIL）。

**V-m3　確認的等待時間：舊控制台 15 s，計畫寫 60 s，§2.3 又說「行為與句子和舊控制台相同」。** 舊 `_confirmNetwork` 用 `_ask` 的預設 15 s（nodes.dart:1244、:507），逾時的句子會帶秒數（:531「15 秒內節點沒有回應…」）。計畫 §2.5「確認回答 60 s」、§2.8「每筆確認 ≤ 60 s」取自設計 §5.4 表（329-app-uiux.md:738），但設計 :574 也寫「一般請求 15 s … 本設計不加新的逾時」。請擇一寫進 §2.3（`OwnerConsole.confirmNetwork` 的 wait），用 60 s 的話列進 D6。

**V-m4　頁面消失之後還會不會開新的請求，要寫清楚。** §2.5 寫「等當前請求做完，不做之後的送新密碼與連線檢查」，沒有提到建立後的**自動檢查**（重新 `loginFor` 60 s + 確認），也沒說 `loginFor` 正在跑時頁面消失，之後還送不送建立 / 加入。最壞的情況是登入、建立 360 s、再登入、確認依序跑完，會超過 420 s 期限 → `_revoke` →「上一個操作可能沒有存完」。舊控制台的規則是頁面不在了就不開新的請求（nodes.dart:518-520 `if (!mounted && !held) return null;`）。請寫明「`pageGone` 之後不開任何新的請求（含 `loginFor`、自動檢查）」，並在 T-M1(g) 補一條：建立回來之前頁面消失 → 確認次數 0。另外：頁面消失時國家問題的對話框正開著（不計時）→ 由 420 s 期限收尾；寫一句即可。

**V-m5　頁面堆疊的契約。** 沒寫的有：
- 迴圈頁 / 結果頁是 push 在 4.1 上面還是取代 4.1？結果頁 pop 之後回到哪一頁？
- 檢查網路頁「建立網路」的「開 4.1 建立表單」由誰 push？從 4.1 進來時，底下已經有一個 4.1（加入表單）。
- 從節點頁進來時：節點頁不放建立（D6），但檢查網路頁可以把使用者帶到 4.1 建立表單。這是允許的，只是要寫明。
- 借用的檢查網路頁「完成」（有升級）回結果頁之後，那一列要不要更新成「已建立」？還沒做的加入列能不能接著「再試」（見 V-M1）？S 的走查假設要回首頁重新來，計畫沒寫。

建議寫成：檢查網路頁的出口一律 pop 一個值（返回 / 完成 / 去建立）。自己拿佔用時，呼叫它的頁面（4.1 或節點頁）收到「去建立」後用 `pushReplacement` 開 4.1 建立表單；借用時由結果頁照 §2.8 處理。

**V-m6　節點頁「這台可能是建立者」沒有定義。** §2.4「手機有 pending 紀錄而這台可能是建立者 →『檢查網路』」。登入前能用的只有名稱 `node-<last4>`（owner.rs:1079），pending 建立者的 `last4` 是空的（device_id 只在套用後填）。請寫明判斷方式（例如「任何一筆 pending 的建立者名稱對到這台」），以及對不上時節點頁有沒有「檢查網路」。§6 的「節點已在網路但紀錄 pending → 有檢查網路」要照這個定義寫 fixture。
