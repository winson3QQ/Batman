## 發現

### MAJOR

#### M1 「佔用下的登入」（流程自己登入）沒有契約：自動輪的所有規則（8 s 上限、單一候選例外隔離、備忘、N9 的 30 s 例外、結束種類對應到節點狀態）都只定義在自動輪，而每一個操作，包含展示路徑「新增完 → 建立網路」，都走這一條

**情境 A（展示路徑，需求 1）**：一支手機、一台新節點。
1. 3.1 掃 QR → 3.2 取名 → 認領完成（原始佔用寫入 `node/<id>`，流程結束 → 釋放）。
2. 3.5 的主要按鈕「建立網路」→ 4.1（名稱預設「Batman」、勾這台、頻道預設 40）→ 按「建立」。熟手 3–5 秒內做得完。
3. 建網 controller 拿 session 佔用，第一步「登入（60 s）」（§5.4 表第一列）。
4. 節點還沒做下一次 4 s 輪詢（N9；provd/server.go:21、:368-369），對正確的紀錄回「解不開」。
5. 設計對 N9 的處理（釋放後 6 s 才讀、30 s 內的解不開不記備忘、同一對 6 s 後再試；§4.3.2、§4.3.3-4、§4.4「釋放之後」）**只寫在自動輪**。流程登入用什麼規則，設計沒有寫。如果是搬過來的現有 `_login`（§4.7 的搬移規則「逾時值一個都不改」）：它每個位址只試一次（`tried`，lib/nodes.dart:352-408），節點約 5 s 後用同一個位址重新廣播時不會再試 → 60 s 後顯示「[NOT_FOUND] 60 秒內找不到節點…（剛認領完的話，等幾秒再試一次）」（:399）。這句提示本身就證明現況會發生這件事。
6. `loginflow.rs:6-7` 的註解寫「剛認領完呼叫者重試 3 次、間隔 3 s」；我搜尋了 `lib/` 與 `rust/`，**沒有任何呼叫者這樣做**（claim.rs:347、replay.rs:138 只各自處理認領 / 恢復自己的解不開）。所以現況與設計都沒有人負責這段空窗。

**情境 B（每天回來用，需求 4）**：節點頁剛讀完那一台（P1 → P0），使用者按「手機 Wi-Fi」。
1. X10：取消讀取 → 等斷線完成 → 發佔用 → 流程自己登入。
2. 那台節點剛被這一輪連過，約 4.9 s 後才重新廣播（M-1 R：隔 0 s 再掃要 4.86–4.92 s，整次 7.3–8.8 s；N8）。T16 寫的代價只有「握手段實測 ≤ 5 s」，漏了這 5 s。
3. `NodeLink` 手上有「位址 a 是 Y」的備忘，但流程登入用不用它、先試哪個位址，沒有寫。現有 `_login` 依掃到的順序試，會先對附近別人的節點握手（現有逾時：連線 15 s、等回應 20 s，lib/nodes.dart:185、:194；不是 §4.3.3-3 的 8 s）。附近有一個不回應的位址時（§4.3.7 已經承認可能有人故意廣播這個 UUID），每次操作前要多等最多 35 s。
4. F50：現有 `_login` 裡，只要一個候選在 `requestMtu` 或第一次讀取丟例外，整個登入就結束（lib/nodes.dart:198-199 在 try 之外）。設計只在自動輪修了它（§4.3.3-4 最後一列、T-L15），流程登入沒寫。

**情境 C（安全，需求 3）**：流程登入時遇到 `CertRejected`（身分不符）或 `AuthRefused` + `EForbidden`。
- 自動輪遇到這兩種，會把 Y 設成 `unreachable(身分不符)`（bad）或「登入被拒」、寫文字紀錄、記備忘（§4.3.3-4）。流程登入遇到同一件事時，畫面顯示什麼？Y 的狀態改不改？備忘記不記？都沒寫。S11 說新畫面不顯示 `login_end_text` 那一句，改由 `NodeLink` 依結束種類選句子，但對應表只寫給自動輪（§4.3.5）。結果是：同一個安全事件，如果是在按按鈕時發現的，可能只在流程頁顯示一行，首頁在 180 s 內仍然是上一次的綠燈。

**情境 D（擁有權）**：備忘表的擁有者是 `NodeLink`（§4.1 表）。流程登入的結果（成功 → 「是 Y」；解不開 → 「不是 Y」）寫不寫進備忘、由誰寫，沒有定義。
- 如果寫：N9 的例外與「是 Y 要連續兩次解不開」也要適用。
- 如果不寫：流程登入對別人節點的握手不受「每一對只試一次」約束，§4.3.7 的握手次數（以及 §8「別人的節點」那一列）漏算了這一部分。
- 多台建網（§5.4）、移除隊員時依序登入每一台自己的節點（現況 `_remove` → `_login`，review-v1-B 引的 nodes.dart:1296），都是連續多次的流程登入。

**證據**
- 只有自動輪有規則：§4.3.3 第 1–9 點、§4.3.4、§4.3.5。流程登入只有一句「流程第一次需要節點時自己登入」，散在 §0 T16、§4.3.6 X4 / X10、§5.4 表的「登入 60 s」、§5.5「登入不到 → 可恢復的錯誤 +『再試一次』」。
- §4.7「不是搬移、是新寫的邏輯」表沒有「流程登入」這一項；§12 的 PR 表也沒有把它放進任何一個 PR（PR 1 的舊控制台用它自己的 `_login`；第一個用 session 佔用登入節點的是 PR 3 的建網）。
- 唯一的測試是 T-X10：「流程沿用讀取的那條連線 → 佔用下的登入次數 0 → FAIL」。它只數次數，不驗規則。
- 原始碼：lib/nodes.dart:352-408（`_login`、`tried`、:399 的提示）、:185 / :194（15 s / 20 s）、:198-199（F50）；rust/batman-proto/src/loginflow.rs:6-7（重試 3 次的說法）；provd/server.go:21、:368-369（N9）；M-1 R（§1.3）。

**為什麼是 MAJOR**：這是每一個操作的第一步，也在需求 1 的展示路徑上。設計把連線模型收斂成只有自動輪（T16），卻沒有把同一套規則套到另一半。後果是：情境 A 在展示時有機會直接卡 60 s 後失敗；情境 C 讓身分不符的顯示方式取決於它是在哪裡被發現的。

**建議**（不加新機制，只把已有的規則套到另一個呼叫者）
1. 在 §4.3 加一小節「佔用下的登入」：`NodeLink.loginFor(Y, 截止 60 s)`，由 `NodeLink` 執行（它是 session 與備忘的擁有者）。嘗試規則照 §4.3.3-3 / -4（8 s 等到 msg2、單一候選的例外只結束那一次、同一位址隔 6 s）；先試備忘「是 Y」的位址；目標只有 Y，所以「一個位址 2 次」改成「直到截止」。
2. N9：「最近一次佔用寫入、釋放未滿 30 s 的紀錄」，它的解不開不記備忘、同一對隔 6 s 再試（和自動輪同一條規則，錨點不變）。這樣情境 A 自然被蓋住，也順帶落實 loginflow.rs:6-7 的意圖。
3. 結果對應：
   - 成功 → 記「是 Y」；如果流程有讀狀態，把那次回答當成一次讀取。
   - `CertRejected` → Y 變成 `unreachable(身分不符)`、寫文字紀錄、流程頁顯示同一句 bad。
   - `AuthRefused` + `EForbidden` → 「登入被拒」。
   - 其他 → 流程頁顯示「可恢復的錯誤 +『再試一次』」，Y 的狀態不變。
4. 把流程登入算進 §4.3.7 的握手次數與 §8「別人的節點」那一列；T16 的代價補上 N8 的約 5 s。
5. 測試（各附負向對照）：
   - T-L17（新）：假節點在佔用釋放後的前 4 s 對正確的紀錄回解不開 → 建網的登入在 60 s 內成功，沒有記「不是 Y」。對照：流程登入改回「每個位址只試一次」→ FAIL。
   - T-L18（新）：備忘「是 Y」+ 3 個不回應的位址 → 流程登入的第一個嘗試就是那個位址；一個候選丟例外 → 登入繼續。對照：拿掉順序 / 拿掉例外隔離 → FAIL。
   - T-S3 補一例：流程登入遇到 `CertRejected` → 首頁那一台是 bad。對照：只在流程頁顯示 → FAIL。
6. §4.7 的新邏輯表與 §12（PR 3，或併進 PR 1）各加一行。

### MINOR

#### m1 180 s 的推導只算了 30 s 的掃描窗；附近位址多、那一輪跑到 90 s 上限時，只錯過一輪的正常節點會短暫變成不明

- 情境：Y 有備忘「是 Y」，上一次讀取在 t = 0。下一輪約在 t = 60 s 開始，剛好撞上另一支手機連著 Y（§4.3.7 最後一點）。附近有很多還沒認出來的位址，這一輪照 §4.3.3-7c 跑到 90 s 上限（約 t = 150 s）；10 s 後提前再讀（t = 160 s）。Y 還要約 5 s 重新廣播，加上登入與讀取約 11 s，到 t ≈ 176 s；這一輪本身晚一點開始就會超過 180 s。
- 證據：§4.3.1（「60 + 30 + 10 + 30 s = 130 s，留餘量」）、§4.3.3-7、§4.3.5 最後一點（作者自己寫了跑到 90 s 時，每輪多約 100–150 s）。
- 影響：只影響顯示（綠變成不明），不會顯示錯的顏色，所以是 MINOR。
- 建議：推導分兩種情況寫，並寫明後果（「附近位址很多時，錯過一輪就可能短暫顯示不明」）；或者把到期改成以「連續兩輪沒讀到」為準，不用固定秒數。至少在 §4.3.1 寫出 90 s 的情況，並在 T-L14 加一個「錯過一輪 + 90 s 上限」的案例，記下實際顯示不明的時間。

#### m2 §12「每個 PR 都保留全部現有功能」，與 PR 2「舊控制台移到開發者選項」、§5.8「開發者選項只有 devTrust 才有」互相矛盾：field 版本在 PR 2 到 PR 3 / 4 之間沒有任何管理節點的入口

- 情境：PR 2 合併後的 field 版本，首頁有狀態、有「從這支手機移除這台節點」，但建網、加入、設定、更新都還在舊控制台（PR 3 / PR 4 才搬）。舊控制台在開發者選項裡，開發者選項只有 devTrust 才有（§5.8），而 field 的 `DEV_TRUST = false`（android/app/build.gradle.kts:72-76）。
- 實際影響：field 版本目前不能跑（#255，§9.4 已寫明），所以今天沒有人會碰到。但 §12 那句話照字面不成立；如果 #255 在 PR 2–4 之間修好，就真的會發生。
- 建議：§12 PR 2 那一列二選一寫清楚：「非 devTrust 版本在 PR 3 / 4 之前，『我的節點』（舊控制台）入口留在首頁」，或「PR 2–4 期間 field 版本不提供這些功能（#255 未修，沒有使用者）」。

#### m3 網路摘要表（§4.3.8）沒有寫遇到壞掉或解不開的 net / mnet 紀錄時怎麼辦；§7 沒有「當機 / 當機循環」這一列

- 情境：一筆 `net/<id>` 的檔頭正常但內文壞了。這種檔會存在：F39 說它可以被 CAS 覆蓋。摘要表在「啟動檢查通過時」解開每一筆，設計沒有寫這時是跳過那一筆（fail-open，待辦與第 6 列的按鈕可能少一項），還是整個摘要表失敗（首頁卡住）。如果實作讓例外往外丟，每次啟動都會在同一個地方失敗，而 §7 沒有一列處理這種當機循環。
- 證據：§4.3.8；§7（有「程序被系統殺掉」兩列，沒有 app 自己丟例外 / 當機循環）；F39（rust/batman-proto/src/store.rs:106-112、:136-145）。
- 建議：
  - §4.3.8 加一句契約：一筆紀錄讀不出或解不開 → 跳過那一筆、寫一行文字紀錄、10.5 技術資訊列出檔名；其他筆照算。理由：摘要表只決定顯示與按鈕，真的要寫入時，Rust 會再讀那一筆，由 CAS 與現有的錯誤路徑擋住。
  - §7 加一列「`NodeLink` 或摘要表在啟動時丟例外」：改後 = 那一部分顯示錯誤，首頁其他部分照常；測試 = 放一筆假的壞紀錄 → 首頁照常出現、其他網路照列。

## 依審查規則逐項的結論

1. **擁有權**：§4.1 的擁有權表完整。`ui/state-v1` 只有 `UiState` 寫；金鑰紀錄只有目前的佔用者經 `RecordWriter` 寫；`expectOffline` 只有軟體更新 controller 呼叫；`KeyGate` 只有啟動檢查與「再試一次」寫（X26 只是「要求」重查）。沒有發現兩個寫入者。缺的是 M1 情境 D：流程登入算不算備忘表的寫入者，沒有定義。
2. **契約**：`ui/state-v1`（§4.6）、session 步驟（§4.5）、佔用（§4.4）的契約都寫了資料缺少 / 壞掉 / 過期時怎麼處理，也寫了理由。缺的是流程登入（M1）與網路摘要表遇到壞紀錄（m3）。
3. **生命週期矩陣**：§7 涵蓋安裝、升級、PR 之間升級、降級、程序被殺、重開、藍牙 / 權限、節點重開、各依賴（Keystore 見 X26、節點），以及各平台（Android 13–15 標 ⚠️ 未測；iOS 不適用，有寫理由）。缺「當機循環」（m3）。
4. **證據**：下面「對過原始碼的引用」逐條核對，**沒有發現引錯的**。沒量過的項目（A1、A10、A13、A21、A22、A23 的實際時間、T-L11j 的 5 分鐘門檻、T-Q1 的版本 27）都標了 ⚠️，也寫了什麼時候補量。M-1 的數字沒有被說得比量到的多：§1.3 明寫量到的全是「拿錯紀錄」的握手、登入成功的時間沒量；F22 維持 ❓，不宣稱修好。
5. **安全**：§8 的逐角色表涵蓋附近的攻擊者（假節點、耗盡配額、看廣播、學位址）、別人的節點、同一支手機上的其他 app、旁邊看螢幕、拿到已解鎖 / 鎖著的手機、被入侵的節點、供應鏈、我們自己的錯。我另外用「被入侵的節點」試了中繼攻擊（把握手轉給真的節點）：Noise 加上釘住的 DAC，它拿不到 session（loginflow.rs:62 的 PSK 綁 device_id；:171 的憑證檢查在簽名之前）。缺口只有 M1 情境 C（流程登入裡的身分不符怎麼顯示）。失敗模式除了 `ui/state-v1` 之外都是 fail-closed；`ui/state-v1` 的 fail-open 有寫理由。

**需求對照**
- (1) 可以展示（從零到組網）：§6 情境 1 加上 §5.3 / §5.4 的步驟齊全；但展示路徑上的「認領完立刻建網」受 M1 情境 A 影響。
- (2) 直覺、不顯示多餘的東西：附近裝置清單移到開發者選項（§5.3、S10）；別人的節點不出現在任何清單（§7）。✅ 設計層面符合。
- (3) 節點狀態與錯誤清楚：首頁 14 列由上而下判斷、連不到有六種原因、`node_state == 1` 用 warn。✅；流程登入的錯誤怎麼顯示，見 M1 情境 C。
- (4) 不必每次開 app 都重新連線：自動讀取解決了「看狀態」這一半（U2-4 已在 M-1 真機重現，R-1 是它的正向驗證）。「做操作」仍然每次都要登入（T16，設計自己寫明的代價）；每次多出約 5 s 的重新廣播等待沒寫進去（M1 情境 B）。
- 別人用自己的 Android 手機：設計誠實寫明只在 S20、dev 版本上驗，field 版本的問題 #255 不在本單（§9.4）。沒有 overclaim。
- 只為展示而做的功能：沒有發現。

**過度設計**：這一輪沒有發現新的、四個需求與安全都用不到的機制。
- 420 s 收回 + 待辦：保底「一個卡住的佔用永遠擋住所有藍牙」。每個請求都有自己的逾時，所以它只在程式出錯時觸發。保留合理。

**沒有重現就修**：U2-4 已在真機重現（M-1：75 s、0 次連線）；F22 維持 ❓，設計明寫不宣稱修好；N8 的時間有量，原因標 ⚠️。✅ 沒有發現對沒重現的東西宣稱修好。

**負向對照抽查**
