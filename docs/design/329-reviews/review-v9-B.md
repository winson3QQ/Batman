## 2. MAJOR

### M1 正常的軟體更新路徑上，「預期離線」在更新完成後還顯示「正在重開」約 3 分鐘；T-W2 測的是實際不會走到的路

- **情境**（W9）：情境 7 的正常操作：節點頁 → 軟體更新 → 套用。更新流程本身在佔用中一路等到節點重開回來（`on_reboot`：swupd.rs:1050-1075，「a gone link = still rebooting (5 minutes)」，讀到 phase 5 才 `done("更新完成…")`），頁面執行中不能離開（swupdate.dart:326-327）。所以從套用到「更新完成」整段都有佔用，`NodeLink` 一輪都沒跑、從沒看到「沒找到」。使用者看到「更新完成」、關頁 → 6 s 後自動輪讀到節點 → 依 §4.3.1「設定之後**先有一次「沒找到」、之後再讀到**才清掉」，記號不清 → 節點列與首頁第 9 列顯示 busy「節點 X 正在重開，預計 HH:MM 前回來」，直到 `until`（套用 + 6 分鐘）。重開約 2 分鐘（swupd.rs:74 `T_TAK`），所以「更新完成」之後還有約 3–4 分鐘的錯誤狀態；而且第 9 列在第 10–14 列上面，這段時間首頁不會是「一切正常」。
- 另一個加重：`until` 用哪個時鐘沒寫。若用單調時鐘，鎖屏期間不走，解鎖後顯示的「預計 HH:MM 前回來」可能是已經過去的牆上時間。
- **證據**：§4.3.1「預期離線」段；§4.8「佔用只在更新頁開著或有請求 / 上傳在進行時持有；進行中不能離開頁面」；swupd.rs:984-986、:1050-1075；swupdate.dart:161-180、:326-327；T-W2 只測「套用後節點重開前先被讀到一次 → 記號還在；先找不到、再讀到 → 清掉」，兩個前提都需要佔用已經釋放，正常路徑不會發生。X24 的前提（舊版控制台套用後「可能顯示連不到一兩分鐘」）同樣不成立：控制台在堆疊上整段都是原始佔用，也不會有自動輪。
- **為什麼是 MAJOR**：需求 3（節點狀態要清楚），在主要情境 7 的每一次正常更新之後，app 對一台已經更新完、正常的節點說「正在重開」。現有測試不會抓到。
- **修法**（不加資源）：唯一的呼叫者是更新 controller，讓它在流程結束時結束記號：流程以 phase 5 / 6（完成、退回）結束 → 清掉記號（`expectOffline(Y, 現在)`）；只有以 `T_LATER`（5 分鐘沒回來 / trial 太久）或「結果不明」結束、或流程沒做完頁面就沒了時才保留記號，`until` 從那一刻起算。`until` 寫明用單調時鐘並在進背景時處理（或改成「從背景回來時清掉，交給兩輪規則」）。T-W2 加正常路徑案例：套用 → 佔用中假節點斷線、回來、phase 5 → 釋放 → 下一輪讀到 → **不是** busy（對照 = 現在的清除規則 → busy → FAIL）。另一個選項是承認這個記號只對 `T_LATER` 有用、整個拿掉（§13 加一行）；兩者擇一，技術細節作者自定。

### M2 自己的節點多於一輪讀得完的台數時（A1 = 11 s 約 9 台起），狀態區永遠不是「一切正常」、說錯原因，顏色週期性到期

### M3 T-L11(j) 的負向對照在它自己的假節點參數下不可能 FAIL（第三輪同一個測試）

- **情境**：T-L11(j) 的假節點「一次一條連線、斷線後 5 s 才廣播、每 60 s 超過 20 次握手就斷線」。v9 的對照：「拿掉『不是 Y』備忘 → 每台節點 60 s 內握手 > 20 → FAIL」。
  - 一台假節點連著時不廣播、斷線後 5 s 才再廣播，所以兩次握手之間至少 5 s（再加握手本身）→ 任何 60 s 內最多 12–13 次，**和手機做什麼無關**。即使假藍牙讓手機在不廣播時也連得上，假節點自己的 N4（第 21 次斷線）也把計數封在 20。這個斷言量的是假節點自己的限制，不是 `NodeLink`。
  - 同一個 (j) 的其他斷言也不因拿掉「不是 Y」而 FAIL：「之後 10 分鐘位址不變 → 對別人握手 0 次」——自己的節點讀到、有「是 Y」之後，每一輪第一個嘗試就讀到、目標全讀到就結束（§4.3.3-7(a)），有沒有「不是」都是 0 次（§4.3.7 自己也這樣寫）。「輪換一次 → 對別人 ≤ m−1」只在某支手機輪換後第一輪沒讀到自己的節點時才會被違反，取決於假藍牙的排程，不是確定的。
- **證據**：T-L11 的 (j) 情境與對照欄；§4.3.7「自己的節點都讀到…對別人的節點握手 0 次」；W10。v9-changes.md：「(j) 對照改成拿掉『不是 Y』」。第八輪 B-M1 的修法原本寫「(j) 的 ≤ 20 / 60 s 保留當安全斷言，但寫明它不是任何規則的對照」，v9 反而把它寫成對照。
- **為什麼是 MAJOR**：§9.1 要求 PR 附每個對照實際 FAIL 的輸出；照文件寫，PR 1 拿不出來（「a test unable to fail」），這是第七、八、九輪連續三次同一列。規則本身（「不是 Y」）由 (c)(i) 鎖住，所以影響的是測試計畫，不是出貨行為；但依審查規則這一類算 MAJOR。
- **修法**（一行測試計畫）：(j) 的「≤ 20」寫明是安全斷言、不是對照。給 (j) 一個確定會 FAIL 的對照：輪換之後讓其中一支手機自己的節點**前 3 分鐘不廣播**（其他照舊）→ 這支手機在這 3 分鐘內對每個別人位址恰好 1 次握手（共 m−1 次）；對照 = 拿掉「不是 Y」→ 每一輪（含提前再讀）都對同一批位址再握手 → > m−1 → FAIL。PR 1 實際跑一次對照確認。
