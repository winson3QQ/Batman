## MAJOR

### M1 候選備忘把「明確驗證失敗」當成「不是我的」，但這個結果在原始碼裡明寫著包含「自己的節點剛認領完還沒準備好」

- 情境：新增節點流程認領完 04 → 佔用釋放 → §4.4「被動到的節點立刻排一輪」→ 對 04 握手得到 `Msg2Undecryptable` → §4.3.3-4 把這個位址記為「不是我的」→ 之後每一輪都跳過它，直到位址輪換（設計自己寫約 900 s）或重開 app → 兩輪後首頁顯示「手機連不到節點 04」。使用者剛認領完的節點在展示時顯示連不到，最長 15 分鐘，而且按重新整理也沒用（備忘照樣跳過）。
- 證據：`rust/bridge/src/api/owner.rs:447` `End::Msg2Undecryptable => "不是這台節點（或節點剛認領完還沒準備好）"`（測試 :1862 鎖住這句）；現有文字 `nodes.dart:399`「剛認領完的話，等幾秒再試一次」。節點端 `provd/session.go:416-425` 對 PSK 不符回假的 msg2，手機端分不出「別人的節點」與「自己的節點但 PSK 還沒就緒 / 已被重置」。
- ⚠️ 我沒有在真機上確認「剛認領完」的窗口有多長；但程式的文字與現有提示都承認它存在，設計沒有提到。
- 另外 A17 寫「PR 1 讀程式確認」。現在就能確認：Rust 分得出（`owner.rs:1662-1665` 回 `Ended` + 文字），Dart 分不出（`_tryLogin` 只回 `bool`，`nodes.dart:318` 與 :339 的逾時都是 `false`）。要用備忘就必須改 `OwnerStep` 帶結束種類，這是對現有程式的改動，應該寫進設計而不是留到 PR 1。
- 建議：(a) 「不是我的」不是永久跳過，只是排到最後、每 N 輪仍試一次；(b) 佔用釋放後、以及使用者按重新整理時清掉「不是我的」的備忘；(c) 設計寫明要在 `OwnerStep` 加結束種類；(d) T-L11 加一案例：自己的節點第一次回 `Msg2Undecryptable`、第二次正常 → 必須讀到（對照：永久跳過 → FAIL）。

### M2 「斷線完成」是手機端的事件，不等於節點已經重新廣播；「立刻排一輪」與「從來沒讀到過第一輪就連不到」正好疊在這個空窗上

- 情境 1（展示的主線）：認領完第一台 → 佔用釋放、等手機端 disconnected → 立刻掃描。節點要等 BlueZ 的 `Connected=false` 訊號或 5 s 的 tick 才 `converge` → `register`，而 `register` 還有 `staleLinks()` 與抖動。這台節點「從來沒讀到過」，照 §4.3.4 第一輪找不到就直接 `unreachable(找不到)`，沒有第二輪的緩衝。
- 情境 2：離開節點頁 →「等斷線完成才開始下一輪」→ 同一個空窗。有上一次的 `read` 所以畫面不變，但 10 s 後的提前重讀與掃描次數上限（m7）互相擠。
- 證據：`cmd/batman-provd/bluez.go:731-782`（`nlinks>0 || Sessions()>0` 就撤廣播）、:629-682（訊號 / kick / 5 s tick）、:583-600（`register`）。設計 §4.2「斷線完成 = 連線狀態串流回報 disconnected」、§4.3.2 末句、§4.3.4 表第三列、§4.3.5。
- 這和 ❓F22（60 s 找不到）是同一個形狀。設計說不解釋 F22，卻在最容易撞到它的兩個時刻排了「立刻」的一輪，而且給沒讀過的節點最嚴的規則。
- 建議：(a) 從來沒讀到過的節點也用「連續兩輪」規則（或：這次開 app 內剛被操作動過的節點有一段寬限，畫面是 busy「正在等節點回來」）；(b) 佔用釋放後的一輪延後一個由 M-1 量出來的值（M-1 已經有「斷線後多久能再找到節點」這一列，設計沒有說量到的數字用在哪裡，要寫明）；(c) T-L 加一案例：假節點在斷線後 8 s 才廣播 → 釋放後不得顯示連不到（對照：立刻排一輪 + 第一輪就判 → FAIL）。

### M3 佔用的生命週期自相矛盾：登記表持有 controller，卻又說「佔用者被銷毀時收回」「下一次要求時收回」

- §4.4 同一張表裡寫：「佔用登記表持有 controller 物件，不是頁面」（為了 T-K3 頁面不在也寫完）與「佔用者被銷毀而沒有釋放 → 登記表在它的 `dispose` 或下一次要求時收回」。controller 被登記表持有就不會被銷毀；所以實際上只剩「下一次要求時收回」，而它沒有條件。
- 情境 A（兩個寫入者）：建立網路的請求在等節點（最長 360 s），使用者離開頁面去按另一台的「離開網路」→「下一次要求」→ 照字面收回第一個佔用 → 第一個請求的 Persist 步驟回來時不是被拒絕（紀錄沒寫、節點已經套用 = 半套狀態），就是兩個流程交錯寫。這正是第一輪 B-B2 要擋的事。
- 情境 B（永遠卡住）：如果解讀成「不收回進行中的」，那 §4.5 的「ConfirmRemoved：頁面不在 → 流程停在這裡」、原始佔用的頁面丟例外沒釋放、ConfirmCountry 對話框開著時頁面被系統回收，這些佔用永遠不結束 → 自動輪永遠不跑（首頁全部變不明）、其他操作全部被「另一個操作還在進行」擋住，只能殺 app。
- T-G3 只測「佔用者沒釋放就被銷毀 → 下一個要求成功」，兩種解讀都能過，分不出來。
- 建議：把佔用寫成明確的狀態：`進行中（有請求或寫入在飛）` 不可收回，只能等它的逾時；`停住（等使用者、沒有請求在飛）` 可以被下一個要求收回，收回 = 以「取消」結束並記一筆；原始佔用綁頁面的 `dispose`（原始佔用本來就沒有登記表持有的 controller）。每一種流程列出它的最長佔用時間。測試：請求在飛時第二個要求 → 被拒且第一個照樣寫完；停住時第二個要求 → 成功且第一個的回應函式回「不要」。

### M4 「佔用期間需要時可以在背景重新登入」沒有證據，也沒有編號的假設

- §4.4 與 §7（:589）寫「需要時可在背景重新登入（現況 `_ask` 的行為不變）」。現況的重新登入 = 重新掃描 + 連線（`nodes.dart:500`、:533 → `_login` :379）。app 在背景 / 螢幕關閉時 Android 對沒有前景服務的 app 的掃描有限制；`AndroidManifest.xml` 沒有前景服務、沒有背景藍牙相關宣告。「現況程式會去試」不等於「試得成」。
- 這一條不在 A1–A18 裡，M-1 也沒有量。T-G4 用假藍牙，永遠會過。
- 後果：建網等待中使用者按了 Home → 連線斷 → 背景重新登入掃不到 → 流程以「結果不明」結束。這個結果本身是誠實的，但設計把它寫成「照自己的逾時走完」，§6 的中斷驗收（#329「切背景後回來能接著做」）會照這個假設寫通過條件。
- 建議：加一條假設並放進 M-1（背景 / 螢幕關閉時掃描與連線是否可行）；量出來不行就把規則改成「背景中斷線 → 不重試，回前景時重新登入一次再問結果」，T-G4 跟著改。

### M5 §8 說假節點最壞只是「晚幾輪」，照設計的逾時算是「永遠輪不到」

- 情境（附近的藍牙攻擊者）：廣播同一個服務 UUID、用 5 個以上會換的位址、接受連線後不回話。自動輪對每個候選走現有 `_tryLogin`：連線等待 20 s（`nodes.dart:194`）+ 結果等待 20 s（:339）。一輪上限 90 s → 兩三個假位址就吃完一輪。逾時「不記」（§4.3.3-4），所以下一輪照樣試；攻擊者換位址更不用說。真節點只有在備忘記為 Y 時才排前面，而備忘在每次開 app、每次位址輪換（約 900 s）後是空的。兩輪後所有節點顯示「手機連不到節點」，文字還叫使用者去看電源和距離。
- 這不是全新的弱點（現況也能被拖），但現況是使用者按了才試、看得到在試；新設計把它變成首頁的常駐狀態，而 §8 明寫了一個不成立的上限。沒有對應的負向測試（T-L11 只有一支手機、位址誠實）。
- 同一張表的第三列（別人的節點的配額）：`provd/session.go:402-409` 的 20 次 / 分是**全域**、連真擁有者一起算，攻擊者自己送 20 個 msg1 就能讓擁有者被拒。這是既有行為、不在本單修，但 `unreachable(找不到)` 的說明與技術資訊應該留得下這個可能。
- 建議：(a) 自動輪用自己的每候選預算（例如連線 + 握手合計 8 s，值由 M-1 的「對不是自己的節點握手要多久」決定），不沿用 20 + 20 s；(b) 逾時的位址在本輪之後排到最後（不是「不是我的」，是「上次沒回應」）；(c) §8 改成實際的上限；(d) 加測試：3 個不回話的假位址 + 2 台真節點 → 兩輪內真節點都讀到（對照：沿用 20 + 20 s → FAIL）。

## MINOR

### m1 N5 的引用是錯的
`provd/server.go:27` 的 `ERateMax = 120 s` 是 ctl-poll 判斷 `hERate` 是否過期用的（用在 :390-393、:521），不是狀態讀取的配額。狀態的配額在 `provd/session.go:130`、:868-874（每條連線 1 次 / 秒），helper 的 `hERate` 也會轉成 E_RATE（:588）。`member_ui.dart:320` 的註解只講 1 / s。「最長 120 s」沒有依據。對設計的影響：自動輪每條連線只讀一次，連線層的 1 / s 不會觸發；E_RATE 只會來自 helper。T-H2(c) 仍然有意義，但 N5 要改對。

### m2 N3「滿了會踢掉舊的」不準確
`provd/server.go:776-819` + `session.go:155-168`：只踢「未驗證 / candidate 且不在握手中」的最舊那條；兩條都已登入或都在握手中時，新連線被**拒絕**。影響：dev + dev2 各連著（或攻擊者佔住兩個假握手槽、每 10 s 續一次）時，第三者是連不上、不是擠掉別人。R-6 的預期要對這個行為寫。

### m3 N1 的證據是一行過時的註解
`scan.dart:69-70` 引的 `bluez.go:325,666-669` 行號已經不對。直接引 `bluez.go:731-782`。

### m4 §4.3.3-3 與現有 `_tryLogin` / `_login` 不一致
現況在 `_tryLogin` 期間 `scan.pause()`（`nodes.dart:387`），設計寫「掃描持續的同時」；`requestMtu` / `readCharacteristic`（:198-199）不在 try 裡，一個候選丟例外會讓整個 `_login` 結束（:403）。自動輪必須把單一候選的失敗隔離起來，寫進 §4.7 的搬移規則，並在 T-L 加「第一個候選丟例外 → 第二個候選照樣讀到」。

### m5 §4.4「收下邀請」現況不寫任何紀錄
`nodes.dart:832-843` 只放記憶體。列它為「會寫金鑰紀錄的操作」是錯的；T-G5 用它當案例會測到不存在的寫入。

### m6 `ui/state-v1` 的小洞
- 契約對 `store.rs` 是對的 ✅（見「已查證」）。
- `seal` 走 Kotlin 的金鑰 gate（`MainActivity.kt:135` → `KeyOp.SEAL`）；gate 拒絕時 `UiState` 每次寫入都失敗。設計只寫了旗標的情況（T-O1 / T-O2）；節點表寫入失敗 = 靜默、不重試、不顯示，寫一句即可。
- 欄位 3「Rust 的句子，≤ 64 字」：`statuspage.rs:280-312` 的句子含 `join.tail()`，長度沒有上限的證明。寫明超過就截斷，T-U 加一案例。

### m7 掃描次數上限與 T14 的時間互相打架
一輪 = 1 次啟動；10 s 提前重讀 = 第 2 次；使用者按重新整理 = 第 3 次；佔用釋放後的一輪 = 第 4 次；全部可以落在 30 s 內，第 5 次被延後。「最慢約 2 分 10 秒」與 R-3 的「2 分 30 秒內」沒有算進這個延後。另外 A10 的「30 s 內 5 次」是「一般說法」，設計為它做了畫面文字（「稍等 N 秒再找節點」）與測試 T-L12；在 M-1 量出來之前這是替未驗證的假設做 UI。建議：上限留著（便宜、保守），畫面文字等 M-1 的結果再決定要不要做。

### m8 過度設計的候選

- 候選備忘的「不是我的」那一半：M1 的風險換來的是「附近有別人的節點時少握手」。只留「是我的 Y → 先試」這一半就能拿到大部分好處，而且沒有 M1 的洞。

### m9 R-1 沒有寫 F22 出現時怎麼辦

### m11 被重置 / 被別人認領的自己的節點
