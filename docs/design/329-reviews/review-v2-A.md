## 發現

### BLOCKER

**B1. 自動輪「一個候選試一次、登入成功就知道是哪一台」與登入協定不符；握手次數、備忘、一輪時間的推算全部站不住**

- 情境：手機有兩台節點 A、B（本單的標準情境），兩台都在廣播（位址 X、Y，廣播沒有身分，N7）。自動輪掃到 X。要登入就得先選一筆節點紀錄：PSK 是每台節點各自的（`psk_owner = HKDF(owner_tag_key, device_id)`）。用 A 的紀錄去試 X，而 X 其實是 B → `Msg2Undecryptable`。這時候：
  1. 照 §4.3.3「每一輪對每個 BLE 位址最多握手一次」（T-L11 鎖住）：X 這一輪不能再用 B 的紀錄試 → B 這一輪讀不到。兩台、隨機配對，第一輪有一半機率至少一台讀不到；「從來沒讀到過：第一輪就 `unreachable(找不到)`」（§4.3.4）→ 冷啟動就顯示「手機連不到節點 B」，其實 B 就在旁邊。R-1（20 次冷啟動、90 s 內兩台都有顏色）過不了。
  2. 照 §4.3.3-4 把「明確的驗證失敗」記成「不是我的」：X 被記成不是我的 → B 在位址輪換前（約 900 s）每一輪都被跳過 → 連續兩輪後首頁固定顯示連不到 B。
  3. 如果實作改成「每個位址把每一筆紀錄都試過」：握手次數是「自己的節點數 × 候選數」，§4.3.3 末段、§4.3.6、§8「別人的節點」那一列、T-L11 的數字全部不成立；A1 的「兩台約 22 s」沒有算錯誤配對的那幾次（每次的時間是 A11，未量）。
- 證據：`app/rust/batman-proto/src/loginflow.rs:1-8`（msg2 解不開的意思是 "not this node, or its PSK set not reloaded yet"，而且 "never a verdict"；候選迴圈與握手配額 "are the caller's"）、`:23-31`（`End::Msg2Undecryptable`）；`app/lib/nodes.dart:183`（`_tryLogin(id, record, ownerPub)` 一次只帶一筆紀錄，只回 `bool`）、`:376-398`（現況是「為某一台節點掃描，對每個廣播者用那一台的紀錄試」）。設計 §4.3.3-3 寫的是「對候選一個一個試（現有 `_tryLogin`）：登入成功 → 知道它是哪一台」。
- 第一輪的 A-M3 / B-M2（N×M 握手）因此沒有真的解掉：v2 把它寫成「一輪一次掃描 + 備忘」，但備忘的單位（位址）與登入的單位（位址 × 紀錄）不同。另外，剛認領完的節點在 PSK 重新載入前也回 `Msg2Undecryptable`（同一段註解），所以它**不能**當成「不是我的」的證據。
- 建議：
  1. §4.3.3 寫明候選迴圈是「位址 × 紀錄」：每個位址依序用還沒讀到的每一筆節點紀錄試；備忘記的是「（位址, device_id）試過、不是」，一個位址對**所有**自己的紀錄都失敗才是「不是我的」；剛認領 N 秒內的紀錄不記。
  2. 寫明錯誤配對之後能不能在同一條連線上換一筆紀錄再握手（節點端對握手失敗的連線怎麼處理，要附 `provd` 的 file:line）；不能的話每次都是一條新連線，時間照實算。
  3. 握手配額重算：每輪每個位址最多「自己的節點數」次；N4 的 20 次 / 分對「4 台自己的 + 鄰隊 4 台」這種集合場面夠不夠，列出算式。
  4. T-L11 改成鎖新的規則，並加一個案例：兩台自己的節點、候選順序與紀錄順序相反 → 第一輪兩台都讀到（對照：每位址只試一次 → FAIL）。
  5. M-1 的「用 02 的紀錄去登入 04」要量的是這個錯誤配對一次多久，並把結果放回 A1 的一輪時間。

### MAJOR

**M1. 首頁狀態表：已認領、還沒加入網路的節點是紅色，所以第 4 列永遠蓋過第 7、8 列；「還差一步：建立網路」幾乎到不了**

- 情境：新使用者照情境 1 新增第一台節點，回到首頁。自動輪讀到這台：節點狀態是「已認領、未加入」→ Rust 判定 `NotLinked` → 紅。首頁由上而下第一個成立的是第 4 列：bad「節點 X 沒有連上隊伍網路」，主要動作「看怎麼處理（5.2）」。使用者第一次看到自己的節點就是紅色錯誤，而且唯一的主要按鈕不是「建立網路」。第 7 列（「還差一步：建立網路，或加入隊長的網路」）要等所有節點都不是紅才輪得到；未加入的節點除了開機中（黃）之外一定是紅，所以第 7 列在主要流程裡不可達。同理：新增第二台、還沒加入時也是第 4 列蓋過第 8 列的待辦。
- 證據：`app/rust/batman-proto/src/statuspage.rs:271-277`（`color_of`：除 Linked / LinkedWeak / Booting / Linking 與三種灰以外都是 Red）；`app/rust/bridge/src/api/owner.rs` 約 `:2395-2396` 的測試斷言未加入的節點是 `("red", "7", 1, …)`，句子「這台還沒加入隊伍網路 — 請按…」。設計 §5.1 第 4 列的句子固定寫「沒有連上隊伍網路」，但紅色還包含無線電被關、沒有金鑰、無線電故障、不明代碼——這些不是「沒有連上」。
- 同一張表的其他問題（一起修）：
  - 第 1 列把「藍牙關閉」與「沒有權限」併成同一個主要動作「開啟設定」，但 §5.2 / F28 說權限是由使用者按按鈕時叫 `blePermissions`；兩個條件的動作不同（系統藍牙設定 / 權限對話框 / app 設定）。
  - 第 7 列的樣式是 busy，但它是「等使用者做事」，與 §3.2 的樣式定義不合。
  - 一台永遠連不到的節點（壞掉、送修、已重燒）讓第 5 列永遠成立，第 7–11 列永遠到不了，首頁再也不會出現「一切正常」（見 M5）。
  - 只有 `mnet` 或只有 `mpend`（等同意）的隊員手機沒有對應列：節點未加入是紅 → 等同意期間首頁一直是紅色錯誤。
  - T-H1 只測「相鄰兩列」的先後；上面這種跨列的蓋過測不到。
- 建議：把「讀到、紅、而且節點狀態是已認領未加入」從第 4 列拿出來，併進第 7 列（沒有網路紀錄）或新的一列（有網路紀錄、這台還沒加入 → 主要動作「加入網路」；有 `mpend` → 「等隊長同意」），而且排在一般的紅之前；第 4 列的句子直接用該台的 Rust 句子（多台才用「有 N 台節點有問題」）；第 1 列拆成兩列；T-H1 加「未加入的節點 + 沒有網路紀錄 → 建立網路是主要動作」的案例（對照：照 v2 的順序 → FAIL）。

**M2. 「一輪不解開任何 net / mnet 紀錄」（§4.3.3-8、§8、T-H5）與「每一輪用 `updateHint` 產生待辦」（§5.1、T-H3）互相矛盾；名稱表也不夠 `statusView` 用**

- 情境：隊員的手機，隊長剛移除了別人。自動輪讀到自己的節點，要算待辦「節點還沒換到新的網路密碼」。`updateHint(recordPlain, member)` 的第一個參數就是解開的 net / mnet 紀錄明文（內含網路密碼）。照 T-H5（unseal 次數 = 0）就算不出來；照 T-H3（每一輪都有）就一定要解開。兩個測試不可能同時通過。§8「網路紀錄（含網路密碼）不在每輪解開」因此是不成立的安全宣稱。
- 證據：`app/rust/bridge/src/api/owner.rs:1040`（`update_hint` 收 `record_plain`）；`app/lib/nodes.dart:1087-1107`（現況每次讀狀態都讀 `net/<id>` 或 `mnet/<id>` 的明文再傳給 `teamView` / `updateHint`）。另外 `_netNames` 回傳的不只是名稱：`(names, hasNet, hasMnet, appliedNets, entryMnets)`；`hasNet / hasMnet` 決定 `statusView` 的句子（哪一顆加入按鈕），`appliedNets / entryMnets` 決定離開網路的確認文字。§4.3.3-8 寫「只留網路代號 → 名稱」。
- 建議：二選一並改掉另一邊。(a) 承認每輪要解開「這台節點所在的那一個網路」的一筆紀錄，§8 的代價段照實寫、T-H5 改成「每輪每台最多解開一筆、而且是節點回報的那個網路」；或 (b) `updateHint` 待辦改成只在節點頁算，§5.1 與 T-H3 跟著改。名稱表的內容改成 `_netNames` 現有的五個欄位（都不是秘密）。

**M3. 原始佔用在頁面 `dispose` 時被收回，但認領（與舊控制台）的非同步工作還在跑；認領寫紀錄也不經「紀錄寫入包裝」**

- 情境：使用者在 3.4 等認領，按返回（`ClaimPage` 沒有 PopScope）。`dispose()` 只取消恢復（`_recovery?.cancel()`），進行中的認領 / finish 不中斷。照 §4.4「佔用者被銷毀而沒有釋放 → 登記表在它的 `dispose` 或下一次要求時收回」，佔用立刻釋放 → `NodeLink` 開始自動輪（開掃描、連線），同時認領的 async 還握著它的連線、接著還會寫 `node/` 與刪 `claim-pending/`。結果是下列其中一種，設計沒有說是哪一種：(1) `BleGate` 同時兩條連線（違反自己的不變量）；(2) 憑證失效，`BleGate` 拒絕認領後續的寫入 → 認領在「claim 已送出、finish 還沒送」被打斷，節點進入要恢復的狀態（恢復 = 換 root 密碼、中斷所有連線）；(3) 認領繼續寫紀錄，而這時「沒有佔用」→ 與 §4.1「沒有佔用就沒有人能寫」矛盾。舊版控制台同理：`dispose()` 只有 `_drop()`，進行中的步驟（最長 360 s）裡的 Persist 仍會寫。
- 證據：`app/lib/claim.dart:86-89`（dispose）、全檔沒有 `PopScope`；認領的紀錄寫入走 `ClaimRecords`，不是 §4.5 包裝的那條路；設計 §5.3 寫「`ClaimPage` 與 `ClaimRecovery` 改用 `BleGate`，其餘邏輯不變」，§4.5 的包裝只列了 Persist 步驟與離線操作。
- 建議：原始佔用的釋放條件改成「佔用者回報它的非同步工作結束」而不是 `dispose`（頁面關掉時佔用留著，首頁顯示「另一個操作還在進行：新增節點」直到它結束或逾時）；或者認領進行中加 PopScope（這是邏輯變更，要寫進 §5.3 並從「其餘邏輯不變」拿掉）。§4.1 / §4.5 把 `ClaimRecords` 的寫入列進來，說清楚由誰檢查佔用。T-G3 加一個案例：認領的 finish 還在等回答時頁面被關 → 沒有自動輪開始、紀錄照樣寫完（對照：dispose 就收回 → `BleGate` 計數 2 或紀錄沒寫完 → FAIL）。

**M4. 啟動檢查「部分可用」的結果在新畫面沒有位置；別人的手機最容易踩到**

- 情境：把 dev 版交給別人試用（§2.1）。對方手機的擁有者金鑰是硬體、但復原 / 成員金鑰只有軟體保護（沒有 StrongBox 的機型很常見）。現況：啟動頁每種被拒絕的用途各一行原因、一行「只適合開發使用」的警告、「認領節點」按鈕在不能認領時是灰的；認領時還有一個 dev 專用確認框。v2 只有兩種結果：通過 → 歡迎 / 首頁；整個 app 不可用 → 2.4。部分拒絕的那幾行、警告、灰掉的入口、以及 app 不可用時的「這些節點需要重燒卡回收」清單都沒有去處。首頁第 2 列無條件給「新增節點」。
- 證據：`app/lib/main.dart:96-97`（逐用途的拒絕行、`softOwnerEnc` 警告）、`:178-183`（`_keys.claim` 為 false 時按鈕停用）、`:87-93`、`:162-165`（app 不可用時的節點清單）。設計 §5.2 只寫 2.4 沿用現有 gate 的判斷與文字。
- 建議：§5.1 / §5.2 加一段「金鑰用途被拒絕時」：哪些入口不出現或停用、原因顯示在哪（按下去的位置）、警告行放哪（首頁一行 + 技術資訊）、app 不可用時的節點清單放在 2.4。T-H4 加「不能認領 → 新增節點入口停用並顯示原因」的案例。

**M5. 一般使用者拿不掉一台節點；情境 9 的寫法與現有對話框的文字相反**

- 情境 a：一台節點壞了、送修、或被重燒給別人。它的 `node/` 紀錄還在 → 每一輪都找不到 → 首頁第 5 列永遠是 warn「手機連不到節點 X」，「一切正常」不會再出現；每一輪還多花一個掃描窗等它。唯一的移除方式是開發者選項裡的「忘記節點」，field 版沒有開發者選項（§2.3 自己寫「一般使用者在本單沒有移除節點的方式」）。這直接抵觸需求 3（清楚的節點狀態）與「不顯示不必要的東西」。
- 情境 b：情境 9 寫「離開網路 → 之後首頁新增節點 → 覆寫詢問」。離開網路不會解除認領；覆寫詢問的現有文字是「只有在你剛把這台節點重置回未認領時才重新認領…」（`claim.dart:42-43`），而重置不在 app 裡。照情境 9 走的使用者會被自己 app 的對話框告知不該這樣做。
- 建議：把「從這支手機移除這台節點」放進節點頁（危險按鈕 + 確認，文字寫清楚這不會重置節點、之後要重新新增得先由維修人員重置）——現有 `_forgetNode` 已經有，這只是入口位置，不是新功能。情境 9 改寫成實際可行的路徑。若維持不做，§11 要列成使用者決定（它影響 #329 需求 1、3），而不是只在 §2.3 的表裡一句話。

**M6. 待辦「上次新增節點沒有做完」：來源會誤報，而且它指到的 3.7 在現況是 dev 專用、帶破壞性副作用的恢復**

- 情境 a（誤報）：認領成功、`node/` 已寫入，但刪 `claim-pending/` 那一步沒成功（現有的 `PENDING_KEPT` 情況，`claim.dart:430`）。§5.1 的來源是「有 `claim-pending/<id>`」→ 首頁一直顯示「上次新增節點沒有做完」，但節點其實好好的。
- 情境 b：使用者點待辦進 3.7。§5.3 寫「用現有 claim-pending 恢復，邏輯不變」。現有的不帶 QR 恢復只在 devTrust 版本出現（`claim.dart:96`、`:509`），而且恢復會「更換這台節點的 root 密碼，並中斷它目前所有的連線（包含隊友手機的）」（`:120`），要先確認。3.7 的規格沒有提這個確認、沒有說 field 版怎麼辦（待辦出現但沒有入口？），也沒有說 claim 根本沒送到節點時該引導重新掃 QR。
- 建議：來源改成「有 `claim-pending/<id>` 而且**沒有**同一個 id 的 `node/`」；3.7 寫明：確認框的文字（沿用現有）、非 devTrust 版本的行為、恢復失敗的下一步。T-H3 加 `PENDING_KEPT` 的案例。

**M8. 安全：假廣播者能做到的不只是「晚幾輪」；§8 的上限推算是錯的，也沒有對應的負向測試**

- 情境：附近的攻擊者用三個以上的位址廣播 provd 的服務 UUID，連上後不回握手（或每輪換位址）。自動輪對每個候選的上限是連線 15–20 s + 等回答 20 s，整輪上限 90 s → 兩、三個假候選就吃掉整輪。備忘只記「明確的驗證失敗」，逾時不記；攻擊者每輪換位址時備忘本來就沒用。真節點連續兩輪輪不到 → §4.3.4 判成 `unreachable(找不到)`，首頁顯示「手機連不到節點 X：可能沒開機、離太遠…」——這是一句**錯的診斷**，不是 §8 寫的「晚幾輪」。攻擊者不需要任何金鑰，成本是一台會廣播的裝置，效果是整隊的 app 都說節點連不到（需求 3）。現況沒有這個面（使用者點了才連）。
- 證據：設計 §8「假節點能做到的最壞情況 = 讓真節點晚幾輪才讀到」對 §4.3.3（整輪上限）、§4.3.4（連續兩輪 → unreachable）；`app/lib/nodes.dart:183-200`（連線逾時 15 s / 等 connected 20 s）。§9 沒有任何測試是「有不回應的候選時，真節點仍在 N 輪內讀到」。
- 建議：自動輪用自己的短逾時（數字由 M-1 實測決定）；候選排序：備忘記為自己的 → 新位址 → 上一輪逾時過的放最後；「輪不到」（候選太多、整輪用完）與「掃描窗內沒有任何候選」分成兩種原因，前者不說節點沒開機；加測試：三個不回應的假候選 + 兩台真節點 → 兩輪內兩台都讀到（對照：不排序 / 不縮逾時 → FAIL）。§8 那一列照實改寫。
