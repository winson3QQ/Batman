## 發現

### MAJOR

**M1. `ui/state-v1`「損壞就下次寫入覆蓋」與紀錄庫的實作相反 — 檔頭壞掉後永遠寫不進去**
- 情境：寫入中斷電或檔案被截短（長度 0、magic 不對、檔頭版本不是現版）。之後每次啟動 `UiState` 當成空的（對），但每次寫入都被拒絕：歡迎頁每次都出現（全新安裝者）、暱稱存不住、勾選存不住，而且沒有任何出路。
- 證據：✅ `rust/batman-proto/src/store.rs:106-112`：`write` 在現有檔讀出 `UnknownVersion` 或 `NotARecord` 時**拒絕覆蓋**；`write_cas`（:136-145）走同一條。設計 §4.3「解不開 / 格式錯 / 版本不認得 → 當成不存在，下一次寫入時覆蓋」、§7「損壞 → 下次寫入覆蓋」只對「檔頭正常、AES-GCM 解不開或 CBOR 壞」成立。
- 修法：§4.3 分兩種寫清楚。(a) 檔頭正常但解不開 / 內文壞：用讀到的 generation 做 CAS 覆蓋。(b) `NotARecord` / `UnknownVersion`：`UiState` 先 `storeRemove`（✅ 已存在，`rust/bridge/src/api/claim.rs:87`）再寫。T-U2 要有「截短成 0 位元組 → 之後寫入成功且重載讀得回」這一項，負向對照 = 拿掉 remove → FAIL。

**M2. 擁有權表漏了第二、第三個連線擁有者：舊版控制台與「附近的節點」**
- 情境：PR 1–4 期間（T7）舊 `NodesPage` 留在開發者選項。它有自己的 `FlutterReactiveBle` 與自己的 `OwnerSession`。使用者在舊控制台做一個 360 s 的加入；app 切到背景再回來 ≥ 30 s，或藍牙重開 → `NodeLink` 自動讀一輪，對同一台節點再開一條連線 / 登入。兩個 session 擁有者，正是 §4.1 說「沒有」的情況。`ScanPage` 也自己連線。
- 證據：✅ `lib/nodes.dart:69`、`lib/scan.dart:29`、`:80`、`lib/claim.dart:65`（三個各自的 BLE 實例）。§4.1 只替 `ClaimPage` 寫了讓出規則；§4.2-5 只提認領與軟體更新。
- 修法：§4.1 列出所有會自己連線的頁面（ClaimPage 含其內的 ClaimRecovery `claim.dart:467`、舊控制台、ScanPage），規則統一成一條：這些 route 在堆疊上時 `NodeLink` 已放掉連線**且所有自動觸發（啟動、回前景、藍牙重開、斷線重試）都停用**；`release()` 要等到斷線完成才回。T-L7 對每一個這種頁面各測一次。

**M3. 自動讀一輪 × 「逐台試每個 provd 廣播者」：隊伍集合時會慢到誤報，位址提示救不了**
- 情境（#329 情境 1、4）：桌上有自己的 2–3 台加隊友的數台。已認領節點的廣播不帶 id，所以找節點 X = 對每個廣播 provd UUID 的裝置依序連線、送 msg1、等它失敗。每個錯的候選最多耗 15 s 連線 + 20 s 等回應（⚠️ 數字取自我先前讀的 `_tryLogin` :183-350）。60 s 的視窗試不到兩三個錯的就用完 → 首頁出現「手機連不到節點 X」（warn），其實節點就在手邊。每台節點各自重掃一次，一輪最壞 = N × 60 s；§4.2-5 的「在兩台之間讓出」代表使用者按下操作後最多還要等 60 s。
- 證據：✅ `lib/nodes.dart:3` 的註解寫明已認領節點廣播是 RPA、只有 UUID 清單；✅ `:378-396` 依序試、試過的不再試、視窗 60 s。A1「> 20 s 就逐台顯示進度」只在兩台、沒有別人節點的桌上量。A7 寫「未查證」，但原始碼自己就說是 RPA → §4.2-7 的 BLE 位址提示在位址輪替後無效，卻多存了一個識別碼、多一個機制（違反「只做必要的修改」）。
- 另一個沒有證據的依賴：現在每次開 app / 回前景都會對**隊友的節點**送失敗的登入。節點端對失敗握手有沒有計數、限速、記 log，設計沒有引用任何 provd 原始碼或真機輸出。「應該沒事」不是證據。
- 修法：(1) 設計核准前用真機量：至少 3 台在廣播（含一台不是自己的）時讀一輪的總時間，以及一次失敗登入在節點端留下什麼（log、計數）。(2) 一輪只掃一次，這一輪內記住「這個 BLE id 已登入成節點 Y / 對節點 X 已失敗」，找下一台時跳過 — 只在記憶體、不落地。(3) 使用者操作要能立刻打斷目前的候選，不是等到兩台之間。(4) 拿掉欄位 5（位址提示），或拿真機擷取證明位址在兩次開 app 之間穩定。(5) T-S3 加一項：3 個假廣播者 + 1 台真的 → 真的在界限內被讀到；負向對照 = 拿掉跳過規則 → 超時 FAIL。

**M4. §5.1 待辦與「還差 N 步」的資料來源寫錯或不存在**
- 「節點還沒換到新的網路密碼 ← 現有 `updateHint`，每次載入首頁從紀錄重新算」：✅ `rust/bridge/src/api/owner.rs:1040` `update_hint(&self, …)` 是 **session 方法**，要用上一次狀態頁讀到的資料；沒有登入就算不出來。只能在該節點 `fresh` 之後才有。
- 「節點加入網路沒有做完 ← 網路紀錄裡有加入中的節點」：要在每次載入首頁時解開每一筆 `net/` 紀錄（明文含網路秘密）到 Dart 記憶體。現況只在使用者進那個流程時才解。這是安全面的改變，§8 沒寫。
- 「Wi-Fi 還沒設（僅第一次）」：沒有資料來源。讀設定要 session；`ui/state-v1` 的六個欄位裡也沒有這個旗標。
- 修法：待辦表每一列寫明「何時能算（只靠紀錄 / 要 fresh 讀取）」「要解開哪些紀錄」；Wi-Fi 那一步補欄位或刪掉；T-H3 的四種來源各自要有「還沒 fresh 時不顯示也不誤顯示」的判定。

**M5. §5.4 勾多台建網漏掉現有流程的必經步驟，時間上限也對不上**
- 現況一台節點加入要經過：登入（最多 60 s）→ 國家不同時的確認對話框 →「之前移除過嗎」的詢問 → 送出（360 s 上限）→ 連線檢查（每 10 s、最多 120 s，期間佔住 `_busy`）；建立者還有獨立的「確認網路」步驟，沒確認前其他台加入會被 Rust 拒絕。設計只寫「對第一台做建立，其餘逐台做加入」。
- 證據：✅ `lib/nodes.dart:457-472`（建立）、`:604-649`（加入與兩個詢問）、`:665-694`（連線檢查）、`:1173-1178`（確認網路）、`lib/member_ui.dart:231`（360 s）。
- 時間：設計寫「最多 6 分鐘」，那是**每一台**；#329 寫「建網最多 3 分鐘」；現有畫面文字也寫 3 分鐘而逾時是 360 s。三台最壞 = 3 ×（60 + 360 + 120）s，畫面要怎麼說沒寫。
- 修法：寫一張逐台步驟表（步驟、誰觸發、上限、畫面文字、失敗後這台與其餘台的狀態、中斷後從哪裡接），把確認網路放進去；3 分鐘與 6 分鐘對齊成一個有依據的數字。

**M6. T8「不改 Rust 文字」做不到 #329 的文字要求**
- 情境：錯誤頁顯示 Rust 的句子。`error_text` 把「（代碼 N，原因 M，verb）」嵌在同一句裡 → 「代碼只進技術資訊」做不到；Rust / Dart 現有句子用的是新介面沒有的按鈕名與 §3.3 禁用詞。
- 證據：✅ `rust/bridge/src/api/owner.rs:602-626`；✅ `rust/bridge/src/api/rekey.rs:345`「請網主讓你的節點離開網路…」（用詞表規定「隊長」）；✅ `lib/nodes.dart:48`「稍後在這台按「繼續加入」」；✅ `lib/say.dart:59-60`「未認領 / 已認領」（用詞表規定「新增節點」）；✅ `rust/batman-proto/src/teamview.rs:262`「請按「重新整理」」。T-C4 只擋 `#數字`、`StrongBox` 等，擋不到這些。
- 修法：二選一並寫進設計：(a) 列出要改的字串清單，Rust 只改文字、既有測試跟著改字串；或 (b) Rust 多回一個結構（句子、代碼分開）。T-C4 加「用詞表右欄的詞與舊按鈕名不出現在任何頁面」，負向對照 = 放回「網主」→ FAIL。

**M7. 移除成員：把現有的「事前必勾」誤認成「事後全隊換好」，而且勾選沒有綁版本**
- 現有必勾的文字是「全隊的節點都已更新到新版軟體」，是**開始移除之前**的前置條件 5，沒勾 Rust 直接拒絕。設計 §5.7 寫「確認只一次…之後進檢查清單…『全隊都換好了』才能按下一步（沿用現有必勾的規則）」— 兩件事不同。照寫的結果只有兩種：前置條件被 app 默默代勾（拿掉一道破壞性操作的保護，也違反 §4.4「gate 一個都不改」），或移除永遠被拒。
- 證據：✅ `rust/bridge/src/api/rekey.rs:180-182`、`:254-257`；`lib/nodes.dart:1318` 起的對話框。
- 勾選存在 `{net_id → {成員雜湊 → {已交出, 已換好}}}`，沒有金鑰版本。第二次移除時上一輪的「已換好」還在 → 隊長以為交過了 → 那位隊員留在舊密碼、掉出網路。現況 `_copied`（`nodes.dart:123`）刻意只活在這次執行。
- 修法：前置勾選保留成獨立一步、文字原樣；檢查清單以（net_id, 新密碼版本）為鍵，版本變了就清空；清單頁寫明「這是你自己的記錄，app 無法確認對方真的換好」；補測試：第二次移除時清單是空的（負向對照 = 鍵不含版本 → FAIL）。

**M8. 軟體更新的預期重開機會被 `NodeLink` 當成掉線；軟體更新的狀態也不在擁有權表裡**
- 情境：套用更新後節點重開數分鐘。§4.2-8：連線中斷 → 該節點 `unreachable`、首頁 warn「手機連不到節點 X」、自動重試一次（必定失敗）。使用者在一個預期中的重開機看到警示。離開網路、建網後節點重設網路時同理。
- 證據：✅ `lib/nodes.dart:1521-1577`：`_sw`、`_swHold`、`_swNode` 留在頁面 state、跨頁面開關存活，更新頁經 `ask` callback 共用 owner session（所以它不是「自己的連線」，§4.2-5 的「暫停」不夠描述）。§4.1 沒有列這些，也沒有列 `ReadClock`（`member_ui.dart:320-`）、記憶體中的邀請（`nodes.dart:109-110`）、Kotlin `SwUpload` 的 Wi-Fi 連線（`MainActivity.kt:89-90`）。
- 修法：§4.1 補這些資源與擁有者；`NodeLink` 加一個「預期離線到某時間」的狀態（擁有者 = 軟體更新 controller），這段期間顯示 busy 而不是 warn，逾時才轉 warn；§7 加「節點因我們的操作而重開」一列與測試。

**M9. 測試表不符合「每個測試都有負向對照」，且 #329 的截圖驗收被換掉卻沒有列為使用者決定**
- §9 自己寫「每個測試都有負向對照」，但 T-H4、T-L3、T-L5、T-U1、T-U3、T-U5、T-O1、T-O2、T-V1 的負向對照欄是「—」或「同上類推」。這些正好是升級不顯示歡迎頁、CAS、回前景 30 s 等會靜靜壞掉的行為。
- T-S2「內容不含秘密欄位」無法失敗（要怎麼證明不含）。改成結構性判定：`UiState` 編碼器只接受封閉的型別；測試編一筆全滿的狀態，斷言鍵集合恰為 {1..6}、每個值的型別與長度上限；負向對照 = 多塞一個欄位 → FAIL。
- #329 做法 4 與驗收清單要求「用截圖做前後對照並加入常規測試」「P1、P2 逐項截圖對照」「一致性檢查表逐畫面截圖勾核」。T9 改成 widget 判定、截圖只當附件。理由可以成立，但這是改驗收條件，要進 §11 讓使用者決定，不能只放在取捨表。
- 修法：每列補真的負向對照；T9 進 §11。

### MINOR

**m1. F16「畫面鎖直向」是錯的。** ✅ `AndroidManifest.xml:59` 的 `screenOrientation="portrait"` 屬於 `QrScanActivity`（:55-60）；`MainActivity` 沒有；`lib/` 裡沒有 `setPreferredOrientations`。§7「畫面旋轉：鎖直向 / 不適用」因此不成立。修法：要嘛替 MainActivity 加鎖直向（這是一個改動，寫進設計），要嘛 T-C2 加橫向渲染。

**m2. 名稱長度與 Rust 不一致。** 設計寫隊員名稱「1–24 字」；✅ `rust/batman-proto/src/invite.rs:28`、`:115-118` 是 ≤ 32 個 UTF-8 **位元組**（約 10 個中文字）。畫面放行的名字會在後面被 Rust 拒絕。現有欄位 `maxLength: 32`（`nodes.dart:1695`）也是算字不算位元組。修法：畫面以位元組數驗證，T-V1 加「10 個中文字過、11 個擋」。

**m3. 自動登入的安全面寫得太輕。** ✅ 金鑰沒有綁使用者驗證（`Keys.kt:80-95` 沒有 `setUserAuthenticationRequired`），✅ `open` 不經 gate（`MainActivity.kt:71-72`、`:130-134`），所以自動登入不會跳提示，「與現況相同的權限」大致成立。但改變是：每次啟動 / 回前景，app 不經任何點擊就解開每一台節點的紀錄（含 K、root 密碼）並用擁有者金鑰簽章；現況只對被點的那一台。§8 應寫出這個差異與處理（一次只解一台、用完即丟、不進快取）。✅ msg1 是 NXpsk0、PSK 由紀錄的 owner_tag_key 推得（`loginflow.rs:61-64`），假節點拿不到身分資訊，A2 成立。

**m4. `NodeLink` 讀完一輪後「保持連線」沒有上限。** 切到背景後連線留多久沒寫（§4.2-4 只管「不開始新的」）。⚠️ 我沒有 provd 的證據說明一台節點能同時接幾個 central；若只有一個，前景掛著的 app 會擋住同一台節點的其他操作者。請補證據，並定背景多久後放掉。

**m5. `ui/state-v1` 的寫入頻率。** 每讀完一台就整筆替換一次（Keystore seal + CAS）。請定成一輪結束寫一次，並寫明 `NodeLink` 產生狀態、`UiState` 是唯一寫入者的交接方式。

**m6. 狀態與首頁表的漏洞。** §4.2-8「變 `unreachable` 或回到 `cached`」沒說何時是哪一個；首頁表沒有「有的 fresh、有的還在 connecting」的列；「還差 N 步」排在 `unreachable` 之上，會蓋掉連不到的警示。
