## D4 驗證：pending 的 net 紀錄能不能有其他成員

逐一查了所有能把成員項寫進 net 紀錄的路徑：

| 路徑 | 對 pending 的處理 | 證據 |
|---|---|---|
| 建立（`NetRec::made`） | 沒有 key 11；`members()` 從 key 8 推出建立者一人（`Joining`） | ✅ netrec.rs:375-377、:391-396 |
| 隊長加入（join2） | `rec.state != APPLIED` → `Refused(Pre::NotApplied)`，什麼都不寫 | ✅ join2flow.rs:340-342 |
| 邀請 / 同意遠端隊員（member-join） | `admin_preconditions` 要求 APPLIED | ✅ invite.rs:185-187；approve.rs:181 |
| 移除 / 換金鑰（rekey） | 要求 APPLIED | ✅ rekey.rs:98-99、:543-544 |
| 檢查網路（`confirm`） | 只把建立者升成 Applied，「No member entry is ever added here」 | ✅ netrec.rs:509-535 |
| 忘記加入中的成員 | 只刪不加；不准刪 pending 的建立者 | ✅ netrec.rs:541-554 |
| 隊員匯入（mnet） | 寫 `mnet/`，不碰 `net/` | ✅ member.rs:268-290 |

結論：✅ 成立。在 app 這一側，pending 的網路只會有建立者一台。所以建一個新的網路不會讓**別的節點**分裂。剩下的風險只在建立者那一台身上，見 M2。

### M1　加入模式的閘門因為「有 mnet / mpend」或「有一筆打不開」而拒絕：手機同時是隊長和隊員（或留著一筆申請）時，新頁面永遠加入不了

**情境**
- 隊長 L 曾經掃過別人的邀請、送出申請（留下 `mpend/`），後來自己建了網路 N（applied）。也可能 L 本來就是別隊的隊員（有 `mnet/`），同時自己帶一個小隊。
- L 新增 02 → 首頁第 6 列。`NetIndex` 判定「有已套用的 net」→「加入網路」→ 4.1。4.1 的表裡，「有 net、其中有打得開而且已套用的」排在「只有 mnet / mpend」前面，所以顯示加入表單。
- 按「開始」→ 閘門表第 2 列「有 mnet 或 mpend → 不開始，顯示隊員的句子（兩種表單都一樣）」。每次都被拒，而且顯示的句子還是講「隊員」的。
- field 版沒有舊控制台，這台節點**永遠加入不了**。mpend 要到 PR 5 才有新的丟掉方式。

**證據**
- ✅ 計畫 §2.3 4.1 表（:155-162）與閘門表（:175-182）：閘門第 2 列沒有寫「只有」。v2 審查 D 提出的原文是「**只有** mnet 或 mpend → 不開始」（review-pr3-plan-v2-D.md:131）。
- ✅ 上層設計 §5.1 第 6 列（329-app-uiux.md:673）：「手機有 net 紀錄 →『加入網路』」，也就是 net 優先。home_logic.dart:34「net wins over mnet over mpend」。T-N2（:954）也是「有 net 紀錄 → 隊長的加入」。
- ✅ 兩種紀錄並存是現有程式明確支援的：nodes.dart:1781-1786 `joinChoice` 的 `(true, true) => JoinChoice.ask`，註解寫「PR 2 review B-M2: neither path may vanish」。
- ✅ 打不開的那一筆：上層設計 §4.3.8（329-app-uiux.md:539）寫「那一筆不進表……用到它的地方當成沒有這筆紀錄」，T-L19 也是。計畫的閘門卻是「有 net、其中有打不開的 → 不開始」，加入模式也一樣。這一點和設計不同，§4 沒有列。另外，4.1 表也沒有「有打得開的已套用 + 一筆打不開」這一列（會顯示加入表單，閘門又拒絕），也沒有「pending + 打不開」這一列。

**修法**
- 閘門依模式分開寫：
  - **加入模式**只看目標：目標仍在、打得開、已套用 → 加入。mnet / mpend / 其他打不開的紀錄都不影響（照設計 §4.3.8）。
  - **建立模式**維持現狀：有 mnet / mpend → 不建立；有打不開的 → 不建立（fail-closed 是對的，因為打不開的那筆可能是已套用的網路）。
- 4.1 表補上上面兩個缺的組合，和閘門一一對應。
- 把「打不開的那筆在建立模式下才擋」寫進 §4 成為 D8。
- 測試：net(applied) + mpend → 加入照常開始；net(applied) + mnet → 同上；net(applied) + 一筆打不開 → 加入照常、建立被擋。
- 改壞：加入模式改回「有 mnet / mpend 就不開始」→ FAIL。

### M2　D4 的「套用中的建立者不能當新的建立者」沒有根據；多筆 pending 時「檢查網路」用修改時間挑那一筆，會漏掉節點真正所在的網路

**情境**（§8 的情境 2，真實的現場路徑）
1. 04 建網路 A 時拔電。A 停在 pending。
2. 04 開機後還在套用 A（試用開機或設定中）：info key 10 還不存在，key 11 = true。
3. 使用者按「檢查網路」，得到 InProgress（「還在設定中」）。§2.8 照樣在 Rust 的句子下面給次要按鈕「建立新的網路」：計畫寫「不是 applied → 顯示 Rust 的句子，加次要按鈕」，沒有分狀態。
4. 使用者按下去 → 4.1 建立表單。04 最近一次讀到的是 key 10 不存在。如果 status key 1 = 1，`notInNetwork` 就成立（home_logic.dart:30），04 會是**預設的建立者**（「預設是清單上第一台」）。
5. 對一台正在套用 A 的節點送出建立 B。節點怎麼處理，本 repo 查不到（⚠️ firmware）。結果可能是：
   - 節點拒絕 → 手機多一筆 pending B；
   - 節點改套 B；
   - 節點最後還是停在 A。
6. 如果最後停在 A，手機上有 pending A 和 pending B。§2.7 的待辦只列「修改時間最新」的 B，§2.5 第 6 列與 4.1 的「檢查網路」沒有寫是哪一筆。A 永遠沒機會被檢查。04 在 4.1 裡又是「在網路裡 → 不能當建立者」。
7. 結果：使用者只能一直「建立新的網路」，在 field 版要等 PR 4 的「離開網路」才走得出來。

**證據**
- ✅ 套用中的定義：flow.rs:169-171，key 10 不存在、key 11 = true → `JoinState::InProgress`。也就是說，**套用中的節點沒有網路編號**。
- ✅ 狀態頁本來就有這種情況的句子：statuspage.rs 的 `UNFINISHED_LEFT` 是「key 11 = true，而且 key 10 不存在」時顯示的。
- ✅ 計畫的「在網路裡」只看 `notInNetwork = view.nodeState == 1`（home_logic.dart:30）和 `netId`（P24）。計畫 §2.3 的理由（:184）寫「讀到在網路裡 → 不能當建立者」，但沒有附證據說明套用中的節點 status key 1 不是 1。⚠️ status key 1 在套用中的值是節點端的行為，本 repo 查不到。
- ✅ 要擋這種情況，不用改 Rust：`StatusView.unfinished` / `unfinished_under_verdict`（owner.rs:388-391、:2204-2209）已經是 key 11 = true 時的欄位。
- ✅ 計畫 §2.7（:290）用「檔案修改時間最新」挑一筆；§2.8 只寫「那一筆 pending net」。
- 這正是 E-B1 / F-B1 原本擔心的「結果不明時重新建立」。D4 把影響縮小到建立者自己這一台（上一節已驗證），但沒有擋住它發生。

**修法**（不改 Rust、不加新機制）
1. 建立者的條件改成「讀到 `nodeState == 1`，**而且** `unfinished` 是空的」。`unfinished` 不空時顯示「這台還有沒完成的網路變更，先等一下再檢查」，也不能當建立者。加入模式照舊，join2 自己會處理忙碌的情況。
2. §2.8 的「建立新的網路」只在**這一次檢查**讀到的 `StatusView` 沒有 `unfinished`、也沒有 `netId` 時才顯示。這兩個值在 session 的狀態頁上都有，不需要 Rust 回結構化的 `net_state`。InProgress 或讀不到時只給「等一下再檢查」。
3. 多筆 pending 時，挑對象的順序：
   - 先找手機上某台節點讀到的 `netId` 等於某一筆 pending 的 `net_id` 的，那一筆就是「建立網路沒有確認完」的對象，檢查也對它做；
   - 找不到，才用修改時間最新的那一筆。

   §2.5 第 6 列、4.1、§2.8 都寫明用這個規則。
4. 測試：
   - (a) 建立者讀到 `unfinished` → 不能當建立者；
   - (b) pending A、B，04 讀到 `netId` = A → 待辦與檢查的對象是 A。
5. 改壞：拿掉 `unfinished` 條件 → (a) FAIL；改回只看修改時間 → (b) FAIL。
6. §6 照實寫：建立新網路時，如果建立者正在套用舊網路，節點的行為還沒在真機量過（⚠️）。§8 情境 2 加一條「拔電後馬上（套用中）按檢查」，量一次節點回的狀態頁。

### M3　「4.1 跟著讀取更新」要靠 `NodeLink` 在 4.1 上真的會讀，但計畫沒有指定 4.1 的 `Page`

**情境**：第一次使用的隊長新增 04 → `ClaimDone` → 3.2 暱稱 → 3.5 → 4.1 建立表單。這時 04 還沒被讀到（佔用釋放後 6 s 才開始下一輪，剛認領完約 4–10 s 會解不開，N9）。計畫的解法是 4.1 訂閱 `NodeLink.changed`。

**證據**
- ✅ core.dart:169 `_eligible => started && fg && !lease && page != Page.other`。`Page.other` 時完全不排讀取。
- ✅ 現有慣例：首頁開設定頁前呼叫 `a.link.setPage(nl.Page.other)`（home_page.dart:243），註解寫「no reads while the settings are on screen（T-L8）」。上層設計 T-L8（329-app-uiux.md:927）寫「離開首頁（進設定頁）就不排」。
- ✅ 計畫全文沒有提到 4.1、3.2、3.5、§2.8 頁要設成哪一個 `Page`（`grep setPage|Page\.` 0 筆）。
- 後果：
  - 照慣例設成 `Page.other` → 04 永遠讀不到，`開始` 按不下去，G-M3 原樣回來。
  - 不設定（停在 `Page.home`）→ 會讀，但讀的是所有節點、每 60 s 一輪。剛好遇到 N9 解不開時，可能要等到下一輪，約 60 s。
- 計畫 §7 第 5 步的測試寫「4.1 跟著讀取更新（剛認領完的節點讀到後可當建立者）」，用假 `NodeLink` 送出 changed，**不管 `Page` 怎麼設都會通過**（記憶裡「stub 要照真工具輸出格式」的同類問題）。

**修法**
- 寫明 4.1 的 `Page`：建議從 `ClaimDone`、待辦、節點頁進來時用 `Page.node`（指那一台；core.dart:196 X33「進節點頁就讀」，立刻讀一次），其他入口用 `Page.home`。3.2 / 3.5 / 3.6 同理。離開時還原。
- 測試要用真的 `NodeLinkCore`（sim 時鐘 + 假 `BleGate`，同 T-L17 的接法）：
  - 從 `ClaimDone` 進 4.1 → 不碰時鐘以外的東西，≤ 20 s 內那一台變成可當建立者；
  - 改壞：4.1 設成 `Page.other` → FAIL。

## MINOR

1. **4.1 的「不解密」和表格互相矛盾。** §2.3（:153）寫 4.1 開頁時「不解密、不拿佔用」，但表格的每一列都要知道「打得開、已套用」。要寫明這些來自哪裡：

   - 用 `NetIndex` 最新一次的結果，計算中時顯示「正在讀取網路紀錄」。

   閘門在佔用下自己解密，這部分沒問題。
2. **§2.8 / 結果頁 →「建立新的網路」→ 4.1 的佔用交接沒寫。** §2.8 頁和 `NetworkRun` 的結果頁都持有 session 佔用（「離開頁面時放佔用」）。如果用 push 打開 4.1，舊頁還在堆疊底下，佔用沒放。4.1 按「開始」會得到「另一個操作還在進行」。這和 G-m4 是同一類問題，只是換成新按鈕。
   - 修法：先放佔用，再 `pushReplacement` 到 4.1。
   - 測試：§2.8 → 建立新的網路 → 開始 → 拿得到佔用。
3. **G-m1 沒有處理：重讀的時機。** `ask` 逾時（unclear）時，`FrameInbox` 的佇列可能還在 `persistNet` 中間。這時重讀會拿到寫入之前的紀錄，判成 `absent`，之後寫入才落地，變成待辦。
   - 修法：重讀之前先等佇列閒下來，或先 `close` 再讀。
4. **G-m3 沒有處理：`HandoffProber` 收到 msg2 之後沒有上限。** `SessionProber` 有 20 s 的 `answerMax`（prober.dart:37、:145）。一個送了 msg2 就停住的裝置，可以佔滿整個 60 s，而不是 8 s。照抄並加改壞。

   - 修法：第 9 列也顯示 Rust 的句子（去掉標籤）。
6. **H-M1 修法 2 的「`rel` 讀回來是不存在 = 寫入沒成功」沒有照做。** 從 0 開始的 CAS 寫入失敗（不是金鑰造成的）時，檔案不存在，會落到第 6 列 `unreadable`「讀不到手機裡的網路紀錄」。這是 fail-safe，但句子不對。
   - 修法：不存在 → 歸到第 5 列 `noRecord`。
7. **「補完加入」的標記太寬。** §2.3 寫「`netId` 是目標 → 可勾，標『補完加入』」，連手機紀錄裡已經是 Applied 的正式成員也會這樣標。
   - 修法：只在 `NetIndex` 裡這台是 joining（或沒有成員項）時才標「補完加入」；已套用的成員標「已在網路裡」，不能勾。
8. **§9 的限制少一條。** 建立新網路時如果用了另一台當建立者，舊的建立者可能留在舊網路裡。有已套用的網路之後，舊的 pending 不再有任何入口，要等 PR 4 的「離開網路」。PR 內文要照實寫（計畫只在 §2.3 的理由裡帶過）。
