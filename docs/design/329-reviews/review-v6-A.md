## MAJOR

### M1 「登入成功、狀態是錯誤碼 → 不變」沒有上限：持續性的節點錯誤永遠不會顯示；而且和「登入被拒」「連不到」的結束條件互相矛盾

**情境 A（需求 3：節點出錯要有明顯提示）**
1. 節點 Y 的 helper 回報了一個 provd 不認得的狀態名稱（版本不一致、helper 改版），或 helper 的 `status.get` 持續回 `hEStorage` / `hEState`。
2. provd：未知狀態 → `ERejected`（provd/session.go:885-889）；helper 錯誤碼 → `mapHelper` 原樣轉出（:586-589、:880-881）。這時 provd 的健康檢查仍然通過（`HealthOK` 只看 health.get / info.state 的新鮮度與 E_RATE 持續時間，provd/server.go:517-534），所以節點**照常廣播**，每一輪都登得進去。
3. App：每一輪「登入成功，狀態回答是錯誤碼」→ 6 s 後再試，還是錯誤碼 → 結論「不變」（§4.3.3-4 表第 2 列、§4.3.4）。
4. 結果：
   - Y 之前讀到過綠色 → 240 s 後變成 unk「上次讀取 13:05，當時正常」，**之後永遠是這一句**。首頁第 10 列「還沒讀到節點 X 的狀態」+「重新整理」；按了也一樣。
   - Y 這次執行從沒讀到過 → 永遠是 unk「節點 X 有回應，還沒拿到狀態」。
   - v5 在這種情況會顯示 Rust 的 row 2'（灰色 S2P「狀態未知 — 請按「重新整理」；一直如此請找維修人員」，statuspage.rs:273、:286、:347）——對**持續**的錯誤這句話其實是對的。v6 把它整個拿掉了，沒有任何路徑會走到「找維修人員」。

**情境 B（狀態矛盾）**
1. Y 是 `unreachable(登入被拒)`（§4.3.3-4：`AuthRefused` + `EForbidden`）。節點改成接受這支手機後，下一輪登入成功，但那一刻 helper 忙，狀態回 `EBusy`（provd/session.go:877-879）。
2. §4.3.3-4「節點拒絕」列寫「哪一輪登入成功就恢復」；§4.3.4「不變」列寫「狀態與 `readAt` 都不動」。兩條規則對同一件事給相反的答案：照「不變」，畫面繼續寫「節點 X 不接受這支手機的登入」，而手機剛剛才登入成功。
3. 同樣：Y 是 `unreachable(找不到)`，這一輪登入成功但狀態是錯誤碼 → 「不變」→ 繼續顯示「手機連不到節點 X：可能沒開機…」，其實已經連上了。另外「不變」那一輪算不算打斷「連續兩輪沒找到」的計數，§4.3.4 / §4.3.5 都沒寫。

**證據**
- §4.3.3-4 表第 2 列、§4.3.4「不變」列、§4.3.1 `unread` 的「有回應，還沒拿到狀態」。
- 在新連線上 provd 自己的 1 次 / s 限速不會觸發（`statusAt` 是每個 session 的欄位，provd/session.go:868-876），所以自動讀取看到的錯誤碼**全部來自 helper 或 provd 的內部錯誤**（`EBusy` = `roCall` 失敗、`ERejected` = 未知狀態、helper 的 E_RATE / EStorage / EState）。其中只有 E_RATE 與短暫的 EBusy 是「暫時」的；設計把全部當成暫時。
- 會停止廣播的只有 health / info 輪詢不新鮮（`StaleAfter` 60 s）或 E_RATE 持續超過 `ERateMax` 120 s（provd/server.go:24-25、:521-522）；`status.get` 單獨壞掉不會停廣播。
- T-H2(d) 只測「兩次錯誤碼 → 不變」，沒有任何測試涵蓋「連續很多輪都是錯誤碼」。

**為什麼是 MAJOR**：需求 3 是「節點出錯要有明顯提示」。這是一條有明確原因（節點自己回了錯誤）卻被設計成永遠「不明」的路徑，而且有兩處規則互相矛盾，實作者只能自己猜。

**建議**（不加資源，只改規則）
1. 「不變」只吸收**單一輪**：同一台連續兩輪的結論都是「不變」→ 依 Rust 的 view 顯示（row 2'，灰色 S2P，`readAt` = 這一輪）。和 T14 的兩輪規則同一個形狀。
2. 「登入成功」本身就結束 `unreachable(登入被拒)` 與 `unreachable(找不到)`：那一輪的結論是「不變」時，把狀態改成 §4.3.1 的「節點 X 有回應，還沒拿到狀態」（unk），不要保留舊的 unreachable。身分不符照現在的寫法（只有讀到 / 重新整理 / 紀錄改變才結束）。
3. 寫明「不變」那一輪會把「連續沒找到」的計數歸零。
4. 測試：T-H2(e) 連續 3 輪 `ERejected` → 第二輪結束後是灰色 row 2'；負向對照 = 照 v6 → 一直是 unk → FAIL。T-L2(d) 加一例：登入被拒之後一輪「登入成功 + EBusy」→ 不再顯示「登入被拒」；負向對照 = 照 v6 的「不變」→ FAIL。

### M2 設計預設保留 S20 上 10 筆對不上的舊紀錄（Q5），首頁狀態區因此永遠停在「手機連不到 10 台節點」：展示（需求 1）、「不顯示非必要資訊」（需求 2）與 R-2 / R-3 的判定都受影響

**證據**：§11 Q5（「舊紀錄預設不清」）、§9.2 R-1 / R-2 / R-3、§5.1 狀態表第 8 與第 14 列、§5.2 的 1.7、§4.3.7 多手機那一點（k ≥ 10）。

### m5 結束種類 `Broken` 在登入成功之前（例如附近的裝置回了格式錯誤的 msg2）沒有對應
- `End::Broken` 會在 msg2 之前或解析時出現（loginflow.rs:141、:177）。§4.3.3-4 表裡只有「讀取途中斷線…（登入成功之後壞掉）」這一列，它的處理是「備忘『位址 → Y』保留、6 s 後再試、還是不行 → 這一輪沒找到 Y」。把登入前的 `Broken` 套到這一列，一個亂回的位址就能讓 Y 在這一輪被判「沒找到」。T-F1 會要求每一個結束種類都有對應，但設計沒有給答案。
- 建議：登入成功之前的 `Broken` 歸「沒有回應」（不記備忘、排最後）；T-S3 加一例。

### m6 `loginFor`：v5 A-M1 建議的第 4 點（握手次數入帳）沒有做；「目前這個佔用」的例外是死條款；順序沒有測試
- v5 A-M1 建議 4：「把流程登入算進 §4.3.7 的握手次數與 §8『別人的節點』那一列」。v6 的 §4.3.7、§8 都沒有提 `loginFor`；`v6-changes.md` 也沒有列為「沒有照建議做」。
- §4.3.9 解不開的例外 (1) 包含「Y 的紀錄是在**目前這個佔用**裡寫入的」。`node/<id>` 只由認領（原始佔用，不用 `loginFor`）寫入，session 佔用裡只會刪除（移除節點，不連線）；所以這個分支不會發生，卻讓「6 s 後同一位址再試，直到 60 s」看起來可以對任何位址重複。
- §4.3.9 的「備忘『是 Y』的位址先」沒有測試：T-L18 只測例外隔離與 5 s 重新廣播（v5 A-M1 建議的「備忘是 Y + 3 個不回應的位址 → 第一個嘗試就是那個位址」沒有進來）。
- 建議：§4.3.7 加一句 `loginFor` 對別人位址的握手（每一對最多一次，因為同樣記「不是 Y」；例外 (1) 只在上一個佔用釋放後 30 s 內）；拿掉「目前這個佔用」；T-L18 加順序案例，負向對照 = 依掃到的順序 → 第一個嘗試不是備忘位址 → FAIL。

### m7 `expectOffline` 會被「重開之前的那一次讀取」清掉
- §4.3.1：「讀到一次就清掉」。套用送出後使用者離開更新頁 → 佔用釋放 → 6 s 後一輪（§4.3.2）。節點如果還沒真的關掉 provd（sysupgrade 收尾需要幾秒），這一輪讀到它 → 記號清掉 → 接著節點下線 → 兩輪後顯示「連不到」，正是 `expectOffline` 要避免的畫面。T-W2 沒有這個案例。
- 建議：清掉的條件改成「`until` 之前，先有一次沒找到、之後又讀到」，或「套用後至少 N s 之後的讀取」；T-W2 加「套用後 6 s 讀到一次、之後 2 分鐘找不到 → 不顯示連不到」。

### m8 T-H2(c) 測的是自動讀取不會走到的路徑
- 自動讀取與節點頁的讀取每次都是新的 `OwnerSession`，`fresh == false` 只在同一 session 讀第二次時出現（owner.rs:880-884）。§4.3.4 已經不用 `fresh` 判斷，但「讀到」列仍寫「`fresh == true`，而且 row 不是 2'」，T-H2(c) 的負向對照「讓 E_RATE 更新時間」在新 session 上不會 FAIL。
- 建議：拿掉 T-H2(c)（由 (d) 取代），「讀到」列只寫 row 判斷。

### m9 每個操作前的重新登入沒有門檻
- T16 承認在節點頁按任何操作都要先等「取消讀取 → 斷線完成 → 約 5 s 重新廣播（N8）→ 登入」，而且從 5.6 換到 5.8 是兩個佔用、兩次登入。這是需求 4（「每次都要重連」）的同一類體驗，A1 還沒量。R-7 只記錄「卡住的地方」，沒有判定。
- 建議：R-7 記錄每次「按下操作 → 第一個請求送出」的秒數，並給一個門檻（例如 A1 + 10 s）；超過就回頭考慮在同一節點頁內的連續操作沿用佔用。

## 逐項檢查（沒有發現的部分也寫出來）

**擁有權**：§4.1 每一個資源一個寫入者。`loginFor` 的備忘與節點狀態由 `NodeLink` 寫（§4.3.9 表上方），流程只拿 session，一致。`expectOffline` 只有軟體更新 controller 呼叫、`NodeLink` 寫。「佔用在背景釋放」的記號（X29）屬佔用登記表（`NodeLink` 的一部分）——§4.1 沒有單獨列，但寫入者唯一，不算發現。

**契約**：`OwnerStep` 的結束種類只由 Rust 填（§8 攻擊面）。缺的只有 m5（登入前 `Broken`）與 M1（錯誤碼持續）。`loginFor` 的五種結束都有對應；`AuthRefused` + 其他錯誤碼在 §4.3.9 表裡沒有列，依「規則和 §4.3.3 相同」可推得，建議順手補一列（併入 m6）。

**生命週期矩陣**：§7 涵蓋安裝、升級、PR 之間升級、降級、當機循環、被殺、藍牙 / 權限、節點重開、Activity 重建（AndroidManifest.xml:37 的 `configChanges` ✅）、平台。依賴重啟裡「節點 helper 重啟 / 壞掉」這一列沒有，正是 M1 的情境；建議加一列。

**安全（逐角色）**
- 附近的藍牙攻擊者：能不能偽造「身分不符」？`psk_owner = HKDF(owner_tag_key, device_id)`（loginflow.rs:62、kdf.rs:28-29），而 `owner_tag_key` 是節點在認領時產生、每台不同（flow.rs:23-27、claim.rs:225）；沒有那台的 tag key 就只會得到 `Msg2Undecryptable`。設計 §8 的說法成立 ✅。能做的是拖時間與學位址搶連線，§4.3.7 已寫上限。
