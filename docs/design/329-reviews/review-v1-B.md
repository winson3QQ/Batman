## BLOCKER

### B1 「讀完一輪後保持連線在最後一台」(§4.2-3) 與節點端行為衝突：健康的節點每 5 分鐘會變成「不明」，而且佔住節點的廣播

- 情境：志工打開 app 放著看首頁（情境 4）。`NodeLink` 連著節點 X 不放。
  1. 節點端對已登入但閒置的連線有 300 s 逾時（`provd/server.go:31` `IdleAuthed = 300 s`；`provd/session.go:290-294`）。設計沒有任何保活動作（§4.2-2 明寫「沒有定時器輪詢」）→ 300 s 後節點斷線 → §4.2-8：該節點「立刻變成不明樣式並寫出原因」+ 自動再登入一次 → 又連上 → 300 s 後再斷。**一台完全正常的節點，首頁每 5 分鐘閃一次「不明 / 連不到」，每次再花一次掃描 + 一次 owner 金鑰簽章 + 約 11 s 登入**（11 s 見 #254 留言 6879078695「logged in and status read in 11 s」）。這直接違反 U2-3（掉線才要明顯提示）與 U2-4。
  2. 節點只要有任何一條連線開著就撤下廣播（`cmd/batman-provd/bluez.go:470`「a connection withdraws the advertisement」、`:627-628`「advertisement on exactly when … no link is open」；`254-p2-impl.md` F-P17、§4.4；app 自己也知道：`lib/scan.dart:69-70`）。所以 app 開著的整段時間，節點 X 對**所有其他手機與工具**都是隱形的：第二位 owner 的手機、維修人員、`provclient`、§9 寫的「dev + dev2 兩個版本在同一支或兩支手機上走」、開發者選項裡的「附近的節點」。連線槽也只有 2（BLE + sock 合計，`provd/server.go:35`）。
  3. 這個自動重登入正好落在 F22 那個未歸因的失敗上（見 M3）。
- 設計缺的東西：§10 沒有任何一條假設提到「連線開著節點就不廣播」「閒置 300 s 會被節點斷」；§8 的「附近的攻擊者」列也沒有講佔住廣播 = 自己對自己的可用性攻擊。
- 修法：讀完就斷線（每台 login → status → disconnect），`NodeLink` 不持有閒置連線；只有使用者停在某台的節點頁、或流程進行中才持有。節點主動斷線且沒有進行中的請求時**不算** `unreachable`、不改顯示、不自動重連（下一次操作才重連，= 現況 `_lost` 的語意 `nodes.dart:419-424`）。把 IdleAuthed / 撤廣播 / 槽數寫進 §10 並附上面的證據。新增測試：假 BLE 在閒置時斷線 → 節點狀態維持 `fresh(view, readAt)`、不觸發登入。

### B2 `OwnerSession` 的 run loop 裡有「紀錄寫入」和「對話框」，設計把它們分給兩個擁有者，而且沒有寫頁面不在時怎麼辦

- 事實：`_tryLogin` 的 `run()`（`lib/nodes.dart:207-300` 一帶）在 session 迴圈裡直接做：
  - `persistNet / persistPend / persistMnet`：`seal` + `storeWriteCas` 寫 net / mnet / claim 類紀錄；
  - `confirmCountry`、`confirmRemoved`：用**頁面的 `context`** `showDialog`，等待期間 `_wait?.cancel()`（逾時計時器被取消）；
  - `sign / signAdmin`：呼叫 Keystore。
  這些步驟到處檢查 `mounted` / `gone()`。
- 設計：§4.1 說 BLE 連線、`OwnerSession`、進行中的請求歸 `NodeLink`；金鑰紀錄歸「各流程的 controller」；§4.2-9 說 `_ask`「原樣搬進來，不改語意」；§4.4 說「寫入順序一個都不改」。但 run loop 搬進 app 層級的 `NodeLink` 後：
  1. 寫 net / mnet 紀錄的是 `NodeLink`（run loop）還是 controller？兩者都寫 = §4.1 自己說不能有的兩個寫入者；設計沒有定義 run loop → controller 的回呼契約（誰 seal、CAS 失敗誰處理、回呼沒人接怎麼辦）。
  2. 建立網路等 360 s（`lib/member_ui.dart:231`）期間使用者離開流程頁、鎖屏、或 app 被切到背景：`persistNet` 步驟到的時候沒有頁面。現況靠 `mounted` 中止；搬到 app 層級後「節點已套用、手機紀錄沒寫」的那條路（`rust/bridge/src/api/owner.rs:1128`「節點已套用，手機紀錄沒存好…請按『確認網路』」）會不會更常發生、由誰恢復，設計沒寫。
  3. `confirmCountry` 對話框跳出時頁面已經不在（或 app 在背景）：逾時計時器已取消 → 這個請求永遠不結束 → `NodeLink` 永遠 busy → 之後所有讀一輪與操作都卡住。
- 這不是實作細節：它就是 #274 那一類「各自正確、介面沒寫」的問題，而且壞掉的後果是節點與手機紀錄不一致。
- 修法：§4.2 加一節「session 步驟契約」，逐個 `OwnerKind` 寫：誰執行、需要什麼（Keystore / 紀錄庫 / 使用者決定）、沒有 UI 可問時的結果（建議：`confirm*` 沒有註冊的回答者 → 當成「否」並結束請求，fail-closed；`persist*` 一律由 `NodeLink` 透過注入的 store 執行，不依賴頁面是否存在，controller 只收結果）。§4.1 把「session 進行中寫入的紀錄」那一列的擁有者寫清楚。測試：流程頁在 360 s 等待中被 pop → `persistNet` 仍然寫入；`confirmCountry` 沒有回答者 → 請求在有限時間內結束且 `NodeLink` 不再 busy（負向對照：拿掉預設回答 → 測試逾時）。

## MAJOR

### M1 `fresh` 沒有到期規則，加上 E_RATE 的回答，T2 擋不住「舊的綠燈」

- 情境 a：首頁開著 20 分鐘沒動。§4.2-2 沒有任何觸發（沒切背景、沒按重新整理）→ 節點維持 `fresh` + 綠色 +「一切正常，可以使用」，其實是 20 分鐘前的事。T2 只管「快取」，不管「這次開 app 讀到但已經舊了」。
- 情境 b：操作完成後「只讀那一台」（§4.2-2 第 4 點）緊接在操作之後，節點狀態讀取配額 1 次 / s（`lib/member_ui.dart:320` 註解）；E_RATE 時 Rust 回 `fresh=false` 並沿用**前一次**的判定與時間（`lib/nodes.dart:97`、`:1113`、`:1125`）。設計的 `fresh(view, readAt)` 沒有說 `view.fresh == false` 時怎麼算 → 可能把操作前的綠色當成操作後的結果。命名也撞在一起（`NodeLink.fresh` vs `StatusView.fresh`）。
- 修法：(1) `fresh` 加年齡上限（例：> 2 分鐘就改用「不明」樣式，句子保留、寫讀取時間）；首頁在前景時由畫面上的時鐘重算樣式，不需要輪詢節點。(2) 明寫 `StatusView.fresh == false` → 狀態不前進、`readAt` 不更新。(3) 測試 T-H2 補兩個案例（時間前進 → 樣式變不明；E_RATE 回答 → 不變綠），負向對照 = 拿掉年齡檢查。

### M2 掃描模型：每台節點一次 60 s 掃描，一台不在就卡住整輪；候選逐台試的成本是 N×M；有撞到 Android 掃描節流的風險

- 事實：`_login` 每次呼叫開一次新的 `scanForDevices`（lowLatency，最多 60 s，`lib/nodes.dart:377-399`）；節點廣播沒有身分（RPA、只有 UUID，`lib/nodes.dart:3`、`lib/scan.dart` 檔頭），所以每個候選都要連線（15 s / 20 s 逾時，`:185-197`）+ 簽章才知道是不是這台。
- 情境：我有 02、04，04 沒開機，清單順序 04 在前。啟動後首頁顯示「正在連到你的節點…」整整 60 s（§5.1 第 4 列「還沒有任何一台讀完」），02 明明就在旁邊。期間 02 會被當成 04 的候選連一次（失敗），輪到 02 時再連一次。
- 「使用者操作優先：在兩台之間讓出」(§4.2-5)：使用者在這 60 s 內按「建立網路」→ 要等到這台掃完。現況 `_login` / `_ask` 在 busy 時是**直接 return、沒有任何訊息**（`lib/nodes.dart:353`、`:493` 一帶）；「原樣搬」就是按了沒反應。
- Android 對同一個 app 30 s 內第 6 次開始掃描會靜默不給結果（推論：Android 7+ 的已知行為，repo 內沒有證據，A 表也沒列）。本設計的掃描來源：每輪每台 1 次 + 斷線自動重試 1 次 + 藍牙打開觸發 1 輪 + 操作完成重讀 + 使用者按重新整理。兩三台節點加一次重新整理就可能到 6 次；被節流的表現就是「60 s 後找不到節點」，跟 F22 的症狀一樣。
- A1 的數字也不對：設計寫「單台約數秒（未記確切秒數）」，但留言 6879078695 有記：藍牙打開後「logged in and status read in 11 s」。兩台 = 約 22 s，已經超過 A1 自己訂的 20 s 門檻。
- 修法：一輪只開**一次**掃描，候選共用：對每個候選依序用各台的紀錄試登入（登入本身就是身分判定，A2 不變），一輪內記住「候選位址 → 哪一台 / 都不是」；掃描窗結束後沒配到的才標 `unreachable(找不到)`。使用者操作要能**取消**讀一輪中還沒登入完成的掃描 / 連線（登入前沒有副作用；讀狀態是唯讀）。把掃描次數上限寫成 `NodeLink` 的不變量（例：任意 30 s 內 ≤ 4 次開始掃描）並加測試。A1 改成引用 11 s 的實測。

### M3 「斷線後自動再試一次」(§4.2-8) 正好踩在 F22 未歸因的失敗上，而且設計沒有先重現

- 留言 6879078695：「找不到節點 4×, each time the first login after LINK_LOST; the immediate retry succeeded every time」，其中一次節點端 60 s 內完全沒看到這支手機的連線。設計的自動重試就是「LINK_LOST 後的第一次登入」→ 依現有證據它會花 60 s 然後失敗 → 設計規定「之後不再自己重試」→ 節點停在 `unreachable(60 s 內找不到)`，直到使用者手動重新整理（而手動那次會成功）。也就是：**新設計在已知的失敗模式下，穩定地把一台正常節點顯示成「手機連不到節點」**。
- §4.2-4 說「不宣稱修好它」可以，但不能把新機制建在它上面而不先歸因。使用者規則：bug 先在真機重現再修；每個 FAIL 要歸因或標 ❓。
- 修法：實作 `NodeLink` 前先在真機歸因 F22（候選：斷線後節點重新註冊廣播 / 換 RPA 的時間差——`254-p2-impl.md` F-P17、§4.4；Android 掃描節流；app 在背景時掃描）。歸因前的設計：斷線後不立即自動重登（見 B1），或延後數秒再試並且試兩次、兩次都失敗才標 `unreachable`。T-L2 的判定跟著改。

### M4 `NodeLink` 的互斥規則沒有涵蓋會自己切換節點、或長時間佔用 session 的現有流程

§4.2-5 只列「認領、軟體更新傳送期間暫停讀一輪」。現有程式裡還有：

| 流程 | 行為 | 證據 |
|---|---|---|
| 移除成員 `_remove` | 自己依序登入每一台自己的節點 | `lib/nodes.dart:1291-1305`（`_login(o.deviceId)` :1296） |
| 加入後連線檢查 `_watchLink` | 佔住 busy 最多 120 s，每 10 s 問一次 | `lib/nodes.dart:41-43`、`:665-694` |
| 建立 / 加入 / 隊員加入 / 離開 | 單一請求最多 360 s | `lib/member_ui.dart:231`、`lib/nodes.dart:470`、`:624`、`:1020` |
| 軟體更新 | 上傳期間每 10 s 經 BLE 送一次保活；`SwHold` 在頁面關掉後仍保留（準備好、還沒套用） | `lib/swupdate.dart:197-206`；`lib/nodes.dart:1554-1577` |
| `_ask` | 沒有 session 時自己重新登入 `_lastNode`；寫入失敗再登入重試一次 | `lib/nodes.dart:500`、`:537` 一帶 |
| 認領恢復 `ClaimRecovery` | 自己的掃描 + 連線，最長 300 s | `lib/claim_recovery.dart:186-197` |
| 設計新增：4.1 勾多台 | 第一台建立、其餘逐台加入 = 最多 N×(360 + 120) s，中間要換節點 | §5.4 |

沒寫的情況：(a) `SwHold` 存在但不在傳送中時，回到前景觸發讀一輪 → 切到別台 → 原 session 斷 → 已準備好的更新怎麼了？(b) `_remove` 換節點途中讀一輪插進來；(c) `_ask` 的「自己重新登入」在背景時算不算 §4.2-4 禁止的「新的登入」——如果算，背景中的 360 s 請求遇到一次寫入失敗就不能重試，語意已經改了，跟 §4.2-9「不改語意」矛盾；(d) 4.1 多台流程在第一台等 6 分鐘時手機自動鎖屏（4.2 只寫 PopScope，沒有寫保持螢幕；`keepScreenOn` 目前只有軟體更新用，`lib/swupdate.dart:137`）→ app 進背景 → 第二台的登入依 §4.2-4 不會開始 → 流程停住到使用者解鎖。
- 修法：定義一個明確的「佔用」(lease)：流程 controller 向 `NodeLink` 取得佔用、指定節點、可在佔用內切換節點；佔用存在期間不跑讀一輪、不因生命週期事件切節點；`SwHold` 存在 = 佔用存在。佔用內的重登入不受背景規則限制（它屬於已開始的操作）。等待 > 30 s 的畫面一律保持螢幕開啟。生命週期矩陣補「鎖屏 / 背景發生在 360 s 等待中」「多台流程中途被殺」兩列（多台流程被殺後：第一台已建網、其餘未加入 → 首頁待辦要能接，設計目前的待辦來源只涵蓋「加入中」，不涵蓋「還沒開始加入」）。T-L7 改成對每一種佔用各一個案例。

### M5 「回到前景」的定義會被 app 自己開的系統畫面觸發

掃 QR 是另一個 Activity（`AndroidManifest.xml:53-59` `QrScanActivity`），藍牙權限是系統對話框（`MainActivity.kt:139-143`，而且同時第二個請求會回 error「a permission request is already open」），軟體更新要選檔、要去 Wi-Fi 設定，2.2 / 2.3 會帶使用者去系統設定。每一個回來都是一次 resumed。§4.2-2「回到前景且距上次 ≥ 30 s → 再讀一輪」在這些時刻會：掃完邀請 / 認領 QR 回來就開始掃描登入，和接下來的流程搶藍牙；讀一輪的 `blePermissions` 和使用者流程的 `blePermissions` 同時發出。另外 `_login` 裡的 `blePermissions` 會**彈出系統權限對話框**（不是只檢查）——自動讀一輪不該彈對話框。
- 修法：讀一輪只「檢查」權限、不請求；請求只在使用者按 2.2 的按鈕時做。前景觸發在有佔用（M4）時不動作。T-L3 補「從 QrScanActivity 回來」案例。

### M6 BLE 位址提示（§4.2-7、`ui/state-v1` 欄位 4.5）幾乎沒有作用，應該刪掉

- 節點廣播用 RPA（`lib/nodes.dart:3`、`lib/scan.dart` 檔頭、`bluez.go:226-229` 一帶），RPA 900 s 到期重算，斷線重新註冊時也可能換（`254-p2-impl.md` F-P17、§4.4 對照表「斷線重註冊 → 新 RPA」）。所以提示只在同一個 15 分鐘窗內有機會命中，跨 app 啟動基本上都不中。A7 寫「未查證」，但 repo 裡的註解與設計文件已經寫明是 RPA —— 這是可以查而沒查的假設。
- 代價：多一個持久化的欄位、多一條「提示錯了」的路徑、`ui/state-v1` 每次登入都要寫。使用者規則：只做必要的修改，不加用不到的機制。
- 修法：刪掉欄位 5 與 §4.2-7；要加速就做 M2 的「一輪一次掃描 + 一輪內記住候選」（只在記憶體）。

### M7 Rust / Dart 現有文字裡寫死了舊畫面的按鈕名稱；T8「不改 Rust 文字」會讓新畫面叫使用者去按不存在的按鈕

- 狀態句子：`rust/batman-proto/src/statuspage.rs:128-148`、`:174-182` —「請按『重新整理』」「請按『加入網路／繼續加入』」「請按『加入隊伍網路』」「可按『建立網路』，或向管理者要邀請」。這些句子是首頁與節點頁 `StatusHero` 的主文，還會被存進 `ui/state-v1`。

### M10 §12 實作順序：PR1–PR4 期間有兩個 session 擁有者

T7 把舊 `NodesPage` 留在開發者選項。它自己持有 BLE 連線與 `OwnerSession`（`lib/nodes.dart:68-130`）。PR1 起 `NodeLink` 也持有 → 同一支手機兩個擁有者，直接違反 §4.1「沒有任何資源有兩個寫入者」，而且 PR1 之後建立網路、Wi-Fi、邀請等**只能**從舊控制台做（新首頁 / 節點頁在 PR1 只有狀態）——也就是每次真正操作都會走到兩個擁有者並存的路徑。舊控制台連上節點時 `NodeLink` 的那條連線還在的話，節點不廣播（B1-2），舊控制台會等 60 s 回 NOT_FOUND。
- 修法：寫明進入舊控制台 = 取得一個佔用（M4），`NodeLink` 先放掉連線、暫停讀一輪，離開後恢復；T-L7 涵蓋。或 PR1 就讓 `NodesPage` 改用 `NodeLink` 的 session（工作量大，不建議）。另外 §12 第 1 步一次塞了 token、元件、`UiState`、`NodeLink`、首頁、節點頁、首次使用、關於——這是整個設計風險最高的部分全在一個 PR，建議把 `NodeLink`（含真機量測 A1、F22 歸因）獨立成第一個 PR。
