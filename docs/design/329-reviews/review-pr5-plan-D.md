## MAJOR

### M1. 拿掉 `update_hint` 之後，新 UI 沒有任何地方顯示「這台還在舊密碼」。被移除的人仍連得上，UI 不會提示

**情境 A（隊長）**：隊長在 8.3 移除 X，在 8.4 把更新包交給隊員。照基準的順序（「包都交出去之後，再換自己的節點」，remove-member :164），隊長這時要等隊員回報，可能等幾小時，所以會離開 8.4。之後可能發生這些事：
- app 被系統殺掉；
- 隊長自己的第二台節點沒開機；
- 8.4 的「送出」遇到 360 s 逾時（unclear）。

結果隊長的節點留在舊密碼，X 仍然連得上，而新 UI 沒有任何一處告訴他。8.4 的「已送出」只在記憶體（plan 2.6-10）；8.1 頂端那一行只算更新包，不算節點（2.5）；節點頁的「把新密碼送給節點」是不分狀態的常駐列（2.7）。

**情境 B（隊員）**：隊員在 8.5 匯入新密碼。照 T30，匯入不會自動送出，所以他離開時節點還沒換；或者他有兩台節點，8.5 只送了目前那一台。之後這幾台都留在舊密碼，被移除的 X 可以連上它們，而 UI 同樣不提示。

**證據**：
- 凍結基準 254-app-remove-member v6.5 就是靠一條共用規則處理這件事：
  - :27「自己擁有的節點版本落後於手機紀錄 → 狀態頁出現『把新密碼送給節點』」；
  - :185「這台還在舊密碼 — 把新密碼送給節點」；
  - :184「這支手機沒有它的新密碼 — 請網主重新產生你的更新包」；
  - 生命週期 :235（成員匯入後、送出前被殺）與 :236（網主自己的節點之後才開機），都靠「狀態頁共用規則出現按鈕」收尾，測試是 T7 / T7b。
- 舊控制台照這條規則做：`nodes.dart:1160-1176` 每次讀狀態頁，就對 `net/` 或 `mnet/` 紀錄跑 `s.updateHint` 並顯示那一行。
- 規則本身在 `rekey.rs:466-499`：比較 info k9 與紀錄版本，再看 k10。
- 節點頁每一輪讀到的 `StatusView`（owner.rs:373-402）只有 `net_id`、沒有網路版本（k9），所以節點頁自己判斷不了。v2 2.3 說得對：prober 的那一輪不能用。但 v2 從這裡推出「整個不用 update_hint」，就把基準的共用規則一起拿掉了。§4 沒有列出這個偏離。
- `page_info` 在任何一次 `statusPage` 之後都會設好（owner.rs:950-965）。所以 update_hint 在 `OpSession` 裡完全可用：登入 → `statusPage` → `updateHint(record)`。

**後果**：這是 fail-open。移除流程在 UI 上看起來完成了，被移除的人卻可以一直留在隊長或隊員還沒換的節點上，沒有時間上限，也沒有任何畫面提示。基準 :235 / :236 兩條生命週期路徑在新 UI 裡沒有了。

**修法**（不改 Rust，不改 PR 3 的讀取規則）：
1. 節點頁的「把新密碼送給節點」列，按下後先在同一個 `OpSession.once` 裡跑 `statusPage` 與 `updateHint(紀錄)`：
   - `line` 為空：顯示「這台已經是新密碼」，不送；
   - `button` 為 false：顯示 Rust 的那一句，例如「手機沒有它的新密碼」，不送；
   - `button` 為 true：才進確認框，然後 `sendUpdateFor`。
   這就是基準 §3.5 的共用規則，只是從「讀狀態頁時」改成「按這一列時」。§4 要列成一條 D 項。
2. 8.4 的「把新密碼送到我的節點」那一段，進頁時（以及每次按「重新檢查」時）照 8.3 讀 `info` 的方式，逐台跑上面那一組。每台顯示「新密碼 / 還在舊密碼 / 讀不到」。這個狀態從節點讀出來，不是記憶體，app 重開之後也能重算。「已送出」改成依送完之後重讀的結果，unclear 也就有了答案（併入 m8）。
3. 8.5 匯入成功之後，列出這支手機在這個網路裡的每一台節點，每台都可以「送到節點」，不只目前那一台（T37 一人多台）。
4. 測試：
   - 搬 T7 / T7b：紀錄版本 > 節點 k9 → 看得到「還在舊密碼」與送出；
   - 同版 → 不送；
   - 負對照：把 hint 拿掉（永遠可送或永遠不顯示）→ FAIL。

### M2. 同名的第二組身分：8.2 / 8.3 / 8.4 沒有搬指紋與「另有同名的一組」。隊長移掉一組，又把新密碼交給另一組

**情境**：惡意隊員 X 先後用兩支手機（或重裝 app）入隊。兩次都過了 SAS，所以名單上有兩組都叫「X」，owner_pub 不同。之後隊長要移除 X：
1. 在 8.1 點第一組 → 8.2 → 8.3 → 移除。8.2 與 8.3 都沒有提到另一組。
2. 8.4 的「留下的隊員」裡還有一列「X」（第二組）。隊長以為那是別人或同一個人，照樣「複製更新包」交出去。
3. X 拿到新密碼，被移除後仍然連得上。

**證據**：
- 基準 remove-member :139：「同名的組**在移除對話框**列出『另有同名的一組：〈指紋〉』，要一起移除得各按一次（B-m4）」；:531 A-F7：「同名提示進對話框」。
- 舊程式 `_members` 算 `sameOf(owner)`，傳進 `_remove(sameName:)`，在確認框裡用橘色顯示（nodes.dart:1326-1329、:1343、:1397）。名單與更新包清單都顯示 `fpr`（:1331、:1482）。
- plan 2.6-8 的 8.2 只有「名字、節點後四碼、加入中與否」；2.6-9 的 8.3 步驟 1–5 沒有 sameName；2.6-10 的 8.4 每列內容沒有寫指紋。只有 8.1 寫了「同名的另一組標出來」，但做決定的頁面是 8.2 / 8.3。
- `net_recipients` 的 `note` 不含同名提示（rekey.rs:311-327）。所以 8.4 這一行 Dart 要自己標。

**後果**：基準審過、要放在確認框的防線，在新頁面上掉了。被移除的人可以留在網路裡，UI 不顯示。

**修法**：
- 8.2 顯示 `fpr`；有 `sameName` 時，在 8.2 與 8.3 的按鈕之前顯示基準那一句（照 :1397 的文字與顏色）。
- 8.4 每列顯示名字與 `fpr`。名字與這次被移除的人相同時，標「與剛移除的〈名字〉同名，確認是不是同一個人」。
- 測試：兩組同名 → 8.3 看得到那一句、8.4 看得到標記；負對照：拿掉 → FAIL。

### M3. A-M2 的後半沒有關：離開 8.4 之後沒有路回到 8.4，更新包無法重新產生

**情境**：隊長在 8.4 交出一半的更新包，app 被殺，或者他回首頁去處理別的事。之後：
- 隊員 B 說他沒收到；
- 或者 B 還在等，要重傳。

隊長從設定頁或節點頁進 8.1，畫面上只有名單、「邀請隊員」、頂端那一行（plan 2.6-1），沒有「產生更新包 / 換密碼清單」。要回到 8.4，只能再移除一次。

**證據**：
- A 第一輪 M2 的第一點就是這件事：「隊長離開 8.4 以後，沒有任何頁面能回到 8.4 重新產生更新包；設計情境 6 的出路正是『更新包可以重新產生』（329-app-uiux.md:807）」。
- 舊程式的 `_makeUpdates` 隨時可以按（nodes.dart:1450-1454）。
- v2 只修了「入口不看節點」，3.3 表格寫「進得去 8.1 / 8.4」，但 2.6 沒有任何一條路通到 8.4。

**後果**：
- 留下的隊員拿不到新密碼。等隊長的節點換了（M1 修好之後），他們就斷線。
- 或者隊長為了不讓他們斷線，乾脆不換自己的節點，那 M1 的 fail-open 就永遠留著。
- PR 5 期間可以回舊控制台繞過去，但新 UI 的使用者不會知道。

**修法**：
- 8.1 常駐一列「換密碼清單（產生更新包、換自己的節點）」，進 8.4。它不看 RemoveTicks；`netRecipients` 本來就由紀錄決定（nodes.dart:1465-1468）。
- 8.1 頂端那一行改成可以點，也進 8.4。
- 測試：app 重開（RemoveTicks 空）→ 8.1 → 8.4，看得到每位隊員與自己的節點；負對照：拿掉入口 → FAIL。

## MINOR

### m1. D1 的 v27 上限讓第二位以後的當面加入只能複製文字，沒有網路的現場就走不下去

- **證據**：
  - 同意碼帶整份名單（approve.rs:312-319），上限 16 人（netrec.rs:27 `MAX_MEMBERS`）。
  - ⚠️ 推算：v27-L 英數模式的容量約 2132 字元，F36 的 2082 字元已經接近上限。多一位成員之後，就到 v30 以上了。
  - plan D1 自己也寫了這個後果。
- **情境**：防災現場沒有行動網路。隊長與第二位隊員當面加入：7.6 只有「複製文字」，兩支手機之間沒有可以貼的通訊軟體。
- **為什麼不是 MAJOR**：v27 是量過的上限，不畫一個掃不到的 QR 是 fail-safe。上層 §5.7:773 也已經接受「只留複製文字」。
- **修法**：
  - PR 前用 R-8 的電腦螢幕裝置補量 v31 / v35 / v40（同一套程式，一小時內做得完），把上限換成量到的值；
  - 7.1「在旁邊」的說明要寫：碼太大時要怎麼傳，例如 Android 的「分享 → 鄰近分享」不需要網路（⚠️ 未在 S20 試）；
  - 把這件事寫進 #329 checklist。

### m2. `SecureScreen(fallback:)`：`_on == null` 的行為沒寫；Wi-Fi 頁的「不變」其實沒有測試鎖住

- plan 2.2 說用 settings_pages_test 鎖住「沒給 fallback 時行為不變」。但 `test/ui/settings_pages_test.dart:29` 的 mock 對 `set` 一律回 `true`，從來沒有跑過 `false`。`secure_screen_test.dart` 只測通用的 `Text(secret)`。
- **修法**：
  - 明寫 `_on == null` 時連 fallback 也不建（不能讓「複製文字」在 Android 回答之前出現）；
  - 加兩個測試：Wi-Fi 頁在 `set → false` 時沒有密碼欄（負對照：給它 fallback → FAIL）；CodeView 在 `null` 狀態既沒有 QR 也沒有複製按鈕。

### m3. 剪貼簿：自動複製還在不在沒寫；8.4 的複製與貼上後清除沒有走新的 method

- 舊的 `_runOp` / `_runRemove` 一做完就 `Clipboard.setData` 自動複製（nodes.dart:788-789、:1440-1441）。plan 2.4 寫「複製剪貼簿……由頁面做」，但沒說是自動複製，還是只有 CodeView 的按鈕。
  - 如果保留自動複製：碼會繞過 `copyCode` 的 sensitive 旗標；CodeView 也不知道複製過，就不會出現「清除剪貼簿」與離開時的提醒。
- 8.4 的「複製更新包」不在 CodeView 裡，「清除」與離開時的提醒都沒有規格。
- `CodeInput` 貼上後清除用的是 `_takeClipboard` 的 `setData('')`（nodes.dart:728-732）。在 Android 13 以上，這會跳出一個空的「已複製」浮層，鍵盤的剪貼簿紀錄也還在。新的 `clearClip()` 比較乾淨。
- **修法**：
  - 明定不自動複製，所有複製都走 `copyCode`；
  - 8.4 共用 CodeView 的「清除剪貼簿」與離開時的提醒；
  - 貼上後清除改用 `clearClip()`；
  - 負對照：拿掉貼上後清除 → FAIL。

### m4. `OfflineOp`「例外照常往外丟」和 `OpSession` 只記型別的規則不一致

- `OpSession` 只記 `e.runtimeType`（op_session.dart:123、:183）。
- Kotlin `keyCall` 的錯誤訊息裡有 `e.message`（MainActivity.kt:78）；Rust 的錯誤是中文原因句。
- `OfflineOp` 丟出去的例外如果在頁面的 async 按鈕裡沒有被接住，Flutter 預設會把整個訊息印到 logcat。這和 §5「紀錄只寫種類」的規則不一致，T-U6 也搜不到這種輸出。
- **修法**：`OfflineOp` 自己接住例外，只記 `runtimeType`，回傳 `failed(line)`；`work` 裡的釋放與歸零仍在 `finally`。
- 測試：`work` 丟出一個含假秘密的例外 → 紀錄裡找不到它。

### m5. `ConsolePlatform` 沒有 `ecdh`；`_ownCopy` 沒寫進計畫

- `ConsolePlatform`（owner_console.dart:131-152）只有 seal / sign / publicKeys / readRecord。`runNetOp(…, platform)` 與 7.10 / 8.5 的 work 需要一個 `ecdh`。
- 舊程式先把回傳值複製一份（`_ownCopy`，nodes.dart:719-724），再對那份歸零（:1035、:1540）。註解寫明：平台回傳的 byte list 可能是唯讀的 view（S20 實測）。直接對它 `fillRange` 會在 `finally` 裡丟例外，蓋掉已經寫成功的匯入結果，畫面就顯示失敗。plan 2.4 只寫「照 1035」，那是歸零那一行，不是複製那一行。
- **修法**：`ConsolePlatform` 加 `ecdh`，回傳值在 platform 層就先 `Uint8List.fromList`；nodes_zero_test 的做法要涵蓋 7.10 與 8.5，負對照：拿掉複製、用唯讀 view → FAIL。

### m6. 「在佔用裡重讀」的清單漏了產生更新包

- 舊 `_updates` 在按下時重讀紀錄，Rust 只從那一份紀錄的 key 11 取人（nodes.dart:1489-1491）。
- plan 2.4 只列了同意、移除、匯入。如果 8.4 用進頁時讀到的紀錄產包，而中間又做了一次移除（M3 修好之後，8.4 會被重複進入），交出去的就是舊版本的密碼。那個版本，後來被移除的人也知道。
- **修法**：把 `startBundle` 加進 2.4 的重讀清單。

### m7. devTrust gate：「把新密碼送給節點」在 Rust 沒有 gate；`NodePage` 還沒有 devTrust 參數

- `request_send_update` 沒有呼叫 `dev_gate`（owner.rs:1041-1044；`request_joinreq` / `request_member_join` 有，:1255、:1284）。所以這一列只有 Dart 一層。§5「三層 gate 不變」對這一列不成立。
  - 在 field 版這一列送的是「手機目前的紀錄」，害處很低，但計畫要寫實。
- `NodePage` 的建構子沒有 `devTrust`（node_page.dart:20），首頁開它的地方也沒傳（home_page.dart:248）。
- **修法**：
  - `devTrust` 設成必填參數（其他頁是可選、預設 false，一樣是 fail-closed，但必填可以避免漏傳）；
  - T-S5 涵蓋節點頁的三項（隊員分組、送新密碼、貼新密碼）與設定頁的「隊員」：field 版都不出現；
  - §5 寫明送新密碼這一列只有 Dart 一層。

### m8. 8.4 / 8.5 送出遇到 unclear（360 s 逾時）時怎麼顯示，沒有規格

- 現在只寫了成功與「讀不到或失敗」兩種。unclear 時節點可能已經換了，也可能沒換。
- **修法**：照舊控制台的 `_sendUnclear` 句子；M1 的重讀上線之後，用重讀的結果決定顯示什麼。

### m9. `qrMatrix` 的實作細節

- `QRCodeWriter.encode` 回傳 `BitMatrix`，不會告訴你版本。要用 `Encoder.encode(text, L, hints).version`，或者在 margin 0 時用 `(size − 17) / 4` 算出來。
- `WriterException` 要對應到錯誤 `qr`。
- Dart 要檢查 `size == 17 + 4 × version`，並檢查 `bits` 的長度與 size 相符。不合就當失敗，不畫。
- T-Q1 的「解回來要相同」要真的用 ZXing 的 reader 解碼，不能只比對點陣。

### m10. 貼上沒有任何長度上限

- 邀請、申請、同意的解析在 `from_hex` 之前沒有長度檢查（invite.rs:75-97）；只有更新包有（mupdate.rs:90）。
- 剪貼簿裡如果是一大段文字（例如誤複製的檔案內容），會被整段複製進 Rust。這是自己對自己造成的阻斷，影響低。
- **修法**：Dart 在貼上時設一個寬鬆的上限，例如 `2 × (MAX_BUNDLE + 16) + 1024` 個字元，超過就顯示「這不是碼」，不交給 Rust。
