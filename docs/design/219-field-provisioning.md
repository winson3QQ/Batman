## 0. 一句話

一般使用者買了幾台節點,**完全離線**、只用手機 app:掃機身 QR 認領 → 建立或加入網路 → 看狀態 → 需要時離開網路或恢復出廠。**系統能做的都藏起來**,使用者只看到結果與需要他決定的事。

## F2. 現在就要固定的介面(之後加戰術版不能改壞)

| 介面 | 規則 |
|---|---|
| API | 有版本(`/v1/*`);新版本只能**新增**訊息類型,不改既有的語意;app 不認得的版本只允許查狀態與恢復出廠 |
| 訊息與傳輸 | 請求 / 回應訊息與傳輸無關(GATT 或 HTTP 都能承載);**安全通道一律在應用層(§3.4)**,走 HTTP 時也在裡面再跑一次,不依賴 TLS |
| 大量資料 | BLE 只負責控制;大量資料(image、診斷包)由 BLE 指示節點**暫時**開 WiFi 通道傳輸,傳完即關(§6.9) |
| 簽章 | 所有 DAC / 擁有者 / 網主簽章都對**帶用途標籤的結構**簽(`"batman-hs-v1"`、`"batman-peer-v1"`、`"batman-net-v1"` …),**不直接簽對方提供的值** |
| BLE 廣播 | 有格式版本;欄位只增不改;戰術版以新的格式版本加嚴 |
| 能力清單 | 開放集合:app 遇到不認得的能力就提示更新,其他功能照常 |
| 成員提供者 | 統一介面:`join`、`approve`、`verify(peer)`(非同步)、`remove`、`revoke`(撤銷清單會散播,與 remove 分開)、`rekey`、`renew`、`apply(update, version)`、`persist` / `restore`(OTA 後還原)、`export_invite`、`net_config()`(產生網路層設定:民用 = SAE,戰術 = WireGuard peer);民用與戰術各自實作 |
| 設定 | 依能力分組的命名空間(`halow.*`、`lora.*` …);兩類推送(擁有者 / 網主簽章);網主設定**簽發端每次只能 +1**,節點接受**簽章鏈**(從目前版本到最新版本的每一版都有網主簽章),不接受跳號 |
| 重置 | 分級列舉預留 L3(戰術),民用版回報「不支援」 |
| 角色 | 擁有者、網路管理者、成員;戰術版加入新角色時不改既有角色的權限 |

## 2. 使用者看到的(驗收標準)

| 內部 | 畫面上 |
|---|---|
| 認領 | 加入我的裝置 |
| region | 國家 / 地區 |
| BLE 連線 | (不出現;app 自己處理) |
| mesh 密碼 | 網路密碼 |
| L1 | 離開網路 |
| L2 | 恢復出廠設定 |
| 名冊外節點 | 不認識的裝置 |
| DAC 指紋末碼 | 確認碼(「兩支手機上的確認碼要一樣」) |

### 2.2 各流程的步驟上限

步驟數**包含系統對話框**;前置動作(例如「機台已認領」)不重算。BLE 不需要切換手機的 WiFi;只有第一次使用 app 時要允許藍牙權限(一次性,不計入各流程)。

| 流程 | 使用者做的事 | 上限 |
|---|---|---|
| 開箱認領 | 掃機身 QR(app 依廣播找到這台,不需切換 WiFi)→ 確認國家 → 取名 | 3 |
| 已有網路時加入新機 | 認領的最後一步自動問「加入『家裡網路』?」→ 加入 | +1(接在認領之後) |
| 一次認領多台 | app 首頁列出「附近的新裝置」→ 依序掃每台 QR(自動命名「節點 1、2、3」,可事後改) | 每台 1 |
| 建立網路 | 「建立網路」→ 勾選要加入的機台 → 完成(名稱與密碼自動產生) | 3 |
| 邀請朋友(當面) | 網主手機顯示邀請 QR(內含一次性預先同意;一個邀請可讓同一人的多台一起加入) | 1 |
| 邀請朋友(遠端) | 「邀請朋友 → 傳給不在身邊的人」→ 以 LINE / 訊息等分享**邀請 QR 圖片** | 2 |
| 邀請朋友(只能講話) | 念出**加入碼**(最後備援,例如電話、無線電) | 1 |
| 加入朋友的網(當面) | (機台已認領)掃網主的邀請 QR → 選要加入的機台(預設全選;原本在別的網路時提示「會離開『家裡網路』」)→ 加入 | 2 |
| 加入朋友的網(遠端) | (機台已認領)從相簿選取邀請 QR 圖片(或在聊天 app 長按圖片「分享到 Batman」)→ 選機台 → 等網主同意(「等待中:請網主打開 app」,可取消) | 3 |
| 加入朋友的網(只能講話) | (機台已認領)輸入加入碼 → 選機台 → 等網主同意 | 3 |
| 網主同意新成員 | 收到「小明的『客廳』想加入」→ 同意 | 1 |
| 看狀態 | 打開 app:「**附近**」直接由 BLE 看到;「**全隊**」透過附近任一台經 mesh 查詢(沿用 #131 / #14);每台顯示「最後看到的時間」 | 0 |
| 離開網路 | 選機台 → 離開網路 → 確認 | 3 |
| 恢復出廠 | 選機台 → 恢復出廠 → 確認(之後要在機台上按一下按鍵才能重新加入) | 3 |
| 二手機第一次認領 | 在機台上按一下按鍵 → 掃機身 QR → 確認國家 → 取名 | 4 |
| 移除成員(網主) | 網路頁 → 選成員 → 移除(**自動換密碼**,不另外問) | 3 |
| 回報遺失 | 機台頁 → 回報遺失 → 確認(自動移除並換密碼) | 3 |
| 重建網路(網主手機遺失、沒有備用管理手機) | 網路頁 → 重建網路 → 邀請其他人重新加入 | 2 + 每人 2 |
| 解散網路(網主) | 網路頁 → 解散 → 確認(在線的機台自動離開;不在線的下次靠近時處理) | 3 |
| 更新軟體 | (機台在附近)機台頁「有新版本」→ 更新 → 確認 →(系統:加入機台 WiFi)→ 等待;**傳完之前不要離開畫面**,傳完後可以離開 | 4 |
| 看診斷 / 匯出診斷包 | 機台頁 → 診斷(白話摘要);「匯出」經藍牙存到手機,之後再分享 | 1–2 |
| 換手機 / 手機壞了 | 「設定 → 我的手機遺失了」→ 掃機身 QR → 在機台上按一下按鍵 → 確認(「舊手機將不能再管理這台」;**網路設定保留**) | 4 |
| 轉賣 | 恢復出廠 → 把機台(含機身 QR)交出 | 3 |
| 機台回不了網 | app 首頁出現「客廳 沒有連上網路」→ 點一下看原因 / 修復(**修復 = 先送出這台還沒收到的新密碼;沒有待送的才重新套用最近一份成功的網路設定**,不行再提示其他做法) | 1–2 |
| 換網路密碼(擋掉不認識的裝置) | 收到提示 → 換密碼 → 確認 | 2 |

### 2.3 會跳出來的提示(只有這些)

- 「有一台不認識的裝置連進你的網路。要換密碼把它擋掉嗎?」(**加入申請優先顯示**,不認識裝置的告警延後幾分鐘,避免把正在加入的朋友擋掉)
- 「小明的『客廳』想加入你的網路。」
- 「客廳 沒有連上網路:<原因>。」(沿用 #127 的加入失敗原因)
- 「附近有 2 台還沒換到新密碼,要現在更新嗎?」
- 「這台設定沒有存好,下次更新軟體後可能會遺失。」(p5 寫入失敗,§6.4)
- 「app 版本太舊 / 太新,只能查看狀態與恢復出廠。」
- 「小華的機台不支援目前的網路設定。要調整整個網路讓他加入嗎?通訊距離可能變短,全部機台會重新連線約 1 分鐘。」(混合能力,§3.2;不出現頻寬、channel 等數字;加入的一方也收到「正在等網主調整網路」)
- 「這台新機已經被別人加入過了。如果不是你,請在機台上按一下按鍵後重新加入。」
- 藍牙前置條件(app 逐項檢查並引導):「請允許藍牙權限」「請打開手機藍牙」(iOS 無法由 app 直接打開,引導到「設定」)「請打開定位服務」(Android 11 以下)「找不到機台:確認機台已開機、燈號是藍色慢閃」。
- 確認碼不一樣時:「確認碼不同,請按拒絕」;遠端加入時:「請打電話和對方核對確認碼」。
- 成員(不是網主)看到不認識的裝置時:「已通知網主」,不讓成員換密碼。

「設定沒有存好」的提示要附做法:「請保持開機並重試;仍失敗請匯出診斷包」。

### 2.4 畫面規格(UX)

**導覽(四個分頁)**

| 分頁 | 內容 |
|---|---|
| 首頁 | 「附近」與「全隊」兩區;每台一張卡片:名稱、狀態(在網內 / 沒連上 / 待更新 / 新機)、電量、最後看到的時間、能力小圖示(對講、LoRa) |
| 網路 | 我的網路(或「建立 / 加入網路」);成員清單與能力統計(「可對講 3 台 / 有 LoRa 備援 2 台 / 一般 1 台」);邀請;換密碼;解散 |
| 新增 | 掃 QR(認領新機台、加入網路);一次認領多台 |
| 設定 | 我的手機(換手機、加一支手機);app 版本;說明 |

**依身分顯示**:網主看到邀請、換密碼、移除成員、解散;**成員**只看到網路狀態、成員清單與「離開這個網路」。一支手機可以是自己網路的網主,同時是別人網路的成員;**同一台機台一次只屬於一個網路**。

**機台頁**:狀態 → 能力分組的設定(只顯示這台有的)→ 診斷 → 軟體更新(機台不在附近時顯示「靠近機台才能更新」)→ 回報遺失 → 離開網路 / 恢復出廠(放最下面,紅字,要確認)。

**狀態**:在網路裡 / 還沒加入網路 / 沒連上網路 / 還沒換到新密碼 / 有新版本 / 新機。

**狀態呈現**:每種狀態有固定顏色、圖示與一句白話;沒有 LoRa 的機台不顯示 LoRa 區塊,但在網路頁的能力統計裡看得到。

**機台燈號(#128,三色,GPIO 16 / 20 / 21)**:

| 狀態 | 燈號 | app 畫面 |
|---|---|---|
| 未認領、藍牙就緒 | 藍色慢閃(1 秒一次) | 「附近的新機台」 |
| **按鍵後可以加入**(認領窗口開啟) | **藍色快閃**(1 秒 4 次),持續到窗口關閉 | 「現在可以加入」 |
| 加入中 / 換設定中 | 藍綠交替 | 進度畫面 |
| 在網路裡 | 綠色恆亮 | 「在網路裡」 |
| 還沒加入網路 | 綠色慢閃 | 「還沒加入網路」 |
| 沒連上網路 | 黃色慢閃 | 「沒連上網路」+ 原因 |

**野外條件**:按鈕大(戴手套可按)、高對比、可單手操作、深色模式;重要操作不靠滑動手勢。

## 3. 架構

```
手機 app ──BLE(主)/ WiFi HTTPS(備援)── 節點
                                         ├─ batman-provd(新):認領 / 設定 / 狀態 API(同一套訊息,走 GATT 或 HTTPS)
                                         │     └─ 608B(cryptoauthlib):DAC 簽章、CheckMac、ECDH
                                         ├─ 既有:batman-config-save / 96 / joinwatch / meshjoin / keyguard
                                         └─ 新 hook:依狀態產生 AP / firewall / dropbear(§6.3)
```

### 3.1 節點端:`batman-provd`

- 一支常駐服務,提供 §5 的 API。**傳輸無關**:同一套請求 / 回應訊息(JSON 或 CBOR)可以走 **BLE GATT**(主)或 **HTTPS**(備援);上層邏輯只有一份。
- 安全通道**不依賴 BLE 配對**(BLE 配對的 PIN 機制很弱),而是在應用層建立(§3.4)。
- WiFi 備援直接用 **HTTP 承載 §3.4 加密後的訊息**,不需要 TLS(所以不必讓 TLS 用 608B 的 DAC;原 B3 取消)【依 v2.3 review】。
- 只做三件事:驗證請求、把設定寫入 uci 並呼叫既有工具、回報狀態。入網、存 p5、keyguard 等邏輯**沿用既有程式**,不重寫。
- **強化**【依 v2.3 安全 review】:BLE 只開 LE,關閉 BR/EDR;不註冊配對 agent、不允許 bonding;只留必要的 GATT 服務;`batman-provd` 以非 root 執行並加沙箱;BlueZ 列入安全更新清單(#247)。
- **資源保護**:未通過交握的連線設逾時並可被擠掉(BLE 同時連線數很少,防止被佔住);每個連線的交握次數限速(每次交握 608B 都要簽一次,I2C 與 INA226 / RTC 共用);重組前先限制訊息大小(防止吃光 512 MB)。

### 3.2 能力模型(superset)

**機台回報能力,app 依能力顯示;網路參數取所有成員的交集。**

| 能力 | 偵測方式(節點自己判斷,不靠型號猜) | SKU(Batman-P `boards.py`) |
|---|---|---|
| `halow` | MM6108 介面存在 | 全部 |
| `gps` | GNSS 裝置 | 全部 |
| `ptt` | CM108 / OpenVLM USB 音訊裝置 | C1、C3、T1、T2 |
| `lora` | RAK4631(Meshtastic)USB 序列埠 | C2、C3、T2(T0 / T-TAK 選配) |
| `se` | 608B 回應 | 全部(P3) |
| `battery` | INA226 | 依硬體 |
| `ots`、`tak`、`secureboot`、`rtc` | 戰術專屬,民用版 app 不顯示 | T 系列 |

- 板子型號與能力偵測**沿用 #110 的執行期板子設定檔**,不另寫一套(#110 尚未實作,列為 P1 依賴)。
- **畫面取聯集**:app 內建所有功能模組;只顯示這台有的。沒有 LoRa 的機台,網路頁的能力統計寫明「沒有 LoRa 備援通訊」。**C3 的 LoRa 在 #220 W10 通過前顯示「之後更新開放」,不是直接不顯示。**
- **網路參數取交集**:建網 / 加人時,國家、channel、頻寬、LoRa preset 只能從**所有成員都支援**的範圍選;新成員不支援時,加入前就告知,不等失敗。
- **未知能力**(機台比 app 新):顯示「這台有新功能,請更新 app」,其他功能照常。
- **設定依能力分組**(`halow.*`、`lora.*`、`ptt.*`),各自帶版本;節點拒絕自己沒有的能力的設定並回報原因。

### 3.3 BLE 傳輸

**限制**:3A+ 是藍牙 4.2,只有傳統廣播:廣播封包 31 bytes,加上 scan response 31 bytes【事實,依 review】。128-bit service UUID 就佔 18 bytes。

**廣播預算**(待 B16 逐 byte 定案):

| 封包 | 內容 | 約佔 |
|---|---|---|
| 廣播 | Flags(3)+ 128-bit Batman service UUID(18) | 21 / 31 |
| scan response | service data 標頭 + 格式版本(1)+ 狀態旗標(1)+ 依狀態而定的內容(見下) | ≤ 31 |

| 狀態 | scan response 的內容 |
|---|---|
| 未認領 | `device_id` 末碼、能力位元、認領窗口是否開啟 |
| 已認領、未入網 | **擁有者標記**:以認領時交換的擁有者金鑰(類似 IRK)與短計數器算出的截短 MAC → **只有擁有者的 app 認得出是哪一台** |
| 網路成員 | **成員狀態摘要**:以網路金鑰經 HKDF(加標籤)導出的金鑰,AEAD 加密(短計數器 nonce + 截短 tag;截短後的安全強度要在 B16 寫明);不放固定識別碼,改用以 nonce 為鹽的短雜湊,只有成員算得出是哪一台 |

- **藍牙位址**:BlueZ 預設用固定的 public BD_ADDR,本身就是固定識別碼 → `main.conf` 開 `Privacy`(RPA),與摘要的計數器同步更換【依 review】。
- **摘要只用於顯示**,不能觸發任何安全動作(網路金鑰外洩時,外人可以讀、也可以偽造)。
- **換密碼期間**,成員 app 保留舊網路金鑰一段時間,才認得出還沒更新的機台。
- **iOS 背景**:同一台的重複廣播會被合併,看不到持續變化的摘要 →「不連線看整隊」只在 app **前景**成立;背景只用來發現「附近有待更新的機台」。
- 廣播間隔在耗電與發現速度之間取捨(B16 一併定)。
- 戰術版的 OPSEC 要求(#220 W6)以後以新的格式版本加嚴。

**GATT 傳輸規格**:一個請求特徵值 + 一個回應特徵值(notify)。每段帶長度與序號;單則訊息上限(成員名單、DAC 憑證鏈可能幾 KB);流量控制(iOS `peripheralIsReady`);MTU 協商(iOS 約 185 / 527,Android 最多 517)【依 review】。

### 3.4 應用層安全通道(BLE 與 HTTP 共用)

**兩種模式**【依 v2.3 安全 review】:

| 對象 | 交握 | 身分揭露 |
|---|---|---|
| 未認領的機台 | **SIGMA 式**:app 送臨時 ECDH 公鑰 → 節點回臨時公鑰 + DAC 憑證 + DAC 對交握的**帶標籤簽章**(`"batman-hs-v1"`)| 節點先出示 DAC(它本來就在廣播 `device_id` 末碼) |
| 已認領的機台 | **對方先證明身分**(類 Noise IK / KK):節點的靜態金鑰用 608B 的 ECDH 金鑰;app 必須先證明持有擁有者金鑰或網路金鑰,節點才送出 DAC 與 `device_id` | 防止任何人連上 GATT 就拿到明文的身分(追蹤) |

**規格要求**:
- 交握紀錄的雜湊涵蓋:協定版本、加密套件、傳輸類型、雙方臨時公鑰、DAC 憑證。app 要確認簽章裡是**自己的**臨時公鑰。
- session key 由同一份交握紀錄導出,**兩個方向各一把**;AES-GCM 的 nonce 用各方向的計數器,重組時拒絕重複與亂序。
- 所有簽章都**帶用途標籤**(F2);節點**不直接簽對方提供的值**,peer 挑戰由節點自己混入 nonce。否則節點會變成簽章 oracle,攻擊者能拿「正牌節點對自己臨時金鑰的簽章」冒充節點,騙走擁有者送出的網路密碼【依 review,MUST】。
- 走 WiFi / HTTP 時**一律再跑一次本通道**;app 不得在 BLE 失敗後改用較弱的流程。
- 交握雜湊用來綁定認領挑戰(§6.1)與擁有者簽章(§5)。
- 協定選型(自訂或採用 Noise 等現成框架)列為 B11。

### 3.5 手機端

- **跨平台框架(Flutter 或 React Native)+ 原生外掛**:BLE(iOS CoreBluetooth + bluetooth-central 背景模式與狀態還原,背景掃描必須指定 UUID;Android 12 以上 `BLUETOOTH_SCAN` / `CONNECT` 權限、背景掃描用 PendingIntent 且會被限流,可靠的背景連線要 connectedDevice 類型的 foreground service)、系統 keystore、QR 掃描;WiFi 大量傳輸時才用 WiFi 外掛。選型列為 B4。
- 內建 **Batman 製造商根憑證**,離線驗證機台是正牌。
- 本機資料庫:我的機台、我的網路(名稱、密碼、成員)、待更新清單。
- **發佈**:野外無法下載,出發前要裝好;Android 可直接裝 APK,iOS 只能走 App Store【事實,依 review】。

| 東西 | 存在哪 | 誰知道 |
|---|---|---|
| 機台出廠身分(DAC 私鑰 + 憑證) | 608B,私鑰不可讀 | 只有晶片 |
| 認領秘密(256 bit) | 608B(`IsSecret=1`、`NoMac=1`、只允許 `CheckMac`;出廠後鎖槽);機身 QR、盒內卡 | 持有 QR 的人 |
| 換密碼用的 ECDH 私鑰 | 608B,與 DAC 分開 | 只有晶片 |
| 擁有者金鑰 | 手機 keystore;公鑰在節點 p5 + `authorized_keys` | 擁有者的手機 |
| 擁有者標記金鑰(類似 IRK,廣播用) | 認領時交換;節點 p5 + 擁有者 app | 擁有者 |
| 網路管理金鑰 | 網主手機 keystore(+ 備用管理手機) | 網主 |
| 網路密碼(SAE) | 各成員節點;網主 app | 網路成員 |
| 成員名單 | 網主簽章,存在各節點 p5 與各成員 app | 網路成員 |

## 5. API(節點 `batman-provd`,v1)

所有請求走 §3.4 的安全通道(BLE 或 HTTP);下表的路徑是訊息類型,不限 HTTP。`/info` 與 `/claim/*` 不需擁有者身分,其他都需要。

| 端點 | 用途 | 身分 |
|---|---|---|
| `GET /v1/info` | device_id、型號、韌體版本、**API 版本**、**能力清單**(§3.2)、狀態(未認領 / 已認領 / 成員)、認領窗口是否開啟 | 無 |
| `POST /v1/claim/challenge` → `POST /v1/claim` | 認領(§6.1) | 無(靠認領秘密) |
| `POST /v1/owner` | 新增 / 移除擁有者公鑰(換手機) | 擁有者 |
| `PUT /v1/settings` | 名稱、國家 / 地區,以及**依能力分組**的個別設定(`ptt.*`、`gps.*` …) | 擁有者 |
| `POST /v1/network/join` | 加入網路(網路參數 + 網主簽章的成員名單) | 擁有者 |
| `POST /v1/network/update` | 網主簽章的設定(換密碼、更新名單),**附版本號** | 網主簽章(任何人可轉送) |
| `POST /v1/network/leave` | 離開網路 | 擁有者 |
| `GET /v1/status` | 沿用 #131 的 status JSON + 入網失敗原因(#127)+ p5 是否存好;**全隊**狀態經 mesh 查詢 | 擁有者 / 同網成員(唯讀) |
| `GET /v1/peers/challenge` | 回應成員名單偵測的挑戰(§6.6);節點自己混入 nonce,簽章帶標籤 `"batman-peer-v1"` | 同網成員 |
| `GET /v1/diag/summary` | 白話診斷摘要(§6.10) | 擁有者(同網成員只看摘要) |
| `POST /v1/bulk/open` → `/v1/bulk/close` | 請節點**暫時**開 WiFi 大量傳輸通道(一次性金鑰經本通道交付),供 image 用(§6.9) | 擁有者 |
| `GET /v1/diag/bundle` | 完整診斷包(經 BLE 分段) | 擁有者 |
| `POST /v1/report-lost` | 回報遺失(網主 app 對網路執行) | 網主 |
| `POST /v1/update/check` / `prepare` / `apply`、`GET /v1/update/status` | 軟體更新(§6.9) | 擁有者 |
| `POST /v1/reset` | 恢復出廠 | 擁有者 |

**擁有者身分驗證**:每個請求附 `owner_pubkey_id`、節點先前發的 nonce、與以擁有者私鑰對(`"batman-owner-v1"` ‖ 交握雜湊 ‖ 方法 ‖ 路徑 ‖ body 雜湊 ‖ nonce)的簽章。不依賴時間(P4)。

**同網成員身分驗證**:以網路金鑰導出的挑戰回應(節點出 nonce)。

**版本協商**:`/v1/info` 回報 API 版本;app 不認得時,**只允許查看狀態與恢復出廠**。

## 6. 流程

### 6.1 認領

**認領窗口**:
- **從未被認領過的機台,每次開機都開放**(開箱後先充電、隔天才裝 app 也沒問題)【依使用性 review】。
- 曾被認領、後來恢復出廠的機台:要**在機台上按一下按鍵**(或放 SD 卡標記檔)才開放 N 分鐘。這樣看過機身 QR 的人(修理行、前任擁有者)不能在你恢復出廠後搶先認領。
- 「是否曾被認領」記在 608B 的單調計數器(不會因重燒卡而重置)。
- app 偵測到窗口沒開時,用圖示教使用者按哪裡。

**步驟**(使用者只看到「掃 QR → 確認國家 → 取名」):
1. app 解析 QR:`device_id`、認領秘密。
2. app 依廣播中的 `device_id` 末碼找到這台(不需切換 WiFi),建立 BLE 連線。
3. 建立安全通道(§3.4),驗證 DAC 憑證鏈與 `device_id`。
4. 節點發 nonce,計算 `c = SHA-256(nonce ‖ 交握雜湊 ‖ DAC 雜湊 ‖ 擁有者公鑰)`;app 回 `HMAC(認領秘密, c)`;608B `CheckMac` 比對。**失敗次數只在每個連線內限制、存在記憶體**(256 bit 秘密無法暴力猜測;全機鎖定只會讓旁人把真正的買家鎖在外面,寫 p5 也會磨損 SD 卡)【依 v2.3 review 修正】。
5. 節點寫入擁有者公鑰與擁有者標記金鑰(§3.3),**就地完成 #137 鎖定**:`authorized_keys`、隨機 root 密碼(經安全通道交給 app 保存)、dropbear / ttylogin 鎖定、寫 `state/lock-status`、`batman-config-save --seed`【依 review 核對 137 / 96 / halow-status】。
6. 國家 / 地區**預設台灣 TW**(P13),**畫面顯示國家名稱請使用者確認**,可修改;不可靜默套用【依 review】。

**新機被搶先認領**:從未認領的機台每次開機都開放窗口,開過盒的人(店員、物流)可能先認領 → app 遇到「新機已被認領」時提示(§2.3),擁有者按鍵後以 QR 重新認領即可取回。

### 6.2 未認領時的保護

現行未 seed 的節點 root 是空密碼、dropbear 開密碼登入、AP 橋接進 ahwlan、firewall 全收 → 連上 AP 就能 SSH 成 root【事實,依 review】。所以:
- **未認領時不開 WiFi AP**,只開 BLE;認領只能經 §3.4 的安全通道。這也省掉了 v2 的「第一次接觸 AP」與其密碼。
- image 預設 dropbear `PasswordAuth=off`;開發用工作台入口改走既有 `/etc/batman-dev-open`(`96` L164)——**現在它只寫 DEV-OPEN 標記,要改成主動打開 `PasswordAuth`**【依 review】;**量產 image 不帶**。
- 已認領後的 WiFi AP(隊伍 AP、大量傳輸通道)金鑰來源:隊伍 AP 由網路設定產生;大量傳輸通道每次由 `bulk/open` 產生一次性金鑰,經 BLE 安全通道交給 app。
- 未認領時 LuCI 不開;`halow-status` 對未認領狀態的提示文字改寫(目前會說 anyone may get root)。

### 6.3 狀態在 OTA 後保住【依可行性 review】

- p5 記錄**狀態**(未認領 / 已認領 / 成員)與必要參數(擁有者公鑰、網路參數、成員名單、版本號),**不直接存 firewall 設定**;p5 schema 升到 2,`96` 的 `schema_migrate` 處理舊版。
- AP / firewall / dropbear 設定由**一支新的 uci-defaults hook 統一產生**,檔名排在 `99-halow-identity` 之後(例如 `99-zz-*`;放在 `96` 尾段會被 99 改 SSID 蓋掉)、keyguard(S18)之前。uci-defaults 只在 fresh overlay 執行 → **執行期的狀態轉換(認領、入網、離網)由 `batman-provd` 當場套用**,hook 只負責 OTA 後還原。
- **關 AP 一律以「key = placeholder」表示**:keyguard 在 MARK 存在、但 key 已不是 placeholder 時會刪掉 `disabled`(L40–45),可能把刻意關掉的 AP 重新打開【依 review】。
- `batman-config-save` 的 PRESERVE 清單加入上述欄位。
- `batman-autocommit` 的 `expected_in_mesh()` 改為依「p5 是否有成員資格」判斷(現在「已認領、未入網」的節點 OTA 會一直 revert)【事實,`batman-autocommit:133-141`】;**只有一台的網路**(建網的第一台沒有鄰居)也要能 commit。

### 6.4 設定推送

| | 擁有者的設定(加入網路、國家、名稱) | 網主簽章的設定(建網、換密碼、名單) |
|---|---|---|
| 成功條件 | N 分鐘內入網(沿用 `meshjoin.sh` 的 `meshjoin_joined`) | 簽章與版本號正確、radio 以 mesh point 起來(不要求看到鄰居) |
| 失敗 | **自動回滾**,app 說明原因 | **不回滾**(防止干擾逼回舊密碼),app 提示網主 |
| 版本號 | — | **簽發端每次只能 +1**;節點接受**簽章鏈**(從目前版本到最新的每一版都有網主簽章),拒絕舊版本與跳號【依 v2.3 review:漏掉兩次以上換密碼的節點也能追上,又不會讓版本號被一次耗盡】 |

共同規則:
- 換網路參數時,**BLE 不受影響**,手機不會失聯;**機台回不了網時,擁有者仍可經 BLE 連上修正**(不需要另開救援 AP)。
- 成功後**明確呼叫 `batman-config-save`** 並**同步更新 `lkg/`**:現行 `joinwatch` 每次開機只存一次(L138),而 `96` 在 `overrides.uci` 損壞時會退回 `lkg/`,若 lkg 沒更新就會用回舊密碼【事實,依 review】。`96` 讀 lkg 前比對版本號,不准退回舊版。
- 寫入 p5 失敗 → 提示擁有者(§2.3),不能等到下次 OTA 才爆。依賴 **#202**。
- 擁有者可以修改網主設定裡**密碼以外**的參數(例如網主建網時國家選錯)【依 review】。

### 6.5 建網與加入

**一個「網路」同時包含 HaLow 與 LoRa**(使用者只看到一個網路):

| | HaLow | LoRa(有 `lora` 的機台) |
|---|---|---|
| 產生 | 網路名稱 + SAE 密碼 | Meshtastic 頻道名稱 + PSK、modem preset(全網一致) |
| 成員身分 | DAC 公鑰列在成員名單 | 各台 Meshtastic PKC 公鑰**也列在成員名單**(與 DAC 綁定,沿用 #220 W13 的每台 PKC) |
| 換密碼 | SAE 密碼 | 頻道 PSK 一起換 |

**建網**:app 產生上表參數(使用者也可自訂密碼,最短長度沿用 #103)→ 網主成為管理者 → 對勾選的機台送 `network/join`;沒有 LoRa 的機台只收 HaLow 部分。完成後提示一次「加一支家人的手機當備用管理?」(掃一下即可)。

**加入朋友的網**:
1. 自己的機台已認領。
2. 取得網路參數(**國家、channel、頻寬**、HaLow 密碼、LoRa 頻道 / PSK / preset、網主公鑰):
   - **當面**:掃網主手機上的**邀請 QR**,內含**一次性的預先同意**(網主簽章 + 一次性 ID)→ 加入後不用再等網主。**不依賴時間**(P4):一次性 ID 用過即記入名單、不能再用;網主可在 app 上收回還沒用的邀請(收回紀錄隨名單散播)。混合能力的機台用預先同意的 QR 加入時,仍會先走「調整整個網路」的提示。
   - **遠端(傳圖片)**:網主分享**遠端用的邀請 QR 圖片**;朋友在 app「從相簿選取」或由聊天 app 分享進來。**這種 QR 不帶預先同意**(圖片容易被轉傳)→ 入網後送出加入申請,app 顯示「等待中」並可取消,網主核對確認碼後同意。QR 格式內以一個欄位區分「當面(帶預先同意)」與「遠端(需同意)」,使用者不必知道差別;當面用的 QR 不提供分享或存圖功能。
   - **只能講話(最後備援)**:念出**加入碼**(能還原所有參數;不能只有密碼,否則機台不知道 channel),之後流程同遠端。加入碼的字元集(數字或英數)於 B4 決定。
3. app 對自己的機台送 `network/join` → 機台入網 → 遠端加入時,網主 app 對新鄰居發挑戰(§6.6),顯示「小明的『客廳』想加入」與確認碼(兩支手機要一樣)→ 網主同意 → 更新名單並散播。
4. **混合能力**:新成員不支援目前的網路參數(例如 channel / 頻寬)時,網主收到「要把整個網路改成 X 讓他加入嗎?(全部機台會重新連線)」;選「是」即為一次網主簽章的設定更新(§6.4)。

**移除成員 / 解散網路**:移除後**自動換密碼**(不換的話被移除的機台仍連得上);解散的確認說明「朋友的機台也會離開;不在線的機台之後靠近時處理」。

**已有網路時加入新機**:認領完成後,app 直接問「加入『家裡網路』?」。

### 6.6 不認識的裝置與換密碼

- 偵測:網主(及成員)app 定期以 mesh 鄰居表為準,對每個鄰居 `GET /v1/peers/challenge`,要求 DAC 簽章;不在名單或答不出 → 告警。
- **誠實界線**:只能擋「不小心」的人(偽造 MAC 並拒答的人和暫時斷線的機台難以區分)【依 review】。
- 換密碼:網主 app 為名單內每台產生「新密碼封包」(HaLow 密碼 + LoRa PSK;以該台 ECDH 公鑰加密、網主簽章、版本 +1),經 mesh 送出,指定切換時刻。
- **不在線的機台**:封包(含簽章鏈)同步到每位成員的 app;成員的 app 發現還沒更新的機台時送出封包。**送出前必須**:
  1. 完成 §3.4 交握,**確認對方 DAC 就是封包的目標**(不能只看廣播的「待更新」標記;廣播摘要只用於顯示);
  2. 比對手邊最新的名單:目標已被移除或回報遺失,或名單版本高於封包 → **不送**。
- 背景能力受作業系統限制(iOS 背景會合併重複廣播、Android 背景掃描被限流)→ **前景時**提示「附近有 N 台還沒換到新密碼,要現在更新嗎?」,點一下送出;背景只用來發現並提醒。網主畫面常駐「N 台還沒更新」。B14 列 P2。
- **遺失的機台**:網主按「回報遺失」→ 先從名單移除,再換密碼;**不為已移除的機台產生封包**;遺失之前已同步到成員 app 的封包,依上面的第 2 點不會送出【依 review】。

### 6.7 LoRa(C2 / C3)

- **透過節點設定,不直接用 BLE 連 RAK**:RAK4631 以 USB 接在 Pi 上(`/dev/ttyACM0`,#181 實測),`batman-provd` 經序列埠呼叫 Meshtastic API。
- **RAK 自己的 BLE**:預設固定 PIN `123456`(#181 實測)太弱 → 出廠時**關閉**,或改為隨機 PIN。
- **preset / 頻率 / 功率不做執行期自適應**:改了就和其他節點說不同語言(`181-survival-strategy.md`)→ 只能由網主以網主簽章的設定全網一起改。
- **依賴 #220 W10(HaLow + LoRa 同機共存的 go / no-go)**:W10 未過之前,LoRa 設定功能不上線;HaLow 部分不受影響。
- RAK 韌體更新屬另一個韌體領域(單槽、無 A/B),只在實體接觸時做(#181),不由 app 推送。
- 序列埠控制工具的選型列為 B8(官方 meshtastic python CLI 在 512 MB 的 3A+ 上可能太重)。
- **`/dev/ttyACM0` 同時只能一個程式用**:#220 W2 的 LoRa gateway 也要用它 → 指定由一支常駐程式獨佔,其他程式(含 `batman-provd`)經它代理(B17)。

### 6.8 換手機

- 舊手機還在:舊手機在 app 上「加一支手機」,掃新手機的 QR → 新增擁有者公鑰。
- 舊手機沒了:**新手機掃機身 QR + 在機台上按一下按鍵**(開啟認領窗口)→ 以認領挑戰證明持有 QR → **替換擁有者,網路設定保留**【依使用性 review;實體持有本來就等於控制,不降低安全】。替換時**清掉所有舊的擁有者金鑰、擁有者標記金鑰與 `authorized_keys`,並重新產生 root 密碼**【依安全 review】。
- 網主手機沒了且沒有備用管理手機:網路仍可運作;無法再加人或換密碼 → 任一成員可「重建網路」:由他建立新網路並發出邀請,其他成員以邀請 QR(當面或圖片)/ 加入碼重新加入(每人 2–3 步)。

### 6.9 軟體更新

**範圍**:
- **系統 image(rootfs + boot 分割)**:HaLow 模組韌體(`/lib/firmware/morse/mm6108.bin` 與 BCF)在 rootfs,每次開機由驅動載入模組記憶體,不燒進模組【事實】→ 隨 image 更新與回滾,不會刷壞無線電。
- **OTA 帶不到的部分**【依 v2.4 可行性 review】:`config.txt`、`distroconfig.txt`、`cmdline.txt` 不隨 OTA 更新(`batman-slot:396-400,412`;`boards-and-builds.md`);Pi 3 的 p7 `bootcode.bin` 燒卡後凍結;firmware 白名單讀的是**正在跑的舊 image** 裡那一份(`batman-slot:34,319-329`),新的 `start*.elf` 要分兩次更新。→ F3 / §9 對 distroconfig 的改動(保留 BT、`miniuart-bt`、`core_freq`、新 HAT 的 GPS 改線)**無法經 app 送到已出廠的機台**,P1 試用機要重燒卡;`update/check` 要能回報「需要先裝中間版本」或「需要重燒卡」。
- RAK 韌體維持手動(#181);3A+ 沒有 EEPROM。

**簽章**【依 review,MUST】:現行 payload 是 gzip tar(`root.squashfs`、boot、metadata、`SHA256SUMS`),只驗完整性、**沒有簽章**(`platform-ab.sh:7-13`;`build-ab-payload.sh:73`)。新增:
- 以分離式簽章簽 `SHA256SUMS` + metadata(含 board、version);簽章**先經 BLE 送到節點驗過**,才接收 payload;`batman-slot` 讀回比對 `SHA256SUMS`,綁定內容。
- 驗簽不能只放在 `check_image`(`sysupgrade -F` 會略過)。
- 簽章格式與金鑰保管列為 B18。

**流程**:
1. `update/check`:版本、板子(bcm2710 / bcm2711 各一份 image)、**拒絕原因**(試用中拒寫 `batman-slot:285`、p5 還沒 seed、板子不符、需要中間版本 / 重燒卡)、**所需空間指 RAM**(3A+ 的 `/tmp` 只有 212 MB,payload 最大約 120 MB,只能落地一份)。
2. 經 BLE 送簽章 → 節點驗簽。
3. `bulk/open` → app 連上暫時 WiFi(系統對話框)→ 傳 payload 到 `/tmp` → `bulk/close`。
4. `update/prepare`:`batman-slot` **只寫入並驗證**,不 arm。
5. `update/apply`:arm tryboot → 重開 → autocommit。
6. `update/status`。

- **`batman-slot` 要拆成「寫入 + 驗證」與「arm」兩步**(現在寫完驗完就直接 arm,`batman-slot:423-443`)→ 兩板共用檔,列入 §9,兩板實測。
- `batman-provd` 以非 root 執行(§3.1),寫 `mmcblk0`、`vcmailbox` 需要 root → 經**權限受限的 root helper** 呼叫。
- **autocommit 的健康檢查加入 BLE**:現在只看 mesh11sd、openmanetd、wpad(`batman-autocommit:164`);新 image 的 BLE 若壞了仍會被 commit,而 3A+ 只能靠 BLE 管理 → 加入 bluetoothd、`batman-provd`、廣播在跑。
- **降版**:預設不允許,除非 image 的 metadata 標記允許降到該版本。
- **iOS**:app 進背景時本地 WiFi 上傳可能被暫停 →「可以離開畫面」只在傳完之後成立。
- 新版本由 app 在有網路時**背景自動下載**,使用者不用操作。
- 之後:手機只傳給一台,再經 mesh 分發給整隊(#116)。

**大量傳輸通道(`bulk/open`)**【依 review】:
- 暫時 AP 放在**獨立的 network / firewall zone**,只開 `batman-provd` 的埠;**不被 `meshpoint` 橋接進 ahwlan**(`meshpoint-1.8.0:67-70` 會把每個 `mode='ap'` 介面橋接進去,ahwlan zone 全收)、**不被 keyguard 處理**。
- 有逾時;**開機時一律清除**(否則斷電重開後 AP 會帶著用過的金鑰回來)。
- 與 HaLow 是不同無線電(MM6108 走 SPI,CYW43455 走 SDIO),理論上可同時運作,要實測(併入 B13)。
- 與隊伍 AP 共用 CYW43455:brcmfmac 能否同時開兩個 AP 未確認(B2)→ 預設**暫時取代隊伍 AP**(傳輸期間隊伍的手機連線會斷),傳完恢復。
- 5 GHz 時選非 DFS 頻道,設定國家碼。

### 6.10 診斷與 log

| 內容 | 傳輸 | 誰能看 |
|---|---|---|
| 白話摘要:目前狀態、加入失敗原因(#127)、最近幾次開機原因(boot-reasons)、異常告警、p5 是否存好 | BLE(`diag/summary`) | 擁有者;同網成員只看狀態摘要 |
| 完整診斷包:#127 既有的 bundle 內容(dmesg、logread、最多 5 份 ramoops、2 份 shutdown log),壓縮後約數十到數百 KB | **BLE**(`diag/bundle`,分段傳輸);大量傳輸通道只留給 image | 擁有者 |

- 診斷包**存在手機**,之後回到有網路的地方再分享給支援人員。
- 內容**不含金鑰**(`halow-status`、`joinwatch` 只顯示 SET / PLACEHOLDER)【事實,依 review】,但有使用者取的名稱、mesh_id、鄰居 MAC、IP、logread 裡的手機 MAC → 分享前提示「包含裝置名稱與位址」。
- **現有 `/cgi-bin/bundle` 經 uhttpd 對 ahwlan 上任何人開放、不需驗證** → 民用 image 關閉(或加驗證);由 `batman-provd` 自己執行收集腳本,經 §3.4 傳出。
- log **不得包含密碼或金鑰**(§7)。

## 7. 重置

| | 離開網路 | 恢復出廠 |
|---|---|---|
| 清除 | 網路密碼、成員名單、隊伍 AP;p5 的網路部分與 `lkg/`;p6 的 `mesh-expected` / `mesh-joined`;`/etc/halow-keyguard.blocked` | 上一欄 + 擁有者、`authorized_keys`、root 密碼、`lock-status`、整個 p5(**先清 p5 再清 overlay**,否則 `96` 會把擁有者還原回來)、p6 資料、**另一個 A/B 槽的 overlay**(整槽作廢,由 `batman-slot` 執行;**試用期中拒絕**) |
| 保留 | 擁有者、出廠身分 | 出廠身分(608B) |
| 觸發 | app | app;**SD 卡標記檔**(現行 HAT 沒有按鍵時唯一的實體方式);之後 HAT 上的按鍵 |
| 中途斷電 | — | 開始前寫清除日誌標記,開機看到就續做 |

- **誠實界線**:p5 / p6 / overlay 都是明文,清除是「盡力覆寫」;SD 卡磨損平均下不保證讀不回。說明書要寫明「轉賣前恢復出廠,但最安全是換一張新 SD 卡」。
- **SD 卡標記檔**:每次開機都執行的 init(在 S10 之前或之內),讀目前開機槽的 FAT(由 `batman-slot active` 判斷;p1 / p3,Pi 3 另有 p7),清完刪除標記並重開。**也會開啟認領窗口**。
- **長按電源鍵不能用**:LTC2955 長按約 5.3 秒會硬體斷電【事實,#225】。
- 日誌(flightrec、ramoops、logread)**不得記錄密碼或金鑰**。

## 8. 出廠

1. 燒錄站:設定並鎖定 608B → 晶片內產生 DAC 與 ECDH 金鑰 → 產線 CA 簽 DAC,壓縮憑證寫回 608B → 寫入認領秘密 → 鎖認領秘密槽。
2. 印兩份 QR:機身貼紙(**貼在 HAT 上**,換外殼也對得上)與盒內卡。
3. **裝箱前驗證**:掃卡、實際連線完成一次認領挑戰。驗證用專用的「出廠測試」模式,不遞增「曾被認領」計數器,驗完不留擁有者。
4. 整卡清零後燒 image(#208 規則)。
5. **mesh / AP 密碼都不烤入**(`depersonalise.sh` 不再用 `--mesh-key --ap-key`)→ 改 #208 DoD / A5 與 `golden-image.md`。
6. 工廠**不保存**認領秘密。

## 8.5 對 HAT 的硬體需求(給 v4 HAT 設計,#240)

硬體路線:**先設計 HAT,外殼(#228)再配合**(使用者 2026-10-06)。本節是民用供裝對 HAT 的需求;同樣內容記在 #240。

| # | 需求 | 理由 | 現況(HAT v1) |
|---|---|---|---|
| H1 | **所有 SKU 都焊 ATECC608B-SSHDA**(未設定版,I2C `0x60`) | 出廠身分、認領秘密都存在裡面;重燒 SD 卡後 QR 仍有效(P3;#47 已決定「SE 是每塊板子的外加元件」) | 放的是 608C-TFLXTLS(設定區不可改)→ 換料;SOIC-8 腳位相同,footprint 不用改(#240) |
| H2 | **一顆瞬時按鍵**,與電源鍵分開 | 開啟認領窗口(恢復出廠後、換手機);恢復出廠也可用(開機時長按)。電源鍵不能用(LTC2955 長按約 5.3 s 硬體斷電,#225) | 沒有 |
| H3 | 按鍵:**凹陷式、不需工具、戴手套可按**,按下有燈號回饋 | 使用性 review:針孔需要迴紋針、戴手套無法操作 | — |
| H4 | 按鍵接一支**開機預設下拉**的 GPIO,接成「按下 = 拉到 3V3」 | GPIO 9–27 開機預設下拉(BCM2711 / BCM2837 相同) | HAT v1 **沒有剩餘 GPIO** → 依 #240 的 TPM 決定:TPM 拿掉 → GPIO16 / 18–22 全空;TPM 改 I2C(SLB9673)→ 18–22 空 |
| H5 | 狀態燈維持 #128 的 GPIO 16 / 20 / 21 | 認領、入網、錯誤的回饋 | 與 TPM 的 SPI1(20 / 21)及 TPM_RST(16)衝突(#240) |
| H6 | **QR 貼紙位置**:在 608B 所在的 HAT 上留貼紙區 | 民用 QR 印在機身,必須和 608B 綁在同一塊板;外殼要讓使用者看得到(開電池蓋或外殼複印一份) | 沒有 |

## 10. 分期(三個階段,2026-10-06)

順序:**① 入網(軟體身分)→ ② 既有 HAT 接 608B → ③ 新 HAT**。每個階段都能獨立驗收,前一階段的成果直接沿用。工作細項與驗收條件見各子單。

| 階段 | 目標 | 主要內容 | 依賴 | 子單 |
|---|---|---|---|---|
| **1 入網**(只限內部開發,不可出貨) | 使用者只用 app(BLE)完成:**S1** 設定自己的機台(1 台或多台)並組網;**S2** 邀請別人的機台;**S3** 加入別人的網;**S4** 看狀態、log、診斷包;**S5** 軟體更新;**S6** 離開網路 / 恢復出廠、回不了網的修復、移除成員、改名與國家 / 地區 | p5 狀態模型與 OTA 還原(§6.3)、`batman-provd` + 安全通道(**軟體身分**)、兩類設定推送、邀請 QR(當面 / 圖片)、全隊狀態、診斷(BLE)、軟體更新(簽章、`batman-slot` 拆兩步、autocommit 加藍牙)、BlueZ + GATT、`miniuart-bt`、app 骨架 | **#202**、BlueZ 打包(B12、B15)、B4、B11、B18 | #254 |
| **2 既有 HAT + 608B**(= P1,內部試用) | 真正的機台身分與認領保護 | 608B 槽位與位址(B1、B9)、cryptoauthlib(#196 ①)、開發用出廠腳本、軟體身分換成 608B、認領與認領窗口、未認領保護(§6.2)、#137 就地鎖定、換手機、BLE 廣播加密摘要與擁有者標記(B16)、不認識裝置偵測與換密碼;LoRa(等 #220 W10) | 階段 1、#196、#220 W10(LoRa) | #255 |
| **3 新 HAT**(= P2,第一個對外版本) | 實體按鍵、燈號、出廠流程;§2.2 步驟上限開始驗收 | 新 HAT 滿足 H1–H11(§8.5、#240)、bring-up、按鍵與燈號軟體、拿掉 `miniuart-bt`、正式出廠燒錄站與 QR 貼紙、使用性驗收 | 階段 2、#240、#228 | #256 |
| **之後** | | 經 mesh 整隊分發更新(#116)、背景 BLE 強化(B14)、戰術版(#54) | | |

**階段 1 的風險說明**:軟體身分存在 SD 卡上,未認領時也還沒關閉 AP / 密碼 SSH,所以階段 1 的機台**只能在內部使用**;這些保護在階段 2 補上。
