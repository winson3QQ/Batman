## 0. 一句話

使用者買到節點後,**完全離線**、用手機 app 完成:認領自己的機台 → 建立或加入網路 → (戰術版)取得憑證並使用 TAK → 任務結束或機台遺失時,以分級重置收回。身分分三層:**① 擁有者**(永遠是個人或單位)、**② 網路成員**(網路有自己的管理者)、**③ 應用身分**(TAK,只有戰術版)。民用與戰術版共用同一套流程與程式,**只有「成員資格如何執行」與「秘密如何保護」不同**。

### 1.1 使用者看得到的部分:原則與步驟上限

**原則**(P17):
- 使用者只看到**結果**與**需要他決定的事**;不出現「憑證、中繼 CA、分持、權杖、版本號、名冊、commit-confirm」等名詞。
- 每個新規則加入前,先問「能不能由系統自動完成」;不能時,才變成一個白話提示,並計入下表的步驟上限。
- 罕見事件(遺失、被俘、分區合併)可以多幾步,但必須是**引導式流程**(app 一步一步帶),不能要求使用者記得規則。

**各角色的步驟上限(驗收標準)**:

| 角色 / 情境 | 使用者做的事 | 上限 |
|---|---|---|
| 民用:開箱認領 | 掃機身 QR → 確認 region(由手機地區自動帶入)→ 為機台取名 | 3 |
| 民用:建網 | 按「建立網路」→ 取名(密語由 app 自動產生)→ 選要加入的機台 | 3 |
| 民用:加入別人的網 | 認領自己的機台 → 掃網主手機上的 QR(或輸入密語)→ 等網主按「同意」 | 3 |
| 戰術隊員:加入 | 掃卡 → 掃隊長手機上的加入 QR → 等核准(ATAK 自動設定完成) | 3 |
| 戰術管理者:建網 | 按「建立網路」→ 從附近隊員中點選副管理者與分持保管人 → 各人在自己手機上按「接受」→ 完成 | 5 |
| 戰術管理者:核准隊員 | 收到「XXX 申請加入」→ 生物辨識 → 核准 | 2 |

**自動處理、使用者看不到的**:認領挑戰、#137 鎖定、p5 寫入、狀態保存(§6.9)、commit-confirm 與回滾(§6.2)、版本號、權杖移交(§4.3)、重新加入封包的產生與遞送(§7.1)、時間下限的日常推進(§4.4)、多期 key 輪替、續期(管理者手機在附近時)、分持配發(§4.2)、DAC 驗證。

**會跳出來、需要人決定的**(白話範例):
- 「有一台不認識的裝置連進網路了。要換密碼把它踢掉嗎?」(民用名冊偵測)
- 「小明的機台申請加入。同意嗎?」(核准)
- 「機台的時間將從 10/1 跳到 10/8。確定嗎?」(時間跳幅超過 Δ)
- 「這次任務快到期了。要延長嗎?需要 <分持保管人> 在附近。」(任務延長)
- 「回報遺失」引導式流程(撤銷、換 key、DAC 黑名單一次完成)。

## 2. 威脅模型(依 SKU)

| | 民用(3A+) | 戰術(Pi 4 / CM4) |
|---|---|---|
| 主要威脅 | **key 無意外流**;外人加入 mesh 後做協定層干擾(灌 OGM、亂報路由,#49);附近的人搶先認領或亂改設定 | **機台被俘**(軍用通信的標準前提:設計時假設機器一定會落入敵手) |

## 3. 硬體與秘密

### 3.1 HAT 改版

- **安全元件改回 608B-SSHDA-B(`0x60`)**:`hat-v1-spec.md` §5.2 目前寫 608C-TFLXTLS(`0x36`),但 TrustFLEX 的設定區出廠固定、不能改【事實,hat-v1-spec §5.2】,本設計需要自訂槽位(§3.3)。→ 回寫 hat-v1-spec §4.2 / §5.2 / §7,關閉 #240 第 1 項。
- **TPM 由 SLB9672(SPI)改為 SLB9673(I2C)**:同系列、同 PG-UQFN-32 封裝,Linux `tpm_tis_i2c`【事實,Infineon / kernel DT binding `tcg,tpm-tis-i2c`】。與 608B、INA226、RV-3028 並排在 I2C1,**匯流排維持 100 kHz**(hat-v1-spec 的既有設定)。SLB9673 的 I2C 位址不得與 0x40 / 0x41 / 0x52 / 0x60 衝突【待查證,規格書】。
- I2C1 是共用匯流排 → TPM 的 unseal **一律走加密的 salted session**(hat-v1-spec §5.1 第 2 點)。
- **新腳位表**【提案】(SPI1 + PIRQ 釋放出 GPIO 18–22):

| GPIO | 原用途 | 新用途 | 備註 |
|---|---|---|---|
| 16 / 20 / 21 | TPM RST / SPI1 MOSI / SCLK | **#128 狀態燈(維持 #128 原定案)** | #128 選這三支是因為 pin 36/38/40 相鄰、旁邊就是 GND pin 39;SPI1 拿掉後衝突自然消失 |
| 22 | TPM PIRQ | **TPM RST** | 開機預設下拉 → 每次 SoC 重置都把 TPM 一起重置(hat-v1-spec §5.1 的要求);外加 10 kΩ 下拉照舊 |
| 18 | SPI1 CS | **針孔重置鍵** | GPIO 9–27 開機預設下拉(BCM2711 與 BCM2837 相同)【事實】→ 按鍵接成「按下 = 拉到 3V3」 |
| 19 | SPI1 MISO | **zeroize 開關**(戰術) | 同上 |
| 12 / 13 | UART5 → GNSS | 視 §3.2 C1 而定 | |

### 3.3 608B 槽位規劃【提案,P0 阻擋項】

ATECC608B 的設定區鎖定後不可逆,**鎖錯只能換晶片**【事實,hat-v1-spec §5.2】。槽位要先在消耗品上練過再定案(併 #196)。

| 用途 | 金鑰型態 | 存取規則 | 兩版 |
|---|---|---|---|
| DAC 私鑰 | P-256,晶片內產生 | 只能簽章;**不可讀、不可做 ECDH** | ✅ |
| ECDH 私鑰(換 key 派送用) | P-256,晶片內產生 | 只能 ECDH;與 DAC 分開,一把 key 不兼兩種用途 | ✅ |
| **認領秘密** | 32 bytes 隨機值 | **`IsSecret=1`、`NoMac=1`,只允許 `CheckMac`**(不得允許 MAC / HMAC 命令輸出結果,否則晶片會成為替任意輸入算出答案的 oracle)。戰術版:可加密寫入以輪替(§6.8),**write key 由 Pi 4 OTP 衍生**,不得是韌體常數;民用版:出廠後**鎖定該槽**(`SlotLocked`),不可改寫 | ✅ |
| IO protection key | 對稱 | 只保護 ECDH / KDF 的輸出與 Verify 結果(§3.5);host 端存在 Pi 4 OTP | 戰術 |
| DAC 憑證 + 產線中繼 CA 憑證 | 壓縮憑證格式 | 可讀;**存在 608B,不存在 SD 卡**(整卡清零或換卡後仍可認領) | ✅ |
| 第一次接觸 AP key | 資料 | 可讀(hostapd 需要明文) | ✅ |

**防重放不用單調計數器**:608B 計數器有寫入次數上限(約 200 萬次),且多支手機之間要同步計數值 → 改用節點出題的 challenge nonce【決策,依 review】。

### 3.4 秘密不落盤【提案,P1 阻擋項】

v1 宣稱「清除時只要銷毀金鑰」,但**現在執行中的秘密是以明文放在 overlay**:mesh / SAE key、AP key 在 `/etc/config/wireless`,`authorized_keys` 在 `/etc/dropbear`,OpenWrt 的 WireGuard 私鑰在 `/etc/config/network`;**另一個 A/B 槽的 overlay 也有一份**(`96` 在每個 fresh slot 都會從 p5 還原,`p5-config-partition.md`)。SD 卡又因磨損平均無法可靠覆寫【事實,業界共識】。所以:

- **要求**:秘密只在 tmpfs 中以明文存在;overlay 與 p5 只放加密後的版本或不含秘密的設定。候選做法:開機時(早於 S18 keyguard)由一支 hook 從加密來源解出秘密,寫入 `/var` 下的生成設定,再讓 uci / hostapd 讀取。可行性要先做原型(uci commit 會以 rename 取代檔案,單純 symlink 不可行)。
- **在 §3.4 完成之前,本文件所有「加密抹除」「清除後讀不到」的保證都降級為「盡力覆寫」**,包括戰術版。**§3.4 是戰術版的出貨門檻**,不只是 P1 的阻擋項。
- **日誌不得記錄秘密**:flightrec、ramoops、logread、boot-reasons 都不得輸出 uci 的 key 欄位或任何金鑰內容(民用版 p6 是明文)。
- 民用版 p5 / p6 不加密(P11):民用版的轉賣隱私只有 L2 的盡力覆寫,說明書要寫明這個限制。§3.4 對民用版的意義是「秘密不散落在 overlay 各處」,讓 L1 / L2 的清除範圍明確可控。

### 3.5 綁定:防止整片 HAT 或 SD 卡被移到別台 Pi

Pi 沒有 measured boot,PCR 值固定,用 PCR 封存的 key 移到另一台 Pi 照樣解得開【事實,hat-v1-spec §5.1】。所以「只綁 LUKS」不夠:TPM 裡的中繼 CA、成員金鑰,以及 608B 的 DAC,換一台 Pi 都能被攻擊者直接使用。戰術版【決策,依 review】:

- **TPM**:所有物件(LUKS 封存、成員金鑰、中繼 CA)的 authValue / policy 都要納入 **KDF(Pi 4 OTP 裝置私鑰)**;只有 signed boot 後的系統讀得到 OTP → 換一台 Pi 就無法使用 TPM 物件。
- **608B**:啟用 **IO protection key**(host 端存在 Pi 4 OTP)。**它只加密 ECDH / KDF 的輸出、保護 Verify 結果,擋不住 Sign、MAC、CheckMac**【事實,依第二輪 review 更正 v1.1】→ HAT 移到別台 Pi 後,**DAC 仍然可以簽章**,攻擊者能以「正牌」身分送 CSR 或回應名冊挑戰。補救:
  - 撤銷清單支援 **DAC 黑名單**(擁有者回報遺失時,把該台 DAC 列入,所有網路都拒絕它);
  - DAC 只證明「是 Batman 製造的硬體」,**不代表授權**:加入網路永遠需要管理者核准(§6.6)。
- 中繼 CA 與成員金鑰**在 TPM 內產生,設為不可複製**(`fixedTPM`)。
- **殘餘風險**:TPM 的綁定前提是 signed boot 之下的系統沒有遠端程式執行(RCE)漏洞;一旦被 RCE,攻擊者可以在本機叫 TPM 運算。這由 #74 / #97 的系統強化處理,不在本文件範圍。
- 民用版沒有 OTP、沒有 signed boot,**不提供這項保證**(§2)。

|---|---|---|---|---|

**WireGuard 的 Curve25519 無法放進 608B**(只支援 P-256)【事實】;SLB9673 是否支援【待查證】→ 預設 WireGuard 私鑰放 LUKS 內、執行時在 tmpfs(§3.4),由節點憑證綁定其公鑰。

## 4. 身分與信任結構

### 4.1 三層身分

| 層 | 民用 | 戰術 |
|---|---|---|
| **⓪ 出廠身分** | 608B 的 DAC(終端憑證,由 Batman 產線中繼 CA 簽發) | 同左 + TPM 原廠 EK 憑證 |
| **① 擁有者** | app 產生的 P-256 金鑰對(可多把:多支手機、單位多位管理員);公鑰寫進 p5,**同時作為 #137 的 operator pubkey** | 同左 |
| **② 網路成員** | mesh 參數 + SAE key + **管理者簽章的名冊** | 同左 + **網路 CA 簽發的節點憑證**(綁定 WireGuard 公鑰) |
| **③ 應用身分** | 無 | TAK 中繼 CA 簽發的 ATAK client 憑證 |

- **擁有權和成員資格分開**:網主只能把你移出名冊或撤銷憑證(效果等同 L1),**不能管理你的機器,也不能遠端 zeroize**(§8.3)【決策】。
- 民用版不需要 CA;**每個節點一次只屬於一個網路**(HaLow 只有一張 mesh 介面)【事實】。
- 待查證:dropbear 是否編入 ECDSA(P-256 的 `authorized_keys`);不行就另產 ed25519 的 SSH 金鑰給 `authorized_keys`。

### 4.2 戰術版的 CA 結構

```
網路根(建網時產生;散戶:拆成 3 份;機構:由機構的根簽發)
 ├─ 管理者中繼 CA ×N(各管理者節點的 TPM,依順位 1..N) → 簽發節點憑證
 └─ TAK 中繼 CA       (OTS 節點的 TPM)                → 簽發 OTS 伺服器憑證 + ATAK client 憑證
```

- **網路根屬於「網路」,不屬於任何一台機台**:建網時才產生。機台出貨時不知道、也不需要知道誰會是管理者;**每位戰術版持有人都是潛在的管理者**,組網時由發起人建網、成為順位 1,再指定其他管理者【決策,U3】。
- **網路根的保存依使用者類型分兩種模式**(共用同一套程式)【決策,U3】:

| 模式 | 網路根 | 保存 |
|---|---|---|
| **散戶(臨時組隊)** | 建網時由發起人的 app 產生 | **Shamir 秘密分享,拆成 3 份、任 2 份可用**:順位 1 的手機、順位 2 的手機、**一位非管理者隊員(分持保管人)的手機**;紙本為選配備份。完整的網路根**平時不存在任何地方**,需要時湊齊 2 份、在 app 記憶體內重建、用完即丟 |
| **機構** | 機構在基地用自己的離線根,**每次任務簽發**網路根或管理者憑證 | 由機構自行決定(HSM、保險箱、多人控管),我們不經手;app 支援「匯入機構信任根」 |

  - **分持的保管規則**【決策,依第二輪 review】:
    - **第三份給「分持保管人」**:一位**不是管理者**的隊員,由建網者在 app 上從附近隊員中點選,對方按「接受」即完成,全程自動配發【決策,2026-10-05 修訂 U3】。理由:野外印不出紙本;交給隊員手機則現場就能湊齊 2 份。
    - **同一個人不得持有兩份**(app 強制);紙本若作為選配備份,同樣不得交給任何已持有分持的人。否則一人被俘就湊滿 2 份。
    - 手機上的分持放在系統 keystore,**每次使用都要求使用者驗證**(生物辨識或 PIN)。
    - 交付給順位 2:兩人當面以 QR 傳遞,或以順位 2 的 app 公鑰加密後經 mesh 傳送。
    - 管理者換手機:舊手機仍在 → 以新手機的公鑰加密轉移;舊手機已遺失 → 視為**分持遺失**(下一點)。
  - **分持遺失只能換根,不能「重新分持」**:同一把網路根的舊分持無法作廢,任兩份舊分持仍能組回原本的網路根【事實】。所以任何一份遺失或疑似外洩 → 用剩下的 2 份**產生新的網路根**,重新簽發所有管理者中繼 CA 與 TAK 中繼 CA(節點憑證與 ATAK 憑證跟著重發),再拆成新的 3 份。
  - 散戶模式的效果:**任何單一一人被俘,敵方都拿不到網路根**;任何一人遺失手機,其餘兩人仍可使用。
  - **分持保管人離隊或換人**:視同分持遺失 → 現場兩位仍持有分持的人在附近時,app 引導「一鍵換根」(重簽所有中繼 CA、重新配發三份),使用者只需按確認。
  - **「至少 2 位管理者」的後果**(P12):一個人帶多台機器單獨使用時無法建網;可以用兩支手機當兩位管理者繞過,但這樣兩份分持在同一個人身上,散戶模式的保護就不成立。app 要提示。
  - 業界對照:DNSSEC 根金鑰儀式、HashiCorp Vault 解封、加密貨幣錢包的社交復原都採用門檻分持;軍方 / 企業由機構集中產生(NSA KMI、企業 PKI)。
  - 網路可以只用一次(單次任務),也可以長期保留(固定班底),由建網者決定。
- 節點憑證與 TAK 憑證用不同的中繼 CA(#58)。**建議 OTS 不放在網主節點上**;放在同一台時,該台被俘 = 兩個中繼 CA 同時失守,文件與 app 要明確提示【決策,依 review】。
- 管理者有**順位**(建網時由網路根簽章的管理者清單),**至少 2 位**(P12)。
- 效期:節點憑證 = 任務期間,可續期(§7);**中繼 CA = 任務期間 + 寬限期**(比節點憑證長,否則續期時中繼 CA 本身已經到期)。任務延長超過中繼 CA 效期時,要用網路根重簽中繼 CA,也就是**現場要湊齊 2 份分持**(或向機構申請)。
- **撤銷管理者的規則**【提案】:
  - 撤銷某位管理者 = 網路根簽章(散戶:湊齊 2 份),**或其餘管理者中的 2 位共同簽章**。
  - 只有 2 位管理者時無法湊出「其餘 2 位」→ 任一方提出撤銷時,**雙方都進入「凍結」**。凍結期間**所有管理動作都停止**:不簽發、不核准、**不換 key**、不撤銷個別節點(避免被俘的一方藉撤銷全部節點造成 DoS)。既有憑證到期前仍然有效。被俘的一方無法藉此排除另一方。
  - 解除凍結需要網路根:散戶模式下,未被俘的管理者 + 分持保管人**在現場就能湊齊 2 份**,app 引導完成(重建網路根、撤銷被俘一方、恢復管理)。機構模式向機構申請。
  - **延遲**:被俘管理者在凍結之前簽出的憑證,要等網路根重建、撤銷它的中繼 CA 之後才會連帶失效。
  - 凍結是安全的失敗方式:網路繼續運作,只是暫時不能管理。
- 撤銷清單由簽發者簽章、附版本號,在 mesh 內散播(§12 Q4);**撤銷只會累加,不會被覆蓋**。

### 4.3 名冊

- 兩版共用:管理者簽章的成員清單(DAC 公鑰、名稱、擁有者公鑰、(戰術)節點憑證序號),附**版本號 + 簽章者 + 前一版的雜湊**。
- **執行方式依 SKU**:

| | 民用 | 戰術 |
|---|---|---|
| 執行 | **偵測 + 換 key** | **WireGuard**:只和名冊內、憑證有效的節點建立通道 |
| 偵測方式 | 以 mesh peer 表為準,對每個 peer 發 **challenge**,要求以 DAC 簽章回應(不是由節點主動宣告,避免重放);答不出來或不在名冊 → 告警 | — |
| 誠實界線 | **只能擋「不小心」的人**:攻擊者可以偽造名冊內成員的 MAC 並拒答 challenge,和「暫時答不出」難以區分;偽造的告警也會造成告警疲勞 | — |

- **多位管理者的寫入衝突**(網路分區時各自修改)【提案】:
  - 成員新增與撤銷:**取聯集**,撤銷優先。
  - **換 key 只能由「持有現役權杖」的管理者發起**。權杖預設在順位 1;順位 2 在連續 T 小時聯絡不到順位 1 後,可以簽章聲明接手。
  - **權杖有效期**:權杖附到期時間,依可信時間(§4.4)判斷,到期後必須重新聲明;**凍結期間權杖無效**。這樣被俘的權杖持有者無法無限期地發起換 key。
  - 若分區期間兩邊都換了 key,兩邊的網就會分裂且無法自行合併 → 依順位,較高順位一方的 key 為準。敗方的管理者在得知結果後(當面或經任一條仍相通的路徑),由其 app **自動對己方所有節點批次產生重新加入封包**(§7.1),在己方目前的 key 上廣播,節點自行切換到勝方的 key,不需逐台操作。app 要明確警告「分區期間換 key 會分裂網路」。
  - 管理者「復活」後,以接手者在其離線期間的決定為準,復活者需重新取得權杖。

### 4.4 時間

兩版都有 RV-3028(P3),但超級電容只撐約 2 天【推論,hat-v1-spec §5.3】,而且 #174 的歷史問題(時鐘倒退 15 個月導致憑證失效)不能重演【事實,#174】。規則【決策,依 review】:

1. 開機讀 RV-3028 的 **PORF(電源中斷旗標)**:有中斷 → 時間標記為「不可信」。
2. p5 記錄**時間下限**(最後一次可信時間);**系統時間永遠不得早於下限**。
3. 只接受兩種校時來源:擁有者 app(手機時間)與**管理者簽章的校時訊息**。GNSS 可以參考,但不能單獨推翻下限(GNSS 可被偽造)。
4. **下限不能被一次推高太多**【決策,依第二輪 review】:手機時間設錯、被俘管理者送出未來時間,都可能把下限永久推高,導致全網憑證被判過期、再觸發自動 L1(大規模 DoS)。所以:
   - 每次校時,下限最多前進 **Δ**(例如 24 小時);
   - 要前進超過 Δ,必須**擁有者在 app 上確認**(顯示「節點時間將由 X 跳到 Y」);管理者簽章的校時只能在 Δ 以內推進;
   - 擁有者可以**重設下限**(本機確認),用於修正錯誤。
5. 時間不可信時:
   - 多期 mesh key **依序嘗試已預載的期數**,找到能入網的那一期;
   - 憑證驗證採**有上限的寬限期**:最多接受比時間下限晚 G 小時的到期憑證;
   - app 連上時提示並自動校時(受第 4 點限制)。
6. **多期 key 的切換邊界接受相鄰兩期**,避免各節點 RTC 的微小漂移造成短暫分裂。
7. **自動 L1(憑證到期離網)只在時間可信、而且寬限期結束之後才執行**。
8. 民用版不用時間做防重放(§3.3 改用 challenge nonce)。

## 5. 節點狀態機(兩版共用)

```
                認領                  加入 / 建立             commit-confirm 成功
 [未認領] ───────────→ [已認領] ───────────→ [入網確認中] ───────────────────→ [網路成員]
    ↑                   ↑   ↑  ↖                   │ 逾時未入網 → 自動回滾                │
    │                   │   │    ╰─────────────────╯                                  │
    │                   │   ╰──────────────── L1 離網(含過期自動 L1)──────────────────┘
    │      L2 解除認領   │
    └───────────────────┘        擁有權移轉:[已認領/網路成員] → 同狀態,擁有者換人,不清資料
    ↑
    └── L3 Zeroize(只有戰術版;從任何狀態直接回到這裡)
```

| 狀態 | AP | SSH / 管理面 | HaLow |
|---|---|---|---|
| **未認領** | 第一次接觸 AP(key 印在 QR 卡上),**獨立的 firewall zone,不橋接 ahwlan,只開放認領服務** | **全部關閉**:dropbear 不開密碼登入、LuCI 不開 | keyguard 擋住(#103) |
| 已認領 | 同上,但開放擁有者認證後的設定服務 | 只接受擁有者金鑰 | 擋住(還沒有 mesh key) |
| 入網確認中 | 救援 AP(見下) | 擁有者 | 開(新設定) |
| 網路成員 | **隊伍共用 AP**;救援 AP 依下方規則 | 擁有者;隊伍 AP 上的其他手機**不得**直達管理面 | 開 |

**救援 AP**(使用第一次接觸 AP 的 key)在**任何狀態**下都是**獨立的 firewall zone,不橋接 ahwlan**,只開放擁有者認證的設定服務,以及**不需認證、只收簽章封包的服務端點**(收重新加入封包,§7.1)。民用版的救援 AP key 就是機身貼紙上的 key、永不輪替,所以這條隔離規則是必要的。

**救援 AP 與隊伍 AP 能否同時開**:現行只有一個 AP(`default_radio0`,brcmfmac / CYW43455),brcmfmac 在 AP 模式是否支援多個 BSS【待查證,列為 B7】。若不支援,改為**依條件切換**:
- 入網確認中:開救援 AP(隊伍 AP 暫停);
- 網路成員:開隊伍 AP;**離開 mesh 超過 X 分鐘,或擁有者在機台上短按針孔鍵**,切換為救援 AP 一段時間;
- 戰術版因電磁管制關閉 AP 時,上述「離開 mesh 超過 X 分鐘」的規則仍然適用,避免只能靠 L2 救回。

**未認領時必須關閉 root 存取**:現在未 seed 的節點 root 是空密碼、dropbear 開密碼登入,AP 又橋接進 ahwlan、firewall 全收(`137-bootstrap-credential.md` §1)→ 拿到 QR 上 AP key 的人直接 SSH 就是 root,認領形同虛設【事實,依 review 核對 137 / 96】。#137 的前提是「開機 #1 只在可信工作台上」,本設計把第一次開機搬到了野外,所以未認領狀態的預設必須是「沒有 root 存取」。

**隊伍共用 AP 的影響**:任何隊員的手機都連得上每一台節點的 AP → 管理面只能靠節點端的擁有者認證保護,不能依賴 AP key【推論】;隊伍 AP key 也要納入換 key 與撤銷(§7)。

## 6. 流程

### 6.0 出廠

1. 出廠燒錄站:設定並鎖定 608B(§3.3)→ 晶片內產生 DAC 與 ECDH 金鑰 → 產線中繼 CA 簽發 DAC,**壓縮憑證寫回 608B** → 寫入認領秘密與第一次接觸 AP key。
2. 列印 QR:`device_id`、認領秘密(**256 bit,只放在 QR,不需要人工輸入**)、第一次接觸 AP 的 SSID 與 key。**SSID 由 608B 的 `device_id` 決定**(例如 `BATMAN-<device_id 末 6 碼>`),不沿用 hostname:現行 SSID = hostname(`99-halow-identity`),但 hostname 會因換 mPCIe 卡而改變、3A+ 衍生失敗時退回隨機 uuid、使用者也能改,和印好的 QR 會對不上【事實,依第二輪 review 核對 99 L12–21】。→ 改 `99-halow-identity`:第一次接觸 / 救援 AP 的 SSID 取自 608B,hostname 規則不變。QR 放在哪裡依 SKU 而定【決策,U4】:

| | 民用 | 戰術 |
|---|---|---|
| 盒內 QR 卡 | ✅ | ✅ |
| **機身貼紙**(電池蓋內側或外殼內) | ✅ | ❌ |
| 理由 | 民用的威脅模型本來就承認「實體持有 = 完全控制」(§2),貼在機身不會降低安全性,卻能消除「卡片遺失 → 無法認領」的問題(業界對照:Matter / HomeKit 設定碼、路由器預設密碼都印在機身上) | 被俘的機台上若有代碼,敵方就能認領;改由擁有者保管卡片,遺失時以輪替補救(§6.8) |

**機身貼紙貼在 HAT 上**(608B 所在的板子),不貼在 Pi 或外殼上:換外殼或把 HAT 移到另一台 Pi 時,貼紙仍與 608B 對應。
3. **裝箱前驗證**:燒錄站掃描 QR 卡,實際連上該機台完成一次認領挑戰,通過才裝箱,避免卡片裝錯盒【決策,依 review】。
4. 戰術版:設定 signed boot(#115)、寫入 Pi 4 OTP 裝置私鑰、設定 608B IO protection key。
5. 量產燒卡規則沿用 #208:整卡清零,不得只用格式化。
6. **與 #208 / golden image 的衝突(要回寫)**:
   - #208 原本決定出廠時烤入批次 key(`depersonalise.sh --mesh-key --ap-key`)。本設計下 **mesh key 與 AP key 都不烤入**:烤了 mesh key,未認領的節點會直接加入批次網路,違反 §5。→ 改 #208 的 DoD / A5、`golden-image.md`。
   - 第一次接觸 AP key 由一支**新 uci-defaults hook 從 608B 讀出並寫入**,排在 `99-halow-identity` 之後、keyguard(S18)之前;kmodloader 在 S10 中早於 `uci_apply_defaults`,I2C 驅動此時已可用【事實,依第二輪 review】;需要 image 內有 cryptoauthlib 的命令列工具(#196 ①)。**這支 hook 依 p5 的狀態決定行為**(§6.9),只有未認領時才把 AP 設成第一次接觸 AP,否則 OTA 後會把成員節點的隊伍 AP 蓋掉。
7. **批次 QR 等同整批機台的認領權**,外洩就等於整批外洩 → 批次 QR 為選配,要與機台分開寄送或加密【決策,依 review】。
8. **工廠不保存任何認領秘密**【決策,U4】:燒錄站寫入 608B、印出 QR 後即銷毀;不建立「所有機台認領秘密」的資料庫(那會成為攻擊目標,也違反軍方「廠商不持有金鑰」的慣例)。業界對照:安全導向產品(硬體錢包)與軍方採此做法;消費性電子則以「印在機身上」解決遺失問題,民用版即採用後者。

### 6.1 認領(兩版相同)

**認領窗口要由實體動作開啟**【提案,待使用者確認;依第二輪 review】:節點只在**出廠後第一次開機的 N 分鐘內**(開箱即用)或**在機台上短按針孔鍵後 N 分鐘內**接受認領;一般的重開機(包括 L2 之後的重開機)不開放窗口。理由:民用版不輪替(U4),看過機身貼紙的人(修理行、前任、借用者)可以在擁有者用 app 發起 L2 之後、擁有者重新認領之前搶先認領;要求實體動作後,遠端或旁人就無法搶先。戰術版同樣適用(多一層保護)。由 app 發起的 L2 完成後,節點維持未認領、**不自動開放窗口**,等擁有者在機台上操作。

1. 掃 QR → app 加入第一次接觸 AP。Android 用 `WifiNetworkSpecifier` + `bindProcessToNetwork`(`WifiNetworkSuggestion` 需要使用者核准且不會立刻連線);iOS 用 `NEHotspotConfiguration`,並要求「區域網路」權限(被拒時會無聲失敗,app 要偵測並引導)【事實,依 review】。
2. 節點對 captive portal 探測回應 204,避免手機因「沒有網際網路」自動斷線或彈出 portal。
3. app 以 HTTPS 連到節點,**節點直接用 DAC 做 TLS 驗證**(DAC 是終端憑證,不能再簽發下一層)→ app 用**內建的 Batman 製造商根**驗證憑證鏈,並比對 `device_id` 與 QR 一致。**禁止退回 HTTP**。
4. **認領挑戰**【決策,U5】:
   - 節點出 nonce,計算 `challenge = SHA-256(nonce ‖ TLS exporter ‖ DAC 憑證雜湊 ‖ 擁有者公鑰)`;app 回傳 `HMAC(認領秘密, challenge)`;節點把 challenge 與回應交給 608B 的 **`CheckMac`** 比對(608B 的 CheckMac 輸入固定為 32 bytes,所以先由節點算出雜湊)【決策,依第二輪 review】。認領秘密槽只允許 CheckMac(§3.3)。
   - 綁定 TLS exporter 與 DAC → 不能中繼到別台、不能重放。
   - 為什麼不用 SPAKE2+:608B 無法在晶片內執行 SPAKE2+,verifier 必須讓 host 讀得到;攻擊者讀到 verifier 就能離線暴力破解短的認領碼。改用晶片內不可讀的 256 bit 秘密後,沒有可離線破解的東西。
   - **失敗次數限制**:失敗計數持久保存(斷電重開不歸零),超過上限後拉長等待時間。民用版存在 p5,**L2 會把它歸零**(民用可接受,實體持有本來就等於控制);戰術版存在 608B 的單調計數器(失敗是罕見事件,不會耗盡寫入次數)。
5. 節點寫入擁有者公鑰(可多把),並**就地完成 #137 的鎖定**:
   - `authorized_keys` = 擁有者公鑰;
   - **root 密碼由節點隨機產生,經 TLS 交給擁有者 app 保存**(滿足 #137 Decision B「每台非空 root 密碼」的要求);
   - 立刻套用 dropbear / ttylogin 鎖定(不能只靠 `96` 尾段;`96` 只在 fresh overlay 執行)【事實,依 review 核對 137 §5】;
   - **寫入 `/opt/batdata/state/lock-status`**(和 `96` L166–171 的做法相同),否則 `halow-status` 會一直回報 UNPROVISIONED、`--if-healthy` 永遠不會寫 p5【事實,依第二輪 review 核對 halow-status L95–99】;
   - 立刻執行 `batman-config-save --seed` 寫入 p5。
   - 開發用的工作台入口(#208 的 USB 網卡 + 空密碼):image 預設改為 `PasswordAuth=off` 後,改以既有的 `/etc/batman-dev-open`(`96` L164)或建置時的開發旗標保留,**量產 image 不得帶這個旗標**。
6. **region** 由手機的地區設定自動帶入,使用者按確認(#92 是出貨阻擋項)→ 寫入 p5。
7. app 與節點交換**協定版本**,不相容時拒絕操作並提示更新(app 與韌體可能長期不同步)。

**界線**:沒有 QR 卡的人無法透過網路認領。但民用版「實體持有 = 完全控制」(§2);戰術版因 signed boot + IO protection key,小偷就算按針孔重置,沒有 QR 卡也無法認領。

### 6.2 設定推送的通用規則:commit-confirm

**設定分兩類,規則不同**【決策,依第二輪 review】:

| | A 類:擁有者推送(加入網路、改 channel / region、個人設定) | B 類:管理者簽章(建網、換 key、重新加入封包、多期輪替) |
|---|---|---|
| 成功條件 | N 分鐘內成功入網(沿用 `meshjoin.sh` 的 `meshjoin_joined`,不另寫一套) | 簽章與版本號驗證通過、設定已套用、radio 以 mesh point 起來;**不要求看到 peer**(建網的第一台沒有鄰居;換 key 時先切換的節點看不到還沒切的鄰居) |
| 失敗時 | **自動回滾**到上一份設定 | **不回滾** |
| 切換時刻 | 立即 | 管理者指定的切換時刻(換 key),讓全網同時切換 |
| 版本 | — | **key 版本號只增不減**;節點拒絕任何版本較舊的設定或封包,**永遠不會回到已撤銷的 key** |

**為什麼 B 類不能回滾**:緊急換 key 之後,攻擊者只要干擾 RF,讓節點在 N 分鐘內入不了網,節點就會回滾到舊 key,而舊 key 正是遺失機台也知道的那一把。干擾就能讓緊急換 key 失效【事實,依第二輪 review】。B 類失敗時節點維持新設定,靠救援 AP(§5)與重新加入封包(§7.1)處理。

共同規則:
1. 推送前,節點保存目前設定為「上一份」(只供 A 類回滾)。
2. 整個過程保留**救援 AP**(§5),手機不會因為隊伍 AP 改了而失聯。
3. 加入網路需要的參數不只 mesh ID 與 key,還有 **region、channel、頻寬**;手動輸入或 QR 都要包含。
4. 成功後**明確呼叫 `batman-config-save`** 寫入 p5:現行 `joinwatch` 以 `/tmp/config-saved` 擋住,每次開機只跑一次 `--on-join`(L138),同一次開機內換 key 或換網時 p5 不會更新,OTA 後就退回舊 key【事實,依第二輪 review】。依賴 #202。

### 6.3 民用:建立網路(家用多台)

1. app 產生 mesh 參數與 SAE 密語(或使用者自訂;最短長度沿用 #103 的檢查)。SAE 抵抗的是**離線字典攻擊**,它不防 key 外洩(P5)【事實】。
2. 使用者成為網路管理者;名冊 = 這幾台的 DAC 公鑰。
3. 依 §6.2 推送到每一台。
4. **備用管理手機**:建網完成後 app 提示一次「加一支家人的手機當備用管理者?」,掃一下即完成(民用版不強制,但管理者手機遺失時不能讓網路變成無人能管理)【決策,依 review;依 P17 改為一步完成】。

### 6.4 民用:加入別人的網

1. 擁有者先認領自己的節點。
2. 取得網路參數:節點用 HaLow 掃描附近的 mesh ID 列給 app 挑選【待查證:MM6108 在 mesh 模式能否掃描】,或手動輸入 / 掃 QR。
3. 依 §6.2 推送給自己的節點 → 入網 → 網主的 app 對新 peer 發 challenge(§4.3),顯示「新節點:<擁有者> 的 <名稱>」→ 網主核准 → 加入名冊並散播。
4. **加入後若改用隊伍 AP,擁有者要先拿到隊伍 AP 的 key**(網主核准時一併交付),否則手機會斷線;在那之前救援 AP 保持開啟。

### 6.5 戰術:建立網路(個人組隊)

1. 發起人在 app 建網 → 產生網路根 → 簽發管理者清單與管理者中繼 CA(**至少 2 位**,P12)→ 簽發 TAK 中繼 CA 給 OTS 節點(建議不是網主節點)。管理者的中繼 CA 要在**該管理者的節點 TPM 內**產生(CSR 送回簽發),所以建網時所有管理者要同時在場(或經 mesh 完成 CSR)。
2. 網路根立刻**拆成 3 份**,自動配發到順位 1、順位 2、分持保管人的手機(以各人 app 公鑰加密,經 mesh 或當面傳送;各人按「接受」);發起人的 app 隨即丟棄完整網路根(§4.2)。
3. 產生任務期間的多期 mesh key,依 RTC 自動輪替(§4.4);**預載期數設上限**,因為被俘的機台會一併洩漏已預載的期數。
4. 依 §6.2 推送設定(LUKS 內的 p5)。

### 6.6 戰術:隊員加入

1. 隊員認領自己的節點,取得網路參數 → 入網(RF 層)。
2. 節點在 TPM 內產生成員金鑰,在 LUKS 內產生 WireGuard 金鑰,送出 CSR:**DAC 憑證 + 擁有者同意加入的簽章 + WireGuard 公鑰**。
3. **管理者在 app 上核准**(戰術版一定要核准)→ 簽發節點憑證 → 更新名冊 → 各節點建立 WireGuard peer。
4. 同時核准該隊員的 ATAK:TAK 中繼 CA 簽發 client 憑證 → app 經 WiFi 交付 data package(#54)。ATAK 身分綁「人」或「手機」見 §12 Q1。
5. 任務中 TAK 走:手機 → 隊伍 AP → mesh(WireGuard)→ OTS(mTLS 8089,#48)。這是**概念上類似** NSA CSfC 的雙層加密,但 WireGuard 用 Curve25519 / ChaCha20,**不是 CNSA 演算法,不能作為 #93 認證的依據**【事實,依 review 更正】。

### 6.7 戰術:單位整備

同 §6.5 / §6.6,差別:擁有者是單位(**擁有者金鑰為多把**,屬於多位單位管理員,避免綁在單一手機)、網路根由單位離線根簽發(§4.2 機構模式)、在基地集中核准。隊員只有使用權。**機台的 QR 卡由單位自行保管**,屬於單位內部的財產管理。

### 6.8 擁有權移轉與認領秘密輪替

- **移轉(不清資料)**:現任擁有者在 app 上簽章,把擁有者公鑰換成新擁有者的公鑰。用於單位人員異動、家人之間轉手。
**輪替認領秘密(只有戰術版)**【決策,U4】:
- 擁有者可以要求節點產生新的認領秘密(加密寫入 608B 的可改寫槽),app 顯示新 QR 給擁有者保存;舊卡失效。用於卡片遺失、懷疑卡片外洩、轉手。
- **轉手**:先輪替,把新 QR 交給下一位,再執行 L2 → 前任手上的舊卡已失效,無法在 L2 後搶先認領。
- 由 app 發起的 L2 **一律自動輪替**;針孔觸發的 L2 不輪替(只有持卡人才能接手)。

**民用版不輪替**:機身上貼著 QR(§6.0),前任擁有者要用舊卡搶先認領,必須先摸到機器按針孔重置,而摸得到機器本來就等於控制了它(§2)。輪替只會讓機身貼紙失效、徒增混亂。

**卡片與擁有者都不在時**:民用看機身貼紙;戰術(散戶)無法再認領,說明書要寫明「QR 卡要像權狀一樣保管」;戰術(機構)由機構自己的卡片保管處理。

**戰術版轉手一律由 app 發起**:賣家若用針孔觸發 L2(不輪替)又留著舊卡的照片,事後仍能搶先認領 → app 的「轉手」流程強制先輪替再 L2;app 顯示的新 QR 要列印或妥善保存。

### 6.9 狀態在 OTA 換槽後的保存【決策,依第二輪 review】

本設計新增的狀態(未認領 / 已認領 / 成員)與其衍生設定(AP 的 key / SSID / 網段、firewall zone、dropbear 鎖定),**現行的 p5 機制保不住**:
- `batman-config-save` 的 PRESERVE 清單(L22–32)只有 hostname、mesh_id、mesh key、channel、country、ahwlan 位址、openmanetd 旗標,**沒有 AP 的 key / ssid / network**;
- `96` 的 `ALLOWED_PKGS`(L22)刻意排除 firewall(N-R7)。
- 結果:成員節點 OTA 後,隊伍 AP、AP 網段、firewall zone 全回到 image 預設,§6.0 的 AP key hook 再把 AP 改成第一次接觸 AP。

做法(比照 #137 的做法):
- p5 記錄**狀態本身**(未認領 / 已認領 / 成員)與必要參數(隊伍 AP 的 SSID / key、擁有者公鑰),**不直接記錄 firewall 設定**;
- 在 `96` 的尾段(或緊接其後的一支 hook)**依 p5 的狀態在本機產生** AP、firewall zone、dropbear 設定;
- §6.0 的 AP key hook 依狀態決定:只有未認領時才把 AP 設成第一次接觸 AP。
- 這些都是兩板共用的 A/B 檔案(§11),要兩板實測。

## 7. 事件處理

| 事件 | 民用 | 戰術 |
|---|---|---|
| 成員離開 | 擁有者執行 L1;網主移出名冊 | 同左 + 撤銷節點憑證 |
| **演習陣亡** | — | 順位 2 管理者取得權杖(§4.3),不撤銷任何東西 |
| **任務結束** | — | 解散網路 → 在線節點執行 L1;**不在線的節點在憑證到期後自動執行 L1**;TAK 資料依政策封存 |
| **任務延長** | — | 到期前 X 小時 app 預警;管理者**批次續期**;已過期的節點在寬限期內仍可用舊成員金鑰簽章的 CSR 申請續期(經 mesh,不需 WireGuard)。**若中繼 CA 也將到期**,要先用網路根重簽中繼 CA(現場湊齊 2 份分持,或向機構申請),TAK 中繼 CA 與 ATAK 憑證同理 |
| **一般節點遺失** | 移出名冊 + 換 key(新 key 以各節點的 ECDH 公鑰分別加密派送、附管理者簽章與版本號;遺失的那台收不到) | 撤銷節點憑證 + 緊急換 key(取代所有已預載的期數) |
| **管理者節點遺失** | 其他管理者或備份金鑰換 key | §4.2 的撤銷規則;權杖依順位移交 |
| **OTS 節點遺失** | — | 撤銷 TAK 中繼 CA → 在別台重建 OTS → **所有 ATAK 都要重新申請**(§12 Q2) |
| **網路根的分持遺失或疑似外洩** | — | 3 份中仍有 2 份 → 用它們**產生新的網路根**,重簽所有中繼 CA(節點與 ATAK 憑證跟著重發),再拆成新的 3 份;**不能只重新分持**(舊分持無法作廢,§4.2)。只剩 1 份或 0 份 → 整網重建(§7.2) |
| 所有管理者都失聯 | 若有管理者備份就恢復;否則整網重建 | 散戶:兩位管理者都失聯時只剩分持保管人 1 份,**湊不出 2 份 → 整網重建**(§7.2);若有第 3 位以上管理者,其餘管理者依 §4.2 規則處理 |
| **隊員與機台一起被俘** | — | 人、手機、機台同時落入敵手時,**沒有人能遠端 zeroize**(U6 只限擁有者),只能靠撤銷 + 換 key + DAC 黑名單 |
| 擁有者手機遺失 | 用其他擁有者金鑰;都沒有 → 實體 L2 + QR 重新認領 | 同左 |
| QR 卡遺失 | 機身貼紙仍在,不受影響 | 擁有者還在 → 輪替產生新卡(§6.8);擁有者也不在 → 散戶無法再認領,機構由機構處理 |
| 轉賣 | 執行 L2,機身貼紙隨機台轉手(§6.8) | 輪替 → 交出新卡 → L2(內含 TPM Clear) |
| 送修 | 執行 L2;**機台無法開機時,民用版拔下 SD 卡自行保留** | 執行 L2;無法開機時 TPM 物件因綁定 OTP(§3.5)而無法在別台使用;**SD 卡上的 p5 / p6 在 LUKS 內,但 §3.4 完成前 overlay 仍有明文秘密**,建議拔下 SD 卡自行保留 |
| OTA | p5 與 608B 保留 | 同左;TPM 不靠 PCR,OTA 後照樣解得開 |
| 已撤銷的節點再次出現 | 名冊外告警 | 告警 + 拒絕(#49) |

### 7.1 換 key 時不在線的節點:重新加入封包

緊急換 key 後,不在線的節點會被留在外面(SAE 一次只能有一把 key)。回歸方式【決策,依 review】:

- 管理者的 app 對該節點產生**重新加入封包**:新的網路參數,以該節點的 ECDH 公鑰加密,附管理者簽章與 **key 版本號**。
- 封包**本身就能證明來源**,所以任何人的 app 都可以把它推給節點,不必是擁有者 → 單位機台的隊員(非擁有者)也能完成。
- **送達路徑**:被留在外面的節點連不上新的隊伍 AP,救援 AP 的設定服務又只對擁有者開放 → 救援 AP 上開一個**不需認證、只收簽章封包**的服務端點(§5)。節點只接受**版本號比目前新**的封包,防止有人拿舊封包把節點退回舊 key。
- **自動遞送(使用者看不到)**【決策,P17】:換 key 時,管理者的 app 為所有尚未確認的節點預先產生封包,**同步到每位成員的 app**(封包逐台加密,交給任何人都不會洩漏內容)。之後任何成員的手機經過被留在外面的節點附近、看到它的救援 AP 時,app 在背景自動連上並送出封包,節點自行回網。使用者只會看到「已幫 <機台名> 更新」。
- 手動備援:QR、app 對 app。
- 分區合併時,敗方管理者的 app 自動批次產生(§4.3),不需逐台操作。
- 定期輪替因為預載了多期 key,不需要這個流程。
- 換 key 流程沿用 **Bluetooth Mesh Key Refresh Procedure** 的三階段(派送新 key → 切換 → 撤銷舊 key)。

### 7.2 整網重建

網路根遺失、或所有管理者都失聯時的最後手段:任一擁有者建立新網路,其他擁有者以 §6.4 / §6.6 重新加入;舊網路的憑證到期後自動 L1。

### 8.1 清除範圍【決策,依 review 補齊】

| 清除項目 | L1 離網 | L2 解除認領 | L3 Zeroize(戰術) |

**另一個槽的 overlay 無法「部分清除」**:要清另一槽,得掛載它的 f2fs overlay(loop),不實際 → **L1 / L2 直接把另一槽作廢**(清零該槽 squashfs 之後的 overlay 區),由 `batman-slot` 執行(兩板共用 A/B 檔案)。之後 OTA 會重新寫入該槽。

### 8.2 實體觸發

| 方式 | 用途 | 規則 |

### 8.3 遠端觸發的授權

- L1:擁有者;管理者只能以「移出名冊 / 撤銷憑證」間接造成離網效果。
- L2:**只限擁有者**。
- L3 遠端指令:**只限擁有者**(單位機台的擁有者就是單位)。管理者**不能**遠端 zeroize 別人的機器,否則管理者金鑰外洩 = 一鍵清空整網【決策,依 review】。

### 8.4 TPM2_Clear

要經 **platform hierarchy** 執行;若走 lockout hierarchy,攻擊者可故意輸錯把 lockoutAuth 鎖住,或設定 `disableClear` 讓清除被擋【事實,依 review】。

### 8.5 選配:死人開關(戰術)

連續 N 小時看不到有效網路 → 自動 L3。**攻擊者只要干擾 RF 就能觸發**,迷路的隊員也可能被清空 → 預設關閉,由擁有者(不是管理者)依任務設定。
